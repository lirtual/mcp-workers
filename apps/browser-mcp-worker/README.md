## Architecture

`/mcp` accepts an independent `MCP_ACCESS_TOKEN` and uses `@mcp-workers/portal-auth`. `/extension/claim` consumes a 10-minute single-use code generated by `browser_pair`; `/extension/socket` authenticates by a WSS frame instead of a URL query token. `BROWSER_OWNER` is one owner-scoped SQLite-backed DO.

Available source-only MCP tools: `browser_pair`, `browser_endpoints`, `browser_stop`, `browser_revoke`, `browser_tabs`, `browser_snapshot`, `browser_screenshot`, `browser_tab_open`, `browser_tab_navigate`, `browser_tab_close`, `browser_operation_status`, `browser_click`, `browser_fill`, `browser_keypress`, `browser_scroll`, and `browser_select`. The read-only tools use an authenticated current WSS generation and explicit Endpoint / Tab identity, and do not persist webpage data. The extension Popup shows the last observed Tab ID and its session-only source (`Agent-created` or conservatively `Existing / source unknown`), plus credential-protected per-Endpoint Pending/Unknown counts from the Durable Object. When the cloud count is unreachable it displays **UNCONFIRMED**, never an invented zero. Unknown retains its original-key lookup warning even while online. The Popup's **Locate last observed tab** button checks the same document identity before focusing it. Agent-created source markers store only numeric tab IDs in `chrome.storage.session`, are cleared on tab removal or extension update, and never authorize automatic cleanup; Stop, disconnection and turn end retain tabs unless explicitly closed. Remote observation never changes focus, and Stop/reload clears that transient target. Screenshot capture only works on the active tab in a focused window, and refuses recognized forms, frames and other sensitive surfaces; it does not guarantee all secrets are detected. T3 now connects an **internal durable intent ledger and read-only `browser_operation_status`** to the explicit tab open/navigate/close MCP tools, prepare/execute WebSocket exchange, browser-side single-use consumption, and minimal signed-generation receipts. Identified consequential URLs are rejected until independent owner approval exists. Restricted T4 interactions and the conditional T5 approval channel are described below; high-impact execution remains disabled in this checkout pending independently verified configuration. Browser tab open/navigate/close passed in isolated native Chrome/Edge local E2E; the UI approval flow and release installation remain **Not run**.

### T3: durable intent and Unknown foundation (partial)

T3's source-only `src/intents.ts` ledger is instantiated in the existing owner-scoped SQLite Durable Object. It writes a random HMAC-SHA256 secret once to the DO, retaining **only** Endpoint ID, UUIDv7 intent key, operation ID, action name, keyed parameter commitment, admission/dispatch timestamps, original execution generation, execution-token hash, minimal outcome state and optional numeric tab ID. Page URL, query, title, DOM, form body and execution token are not persisted. An existing key is queried before first-admission clock validation, and same-key different-parameters return `intent_conflict`. Fresh keys use a 5-minute admission window (up to 30 seconds future skew); old keys cannot be re-admitted after retention cleanup.

`dispatch` records the intent before returning an execution token, with a **SQLite partial unique index** preventing concurrent `dispatching` rows for the same Endpoint even across async races. A newly constructed DO conservatively marks stale `dispatching` rows as `unknown` rather than replaying them. Unknown markers are not auto-deleted; terminal receipts become eligible for 7-day pruning during a later admission (independent scheduled pruning is not implemented), and Unknown capacity rejects new admissions instead of deleting evidence. A late final result can only update the original operation using its original token and generation. These transitions were verified by real Node SQLite unit tests, including concurrent dispatch and deliberately lost outcomes.

Reads and tab mutations are serialized per Endpoint: a read in flight denies new mutation admission, and a mutation being admitted, prepared or dispatched denies new reads and mutations with `busy`. A short in-memory reservation covers the asynchronous HMAC admission step, closing the read/write race before the durable record is created. Real local workerd protocol tests verify both directions, and an independent coordinator test delays admission deliberately to verify the reservation. No offline mutation queue is added.

The authenticated read-only `browser_operation_status` tool accepts `endpoint_id` and exactly one of the caller's original UUIDv7 `intent_key` or original `operation_id` and returns a minimal status or `not_found`. It does not initiate operations and must **never** be used as a reason to retry with a new key. T3 now exposes explicit tab open/navigate/close calls with UUIDv7 keys and exact observed document identities for existing tabs. Prepare is bound durably to the Endpoint, grant revision and connection generation, while dispatch is recorded before a one-use token is transmitted. The extension consumes each operation in session storage before invoking Chrome tab APIs. Lost dispatch receipts remain Unknown; the same key cannot repeat execution. A `completed` receipt must carry a valid numeric `tab_id`: a malformed completion with a null target remains unconfirmed and ultimately becomes `unknown` if no valid original execution receipt arrives. Unit and real local workerd protocol tests cover this denial. **Local workerd + SQLite DO + WSS protocol smoke passed**, including prepare, completion, denied prepare, collision, and Stop/Unknown. Real Chrome/Edge tab open/navigate/close effects passed on controlled test pages; owner approval and real third-party website verification are **Not run**. Nonfatal tab-group presentation warnings now persist in the original intent-key receipt, verified through SQLite and local workerd protocol tests (not native Chrome/Edge). The existing workerd smoke now uses a disposable persistence directory to avoid synthetic record buildup.

### T4: restricted fixed-schema page interactions (2026-10-29)

All five interaction tools require `endpoint_id`, `tab_id`, `document_id`, a snapshot-issued `element_id`, and a caller-generated UUIDv7 `intent_key`. `click` takes no additional parameters; `fill` takes `text` (at most 2,000 characters); `select` takes one `value` (at most 200 characters); `scroll` takes nonzero integer `delta_y` in [-1000, 1000]; `keypress` takes only ArrowUp/Down/Left/Right, Home, End or Escape. Caller JavaScript, selectors, coordinates, modifier keys, frames and approval flags are rejected at MCP and DO ingress. Keyboard events are synthetic DOM events: they do not guarantee native text editing or website handling.

`browser_snapshot` now supplies up to 100 opaque element references with tag/type and bounded labels, without input values. References reside in the top document's ISOLATED world, expire after 30 seconds, and are invalidated by DOM mutations, a new snapshot, navigation or an attempted effect. Execute rechecks the explicit document, current URL and live element, and the background rechecks local authorization and generation after prepare. There is no active-element or active-tab fallback. Shadow roots and child frames are unsupported.

Until T5 provides trusted owner approval, generic buttons, links, submissions and recognized consequential actions are denied. Only labeled details summaries and checkbox/radio controls explicitly labeled as local presentation/filter toggles can receive clicks. Fill and keypress are restricted to ordinary text/search inputs and textareas; select only handles a single enabled option; scroll targets an explicit referenced element. Benign ordinary form text/search fields, textareas and single-select controls may be edited, but form submit buttons, form checkbox/radio clicks, editable rich text, dialogs, known password/OTP/authentication/approval/secret surfaces, prohibited URLs, ungranted incognito and embedded documents fail closed. Input/change handlers may themselves have external effects, even without form submission. These conservative checks are heuristics, not proof that arbitrary website event handlers are harmless: even a text change or scroll can cause external effects. `completed` confirms only DOM dispatch, never website business success; synthetic keyboard events may be ignored by websites.

T4 reuses T3's durable prepare/execute and one-use consumption protocol. The keyed commitment includes every T4 argument while preserving the existing T3 commitment encoding. DO storage retains neither element references nor fill/select content. Same-key retries return the original receipt, changed parameters conflict, and missing or uncertain outcomes remain Unknown without replay. Prepared commands exist transiently in extension session storage, as in T3; they are not synced or written into the durable ledger.

`tests/t4-public.test.mjs` and `tests/interactions.test.mjs` exercise authenticated MCP → actual coordinator with SQLite → actual extension WebSocket handlers → serialized ISOLATED-world functions using Chrome/DOM adapters. It covers all five actions, fixed schemas at MCP and DO ingress, sensitive/prohibited surfaces, stale documents/elements, owner Stop, execute-time policy changes, keyed conflicts, and lost/uncertain receipts. This is source integration evidence, **not native Chrome/Edge T4 acceptance**. Real T4 MV3/browser behavior, website outcomes, native key behavior, production hibernation and T5 approval remain unverified. The current environment could not retrieve GitHub #422/#418 using `gh issue view` (network unavailable); T4 was implemented against the explicit task requirements and existing local context, so ticket-body acceptance remains to be reconciled.


### T5: independent owner approval (2026-10-29)

The WebSocket `authenticate` frame must explicitly declare `owner_approval_protocol: 1` before the Worker offers independent Owner Approval. Older installed extension code is denied, even if it can authenticate its Endpoint and its service origin matches. An extension reload alone does not upgrade old source files. A failed prepare returns one of the fixed non-content error codes `preparation_unavailable` or `approval_prepare_invalid` rather than a content-bearing error or an unexplained `failed`; these receipts are evidence of a blocked action, not an instruction to replay its original intent. Install the current reviewed extension artifact before testing real Owner Approval.

The same Worker serves `GET /owner/operations/<operation_id>` and explicit form `POST` at that exact path. `Accept: application/json` returns the same authenticated view/decision API as JSON. GET fetches a proposal and issues a nonce; it never grants execution. POST accepts only the exact canonical Origin and form content type, `nonce` and `decision=approve|deny`. The page has no JavaScript or third-party resources, escapes all proposal content, denies framing, sets no-store/no-referrer and uses a restrictive CSP. MCP Bearer, Endpoint credentials and bare email headers cannot authorize these routes. Alternate hosts, previews, direct HTTP, URL queries, foreign Origins, invalid JWT signatures/issuer/audience/expiry/identity and replayed nonces fail closed. Access keys are retrieved only from the configured issuer's `/cdn-cgi/access/certs`, with bounded size/deadline and no redirects; RS256 is the sole accepted algorithm. See [Cloudflare JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).

No approval settings were added to Wrangler, no service origin was enabled, and no secrets or remote configuration were changed. An independently reviewed operator setup must supply all of:

### T6: local sensitive-surface permissions (2026-10-29)

The Popup has two independent owner controls, **direct localhost/LAN** and **private/incognito**, both OFF by default. Enable the Profile first, then review and confirm each desired permission locally. Only the trusted Popup sender can change them; MCP, WSS messages and content scripts have no enable path. Private access additionally checks `chrome.extension.isAllowedIncognitoAccess()` at use time. Observed native denial or failure also invalidates the private session grant; restoring native access requires fresh local consent. Native denial, a missing API or an API exception denies access, and the Popup reports native permission as **DENIED / unavailable**, with Chrome/Edge extension-settings instructions. This extension uses one shared Endpoint and explicit `spanning` mode; no additional pairing identity is created.

Grants and their revision live only in trusted `chrome.storage.session`; they survive Service Worker reconstruction without prompting again. Chromium clears session storage on browser restart and extension disable/reload/update ([storage contract](https://developer.chrome.com/docs/extensions/reference/api/storage)). Stop/Revoke and local Resume also clear these grants. Enable/disable operations serialize their session writes and synchronously invalidate pending work. Prepared commands and observations bind to the permission revision; off/on cannot revive old execution authority. A failed grant write stops local control persistently; Resume must successfully clear sensitive permissions before connecting. Already-issued browser events or requests may still finish: this is not cancellation of in-flight website effects.

`browser_tabs` defaults to `scope: "ordinary"`; explicitly request `scope: "private"` to enumerate authorized private tabs. The two result sets stay separate and carry `scope` on each tab. Enumeration never returns titles, queries, fragments, group IDs or group titles. The Popup labels the last observed scope and hides its target when permission is lost, including native privacy revocation. Existing private tabs can be observed, screenshotted under the existing strict capture policy, navigated, closed or acted on by explicit document/element identity. `browser_tab_open` creates only an ordinary background tab in an explicitly selected ordinary window; it fails if no such window exists. Group reuse is confined to that window, and existing ordinary/private tabs are never moved or regrouped. There is no implicit creation in the currently focused private window.

LAN consent permits ordinary direct localhost, local hostnames, RFC1918/loopback/ULA HTTP(S) targets without an origin registry. URL parsing normalizes numeric aliases before classification. Known cloud metadata addresses/hostnames, link-local targets, ambiguous IPv6 forms, non-web schemes, browser/extension-protected sites and recognized authentication/approval targets remain prohibited. Top-document identity and URL are checked again before reads/effects and after observations; child-frame control and observations around embedded documents remain denied. These checks govern **directly controlled targets only**: URL text cannot establish DNS resolution safety. They do **not** establish full DNS rebinding protection, remote network isolation, page subresource filtering, or prevention of the initial network request during a redirect.

Sensitive permission is **not T5 Owner Approval**. Recognized consequential actions on LAN/private pages use the same independent approval, exact proposal binding and one-shot receipt protocol. Revocation invalidates pending authority; approval cannot expand local permissions. Raw commands/proposals are bounded session-only data. URL/query, DOM, screenshot and input content are not added to local persistent storage or DO receipts.
