# Browser MCP Worker

This component implements Browser MCP [Spec #418](https://github.com/lirtual/mcp-workers/issues/418) with the incremental activation/lifetime contract in [Spec #531](https://github.com/lirtual/mcp-workers/issues/531). **Spec #531 is only implemented in this isolated branch; no production release or Chrome/Edge native acceptance has occurred.**

## Spec #531 verification boundaries

The current `pnpm --filter browser-mcp-worker test:workerd` and `test:workerd:restart` launch real local workerd and SQLite DO with isolated disposable persistence. Without an independent Access JWT they only assert the old pairing protocol is retired, activation cannot be granted, and a pending one-use challenge remains unverified and cancellable across process restart. They **do not** claim successful local WSS mutation or Unknown recovery under Spec #531; those scenarios have isolated DO/extension tests. The pre-531 WSS/Unknown smoke evidence below is historical. The old native `native-wss-smoke.mjs` still assumes manual pairing and is **Not performed** for this protocol; it must be adapted and repeated with real approved Access identity before claiming Chrome/Edge E2E. No test-only bypass is added.

## Architecture and authorized control

A single Cloudflare Worker fronts one owner-scoped SQLite Durable Object. The MCP endpoint `/mcp` uses the existing Portal bearer authentication. An MV3 Chrome/Edge extension connects over generation-bound WSS for explicit Endpoint/tab operations. Persistent intent keys, receipt history and Unknown outcomes remain in the DO; never retry an Unknown website effect using a new key. High-impact operation Owner Approval is separate from pairing, and remains blocked unless independently configured and verified. Sensitive login, mailbox OTP, approval and other protected surfaces are excluded from extension read/write/screenshot controls. LAN and private-window permissions require separate local grants and do not imply Owner Approval.

**Spec #531 activation:** The toolbar icon is the sole primary ON/OFF control. A local click generates a one-time 256-bit proof held in trusted extension session storage. The Worker records a short-lived attempt. The dedicated, Access-protected `/activate/verify/{attempt_id}` GET validates a JWT's signed issuer, audience, expiry and owner mailbox but **does not authorize** the attempt. Its page first verifies that the *same browser Profile* has the pending attempt through Chrome's restricted external messaging, then performs a same-origin POST that marks the attempt owner-verified. The original extension alone supplies the local proof to consume the attempt. A valid existing Access SSO session is sufficient; a fresh email PIN is required only when Access asks. No manual pairing code, Popup, MCP Resume or independent authentication service is used. Old endpoints from the code-based protocol are retained across upgrade but forced OFF once; old enabling protocols fail closed.

Permanent pairing is the default and retains trusted local credentials and last intentional ON/OFF across normal restarts. Temporary pairing is selected in Options before first activation; its credentials reside only in trusted browser-session storage and have a finite DO lease. Restart/reload/disable/update invalidates the temporary local grant; closing a window or service worker suspension does not. Changing modes requires explicit Revoke and new pairing. OFF immediately blocks local admissions and synchronizes cloud Stop; UI distinguishes pending cloud confirmation. Revoke is separate and cannot undo already dispatched effects.

## Release requirements and verification

Source tests use the existing extension VM, public Worker ingress and DO SQLite fixtures. The validated release is one extension ZIP for both browsers, pinned to `https://browser.lirtual.dpdns.org`, built by `python3 scripts/build-browser-extension.py` using the existing GitHub Actions manual release. [Installation and recovery](../../docs/browser-extension/INSTALL.md) explains the supported UI and known evidence limits.

Before any separately authorized production release, configure the existing `browser-mcp-worker` GitHub Environment Variables `BROWSER_ACTIVATION_ORIGIN=https://browser.lirtual.dpdns.org` and a distinct `BROWSER_ACTIVATION_AUDIENCE` for a Cloudflare Access application guarding `/activate/verify/*`. The existing `BROWSER_ACCESS_ISSUER` and `BROWSER_OWNER_EMAIL` remain mandatory; high-impact `BROWSER_APPROVAL_*` settings are independent. The activation page must retain its own Access and JWT boundary. No new Worker, database, Queue, CI or Acceptance environment is required.

Run typecheck, `node --experimental-strip-types --test tests/*.test.mjs`, build ZIP with SHA/manifest verification, and the existing workerd/native Chrome and Edge flows using the matching protocol. Real Access SSO/no SSO, wrong Owner/issuer/audience, copied callbacks, Stop/late callback/restart race, temporary expiry, WSS connection generations, Office/SSO privacy exclusions, upgrade/rollback and Chrome/Edge installed Profile behavior need individually documented evidence. CI passes, GitHub dispatch acceptance, cloud rollout, WSS readiness and real browser effect are different milestones; none is interchangeable with a production E2E pass.
