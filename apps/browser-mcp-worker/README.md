# Browser MCP Worker

This component implements Browser MCP [Spec #418](https://github.com/lirtual/mcp-workers/issues/418) with the incremental activation/lifetime contract in [Spec #531](https://github.com/lirtual/mcp-workers/issues/531). **Spec #531 is merged into `main` and released to production; see the verified and still-unverified boundaries below.**

The current `pnpm --filter browser-mcp-worker test:workerd` and `test:workerd:restart` launch real local workerd and SQLite DO with isolated disposable persistence. Without an independent Access JWT they only assert the old pairing protocol is retired, activation cannot be granted, and a pending one-use challenge remains unverified and cancellable across process restart. They **do not** claim successful local WSS mutation or Unknown recovery under Spec #531; those scenarios have isolated DO/extension tests. The pre-531 WSS/Unknown smoke evidence below is historical. The old native `native-wss-smoke.mjs` still assumes manual pairing and is **Not performed** under this protocol; scoped Chrome/Edge activation and temporary-lifetime E2E have separate production evidence, but that evidence does not pass the obsolete native mutation/WSS/Unknown smoke. No test-only bypass is added.

## Architecture and authorized control

One Cloudflare Worker and one owner-scoped SQLite Durable Object connect an MV3 Chrome/Edge extension over generation-bound WSS. Profile grants allow eligible HTTP(S) browsing, fixed DOM interactions and normal form submission; labels, paths and query business words are not a safety oracle. Only the Owner's specific task authorizes site effects or cross-site nonpublic data transfer. Page text is untrusted, not a new Agent instruction. Recognized credential fields, the Browser MCP Owner activation/review channels, forbidden schemes/metadata and ungranted LAN/private targets remain blocked. Normal forms do not by themselves prevent guarded screenshots; uninspectable visible embedded surfaces still do. No per-action approval, semantic DLP or guarantee against prompt injection or website effects is provided. Unknown operation receipts must not be replayed with a new key; completed means browser event dispatch, not business success. Owner OTP and Unknown review require a truly independent channel beyond every Agent-controllable browser, mail or remote tool, verified before claiming acceptance.

**Spec #531 activation:** Only the pinned public-manifest-key-derived Chrome/Edge extension ID is accepted as an extension Origin or target for the Access verification page. The ID is public and not cryptographic code attestation: Owner Access, local presence and the one-use proof remain independent requirements. The toolbar icon is the sole primary ON/OFF control. A local click generates a one-time 256-bit proof held in trusted extension session storage. The Worker records a short-lived attempt. The dedicated, Access-protected `/activate/verify/{attempt_id}` GET validates a JWT's signed issuer, audience, expiry and owner mailbox but **does not authorize** the attempt. Its page first verifies that the *same browser Profile* has the pending attempt through Chrome's restricted external messaging, then performs a same-origin POST that marks the attempt owner-verified. The original extension alone supplies the local proof to consume the attempt. A valid existing Access SSO session is sufficient; a fresh email PIN is required only when Access asks. No manual pairing code, Popup, MCP Resume or independent authentication service is used. Old endpoints from the code-based protocol are retained across upgrade but forced OFF once; old enabling protocols fail closed.

Permanent pairing is the default and retains trusted local credentials and last intentional ON/OFF across normal restarts. Temporary pairing is selected in Options before first activation; its credentials reside only in trusted browser-session storage and have a finite DO lease. Restart/reload/disable/update invalidates the temporary local grant; closing a window or service worker suspension does not. Changing modes requires explicit Revoke and new pairing. OFF immediately blocks local admissions and synchronizes cloud Stop; UI distinguishes pending cloud confirmation. Revoke is separate and cannot undo already dispatched effects.

**Compatibility boundary for the 2026-10-31 increment:** The candidate Chrome/Edge ZIP and Worker now share extension version `0.2.1` and WSS protocol `3`. Installed `0.2.0` extensions cannot reconnect after Worker publication, and old protocol-2 sockets cannot dispatch new commands. Updating the Worker does not update a local browser extension; upgrade both profiles separately with the version-matched release artifact before claiming browser readiness. Preserve Stop and Unknown receipts; do not work around the version guard by accepting legacy frames.

## #418 approval-retirement rollout boundary

Per-operation approval retirement has its own previous production evidence. This 2026-10-31 usability increment is source-only until separately authorized Worker/extension deployment, Portal readback and version-matched native Chrome/Edge E2E. Earlier #531 and approval-retirement evidence does not pass this increment. A rollback to a Worker version that restores `/owner/operations/*` or allows an approved execute frame is **not** a safe rollback for the current #418 contract; keep control stopped instead of re-enabling the retired approval route.

## Release requirements and verification

Source tests use the existing extension VM, public Worker ingress and DO SQLite fixtures. The validated release is one extension ZIP for both browsers, pinned to `https://browser.lirtual.dpdns.org`, built by `python3 scripts/build-browser-extension.py` using the existing GitHub Actions manual release. [Installation and recovery](../../docs/browser-extension/INSTALL.md) explains the supported UI and known evidence limits.

For any future separately authorized production release, retain the already configured `browser-mcp-worker` GitHub Environment Variables `BROWSER_ACTIVATION_ORIGIN=https://browser.lirtual.dpdns.org` and a distinct `BROWSER_ACTIVATION_AUDIENCE` for a Cloudflare Access application guarding `/activate/verify/*`. The existing `BROWSER_ACCESS_ISSUER` and `BROWSER_OWNER_EMAIL` remain mandatory. Existing `BROWSER_APPROVAL_*` inputs remain solely for Access-protected **Unknown post-fact review**, not per-operation approvals; do not delete or rotate these production resources as part of this code change. The activation page must retain its own Access and JWT boundary. No new Worker, database, Queue, CI or Acceptance environment is required.

For subsequent changes, run typecheck, `node --experimental-strip-types --test tests/*.test.mjs`, build ZIP with SHA/manifest verification, and the existing workerd/native Chrome and Edge flows using the matching protocol. Track uncovered real Access SSO/no SSO, wrong Owner/issuer/audience, copied callbacks, Stop/late callback/restart race, temporary expiry, WSS connection generations, protected-surface exclusions, upgrade/rollback and Chrome/Edge Profile behavior as individual test cases without overriding existing dated evidence. CI passes, GitHub dispatch acceptance, cloud rollout, WSS readiness and real browser effect are different milestones; none is interchangeable with a production E2E pass.
