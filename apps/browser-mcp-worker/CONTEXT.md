# Browser MCP Context

Browser MCP owns **Browser Endpoint**, **Extension Grant**, Browser Control Session, owner pairing and revocation, WSS Connection Generation, Eligible Web Tab, Browser Operation, Owner Unknown Review, Operation Receipt, and Unknown Outcome. It is distinct from the Remote Control device/agent bounded context.

This implementation contains the **T1 pairing/control foundation**, **partial T2 read-only tab discovery, bounded visible text and guarded active-tab screenshots**, and a **T3 durable intent/Unknown ledger and explicit source-only tab mutation protocol with operation-status lookup**. Real Chrome/Edge isolated-profile read and WSS integration evidence is documented in README; it does not establish release readiness. T3 tab mutation/prepare-execute and minimal effect receipts are implemented in source and have a local real-workerd WSS protocol test, but Chrome/Edge real-mutation acceptance is **Not run**. Restricted **T4 fixed-schema page interactions** now use the same intent/prepare/execute chain and snapshot-issued document-bound element references; native T4 acceptance is **Not run**. The 2026-10-31 incremental #418 design retains retired per-operation Owner Approval while enabling standard interactions independent of business keywords, with objective permission and target checks. Unknown receipts still support separate post-fact Owner Unknown Review; full native T4/T5 safety acceptance remains **Not run**. T6 adds independent session-only local LAN/private consent, with native incognito permission, separate enumeration scopes and no cross-scope regrouping. Real T6 browser acceptance is **Not run**. Website business effects and cross-site nonpublic transfers require explicit User Task Authorization at the Agent layer; the extension cannot enforce a semantic DLP. Local tests do not establish release readiness.

- A Browser Endpoint identifies one profile-scoped extension install and its separately generated credential.
- Extension Grant is the owner's persistent authorization, independent of Portal authentication.
- Browser Control Session is locally enabled/stopped; transport online is independent.
- Connection Generation is monotonically advanced on authenticated WSS replacement; stale generations grant no authority.
- Endpoint Revocation is permanent for that identity; it rejects new admissions but does not reverse an already-issued website side effect.
- Passwords and recognized OTP/secret fields are excluded from the curated read path. T2 can transmit bounded visible text and guarded screenshots transiently, but page content and images are never persisted in the DO.
- Only an explicit browser toolbar gesture may initiate a new Access-backed activation. Authenticated MCP exposes Stop/Revoke, never Resume. Legacy manual pairing and local Resume routes are retired in Spec #531.
- The extension ingress and activation callback accept only the published Chrome/Edge installation ID derived from the pinned public manifest key. This coarse identity allowlist does not attest extension code; Owner Access plus a same-Profile one-time local proof are still required.
- Cloud STOP offline reconciliation is best-effort and distinguished from confirmed cloud revocation.
- A live WSS is a transport signal, not browser readiness or website business success.

The eventual T2–T10 semantics and security limits remain canonical in [Spec #418](https://github.com/lirtual/mcp-workers/issues/418).

T2 still requires Chrome/Edge real-device tests, screenshot safety review, and complete DOM/element reference behavior before it can be accepted. The read-only relay has a 5-second bounded response window; it never queues offline work.

Spec #531 supersedes the historical pairing UX: the Chrome/Edge toolbar click toggles local control; protected Access verification and a separate one-use extension secret are both required to issue or reenable a grant. Temporary pairing keeps credentials in `chrome.storage.session`, with a server lease as fallback, and requires a new pairing after browser restart. Independent Unknown review keeps its Access/nonce boundary, but high-impact browser actions cannot be remotely approved. Spec #531 is live: the later manual release #41039823675 shipped the bounded temporary reconnect fix; Chrome/Edge activation, both native temporary lifecycles, Edge transient WSS recovery, and one cross-Profile copied-callback refusal have scoped Pass evidence in [#531](https://github.com/lirtual/mcp-workers/issues/531). A real cross-version extension upgrade and production rollback are explicitly Waived, not Pass; a fresh client tool-cache refresh remains unverified. Do not transfer that evidence to unrelated #418 T2–T7 acceptance.

## 2026-10-31 authorization decision

**Eligible Web Tab** means technically controllable, not business-safe. **Extension Grant** authorizes one Profile, not **User Task Authorization** for site effects or cross-site nonpublic data transfer. DOM, screenshots and tool output are untrusted task data. [ADR 0002](docs/adr/0002-profile-grant-not-business-authorization.md) records the boundary. Owner OTP/Unknown review needs an independently verified channel beyond all Agent tools; the extension cannot attest it. This increment needs its own version-matched Worker/Chrome/Edge E2E; historical #531 evidence is separate.
