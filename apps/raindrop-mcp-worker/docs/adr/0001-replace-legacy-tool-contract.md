# Replace the legacy Raindrop MCP tool contract with official resource semantics

Status: accepted. Date: 2026-09-20.

The existing 17 tools combine reads, writes, and multiple operations, and some parameters or upstream mappings are incorrect. The approved redesign replaces that public surface with resource/action tools grounded in verified Raindrop API semantics, separates reads, writes, deletes, and explicit batch actions, removes old aliases and server-side AI Sampling, and retains the stateless Worker, MCP Portal, and two-credential deployment shape. This deliberately accepts one breaking client migration to avoid preserving incorrect behavior and a permanent compatibility layer; it does not authorize deployment or production-data mutation.

**Design refinement — Grill With Docs round 1 (2026-10-20, Q1–Q4 all A).** Canonical public nouns are `bookmark`, `collection`, `tag`, `highlight`, and `trash` (the upstream API's *Raindrop* remains a data/API term). Public tools default to `resource_action` names in `snake_case`. Read, create, update, and delete intents should be separate atomic tools, with justified bulk actions rather than universal `manage(operation)` or one-tool-per-endpoint exposure. Scope favors reliable bookmarks/collections/tags/highlights/search/bulk workflows plus useful lightweight helpers, not exhaustive API parity. The precise tool names/count, consolidations, and optional additions remain open for later interview rounds; no code or production change is approved.

**Design refinement — Grill With Docs round 2 (2026-10-20).** Confirmed Q5=A: consolidate bookmark listing into `bookmark_search` (including empty-query listing and pagination). Confirmed Q6=A: `collection_list` should provide hierarchy information instead of a separate tree tool. Confirmed Q8=A: scope includes tag listing, highlight listing, upstream-supported filter statistics, and URL-existence checking as lightweight capabilities. Q7 was partial at this stage: `trash_empty` was accepted, while the other cleanup tool names remained undecided until round 3 (see below). Preserve existing safe preview defaults; none of these decisions authorizes runtime changes or production deployment.

**Design refinement — Grill With Docs round 3 (2026-10-20, Q7/Q9/Q10/Q11 all A).** Cleanup tools are named `trash_empty`, `collection_remove_empty`, and `bookmark_remove_duplicates`, preserving current preview-first/destructive-safety guarantees. A single-bookmark move has its own `bookmark_move` intent; documented batch update handles supported bulk movement without a redundant `bookmark_batch_move`. Tags expose distinct `tag_list`, `tag_rename`, `tag_merge`, and `tag_delete` actions. Highlights likewise expose distinct `highlight_list`, `highlight_create`, `highlight_update`, and `highlight_delete` actions, mapped to verified upstream API semantics. Remaining input/output contracts and edge-case behavior are not yet settled; this refinement records decisions only and does not authorize code changes or release.

**Design refinement — Grill With Docs round 4 (2026-10-20, Q12–Q15 all A).** `bookmark_delete` sends ordinary bookmarks to Trash, but refuses to delete an already-trashed bookmark unless `permanent: true` is explicit. `collection_delete` previews the collection subtree and affected bookmark counts by default and requires `confirm: true` to execute; the preview is not a transaction or guarantee against state changes, and uncertain counts cannot be represented as exact. Bulk tag inputs distinguish `tagsToAdd` (append) from `clearTags` (remove all), reject conflicting intentions, and do not suggest bulk replacement that upstream does not provide. Tool results are structured-first: bounded concise lists, full requested details, and evidence-based succeeded/failed/unknown/not-executed scopes for multi-request writes without duplicative verbose text. Specific validation limits, helper names and schemas, edge-case mapping, and acceptance gates remain unresolved. Documentation-only; no implementation or deployment authorization.

**Design refinement — Grill With Docs round 5 (2026-10-20, Q16–Q19 all A).** Public tool schemas reject malformed/noninteger IDs while explicitly allowing only valid reserved collection IDs, enforce bounded zero-based pagination (upstream page size <= 50), and require nonempty, deduplicated explicit IDs plus an invocation bound for batch writes. Creation, update, and deletion use action-specific strict schemas with only applicable fields; update must specify a target and at least one meaningful change. The approved helper tool names are `bookmark_exists` and `bookmark_filters_get`; `bookmark_suggest` was originally discussed but later withdrawn after real upstream HTTP 403 (no Sampling replacement). Confirmed destructive operations perform a fresh preflight and reject materially changed or unverifiable target scope, requiring a new preview, without persistent tokens/snapshots, additional services, or a false atomicity guarantee. Exact endpoint mappings, limit values, failure/result structures and the final public tool inventory remain open. Documentation-only, no code, deployment, merge, or development-ticket authorization.

**Design refinement — Grill With Docs round 6 (2026-10-20, Q20–Q23 all A).** Keep the existing centralized Raindrop API service and verify request/response behavior against official docs and targeted contract tests instead of generating a full client from the local OpenAPI description or issuing HTTP from each tool. Permit only bounded read retries; writes submitted upstream are not replayed. Check transport and upstream application outcomes (including `result: false`) and report only proven success, failure, unknown, and not-executed scopes without assuming transactionality or per-item guarantees. Before batch deletion, verify every explicit ID belongs to the declared collection and is safe to remove; any mismatch, unknown, or unintended permanent-delete risk rejects the entire batch before mutation. The public MCP contract baseline is 26 candidate business tools, enumerated in `CONTEXT.md`: 9 bookmark, 5 collection, 4 tag, 4 highlight, 1 upstream-backed helper, and 3 cleanup; `diagnostics` is internal, redundant `library_audit` and `suggest_tags` and legacy aliases are removed. The next design frontier covers global-cleanup semantics, bounded scanning and request budgets, acceptance evidence, and overengineering review. These are documentation decisions only, not permission to implement or deploy.

**Design refinement — Grill With Docs round 7 (2026-10-20, Q24–Q28 all A).** Replace unscoped global empty-collection cleanup with finite individually scoped, freshly validated deletions; fail closed on unverifiable or changed scopes and preserve existing deletion safety. Enforce bounded upstream request/scan budgets and explicit batch limits; incomplete discovery may be reported but must not authorize cleanup. Acceptance requires verified official API contracts plus real MCP read-only checks and narrowly scoped disposable-data write checks, reusing unaffected prior evidence and recording code/test/live acceptance separately. The 26 candidate tool names are a target inventory rather than a release quota: withhold unverified tools instead of inventing behavior or new infrastructure. To make preview-first actions stateless yet freshness-aware, return a minimal canonical expected-impact summary and require its echo on confirmation; compare against fresh upstream state, reject changed/missing/unverifiable impact, and do not misrepresent the summary as an approval token, lock, or atomicity guarantee. Exact budgets, scope-summary data and large-target edge cases, and detailed acceptance gates remain open. This ADR update does not authorize feature work, Tickets, merge, or deployment.

**Design refinement — Grill With Docs round 8 (2026-10-20, Q29–Q32 all A).** Set a simple hard cap of 60 upstream HTTP requests per MCP invocation, inclusive of retries, 50 explicit bookmark IDs per batch write, and 50 items per read page; these are local protection limits, not a replacement for Raindrop's user-wide rate limits. `collection_remove_empty` deletes only independently confirmed leaf collections with zero direct bookmarks and zero children, bottom-up with a fresh preflight before every delete; never remove a parent with remaining descendants as an optimization. `trash_empty` requires a complete enumeration of Trash bookmark IDs at preview and again at confirmed execution; fail closed when the entire set cannot be verified within budget, regardless of whether counts match. Preview and confirmation exchange a deterministic summary over the complete canonically sorted ID membership set, scoped to the intended target and count, without persisting approval state, adding locks, or claiming authorization/transaction guarantees. Unknown write outcomes and already acknowledged partial completion must remain distinct. Canonical serialization, additional safety checks for collection metadata changes, and exact release acceptance remain for subsequent rounds. This is documentation only and does not authorize implementation, Tickets, merge, or deployment.

**Design refinement — Grill With Docs round 9 (2026-10-20, Q33–Q37 all A).** A multi-request mutation stops on the first explicit failure or unknown result, returning only upstream-evidenced confirmed-succeeded, confirmed-failed, unknown-outcome, and not-executed target scopes; no write replay or fabricated rollback. Deletion preflight checks collection parent/child relationships, direct bookmark counts, and privileges in addition to membership-ID digests, but does not expand scope to unrelated display metadata. The fixed per-invocation request budget coexists with official rate-limit headers/429 handling, bounded eligible-read backoff, and no centralized limiter. If Trash membership cannot be fully enumerated within budget, `trash_empty` refuses global deletion and recommends only separately authorized, explicit finite-ID deletion, without a background workflow. Acceptance uses upstream-aligned contract mocks, real MCP read-only smoke tests, and limited disposable-data writes, while marking untestable global destructive paths as acceptance-limited and reusing evidence unaffected by changes. The remaining frontier is the minimal result/error schema, digest serialization/echo fields, release gate and final complexity audit. This is a documentation-only decision record and does not authorize implementation, development Tickets, merge, or deployment.

**Design refinement — Grill With Docs round 10 (2026-10-20, Q38–Q41 all A).** Use a minimal structured public tool-result contract with `status`, applicable `reason`, and `succeeded`/`failed`/`unknown`/`notExecuted` scopes only for operations requiring such granularity; older conceptual scope labels in round 9 map to these final public names. Neither aggregate success flags nor a `modified` count prove individual bookmark outcomes. Use a **versioned SHA-256** digest over an unambiguous canonical serialization of the target ID, complete count, and numerically sorted full member-ID set for stateless preview/confirmation comparison; separately verify deletion-relevant collection structure/count/access, without introducing signed approval tokens or persistence. Track code completion, official API contract-test pass, and real MCP acceptance separately per tool; only verified tools qualify for future release candidacy and destructive tools require bounded safe disposable-data testing, with untestable global paths explicitly limited and never reported as live validated. Finish the Grill With Docs interview after a full Q1–Q41 review if no substantive design blocker remains; leave this PR Draft pending separate authorization for development, tickets, merge, or deployment. The exact serialization bytes/test vectors and actual official API conformance remain implementation/acceptance checks, not a reason to invent another design round.

**Final review consensus (2026-10-20).** The independent review found no substantive blocker to the accepted stateless architecture and 26 candidate resource/action tools; Grill With Docs is closed by user agreement. Reconcile final API contracts without new infrastructure: highlight writes retain their owning bookmark context and official semantics; tag operations share an accurate request adapter; URL-existence results must not invent URL-to-ID pairs and a valid absence is not an upstream error. A confirmed cleanup may operate only on the previewed set and cannot silently extend itself to collections newly qualifying mid-run. Per-tool verification does not authorize a production cutover that drops important working legacy operations; the breaking replacement requires tested core-flow coverage and separate deployment authorization. These are refinements of Q1–Q41 and implementation acceptance risks, not authorization to implement, create Tickets, merge, or deploy. Detailed historical round entries remain in this ADR for traceability until any separately authorized documentation consolidation.
