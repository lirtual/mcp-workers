# Replace the legacy Raindrop MCP tool contract with official resource semantics

Status: accepted. Date: 2026-09-20.

The existing 17 tools combine reads, writes, and multiple operations, and some parameters or upstream mappings are incorrect. The approved redesign replaces that public surface with resource/action tools grounded in verified Raindrop API semantics, separates reads, writes, deletes, and explicit batch actions, removes old aliases and server-side AI Sampling, and retains the stateless Worker, MCP Portal, and two-credential deployment shape. This deliberately accepts one breaking client migration to avoid preserving incorrect behavior and a permanent compatibility layer; it does not authorize deployment or production-data mutation.

**Design refinement — Grill With Docs round 1 (2026-10-20, Q1–Q4 all A).** Canonical public nouns are `bookmark`, `collection`, `tag`, `highlight`, and `trash` (the upstream API's *Raindrop* remains a data/API term). Public tools default to `resource_action` names in `snake_case`. Read, create, update, and delete intents should be separate atomic tools, with justified bulk actions rather than universal `manage(operation)` or one-tool-per-endpoint exposure. Scope favors reliable bookmarks/collections/tags/highlights/search/bulk workflows plus useful lightweight helpers, not exhaustive API parity. The precise tool names/count, consolidations, and optional additions remain open for later interview rounds; no code or production change is approved.

**Design refinement — Grill With Docs round 2 (2026-10-20).** Confirmed Q5=A: consolidate bookmark listing into `bookmark_search` (including empty-query listing and pagination). Confirmed Q6=A: `collection_list` should provide hierarchy information instead of a separate tree tool. Confirmed Q8=A: scope includes tag listing, highlight listing, upstream-supported filter statistics, and URL-existence checking as lightweight capabilities. Q7 was partial at this stage: `trash_empty` was accepted, while the other cleanup tool names remained undecided until round 3 (see below). Preserve existing safe preview defaults; none of these decisions authorizes runtime changes or production deployment.

**Design refinement — Grill With Docs round 3 (2026-10-20, Q7/Q9/Q10/Q11 all A).** Cleanup tools are named `trash_empty`, `collection_remove_empty`, and `bookmark_remove_duplicates`, preserving current preview-first/destructive-safety guarantees. A single-bookmark move has its own `bookmark_move` intent; documented batch update handles supported bulk movement without a redundant `bookmark_batch_move`. Tags expose distinct `tag_list`, `tag_rename`, `tag_merge`, and `tag_delete` actions. Highlights likewise expose distinct `highlight_list`, `highlight_create`, `highlight_update`, and `highlight_delete` actions, mapped to verified upstream API semantics. Remaining input/output contracts and edge-case behavior are not yet settled; this refinement records decisions only and does not authorize code changes or release.

**Design refinement — Grill With Docs round 4 (2026-10-20, Q12–Q15 all A).** `bookmark_delete` sends ordinary bookmarks to Trash, but refuses to delete an already-trashed bookmark unless `permanent: true` is explicit. `collection_delete` previews the collection subtree and affected bookmark counts by default and requires `confirm: true` to execute; the preview is not a transaction or guarantee against state changes, and uncertain counts cannot be represented as exact. Bulk tag inputs distinguish `tagsToAdd` (append) from `clearTags` (remove all), reject conflicting intentions, and do not suggest bulk replacement that upstream does not provide. Tool results are structured-first: bounded concise lists, full requested details, and evidence-based succeeded/failed/unknown/not-executed scopes for multi-request writes without duplicative verbose text. Specific validation limits, helper names and schemas, edge-case mapping, and acceptance gates remain unresolved. Documentation-only; no implementation or deployment authorization.

**Design refinement — Grill With Docs round 5 (2026-10-20, Q16–Q19 all A).** Public tool schemas reject malformed/noninteger IDs while explicitly allowing only valid reserved collection IDs, enforce bounded zero-based pagination (upstream page size <= 50), and require nonempty, deduplicated explicit IDs plus an invocation bound for batch writes. Creation, update, and deletion use action-specific strict schemas with only applicable fields; update must specify a target and at least one meaningful change. The approved helper tool names are `bookmark_exists`, `bookmark_filters_get`, and `bookmark_suggest` (official suggestions, no Sampling). Confirmed destructive operations perform a fresh preflight and reject materially changed or unverifiable target scope, requiring a new preview, without persistent tokens/snapshots, additional services, or a false atomicity guarantee. Exact endpoint mappings, limit values, failure/result structures and the final public tool inventory remain open. Documentation-only, no code, deployment, merge, or development-ticket authorization.
