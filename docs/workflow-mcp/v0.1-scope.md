# Workflow MCP v0.1 Settled Scope

Status: reduced scope summary; implementation contract is `v0.1-spec.md`
Date: 2026-09-17

The authoritative architecture baseline is [`v0.1-architecture-reduction.md`](./v0.1-architecture-reduction.md), and the buildable implementation contract is [`v0.1-spec.md`](./v0.1-spec.md). Historical ADRs record design rationale; when an earlier ADR conflicts with the reduction baseline/spec, the reduction/spec controls v0.1.

## Goal

Build a small, general Workflow MCP in which adding a workflow made from existing capabilities normally changes only a definition file, while Cloudflare Workflows owns durable orchestration and GitHub Actions is used only for explicitly registered heavy capabilities.

The v0.1 system is an independent `workflow-mcp-worker`; existing MCP applications remain autonomous external capabilities.

## Components and authority

| Component | v0.1 responsibility |
| --- | --- |
| Worker | MCP/API, authentication, validation, trigger/callback ingress, executor authorization |
| Cloudflare Workflows | authoritative DAG progression, waits, controlled retries, timeout/cancellation progression |
| D1 | admission, Step Attempt claim, callback inbox, scheduler progress, query projections, essential lifecycle events |
| R2 | large canonical artifacts |
| GitHub Actions | registered heavy capabilities only |

D1 is not a second DAG scheduler. GitHub reports executor facts but does not decide the workflow's next Step or final business outcome.

## Definitions and versioning

- Git is the v0.1 workflow-definition source of truth.
- YAML is validated at build time for schema, DAG structure, expressions, capabilities and references.
- Definitions are deterministically normalized and SHA-256 hashed; do not build a general compiler/optimizer framework.
- New-run discovery uses a bundled Workflow Registry.
- At admission, every Run pins the normalized definition/plan needed to resume that Run even after a later deployment changes the repository definition.
- Stored plans include `dsl_version`, `definition_digest`, resolved capability contract identifiers/versions, deterministic executor routing and `engine_version` (or equivalent protocol/build field).
- A new engine/runner deployment must remain compatible with all nonterminal v0.1 stored plans or be rejected/deferred until migration/termination is explicit.

## DAG semantics

- Bounded acyclic graph with named Steps, `needs`, parallel independent branches, and a minimal `if` expression language.
- No cycles, general loops, ambient shell/JavaScript/Python `run:`, or generic arbitrary user-code capability in v0.1.
- Independent branches may continue after another branch fails.
- Descendants whose required dependency failed are skipped/blocked.
- An unhandled failed Step makes the final Run failed.
- `always()` may bypass dependency failure for explicit failure notification/finalization, but it does not bypass run-level cancellation.
- After `cancel_requested`, no new Step starts.

## Identity and reliability

Keep these identities distinct:

- Admission Key: stable for one source event/occurrence or caller idempotency key.
- Run ID: one logical Workflow Run.
- Step Run ID: one logical Step execution within a Run.
- Operation ID: one logical business operation; stable across retries/new Attempts.
- Attempt ID: one execution attempt; changes on retry.
- GitHub physical identity: concrete `run_id` / `run_attempt` / workflow identity.

The reliability model has three separate layers:

1. trigger/run admission deduplication;
2. atomic Step Attempt authorization/claim;
3. business idempotency/reconciliation for external side effects.

None implies exactly-once external execution.

## Remote Attempt claim

A remote Attempt may produce duplicate candidate GitHub Jobs when dispatch outcome is uncertain, but at most one candidate may be authorized to perform business work.

The candidate must atomically claim a server-registered `queued` Attempt using a conditional D1 update and succeed only if exactly one row changed. A valid GitHub OIDC token alone cannot claim arbitrary work. The server validates the pre-registered repository/workflow/ref policy and Attempt claim nonce; the successful atomic Claim also binds the actual GitHub `run_id` / `run_attempt`. When dispatch response loss makes the physical run ID unknowable in advance, the first fully valid Candidate may establish that binding.

A claim deadline is an observation/reconciliation deadline, **not** an ownership-transfer lease. Expiry never automatically allows another Job to take over the same Attempt. If outcome cannot be established, record `indeterminate`; create a new Attempt only when retry is proven safe.

## Retry and indeterminate outcome

- Workflow-layer retry policy is explicit; do not inherit generic executor/orchestrator retry defaults for side-effecting work.
- Retry-safe/read-only capabilities may use bounded automatic retries.
- Upstream idempotency uses the stable Operation ID, not Attempt ID.
- A non-idempotent write that may have succeeded but lost its response becomes `indeterminate` when outcome cannot be verified.
- `indeterminate` is not blindly retried.
- A heavy Capability may contain multiple internal operations in one GitHub Job; the Capability must define retry/idempotency semantics for the whole business operation because the internal operations are not transactional merely by being in one Job.

## Callback inbox and reconciliation

Callbacks are authenticated/bound to the registered Attempt and GitHub identity, then idempotently persisted to a D1 callback inbox **before** notifying the waiting Workflow.

If notification fails, the inbox entry remains pending. A bounded maintenance pass may reuse the scheduler tick to resend pending notifications. Result and cancellation wake-ups use an Attempt-specific Workflow event type so an old Attempt cannot wake a later one. A Workflow wait timeout reconciles inbox state, Attempt/claim state and GitHub facts before deciding failure/retry/`indeterminate`.

Late, duplicate, terminal-run, cancelled-run or old-Attempt callbacks may be recorded as facts but cannot directly rewrite the current business outcome. A GitHub Job reporting `success` is not business success unless it is the authorized claim owner and produced a valid Attempt result.

## Cancellation

- `cancel_requested` is durable and stops admission of new Steps.
- Active executors receive a cooperative stop request.
- `cancelled` is terminal only after orchestration resolves active work according to policy; cancellation never claims rollback of completed external side effects.
- If an executor cannot be confirmed stopped, preserve that uncertainty instead of reporting a false confirmed cancellation.
- General Saga/compensation semantics are deferred.

## Triggers and scheduling

v0.1 supports:

- `manual`;
- authenticated `webhook`;
- `schedule`.

One periodic scheduler tick evaluates compiled schedule definitions plus D1 scheduler progress. Default schedule misfire is `latest`; workflows that require every missed time window must implement domain-specific cursor/catch-up semantics instead of assuming `latest` is lossless.

## Capabilities and executors

The Capability Registry is a static TypeScript registry with input/output contract, side-effect/retry classification and deterministic allowed/default executor selection.

Use Cloudflare for ordinary HTTP/MCP I/O, storage metadata, waits and light transformations. Use GitHub only for explicitly registered heavy capabilities such as browser automation, file processing, heavy parsing or full-runtime CLI work.

One remote Attempt may have multiple physical candidate Jobs, but at most one Job is authorized. Do not build automatic Step batching/optimizer logic in v0.1; instead choose business-meaningful Step/Capability granularity.

## MCP connections and credentials

- `mcp.call` remains a generic Capability Adapter rather than mirroring every remote MCP tool into the local registry.
- v0.1 supports only documented/tested MCP transport/auth combinations used by declared Connections; it does not promise arbitrary MCP plug-and-play compatibility.
- Non-secret Connection metadata is static/configured in v0.1.
- Long-lived connection credentials use Workers Secrets; do not build a D1 AES-GCM credential vault in v0.1.
- Connection auth must represent actual wire behavior, including custom header, raw `Authorization`, Bearer, or another explicitly configured prefix/scheme; never assume all credentials use Bearer.
- Updating a Workers Secret may create/deploy a new Worker version; v0.1 does not promise runtime rotation without a Worker version change.

For mutable MCP/tool contracts, record a dependency snapshot/fingerprint when useful for diagnosis, but a changed fingerprint alone is not proof of incompatibility. Validate the selected tool and actual invocation against the live contract; missing/incompatible operations fail explicitly without AI-generated parameter repair.

The generic `mcp.call` Capability resolves a per-`Connection + Tool` Effective Operation Policy. Local explicit policy wins; trusted MCP annotations may be used only when the Connection opts in; otherwise the conservative default is not automatically retry-safe.

## GitHub authentication

Two directions remain separate:

- Worker → GitHub: minimal repository-scoped GitHub platform credential for dispatch/cancel.
- GitHub → Worker: GitHub Actions OIDC, validated against configured issuer/audience/time and expected repository/workflow/run identity, then bound to the server-registered Attempt claim.

Executors receive only server-authorized Capability/Connection material required by their claimed Attempt; they cannot ask for arbitrary secret names.

## Artifacts and logs

- Small results stay inline.
- Large artifacts use R2 and stable Artifact References.
- External heavy executors may receive short-lived object-scoped upload authorization for direct R2 upload.
- D1 stores only essential lifecycle events needed for `workflow_status` / `workflow_logs`; do not build event sourcing.
- Raw GitHub/executor logs remain at the executor by default and are copied to R2 only when explicitly necessary and sanitized.

## MCP control surface

Keep the fixed asynchronous tools:

- `workflow_list`
- `workflow_get`
- `workflow_run`
- `workflow_status`
- `workflow_result`
- `workflow_logs`
- `workflow_cancel`

`workflow_run` returns a durable Run ID/current state rather than waiting for completion. Workflow additions do not generate new MCP tools.

## Explicitly deferred from v0.1

- runtime workflow authoring/install;
- installable/hot-loadable capability plugins;
- generic arbitrary user-code capability;
- encrypted runtime Connection credential vault;
- persisted workflow queue/dynamic concurrency-key subsystem;
- event sourcing/replay platform;
- copying all raw executor logs to R2;
- Saga/compensation engine;
- RBAC/organizations/workspaces;
- automatic remote Step batching/optimizer.

## Acceptance baseline

Implementation and tests must satisfy the fault scenarios in [`v0.1-architecture-reduction.md`](./v0.1-architecture-reduction.md), including duplicate admission, duplicate dispatch candidates, non-transferable Attempt claims, indeterminate external writes, callback redelivery/reconciliation, truthful cancellation, executor unavailability, pinned-plan recovery across deployment, MCP contract drift, and extension without orchestration-core changes.
