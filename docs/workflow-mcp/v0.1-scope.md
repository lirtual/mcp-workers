# Workflow MCP v0.1 Settled Scope

Status: design interview in progress
Date: 2026-09-17

This file records only v0.1 scope decisions already accepted during the design interview. Open questions are intentionally not filled in here.

## Definition ownership

- The architecture preserves a path to both repository-authored and future runtime-authored workflows.
- v0.1 implements repository-authored workflow definitions only.
- Git is the v0.1 source of truth for workflow definition content.
- Runtime persistence is for runs, state, events, deduplication, immutable definition versions, and provenance rather than v0.1 authoring.
- A Workflow Definition Version is identified by SHA-256 over the canonicalized definition content.
- Git commit/path information is provenance, not definition-version identity.
- Every Workflow Run pins one immutable Workflow Definition Version when the run is created.

See ADR 0003 and ADR 0006.

## Workflow control flow

- A workflow is a directed acyclic graph of named steps.
- v0.1 supports declared dependencies (`needs`), conditional execution (`if`), and parallelizable independent branches.
- v0.1 does not support cycles or general loop constructs.
- Workflow execution is not globally fail-fast by default.
- A failed/cancelled step blocks only descendants whose dependency conditions are not satisfied; independent branches may finish.
- The final Workflow Run outcome remains failed when an unhandled Step Run failed, even if independent branches succeeded.
- `always()` is supported for explicit cleanup/notification/audit paths.
- v0.1 does not add `continue-on-error`.

See ADR 0004 and ADR 0008.

## Step attempts, retries, and idempotency

- A Step Run is one logical step execution within one Workflow Run.
- A retry creates another Step Attempt under the same Step Run rather than a new logical Step Run.
- Each logical side effect has a stable Operation ID reused by all retry attempts.
- Capability adapters propagate Operation IDs to downstream idempotency mechanisms where available.
- Retry semantics are owned by the workflow layer rather than inherited from executor defaults.
- Capabilities explicitly classified as retry-safe may receive bounded retries by default.
- Capabilities not explicitly retry-safe default to one attempt.
- Workflow authors may deliberately override retry policy when they accept the resulting semantics.

See ADR 0007.

## Run admission and event deduplication

- The system guarantees at-most-one Workflow Run admission per equivalent trigger event; it does not claim exactly-once downstream execution.
- Webhook and scheduled starts use stable Admission Keys derived from workflow/trigger/event identity and resolve duplicate deliveries to the already admitted run.
- Manual starts create a new run by default, with an optional caller-supplied idempotency key when deduplicated manual admission is desired.
- Duplicate admission requests return the existing `run_id` instead of failing as duplicates.
- v0.1 keeps admission records without a deduplication TTL; retention policy is deferred until actual data volume requires it.

See ADR 0012.

## Workflow concurrency

- `parallel` is the default workflow concurrency mode.
- A workflow may opt into queued execution with a fixed concurrency limit; v0.1 supports the important `queue` + `limit: 1` case for serialized jobs.
- v0.1 does not implement replace-old-run, drop-new-run, or expression-based dynamic concurrency keys.
- The schema remains extensible for future scoped concurrency keys.

See ADR 0013.

## Cancellation and timeouts

- Cancellation is cooperative first: mark cancellation requested, stop admitting new steps, ask active executors to cancel, then hard-terminate remaining work after a bounded grace policy.
- Cancellation does not mean rollback or compensation; completed external side effects remain completed unless a workflow explicitly modeled compensating work.
- v0.1 supports workflow-level and step-level explicit timeouts.
- Workflow timeout has no default finite duration because waiting workflows may legitimately span long periods.
- Timeout uses the same stop path as cancellation but terminates in `timed_out` rather than `cancelled`.
- Generic Saga/compensation semantics are outside v0.1.

See ADR 0014.

## Arbitrary code

- Ordinary steps invoke named capabilities.
- Ordinary steps do not expose ambient shell/JavaScript/Python `run:` execution.
- Arbitrary user-supplied code is available only through an explicit privileged code capability and may be routed only to an executor suitable for that trust boundary.

See ADR 0004.

## Initial trigger surface

v0.1 exposes three start modes:

1. `manual` — an explicit caller/MCP request starts a run.
2. `webhook` — an authenticated external event starts a run after normalization.
3. `schedule` — a declared schedule starts a run.

The trigger abstraction remains extensible so future adapters such as RSS, GitHub, email, Sentry, databases, or MCP-originated events can normalize into the same Trigger Event model without changing workflow execution semantics.

## Scheduling

- Workflow schedules are runtime definitions and do not consume one Cloudflare Cron binding per workflow.
- v0.1 uses one periodic scheduler tick to evaluate due schedule definitions and admit schedule occurrences through the normal trigger-admission path.
- The schedule DSL accepts cron plus an explicit timezone.
- A scheduled occurrence uses a stable key including schedule identity and intended scheduled time.
- Misfire default is `latest`: after downtime, admit only the latest missed occurrence rather than replay every missed tick.
- Additional policies such as `skip` or full `catchup` are deferred.

See ADR 0015.

## Secret ownership and external executor authentication

- Workflow definitions contain secret references, never secret values.
- The workflow system is the authoritative owner of long-lived workflow business secrets.
- External executors receive short-lived, narrowly scoped Credential Leases rather than a durable copy of the secret catalog.
- Dispatch payloads and ordinary run state must not contain secret values.
- The GitHub Executor uses GitHub Actions OIDC to establish job identity; it does not store a long-lived workflow-service bootstrap secret.
- The workflow service validates configured GitHub identity claims before issuing an execution-scoped Credential Lease.
- GitHub dispatch contains a non-secret Execution Request identifier, not business credentials.
- Executor callbacks/results are correlated to their Execution Request and must be replay-resistant.

See ADR 0005 and ADR 0009.

## Artifact model

- Small structured results remain inline Step Outputs.
- Large, binary, or otherwise unsuitable results become Artifacts referenced by stable Artifact References.
- Cloudflare R2 is the v0.1 canonical artifact byte store.
- Executor-native artifact systems may be used for debugging convenience but are not authoritative workflow storage.
- Artifact References are executor-independent and include enough metadata to identify and validate the stored content.

See ADR 0010.

## MCP integration and connections

- MCP is a Capability Adapter, not an Executor.
- `mcp.call` represents a workflow capability; a real Executor still performs the protocol call.
- MCP server targets come from a named Connection Registry.
- Workflow definitions use Connection References and cannot supply arbitrary MCP URLs or raw connection credentials inline.
- Connection Registry entries are runtime-managed resources rather than one source-controlled deployment binding per external connection.
- v0.1 persists connection metadata plus encrypted credential material in workflow runtime storage; one root key held as a platform secret protects connection credentials with authenticated encryption and supports key-versioned rotation.
- Adding, disabling, or rotating a Connection must not require redeploying the Worker.
- v0.1 initially requires only the MCP connection type but the registry model must not prevent later HTTP/database/OAuth connection types.
- Existing MCP applications remain independent bounded contexts and are not copied into the workflow application.

See ADR 0011 and ADR 0016.

## Authoring, expressions, and canonical representation

- YAML is the v0.1 human authoring format, not the workflow's canonical identity format.
- Parsing produces a validated canonical JSON-like intermediate representation before execution or version hashing.
- Validation includes schema checks, DAG validation, expression parsing, and capability/reference validation.
- Expressions compile into a restricted AST and may read declared workflow/trigger/input/step-output/status data and use a small fixed operator/function set.
- Expressions cannot evaluate arbitrary JavaScript, access files/network, dynamically import code, or call undeclared functions.
- Secret references use typed reference objects rather than ordinary string interpolation so secret values cannot accidentally flow through template rendering, output, or logs.
- The canonical representation is deterministically serialized and hashed to produce Workflow Definition Version identity.

See ADR 0017.
