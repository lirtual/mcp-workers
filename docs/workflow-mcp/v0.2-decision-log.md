## Accepted in Round 1

| ID | Decision |
| --- | --- |
| Q1 | Business workflow definitions/acceptance assets live in independent Git source, separate from engine code. |
| Q2 | Authorized GitHub Actions verifies and registers immutable definitions through a protected admin surface; activation requires approval; no arbitrary runtime Git URL reads. |
| Q3 | Git is authoritative for authored definitions; D1 holds active registry, immutable plans, and state; R2 is optional for large packages/artifacts. |
| Q4 | Non-secret Connection metadata can be approved and independently registered; credentials stay in Workers Secrets and unprovisioned references fail closed. |
| Q5 | Workflows use only approved capabilities, connections and operations; cannot supply arbitrary endpoints, secret names, executors or code. |
| Q6 | Version changes affect new Run admission only; older Runs remain pinned. Deactivation blocks new admission without implicit cancellation; no duplicate scheduled occurrences. |
| Q7 | Validate before activation, keep current version on failure, roll back to an approved immutable digest, retain history. |
| Q8 | Focused trusted-Git workflow delivery; seven public MCP tools unchanged; no online editor, arbitrary code, multi-user RBAC, or plugin marketplace. |

## Source findings and to-spec technical obligations

The following are **implementation and test contracts to make concrete**, not requests to reopen Q1–Q16:

1. **Registry and concurrent admission:** `src/registry.ts`, `src/admission.ts`, `src/mcp.ts`, `src/triggers.ts`, and `src/scheduler.ts` currently use a generated static registry. Specify D1 active-pointer schema, registry lookup consistency, compare-and-swap/transaction behavior, admin publisher identity, audit events, and behavior when activation races a manual/webhook/schedule admission. Never admit an unvalidated, inactive or revoked definition.
2. **Immutable plan and compatibility:** `workflow_definition_versions` already stores plans by digest. Specify canonical envelope, source provenance, digest recomputation, DSL/engine/capability compatibility gates and version retention. Restart or cross-version recovery must use the pinned historical plan, not the live registry.
3. **Connection and revoke semantics:** `src/connections.ts`, `effective-policy.ts`, `mcp-client.ts` and `compiler.ts` bind to static Connection metadata and policy today. Specify independently approved metadata/operation registration, version pinning, trusted descriptor validation, live revocation gate and safe policy non-escalation. Existing Worker Secrets remain authoritative; adding an unprovisioned binding fails closed and **may require an explicitly authorized platform Secret/version update**. Do not promise zero platform updates for newly needed credentials.
4. **Atomic scheduling:** `scheduler_state` currently keys `workflow_id:trigger_id` and computes from `last_evaluated_at`. Specify same-key cron/timezone change, activation timestamp and cursor migration, duplicate-tick concurrency, recovery after partial activation failure and bounded scanning. The D1 commit and external Cloudflare `WORKFLOW.createBatch` cannot be treated as one distributed atomic transaction: preserve durable admission and idempotent create/reconciliation.
5. **Publication trust and failure recovery:** Define source-revision pin, immutable package manifest, publisher authorization separate from `MCP_ACCESS_TOKEN`, independent admin verification, approval/activate split, replay protection, safe retry, audit/redaction, pre-activation dry run, and rollback after partial publishing. Avoid running arbitrary CI-supplied JavaScript or arbitrary Git URL contents in the Worker.
6. **v0.1 migration/rollback:** Stage an import of bundled digest-compatible entries and current schedule state before changing readers. Validate exact old definition hashes and nonterminal Runs, then phased activation and separate authorized production cutover. Keep prior lookup/rollback viable until verified; historical #107/#108 acceptance is not proof of v0.2 success.
7. **Budget and acceptance:** Choose numeric limits against Workers/D1 constraints and current test results. Test invalid definitions, unknown credential/reference, unauthorized publisher, tampered digest, duplicate publish, admission/activation races, deadline/retry/indeterminate effects, old-version resume, schedule timezone changes, no unexpected GitHub dispatch for Raindrop, and full heavy GitHub/R2 regression.

## Final architecture consensus

No remaining *product-level architecture choice* in Q1–Q16 blocks writing a buildable specification. The to-spec phase must select precise schemas, endpoints, algorithms, numeric bounds and failure/rollback test cases by inspecting repository code and authoritative platform documentation. If a new **material owner trade-off** appears, record it as an explicit amendment to ADR 0029 instead of silently treating a design proposal as accepted.
