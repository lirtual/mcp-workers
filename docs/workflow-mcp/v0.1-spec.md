# Workflow MCP v0.1 Technical Specification

Status: ready for implementation
Date: 2026-09-18
Authority: `docs/workflow-mcp/v0.1-architecture-reduction.md`

This specification translates the settled v0.1 architecture into implementation contracts, schemas, state transitions, public interfaces, and verification requirements. When an older ADR conflicts with this document, use the ADR's v0.1 disposition plus the architecture-reduction baseline.

## 1. Problem

The repository has multiple independent MCP Workers and needs a small automation runtime that can compose them and other capabilities without turning the monorepo into one shared MCP platform.

The runtime must support durable orchestration, external waits, controlled retries, lightweight Cloudflare execution, and explicitly selected heavy GitHub execution. It must remain safe under duplicate trigger delivery, uncertain GitHub dispatch responses, repeated/late callbacks, executor loss, non-idempotent external writes, cancellation while waiting, and deployment while runs are nonterminal.

The product goal is not to reproduce n8n. The extensibility target is:

1. adding a workflow made from existing capabilities changes only a workflow definition and tests;
2. adding a capability adds one registered capability module and tests without changing orchestration core;
3. a future executor can implement the executor contract without redefining workflow semantics.

## 2. Solution

Add an independent `apps/workflow-mcp-worker` application with five narrow runtime components:

| Component | v0.1 responsibility |
| --- | --- |
| Worker | MCP/API surface, authentication, definition lookup, trigger/callback ingress, static connection metadata, executor authorization |
| Cloudflare Workflows | authoritative DAG progression, durable waits, timeout/cancellation progression, explicit retry decisions |
| D1 | definition snapshots, admission records, run/step/attempt projections, Attempt Claims, dispatch facts, callback inbox, scheduler state, lifecycle events, artifact metadata |
| R2 | canonical large artifacts only |
| GitHub Actions | registered heavy capabilities requiring a fuller Node/Python/browser/file-processing environment |

Cloudflare Workflows decides what may run next. D1 persists durable coordination/query facts but never independently advances the DAG. GitHub reports executor facts but never decides business success or workflow progression.

## 3. User stories

1. As a workflow caller, I want to list available workflows, so that I can discover supported automations without learning implementation details.
2. As a workflow caller, I want to inspect a workflow's inputs and description, so that I can supply valid input.
3. As a workflow caller, I want to start a workflow asynchronously, so that long-running work does not block the MCP request.
4. As a workflow caller, I want an optional idempotency key for manual starts, so that retries of my request can resolve to the same logical run.
5. As a workflow caller, I want to inspect run and step status, so that I can tell what is running, waiting, failed, cancelled, or uncertain.
6. As a workflow caller, I want to retrieve terminal outputs and artifacts, so that I can consume the workflow result.
7. As a workflow caller, I want a concise lifecycle history, so that I can understand retries, waits, failures, and cancellation without reading raw executor logs.
8. As a workflow caller, I want cancellation to report the truth about active external work, so that a cancellation request is never presented as a rollback that did not happen.
9. As a webhook producer, I want repeated delivery of the same event to resolve to one logical run, so that transport retries do not duplicate the workflow.
10. As a scheduled-workflow owner, I want missed schedules to use the declared misfire policy, so that recovery from downtime is predictable.
11. As a workflow author, I want to add a workflow using existing capabilities by adding a definition and tests, so that routine automation growth does not modify orchestration core.
12. As a workflow author, I want invalid workflow definitions to fail before deployment, so that malformed DAGs or references never become runtime surprises.
13. As a maintainer, I want each capability to declare its contract and execution placement, so that retries, timeouts, and executor routing remain deterministic.
14. As a maintainer, I want a dynamic MCP call to resolve the policy of the selected remote tool, so that read-only and unsafe write operations are not treated as equally retryable.
15. As an operator, I want external MCP connections to use named, pre-approved endpoints and platform-managed secrets, so that workflows cannot choose arbitrary destinations or request arbitrary credentials.
16. As an operator, I want connection authentication to reproduce the actual wire format, so that raw authorization values, Bearer credentials, and custom prefixes all work without unsafe assumptions.
17. As an operator, I want duplicate physical GitHub jobs to compete for one Attempt Claim, so that dispatch uncertainty does not authorize duplicate business work.
18. As an operator, I want an uncertain external write to become explicitly indeterminate, so that the system does not blindly repeat a possibly completed side effect.
19. As an operator, I want callbacks persisted before orchestration notification, so that a transient notification failure cannot strand a completed external attempt.
20. As an operator, I want stale or duplicate callbacks isolated to their original attempt, so that old executor facts cannot change a later attempt's outcome.
21. As an operator, I want a waiting workflow to wake when cancellation is requested, so that cancellation does not remain stuck behind a long external wait.
22. As an operator, I want nonterminal runs to resume with their original definition plan after deployment, so that a later definition edit does not reinterpret work already in progress.
23. As an operator, I want external contract drift to fail explicitly when the selected operation no longer matches, so that the runtime never invents replacement parameters.
24. As an operator, I want unavailable or exhausted GitHub execution to produce an explicit state, so that a run does not remain falsely "running" forever.
25. As an operator, I want heavy results uploaded directly into canonical artifact storage, so that large files do not pass through Worker request bodies.
26. As a security owner, I want executor credentials scoped to a registered attempt, so that a valid executor identity cannot retrieve unrelated secrets or execute arbitrary work.
27. As a maintainer, I want end-to-end tracer workflows, so that both local and remote execution paths can be verified before adding business workflows.

## 4. Repository and module boundaries

The new app follows existing monorepo conventions: independent app package, Wrangler configuration, TypeScript source, unit/integration tests, and a `check` script consumed by root CI.

Expected app-level modules:

| Boundary | Responsibility |
| --- | --- |
| entrypoint | HTTP routing, Cron entry, Workflows class export |
| MCP surface | seven stable workflow tools and portal authentication |
| registry/compiler | YAML loading, schema validation, expression parsing, canonical normalization, digest generation, generated registry |
| orchestration | DAG readiness, conditions, run/step/attempt state transitions, retries, waits, cancellation |
| capabilities | static descriptor registry and Cloudflare-side implementations |
| connections/MCP adapter | static connection config, secret resolution, MCP discovery/call, effective operation policy |
| executors/github | dispatch, OIDC Claim endpoint, manifest/lease issuance, callback and cancellation reconciliation |
| storage | D1 repositories/migrations, R2 artifact metadata/object helpers |
| triggers | manual admission, webhook normalization, schedule evaluation |
| observability | essential lifecycle events and redacted operational logs |
| runner | GitHub-hosted generic runner and registered heavy-capability implementations |

The only shared package required by v0.1 is the existing `@mcp-workers/portal-auth` package for the model-facing MCP endpoint. Do not create a generic workflow platform package in `packages/` for v0.1.

Repository additions include:

- `apps/workflow-mcp-worker`
- `.github/workflows/workflow-executor.yml`
- workflow definitions under the new app
- D1 migrations under the new app
- root CI selection for `workflow-mcp-worker`

The GitHub executor workflow is dispatch-only and must not run on ordinary push or pull-request events.

## 5. Workflow authoring contract

### 5.1 Top-level definition

A v0.1 workflow definition contains:

- `version`: DSL major version; v0.1 accepts only version 1.
- `id`: stable workflow identifier.
- `name` and optional description.
- `inputs`: bounded typed input definitions.
- `triggers`: zero or more manual/webhook/schedule trigger definitions.
- `steps`: named DAG steps.
- `outputs`: optional named expressions exposed after successful completion.

Workflow IDs and step IDs use a conservative ASCII identifier alphabet compatible with URLs, D1 keys, and logs.

### 5.2 Inputs

v0.1 supports scalar input types required by the tracer workflows: string, number, boolean, and optional enum constraints. Complex objects may be passed only where the target Capability schema explicitly allows them.

Input validation runs at admission before a Run is created.

### 5.3 Steps

Each Step declares:

- `uses`: registered Capability name.
- `needs`: zero or more upstream Step IDs.
- optional `if`: restricted expression.
- `with`: Capability input template.
- optional Step timeout.
- optional retry reduction within the policy allowed by the resolved operation.

v0.1 does not expose an arbitrary `run:` field and does not allow a workflow definition to override executor routing. Executor placement comes from the pinned Capability contract.

### 5.4 Expression semantics

Expressions may:

- read `input.*`, normalized trigger data, and `steps.<id>.outputs.*`;
- compare scalar values;
- use boolean `and`, `or`, and `not`;
- use the status predicates `success()`, `failure()`, and `always()`.

All declared dependencies must reach a terminal Step state before a dependent Step condition is evaluated.

- no `if` is equivalent to `success()`;
- `success()` is true only when all declared dependencies succeeded;
- `failure()` is true when any declared dependency failed, timed out, or became indeterminate;
- `always()` is true after all dependencies are terminal regardless of their result;
- run-level cancellation is an outer gate: once `cancel_requested` is durable, no new Step starts even when its condition is `always()`.

A false condition produces `skipped_condition`. A Step whose implicit success condition cannot be satisfied because a dependency did not succeed produces `skipped_dependency`.

Expressions have no arbitrary function calls, I/O, dynamic import, JavaScript evaluation, loops, or mutation.

### 5.5 Triggers

v0.1 supports:

- manual start through MCP;
- webhook start through a dedicated HTTP route;
- schedule start through one periodic scheduler Cron.

A generic webhook requires an authenticated trigger secret and a stable caller-supplied event key header. If the event key is absent, the webhook is rejected rather than inventing a hash that might collapse legitimate repeated events.

A schedule occurrence Admission Key includes workflow ID, trigger ID, and intended scheduled time. v0.1 supports `misfire: latest`; business workflows that must recover every missed window must implement their own cursor/catch-up semantics.

## 6. Build-time registry and definition identity

The build step parses every workflow YAML and rejects:

- unknown top-level/Step fields;
- duplicate workflow or Step IDs;
- missing dependencies;
- DAG cycles;
- unknown capabilities;
- invalid static Connection references;
- invalid expression syntax or references;
- Capability input keys that cannot ever satisfy the descriptor schema;
- unsafe retry requests that exceed the resolved static policy.

Normalization must be deterministic:

- object keys are sorted recursively;
- shorthand forms are expanded to one normalized form;
- durations are normalized to one numeric unit;
- expressions are stored in normalized parsed form;
- semantic array order is preserved;
- non-semantic authoring details such as comments/whitespace do not affect identity.

The normalized serialized plan has a v0.1 hard limit of 256 KiB. Its SHA-256 digest is the Workflow Definition Version.

The generated registry bundled into the Worker contains current workflow metadata plus normalized plans/digests for new admissions. It is the discovery source for new Runs only.

## 7. Content-addressed pinned plans

D1 stores each normalized plan once in `workflow_definition_versions`, keyed by `definition_digest`. Every Run references that digest; Runs do not copy the same plan JSON repeatedly.

At admission, the Worker ensures the bundled definition version exists in D1 before starting the Cloudflare Workflow instance.

A waiting Run always reloads its plan through its pinned `definition_digest`; it never resolves the current bundled registry entry by workflow ID.

The stored plan includes the v0.1 information needed for stable interpretation:

- DSL version;
- workflow/Step graph and normalized expressions;
- capability contract version identifiers;
- deterministic executor routing;
- static Connection references;
- normalized default/retry/timeout decisions that affect semantics.

## 8. D1 schema

The implementation uses migrations and foreign keys/indexes suitable for the following logical tables.

### 8.1 `workflow_definition_versions`

Required fields:

- `definition_digest` primary key;
- `workflow_id`;
- `dsl_version`;
- normalized plan JSON;
- source path and source commit when available;
- created timestamp.

### 8.2 `run_admissions`

Required fields:

- Admission Key primary key;
- `run_id` unique;
- workflow/trigger source metadata;
- created timestamp.

For deduplicated webhook/schedule/manual-idempotent starts, Run ID is deterministically derived from the Admission Key. Manual starts without an idempotency key use a random Run ID.

### 8.3 `workflow_runs`

Required fields:

- `run_id` primary key;
- `workflow_id`;
- `definition_digest` foreign key;
- normalized input JSON;
- trigger metadata;
- state;
- created/started/ended timestamps;
- cancellation-request timestamp;
- terminal error/indeterminate code and safe summary;
- `engine_version`;
- Cloudflare Workflow instance ID;
- nullable `cf_workflow_version_id` provenance field.

Use the Run ID as the Cloudflare Workflow instance ID so application and orchestration identities are directly correlated.

### 8.4 `step_runs`

Required fields:

- `step_run_id` primary key;
- `run_id`;
- Step ID;
- stable `operation_id`;
- state;
- resolved Effective Operation Policy JSON or normalized fields;
- output JSON for small safe results;
- terminal error code/summary;
- timestamps.

There is one Step Run per workflow Step per Run. Operation ID remains stable across all Attempts of that Step Run.

### 8.5 `step_attempts`

Required fields:

- `attempt_id` primary key;
- `step_run_id`;
- attempt number;
- executor type;
- state;
- dispatch-generation counter;
- Attempt claim-nonce verifier/hash;
- claim owner;
- claim/observation deadline timestamps;
- bound GitHub run ID/run attempt/workflow SHA when claimed;
- executor/runner version;
- dependency snapshot when relevant;
- terminal result/error fields;
- timestamps.

A retry creates a new Attempt row and retains the Step Run's Operation ID.

### 8.6 `executor_dispatches`

One row per physical GitHub dispatch generation:

- Attempt ID + generation unique key;
- dispatch timestamp;
- request correlation data;
- outcome: `accepted`, `unknown`, or `failed`;
- returned GitHub workflow run ID when available;
- safe error summary when failed.

An `unknown` dispatch is evidence that an unobserved Candidate Job may exist and therefore affects Claim run-ID matching.

### 8.7 `callback_inbox`

Required fields:

- callback ID primary key;
- Attempt ID;
- authenticated/bound GitHub physical identity;
- callback kind;
- normalized result metadata;
- received timestamp;
- notification attempt count;
- next notification time;
- notified timestamp;
- ignored/stale reason when applicable.

Insertion is idempotent by callback ID. Inserting a callback never directly advances the DAG.

### 8.8 `workflow_events`

Append-only essential lifecycle projection:

- monotonically ordered event ID;
- Run ID;
- optional Step Run/Attempt ID;
- event type;
- redacted structured summary;
- timestamp.

This is not an event-sourcing log. It stores only facts needed for `workflow_logs` and diagnosis.

### 8.9 `scheduler_state`

Per compiled schedule:

- schedule key;
- last evaluation;
- last admitted logical occurrence;
- next due occurrence.

Schedule definitions themselves remain in the bundled/pinned workflow definitions.

### 8.10 `artifacts`

Required fields:

- artifact ID primary key;
- Run/Step/Attempt IDs;
- R2 object key;
- name/media type;
- size;
- reported content digest;
- created timestamp.

Artifact bytes are never stored in D1.

## 9. State model

### 9.1 Workflow Run states

`queued`, `running`, `waiting`, `cancel_requested`, `succeeded`, `failed`, `cancelled`, `timed_out`, `indeterminate`.

`indeterminate` is a truthful terminal v0.1 outcome when a potentially side-effecting operation or cancellation cannot be reconciled safely. v0.1 does not add an operator-resolution mutation API.

### 9.2 Step Run states

`pending`, `running`, `succeeded`, `failed`, `skipped_condition`, `skipped_dependency`, `cancelled`, `timed_out`, `indeterminate`.

### 9.3 Step Attempt states

`queued`, `claimed`, `running`, `succeeded`, `failed`, `cancel_requested`, `cancelled`, `timed_out`, `indeterminate`.

GitHub dispatch state is not encoded by inventing more Attempt states; physical dispatch generations live in `executor_dispatches`.

## 10. Admission

Admission is separate from execution.

- manual without idempotency key: create a fresh Run;
- manual with key: Admission Key scopes the key to workflow ID;
- webhook: Admission Key uses workflow/trigger/stable event key;
- schedule: Admission Key uses workflow/trigger/intended scheduled time.

Duplicate admission returns the existing Run ID and marks the response as already admitted rather than failing.

Admission creates/pins the definition version before starting orchestration. Starting the Cloudflare Workflow instance uses the Run ID as its instance ID. If instance creation races with duplicate admission, an already-existing instance is treated as the same admitted Run rather than as a second logical run.

## 11. Orchestration algorithm

Cloudflare Workflows is the only component that determines DAG progression.

For each Step:

1. wait until dependencies are terminal;
2. re-read the Run cancellation gate;
3. evaluate the Step condition;
4. resolve input expressions;
5. validate resolved input against the Capability schema;
6. resolve/pin the Step's Effective Operation Policy;
7. create a Step Run if not already present;
8. create one new Attempt;
9. execute locally or dispatch remotely according to the pinned Capability contract;
10. persist the Attempt result;
11. apply retry policy by creating a new Attempt only when safe;
12. finalize the Step Run;
13. continue independent branches or derive the final Run outcome.

Capability execution is not delegated to Cloudflare Workflows' implicit retry defaults. Steps that dispatch or perform business operations explicitly disable/override platform automatic retries so the workflow engine's Attempt model remains authoritative.

## 12. Capability Registry

The Capability Registry is a static TypeScript registry.

Every descriptor provides:

- stable capability name;
- contract version;
- input and output validation schema;
- fixed v0.1 executor;
- timeout defaults/maxima;
- static effect/retry policy or an Effective Operation Policy resolver;
- implementation reference for the permitted executor.

v0.1 does not support installable plugins, runtime capability registration, or AI/heuristic executor selection.

Initial capabilities are limited to those required by the tracer flows:

- a bounded Cloudflare-side HTTP fetch capability restricted to safe HTTP(S) reads;
- generic `mcp.call`;
- one registered GitHub heavy capability that transforms fetched content into a Markdown archive artifact.

The heavy capability may internally perform several operations, but its descriptor owns retry/reconciliation semantics for the whole business operation.

## 13. Effective Operation Policy

Static capabilities use the descriptor's policy directly.

`mcp.call` resolves policy for the concrete `Connection + Tool`:

1. local explicit tool policy;
2. tool annotations only when the Connection explicitly opts into trusting them;
3. `unknown`.

Minimum classes:

| Class | Default automatic attempts |
| --- | --- |
| `read` | bounded retries allowed |
| `idempotent_write` | bounded retries allowed only under the declared idempotency semantics |
| `unsafe_write` | one attempt |
| `unknown` | one attempt, treated conservatively like unsafe write |

A Step-level retry setting may lower the number of allowed attempts. It may not raise an `unsafe_write` or `unknown` operation above one automatic attempt.

If a write is safe only when an idempotency key is propagated, the local policy must declare how the stable Operation ID is mapped into the remote invocation. Without that mapping, the write is not automatically retry-safe.

MCP annotations never override an explicit local policy.

## 14. Static Connection model

v0.1 Connection metadata is source-controlled/static; credential values live in Workers Secrets.

Each MCP Connection declares:

- stable connection ID;
- Streamable HTTP endpoint supported by v0.1;
- authentication header name;
- auth format: raw value, Bearer, or explicit configured prefix;
- Workers Secret name;
- whether MCP tool annotations are trusted for effective-policy fallback;
- optional per-tool Effective Operation Policies.

The Worker derives secret disclosure from the server-side Connection/Capability configuration. Executor requests never contain arbitrary secret names.

v0.1 does not promise compatibility with every MCP transport/session/OAuth pattern. Only configured/tested combinations are supported.

## 15. GitHub executor protocol

### 15.1 Dispatch

Worker-to-GitHub authentication uses one minimal repository-scoped platform credential with Actions write permission.

The generic `workflow-executor.yml` is invoked only with:

- Attempt ID;
- high-entropy Attempt-scoped claim nonce;
- no business secret values.

Use the GitHub workflow-dispatch response mode that returns run details when available. Each HTTP dispatch attempt increments the Attempt's dispatch generation and creates an `executor_dispatches` record.

- a returned run ID records `accepted`;
- an explicit non-acceptance records `failed`;
- a network/response ambiguity after request transmission records `unknown`.

A bounded retry may create another Candidate Job for the same logical Attempt; it does not create another Attempt.

### 15.2 Candidate identity and Claim

The GitHub job requests an OIDC token with a dedicated audience for Workflow MCP.

The Claim endpoint requires:

- Attempt ID;
- claim nonce;
- GitHub OIDC bearer token.

The server verifies current signature/issuer/audience/time validity and the configured repository ID, workflow identity/ref, and any pre-pinned workflow SHA. It then applies physical-run matching:

- if exactly one accepted dispatch run ID is known and no earlier generation has unknown outcome, the Candidate must match it;
- if any prior dispatch outcome is unknown, a valid Candidate is not rejected merely because a later dispatch returned another run ID.

The Claim is one conditional D1 mutation that succeeds only while the registered Attempt is still `queued`, the nonce verifier matches, the Run is not cancelled, and no physical run has already been bound.

The successful mutation simultaneously records `claimed`, claim owner/timestamp/deadline, GitHub run ID, GitHub run attempt, and observed workflow SHA. Exactly one changed row means authorization succeeded. Zero changed rows means the Candidate performs no business work and exits cleanly.

The claim deadline is only a reconciliation deadline. It never transfers ownership.

### 15.3 Credential Lease and Execution Manifest

After Claim, the server issues a short-lived signed Credential Lease scoped to:

- Run/Step/Attempt;
- bound physical GitHub identity;
- permitted manifest read;
- permitted artifact allocation;
- permitted result callback.

The server constructs the Execution Manifest from the pinned Step, Capability Descriptor, Connection configuration, and resolved non-secret input. The Job cannot choose another Capability or request another Connection/secret.

Every lease-protected endpoint re-checks that the Attempt is still bound to the same physical run and is in an allowed state.

### 15.4 Execution and result

The generic runner maps the manifest's registered heavy-capability name to a checked-in runner implementation. It does not execute arbitrary shell/script supplied by workflow input.

A duplicate Candidate that failed Claim may exit successfully at the GitHub-job level; that never counts as business success.

Business success requires a valid callback from the Claim owner with a result satisfying the Capability output contract.

## 16. Artifact protocol

Large external-executor outputs use direct R2 upload.

The claimed runner requests one Artifact Upload Allocation. The Worker:

- chooses the object key;
- scopes it to the current Run/Attempt/artifact ID;
- returns a short-lived presigned PUT URL;
- never returns durable R2 credentials.

After upload, the callback names the artifact ID, metadata, size, and digest. Before accepting the artifact into the business result, the Worker checks via the R2 binding that the expected object exists and its basic metadata is consistent.

`workflow_result` returns Artifact References. When a caller needs download access, the Worker generates a short-lived read URL on demand; presigned URLs are never persisted to D1 or lifecycle logs.

## 17. Callback Inbox and Attempt event channel

A result callback:

1. verifies the Credential Lease and bound physical GitHub identity;
2. validates the normalized result;
3. idempotently inserts the callback into `callback_inbox`;
4. attempts to send a wake-up event to the Cloudflare Workflow instance.

The event type is `attempt_<AttemptID>`. Attempt IDs must keep the full event type within Cloudflare's 100-character event-type limit and allowed character set. v0.1 UUID-form Attempt IDs satisfy this.

The event payload has only a small `kind` plus correlation metadata. At minimum the kinds are:

- `result`;
- `cancel_requested`.

The event is not authoritative data. After wake-up, orchestration re-reads the callback inbox, Run cancellation flag, Attempt Claim, and relevant executor facts.

Because the event type is unique per Attempt, stale/duplicate events cannot wake a later Attempt. Cloudflare may buffer an event that arrives before the corresponding wait, which is compatible with this contract.

When notification fails, the inbox row remains pending. The existing periodic scheduler/maintenance tick retries a bounded number of due notification rows with backoff. A wait timeout performs the same reconciliation before deciding failure, retry, or indeterminate outcome.

## 18. Cancellation

`workflow_cancel` is idempotent.

For a nonterminal Run it:

1. persists `cancel_requested`;
2. prevents all new Steps from starting;
3. sends `kind=cancel_requested` on the active Attempt-specific event channel when the Run is waiting for a remote Attempt;
4. returns current cancellation state without claiming rollback.

When awakened, orchestration:

- denies any unclaimed Candidate Jobs through the Claim gate;
- requests GitHub cancellation for all known/bound relevant run IDs;
- waits/reconciles callback inbox and GitHub run facts;
- records `cancelled` only when active work is confirmed stopped/resolved;
- records `indeterminate` if the external operation/stop outcome cannot be established safely within the reconciliation policy.

Do not immediately call Cloudflare Workflow `terminate()` as the normal cancellation path. Hard termination is an operational fallback only after durable state has been reconciled enough to preserve truth.

## 19. Retry and indeterminate outcomes

A retry always creates a new Attempt ID under the same Step Run and keeps the same Operation ID.

Automatic retries are allowed only by the Effective Operation Policy.

If an external write may have completed but response/result evidence is missing:

- reconcile callback inbox;
- reconcile bound executor facts;
- use upstream idempotency/status APIs when explicitly supported;
- otherwise mark the Attempt/Step/Run `indeterminate`.

`indeterminate` is not converted to ordinary failure and is not automatically retried.

## 20. External MCP contract drift

Before each `mcp.call`, the adapter verifies the selected tool is present and validates the resolved invocation against the live tool input contract.

When available, store a compact Dependency Snapshot on the Attempt containing connection ID, tool name, remote server version, and schema fingerprint.

A fingerprint change alone is diagnostic and does not imply failure. Fail explicitly only when the selected tool is missing or the actual invocation is incompatible. v0.1 never uses AI to rewrite arguments or select a replacement tool.

## 21. Runtime provenance and deployment compatibility

Every Run records:

- DSL version;
- definition digest;
- application `engine_version`, sourced from the deployed Worker version metadata binding;
- Cloudflare Workflow instance ID;
- nullable `cf_workflow_version_id`.

Every remote Attempt records bound GitHub run identity and runner implementation version/revision.

Cloudflare's REST control-plane APIs expose Workflow `version_id`, but the Worker binding's `WorkflowInstance` creation/runtime event contract does not currently expose that value directly. v0.1 therefore **does not introduce a Cloudflare API token solely to populate this provenance field**. Keep the column nullable and populate it only if it becomes available without widening runtime authority. The field is diagnostic, not required for correctness.

The hard correctness rule remains: a deployed engine/runner must understand all nonterminal stored plan/protocol versions, or deployment must be blocked/deferred until explicit migration/termination. `cf_workflow_version_id` may later allow this policy to be simplified after platform behavior is proven by integration tests; v0.1 does not assume that guarantee.

## 22. MCP public contract

The MCP endpoint reuses `@mcp-workers/portal-auth` and exposes exactly seven tools.

### 22.1 `workflow_list`

Input: none.

Returns workflow ID, name, description, definition digest, supported trigger types, and compact input metadata. Never returns secrets or raw connection config.

### 22.2 `workflow_get`

Input: workflow ID.

Returns the current bundled definition's safe metadata: inputs, outputs, trigger descriptions, Step/capability names, and definition digest. It does not expose secret values.

### 22.3 `workflow_run`

Input:

- workflow ID;
- input object;
- optional manual idempotency key.

Returns:

- Run ID;
- current state;
- definition digest;
- whether this request resolved to an already-admitted Run.

It never waits for terminal completion.

### 22.4 `workflow_status`

Input: Run ID.

Returns Run state, safe timestamps, Step summaries, active Attempt summary, cancellation/indeterminate reason where relevant, and artifact count. It does not return raw executor logs.

### 22.5 `workflow_result`

Input: Run ID.

For a terminal Run, returns terminal state, named workflow outputs, Artifact References, and safe error/indeterminate details. For a nonterminal Run it returns `ready=false` with current state rather than blocking.

### 22.6 `workflow_logs`

Input: Run ID plus optional cursor/limit.

Returns ordered essential lifecycle events from D1. Pagination uses the monotonically increasing event ID.

### 22.7 `workflow_cancel`

Input: Run ID.

Idempotently requests cancellation and returns the current truthful state. Repeating cancellation does not create additional side effects.

## 23. HTTP/internal surfaces

The Worker has four separate trust surfaces.

### 23.1 MCP surface

`/mcp` uses the existing portal-auth package and the application's MCP credential.

### 23.2 Webhook surface

A workflow/trigger-specific route accepts only its configured authentication secret and required stable event key. It can only admit the bound workflow trigger.

### 23.3 Executor Claim surface

Accepts GitHub OIDC plus Attempt correlation material. It can only claim a server-registered Attempt and issue that Attempt's narrow lease/manifest.

### 23.4 Lease-protected executor surface

Supports only the claimed Attempt's artifact allocation and result callback. It cannot list connections, retrieve arbitrary secrets, run workflows, or administer the system.

There is no runtime Connection-admin API in v0.1. Non-secret connection changes are source changes; secret values are managed with Cloudflare Workers Secrets.

## 24. Scheduler and maintenance tick

Use one Cloudflare Cron entry with minute-level resolution.

Each tick:

1. evaluates compiled schedules against persisted scheduler state;
2. admits due occurrences according to `misfire: latest`;
3. processes a bounded batch of pending callback-notification retries;
4. performs only bounded reconciliation bookkeeping that does not itself execute business operations.

The tick must have explicit batch limits so one backlog cannot consume the whole invocation.

## 25. Logging and observability

D1 lifecycle events include only redacted structured facts such as:

- Run admitted/started/waiting/terminal;
- Step started/skipped/terminal;
- Attempt created/claimed/retry/terminal;
- dispatch accepted/unknown/failed;
- callback received/notified/ignored;
- artifact registered;
- cancellation requested/reconciled.

Raw GitHub stdout/stderr remains in GitHub by default. Cloudflare invocation logs remain operational telemetry. Neither is a source of workflow state.

Secrets, Claim nonces, Credential Leases, presigned URLs, Authorization headers, and raw callback payloads must never enter lifecycle logs.

## 26. Security requirements

- No workflow YAML contains a secret value.
- No executor can choose a secret name.
- No unregistered MCP endpoint can be supplied by workflow input.
- `mcp.call` can target only named configured Connections.
- The initial HTTP fetch capability allows only HTTP(S) reads and rejects loopback, link-local, metadata-service, and private-network destinations unless a future explicit capability allows them.
- GitHub OIDC trust is scoped to the configured repository/workflow/ref and dedicated audience.
- Claim nonce values are high entropy, Attempt-scoped, and not logged; store a verifier/hash where practical.
- Claim is denied after Run cancellation or once another physical run is bound.
- Credential Leases are short-lived and scoped to one Attempt and physical run.
- Worker-to-GitHub token and R2 signing credentials are platform secrets and are never delegated as workflow business secrets.
- Connection tool annotations are ignored for retry classification unless the Connection explicitly opts into trusting them.

## 27. Platform configuration

The new Worker requires:

- D1 binding for workflow state;
- R2 bucket binding for canonical artifacts;
- Cloudflare Workflow binding/class;
- one Cron trigger;
- Worker version metadata binding;
- MCP access secret;
- minimal GitHub Actions API token;
- executor lease-signing secret;
- R2 S3 signing credentials needed for presigned URLs;
- static Connection credential secrets referenced by configured Connections;
- webhook secrets for configured webhook triggers.

Do not add a generic Cloudflare account API token solely for provenance.

## 28. Tracer workflows

### 28.1 `web-archive-smoke`

Manual input: a small public HTTP(S) URL.

Path:

1. local bounded HTTP read;
2. registered GitHub heavy archive capability;
3. direct R2 upload of `archive.md`;
4. callback through the inbox;
5. terminal output containing the Artifact Reference.

This proves definition compilation/digest, manual admission, local capability, GitHub dispatch/Claim/OIDC, Attempt-specific event wake-up, callback inbox, R2 artifact, lifecycle events, and result retrieval.

### 28.2 `mcp-connection-smoke`

Manual input selects no arbitrary endpoint; it calls one configured safe/read-only tool on a declared MCP Connection.

This proves named Connection resolution, auth wire format, MCP discovery/invocation, Effective Operation Policy, live-contract validation, Dependency Snapshot, and local execution independently of GitHub.

## 29. Testing decisions

Prefer high-level public seams and real storage/runtime behavior over mock-heavy internal tests.

### 29.1 Compiler tests

Test workflow definitions through the actual compiler entrypoint:

- valid tracer definitions compile deterministically;
- formatting-only edits preserve digest;
- cycles, invalid references, unknown capabilities, oversized plans, and invalid expressions fail;
- unsafe retry elevation fails.

### 29.2 Worker integration tests

Use the Cloudflare Workers test runtime with real local D1/R2 bindings where supported and invoke HTTP/MCP surfaces rather than calling repository internals directly.

Cover:

- MCP tool schemas and auth;
- duplicate admissions;
- content-addressed definition storage;
- status/result/log pagination;
- webhook event-key dedup;
- scheduler `latest` semantics;
- Artifact metadata registration.

### 29.3 Executor protocol integration tests

Exercise Claim/callback HTTP endpoints with cryptographically valid test JWTs from a test JWKS/issuer configuration. Do not bypass Claim logic with a test-only "trusted" flag.

Cover:

- invalid issuer/audience/repo/workflow denial;
- two concurrent Candidate Jobs: exactly one conditional Claim changes one row;
- physical run binding is immutable;
- ambiguous dispatch generation allows the earlier valid Candidate to bind;
- a known unambiguous dispatch run ID constrains Claim;
- arbitrary secret-name requests are impossible;
- duplicate callbacks are idempotent;
- stale callback cannot change a newer Attempt;
- unclaimed duplicate Job success is not business success.

### 29.4 Workflow/cancellation integration tests

At the highest practical seam, verify:

- Attempt result event sent before the wait is still consumed correctly;
- `workflow_cancel` persists cancellation and sends the active Attempt-specific wake-up event;
- failed notification is retried from durable inbox/cancellation state;
- `always()` does not start after run-level cancellation;
- cancellation remains unconfirmed/indeterminate when executor stop cannot be established.

If local Workflows emulation cannot prove these platform semantics, keep local state-machine tests minimal and require the staging tracer below before implementation is accepted.

### 29.5 Staging end-to-end tracer

A manually invoked or release-gated staging test must use actual Cloudflare Workflows + D1 + R2 and actual GitHub Actions OIDC/dispatch to run `web-archive-smoke`.

It verifies the real cross-platform contract without running on every ordinary PR.

## 30. Fault-scenario acceptance matrix

Implementation must satisfy the architecture-reduction scenarios plus the final pre-spec fixes:

| Scenario | Required result |
| --- | --- |
| duplicate trigger | one logical Run |
| dispatch accepted, response lost | multiple Candidates may exist; one Claim owner only; physical run bound on Claim |
| Claim deadline expires | no ownership transfer; reconcile or indeterminate |
| external unsafe write response lost | no blind retry; indeterminate if unreconciled |
| repeated/late callback | durable record only; no stale state overwrite |
| callback stored, Workflow notification lost | maintenance/wait-timeout reconciliation re-notifies/recovers |
| GitHub unavailable/quota exhausted | explicit not-started/executor-unavailable outcome; no forever-running projection |
| cancellation during remote wait | Attempt-specific event wakes orchestration; no new Steps; truthful stop reconciliation |
| deployment while waiting | Run resumes from content-addressed pinned plan |
| MCP schema fingerprint changes | validate actual invocation; fail only on real contract incompatibility |
| unknown MCP tool policy | conservative one-attempt behavior |
| duplicate GitHub Job exits success without Claim | no business success transition |
| second/third workflow using existing capabilities | no orchestration-core edits |
| new capability | descriptor/module/tests only; no admission/DAG/callback-core edits |

## 31. CI and release gates

Add `workflow-mcp-worker` to root CI affected-app selection.

The app's `check` target must include:

- typecheck;
- lint;
- compiler/registry validation;
- unit tests;
- integration tests;
- Wrangler dry-run deployment validation.

The dispatch-only executor workflow is excluded from ordinary CI execution.

A release is not ready when:

- a stored nonterminal plan/protocol version would become unreadable;
- migrations cannot preserve current nonterminal Run/Attempt state;
- the staging cross-platform tracer fails.

## 32. Explicitly out of scope for v0.1

- runtime workflow authoring/install;
- visual workflow editor;
- n8n-compatible workflow ecosystem;
- installable/hot-loadable capability plugins;
- generic user-supplied shell/JavaScript/Python execution;
- encrypted D1 Connection credential vault;
- runtime Connection administration API/UI;
- persisted workflow queue/dynamic concurrency-key subsystem;
- drop/replace concurrency modes;
- Saga/general compensation engine;
- RBAC, organizations, workspaces, multi-tenant isolation;
- automatic executor selection;
- automatic adjacent-Step batching;
- event-sourcing/replay platform;
- copying all GitHub raw logs into R2;
- arbitrary MCP endpoint/transport/OAuth compatibility;
- AI-generated repair of changed remote tool contracts;
- automatic ownership transfer after Claim deadline.

## 33. Implementation completion criteria

v0.1 is implementation-complete when all of the following are true:

1. both tracer workflows compile and run through their intended public surfaces;
2. all seven MCP tools pass integration tests;
3. the D1 migrations represent the specified identities/states without duplicating full pinned plans per Run;
4. duplicate Candidate Jobs cannot both obtain execution authority;
5. unsafe writes cannot be automatically retried from an indeterminate outcome;
6. callbacks survive notification failure and are Attempt-correlated;
7. cancellation wakes waiting orchestration and reports truthful unresolved outcomes;
8. waiting Runs resume from their pinned definition version across a deployment-compatible release;
9. Effective Operation Policy prevents a generic MCP adapter from treating all tools as equally retry-safe;
10. the architecture-reduction acceptance scenarios and this spec's fault matrix pass;
11. adding a third definition using existing capabilities does not require changes to admission, orchestration, retry, cancellation, callback, or executor-core modules.
