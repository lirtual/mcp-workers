# Workflow MCP v0.1 Architecture Reduction

Status: authoritative pre-spec baseline
Date: 2026-09-17

This document closes the design interview for v0.1. It intentionally reduces the earlier architecture exploration and defines the minimum reliability rules that the implementation specification must preserve.

When this document conflicts with an earlier ADR or with `v0.1-scope.md`, this document controls v0.1. Earlier ADRs remain useful design history and rationale; classification below states how each applies to v0.1.

## 1. v0.1 architecture boundary

v0.1 keeps five runtime components with narrow responsibilities:

| Component | v0.1 responsibility |
| --- | --- |
| Worker | MCP/API surface, authentication, input validation, trigger/callback ingress, connection metadata, executor authorization |
| Cloudflare Workflows | orchestration authority: DAG progression, waits, controlled retries, timeout/cancellation progression |
| D1 | admission records, Step Attempt records/claims, callback inbox, scheduler progress, query projections and essential lifecycle events |
| R2 | large workflow artifacts and necessary large structured results |
| GitHub Actions | explicitly registered heavy capabilities requiring browser/full Node/Python/CLI/file-processing environments |

The extension contract is deliberately small:

1. A workflow composed from existing capabilities adds a definition file without modifying orchestration core.
2. A new capability adds one statically registered capability module without modifying admission, retry, cancellation, callback, or DAG core.
3. A future executor can implement the executor protocol, but v0.1 implements only the executors actually required.

v0.1 does **not** attempt to be a general n8n replacement, runtime plugin marketplace, dynamic code platform, compensation engine, multi-user RBAC system, or arbitrary-MCP compatibility layer.

## 3. Identity model

The implementation must keep these identities distinct:

| Identity | Lifetime / rule |
| --- | --- |
| Admission Key | Stable for the same source event/scheduled occurrence or caller-provided manual idempotency key. |
| Run ID | One logical Workflow Run. |
| Step Run ID | One logical Step within one Run. |
| Operation ID | One logical business operation; **stable across retries/new Attempts of that operation** and propagated to upstream idempotency mechanisms when supported. |
| Attempt ID | One execution attempt; every retry creates a new Attempt ID. |
| GitHub physical identity | `run_id`, `run_attempt`, and relevant workflow/repository identity for the concrete candidate Job. |

`execution_request_id` is not a mandatory independent business identity in v0.1. Prefer using the Attempt ID as the external execution correlation ID unless implementation proves a separate dispatch-request identity is necessary.

## 4. Run admission, dispatch, and Attempt authorization

### 4.1 Three independent reliability layers

v0.1 explicitly separates:

1. **Run admission deduplication** — equivalent trigger delivery resolves to at most one logical Run.
2. **Attempt authorization/claim** — duplicate physical executor Jobs must not simultaneously obtain authority to execute one Attempt.
3. **Business idempotency** — an external side effect is retried only when its business semantics make retry safe.

None of these implies exactly-once execution of external systems.

### 4.2 Attempt claim is not a transferable lease

A remote Attempt begins in `queued`. A candidate Job may claim it with a single conditional D1 mutation equivalent to:

```sql
UPDATE step_attempts
SET status = 'claimed',
    claim_owner = ?,
    claimed_at = ?
WHERE attempt_id = ?
  AND status = 'queued';
```

Authorization succeeds only when the mutation changes exactly one row. The implementation must not perform `SELECT` followed by an unconditional `UPDATE`.

A claim deadline/`claim_until` may exist as an observation deadline, but **expiry does not transfer ownership**. If the claimed Job becomes unreachable:

- reconcile executor facts;
- if external outcome cannot be established, mark the Attempt `indeterminate`;
- create a new Attempt only after orchestration establishes that retry is safe;
- never automatically re-execute a non-idempotent write solely because the claim deadline elapsed.

Therefore the contract is:

> One remote Attempt may have multiple candidate Jobs, but at most one candidate Job is authorized to execute it.

### 4.3 Server-side authorization binding

Possession of a valid GitHub OIDC token is necessary but not sufficient to claim a task.

The server must already have the Attempt/dispatch record and must verify that the token and candidate Job match the registered expectation, including at minimum the configured issuer/audience/time validity and expected repository/workflow identity plus GitHub run identity. The server then atomically claims that specific registered Attempt.

The executor cannot submit an arbitrary Attempt ID and receive authority merely because its JWT is valid.

Credential/secret disclosure is derived from the server-side Capability and Connection configuration for the claimed Attempt. The executor cannot request an arbitrary secret name such as `authSecret=FOO` and have the Worker return it.

## 5. Dispatch uncertainty and retries

A successful GitHub dispatch whose response is lost may cause a dispatch retry and therefore multiple physical Jobs. Attempt claim prevents multiple candidates from becoming authorized, but it does not prevent duplicate Job creation.

Dispatch/retry code must use explicit retry settings rather than inheriting generic workflow retry defaults blindly.

For external business operations:

- retry-safe/read-only capabilities may use bounded automatic retries;
- write capabilities with upstream idempotency support reuse the stable Operation ID as the upstream idempotency key;
- when a write may have succeeded but its response is lost and the upstream cannot confirm/idempotently repeat it, the Attempt becomes `indeterminate`;
- `indeterminate` is not automatically converted into a retryable failure;
- a new Attempt is created only after reconciliation or explicit policy establishes that retry is safe.

A business-meaningful heavy Capability may perform multiple internal operations inside one GitHub Job. That does **not** make those operations transactional. The Capability Descriptor must define retry safety for the capability as a whole and must implement its own internal idempotency/reconciliation where required.

## 6. State authority and callback inbox

The authority boundaries are fixed:

| Fact / decision | Authority |
| --- | --- |
| Which Step may start next, whether the DAG continues, terminal workflow outcome | Cloudflare Workflows orchestration |
| Admission, Attempt claim, callback inbox, essential lifecycle/query projection | D1 |
| Whether a physical GitHub Job started/queued/exited and its executor-level result | GitHub |
| User-facing status/history | D1 projection updated under orchestration rules |

D1 is not a second independent DAG scheduler.

### 6.1 Callback handling

A callback must:

1. authenticate the executor and bind it to the registered Attempt/GitHub identity;
2. idempotently persist the callback/fact into a D1 callback inbox;
3. attempt to notify/resume the waiting Workflow;
4. leave the inbox record pending for redelivery/reconciliation when notification fails.

The system must provide a resend path without introducing another queue product. v0.1 may reuse the existing periodic scheduler/maintenance tick to retry a bounded set of pending callback notifications.

A Workflow wait timeout must reconcile in this order:

1. inspect the callback inbox;
2. inspect recorded Attempt/claim state;
3. query executor facts when necessary;
4. only then decide failure, retryability, or `indeterminate`.

Callbacks for terminal Runs, cancelled Runs, or superseded/old Attempts are recorded as facts but **must not directly resume or rewrite the current business outcome**.

A GitHub Job reporting `success` is not by itself business success. For example, an unclaimed duplicate candidate Job may intentionally exit successfully. Business success requires a valid result from the Job that owns the authorized Attempt claim.

## 7. Cancellation and failure semantics

### 7.1 Failure

For normal failure:

- independent DAG branches may continue;
- descendants whose required dependency failed are skipped/blocked;
- an unhandled failed Step causes the final Run to be `failed`;
- `always()` may allow an explicitly authored failure-notification/finalization Step to run after dependency failure.

### 7.2 Cancellation

Cancellation has distinct states/facts:

- `cancel_requested` means stop admitting ordinary new Steps and request active executors to stop;
- `cancelled` means the orchestration reached its terminal cancellation rule after active work was confirmed stopped or otherwise resolved according to policy;
- cancellation never means rollback of already completed side effects.

In v0.1, `always()` overrides dependency failure only; **it does not override run-level cancellation**. Once `cancel_requested` is durable, no new Step (including an `always()` Step) starts. Cleanup required during cancellation must occur cooperatively inside already active executor work; general cancellation-compensation Steps are deferred.

If an executor cannot be confirmed stopped, preserve that fact rather than reporting a false successful cancellation.

## 8. Definition and runtime version recovery

Every Run pins:

- `dsl_version`;
- `definition_digest`;
- the normalized definition snapshot/compiled plan used at admission;
- resolved capability identifiers/contract versions and deterministic executor routing needed by that plan;
- `engine_version` (or equivalent build/protocol version).

The bundled Workflow Registry is the source for **new** runs, but a waiting existing Run resumes from its pinned definition snapshot, not from whatever definition currently exists after a later deployment.

v0.1 does not require a complete historical runtime environment. Instead, deployment compatibility has a hard rule:

> A new engine/runner release must continue to interpret all nonterminal v0.1 stored plans and executor protocol versions, or deployment must be rejected/deferred until those runs finish or a migration is explicitly provided.

A Step Attempt records the actual executor version/identity used. Capability mappings for an existing stored plan cannot be silently rerouted after deployment.

For mutable MCP dependencies, record a dependency snapshot when useful, but validate the actual selected tool and invocation contract at execution time. A schema digest change alone is **not** automatically treated as incompatibility. Explicitly fail when the requested tool is missing or the current invocation no longer satisfies the live contract; do not use AI to guess replacement arguments.

## 9. v0.1 connections and authentication

Connection metadata is static/configured in v0.1; long-lived credentials use Workers Secrets. Do not build a D1 encrypted credential vault yet.

Connection authentication configuration must express the real wire behavior rather than assuming Bearer. At minimum the model must support:

- custom header name + raw secret value;
- `Authorization` with raw secret value;
- `Authorization: Bearer <secret>`;
- an explicit configured prefix/scheme when required by an existing server.

Example shape (illustrative, not the final schema):

```ts
{
  id: "openlist",
  transport: "streamable-http",
  url: "...",
  auth: {
    header: "Authorization",
    secret: "OPENLIST_TOKEN",
    format: "raw" // raw | bearer | prefix
  }
}
```

Updating a Workers Secret may create/deploy a new Worker version, so runtime credential rotation without a Worker version change is **not** promised by v0.1. A custom credential store should be reconsidered only when concrete runtime-management/scale requirements justify its lifecycle and recovery complexity.

`mcp.call` is a common workflow entry point, not a promise to support every MCP transport/auth/session behavior. v0.1 documents and tests only the transport/auth combinations required by the declared connections.

## 10. Reduced implementation scope

v0.1 keeps:

- Git-first workflow definitions;
- build-time schema/DAG validation, deterministic normalization and digest;
- a small bounded DAG;
- fixed asynchronous Workflow MCP tools;
- manual/webhook/schedule starts with one scheduler tick and `misfire: latest`;
- static Capability Registry and deterministic Cloudflare/GitHub routing;
- D1 admission/Attempt/callback/query records;
- R2 artifacts;
- GitHub OIDC runner authentication and minimal Worker-to-GitHub credential;
- essential lifecycle events only.

v0.1 defers:

- runtime workflow authoring/install;
- runtime plugin/capability installation or hot reload;
- generic arbitrary user code capability;
- encrypted runtime Connection credential vault;
- general workflow queue/concurrency-key subsystem;
- event sourcing/replay platform;
- copying all executor raw logs into R2;
- Saga/compensation engine;
- RBAC/organizations/workspaces;
- automatic multi-Step remote batching/optimizer.

## 11. Fault-scenario acceptance criteria

The implementation specification and tests must prove at least the following:

### A1 — duplicate trigger admission

**Given** the same webhook/schedule event is delivered repeatedly, **when** admission is attempted concurrently or sequentially, **then** all equivalent deliveries resolve to one logical Run ID and do not create multiple logical Runs.

### A2 — dispatch succeeded but response was lost

**Given** GitHub accepted dispatch but the Worker did not receive the response and dispatch is retried, **when** multiple candidate Jobs start for the same Attempt, **then** at most one candidate can atomically claim and receive execution authority; all other candidates perform no business work.

### A3 — claim deadline expires while old Job may still exist

**Given** an authorized Job becomes unreachable and its observation deadline expires, **when** the system reconciles the Attempt, **then** ownership is not automatically transferred to another Job. The Attempt becomes resolved, retryable, or `indeterminate` based on evidence; unsafe writes are not automatically re-executed.

### A4 — external write succeeded but response was lost

**Given** an external non-idempotent write may have completed but its response is lost, **when** the engine cannot verify the outcome, **then** it records `indeterminate` and does not blindly create another write Attempt. If the target supports idempotency, all retry Attempts reuse the same Operation ID/idempotency key.

### A5 — duplicate, late, or out-of-order callback

**Given** callbacks are repeated, delayed, or arrive for an older Attempt after a newer state exists, **when** they are received, **then** they are authenticated and idempotently recorded, but only the callback matching the currently authorized Attempt may influence orchestration. Old/terminal/cancelled callbacks cannot rewrite the current Run outcome.

### A6 — callback persisted but Workflow notification failed

**Given** a valid callback is persisted in D1 but notification to the waiting Workflow fails, **when** no additional callback arrives, **then** the pending inbox record is retried by maintenance and/or found by wait-timeout reconciliation; the Run cannot remain waiting forever solely because one notification call failed.

### A7 — GitHub unavailable, queued indefinitely, or quota-limited

**Given** a heavy Step cannot start or complete in GitHub within configured dispatch/start deadlines, **when** reconciliation runs, **then** the Step reaches an explicit executor-unavailable/not-started failure (or another evidence-based state) rather than remaining `running` forever. If no Job ever obtained the claim, retry does not risk duplicating business work.

### A8 — cancellation truthfulness

**Given** cancellation is requested while external execution is active, **when** the executor cannot yet be confirmed stopped, **then** status remains `cancel_requested`/unconfirmed rather than falsely reporting rollback or confirmed cancellation. No new Steps start after the cancellation request.

### A9 — deployment while a Run is waiting

**Given** a Run is waiting and the repository/Worker is later deployed with a changed workflow definition, **when** the old Run resumes, **then** it uses its pinned normalized definition snapshot and deterministic capability/executor mapping. Deployment is not allowed to silently reinterpret a nonterminal plan with an incompatible engine/runner protocol.

### A10 — external MCP contract drift

**Given** a remote MCP tool schema changed after the Workflow Definition was authored, **when** the Step executes, **then** a digest change alone does not prove failure. The adapter validates the selected tool and current invocation against the live contract; missing/incompatible operations fail explicitly without AI-generated parameter repair.

### A11 — extension without orchestration-core edits

**Given** a second and third workflow use existing capabilities, **when** they are added, **then** only workflow definitions/tests are added. **Given** a new capability is required, its module/descriptor can be added without changing admission, DAG progression, callback, cancellation, or retry core.

## 12. Exit condition for architecture work

This reduction is the final v0.1 architecture baseline. `to-spec` should translate these rules into schemas, state transitions, APIs, storage tables, executor protocol, and tests. New architecture features are out of scope unless implementation uncovers a correctness blocker.
