- Status: proposed implementation contract; generated from owner-accepted Q1–Q16, pending design review and ticket breakdown.

## 1. Problem, solution and success definition

v0.1 correctly uses declarative Git-authored YAML, compiles a canonical definition digest, and pins the normalized plan in D1 for each Run. Its discovery registry, compiler Connection policy, and several Raindrop-specific release scripts are nevertheless coupled to a Worker build. Adding a business workflow assembled from existing trusted capabilities should not rebuild/redeploy the orchestration engine or expand the ordinary MCP caller's authority.

v0.2 introduces one independent, Git-owned workflow-definition catalog, one trusted publication pipeline, a minimal separately authenticated administration interface, and D1-backed active-definition lookup. Reuse Cloudflare Workflows, D1 admission and pinned history, one Cron scheduler, existing Capability Registry, GitHub executor and R2 artifact path. New definitions and approved non-secret Connection metadata may be published independently. The release does not make executable capabilities or credential bindings dynamically installable.

Success requires all of the following: (a) publish, update, disable and rollback a definition without an engine deployment; (b) preserve the seven existing MCP tools and accepted v0.1 behaviors; (c) prove old nonterminal Runs use their pinned plans; (d) prevent an unapproved definition, operation, endpoint or Secret reference from gaining authority; and (e) demonstrate correct admission and schedule behavior across concurrent activation and failures.

## 2. User stories

1. As a workflow author, I want to add a YAML definition in a dedicated catalog, so that existing-capability workflows can grow independently of engine code.
2. As a workflow author, I want an exact-source revision and deterministic digest for each definition, so that changes can be reviewed and reproduced.
3. As a catalog maintainer, I want invalid syntax, cyclic DAGs, unknown capabilities and unsafe retry requests rejected before publication, so that runtime never interprets unvalidated source.
4. As an owner, I want a protected publish-and-activate operation, so that ordinary MCP clients cannot install or switch definitions.
5. As an owner, I want publication to leave the current version unchanged until explicit activation, so that a failed candidate cannot interrupt current workflows.
6. As an owner, I want an already validated digest restored by rollback, so that recovery does not overwrite historical content.
7. As a workflow caller, I want listing and retrieval to show the currently active safe metadata, so that I can discover a usable workflow without seeing secrets.
8. As a workflow caller, I want a new Run to pin the exact eligible definition selected at admission, so that a concurrent activation cannot reinterpret the request.
9. As a workflow caller, I want a repeated idempotency key to resolve to the original Run, so that retries do not duplicate downstream work even after a version change.
10. As a webhook producer, I want my trigger and its authentication bound to the admitted version, so that concurrent activation cannot authorize a different trigger.
11. As a scheduler owner, I want a version switch to preserve scheduled-occurrence deduplication, so that no logical time is admitted twice.
12. As a scheduler owner, I want cron/timezone changes to begin at a declared activation point, so that obsolete schedules are not silently replayed.
13. As an operator, I want approved Connection metadata changed independently of the engine, so that routine non-secret configuration does not require a rebuild.
14. As a security owner, I want newly referenced credential names allowlisted and separately provisioned, so that arbitrary YAML cannot read platform Secrets.
15. As a security owner, I want a disable/revocation decision to block new external operations of old Runs, so that an old pinned plan cannot bypass an emergency safety action.
16. As a workflow caller, I want operations that were already in flight at revocation reported truthfully, so that revocation is not misrepresented as compensation or rollback.
17. As an operator, I want historical nonterminal Runs to survive the registry migration, so that deployed work is not lost.
18. As an operator, I want existing GitHub claim, callback, retry and R2 upload rules retained, so that definition delivery does not weaken heavy execution.
19. As an operator, I want bounded publishing and scheduler work with clear failures, so that bad input cannot exhaust a Worker tick or D1.
20. As an owner, I want an isolated rehearsal and explicit production cutover evidence, so that a passing compiler is not confused with a live successful rollout.
21. As a maintainer, I want definition-only checks separated from engine release checks, so that routine YAML changes do not repeat unrelated deployment or executor tests.
22. As an operator, I want a failed publish, duplicate publish, activation race or partial external start reconciled from durable facts, so that no operation remains in a falsely successful state.

## 3. Boundaries and module seams

| Area | Responsibility | Existing seam / change |
| --- | --- | --- |
| Catalog repository | Git authoring of YAML and business acceptance fixtures; no production credentials | New independent repository; group packages by business directories. |
| Trusted publisher | Checkout fixed approved catalog revision, use pinned engine compiler, validate and submit one immutable candidate; require protected approval to activate | One protected GitHub Actions workflow controlled outside author-editable catalog data. |
| Compiler | Strict YAML/schema/DAG/expression normalization, deterministic digest, capability shape and retry bound checks using an explicit trusted Connection policy snapshot | Refactor src/compiler.ts and scripts/compile-workflows.ts; no separate interpretation pipeline. |
| Admin entry | Authenticate trusted publisher/approver, verify bounded canonical data/digest/references, stage, activate/deactivate/rollback; audit durable decisions | Small, separate /admin/definitions and /admin/connections namespace; never part of /mcp. |
| Registry | Read active entries from D1 for listing and admission, read immutable versions by digest for existing Runs | Replace static new-Run read sites in registry.ts; reuse storage.ts and provenance.ts. |
| Admission | Validate input/trigger against a selected digest, conditionally persist that same active version, then idempotently create the Workflow instance | Refactor admission.ts, mcp.ts and triggers.ts; preserve existing identities and error shape. |
| Scheduler | Evaluate active schedules with existing Cron parser and stored progress; reconcile transitions and duplicates | Refactor scheduler.ts; preserve single Cron and maintenance batch. |
| Connections | Store approved non-secret versions and current revocation status; resolve existing protected Secret values on use | Adapt connections.ts, effective-policy.ts, mcp-client.ts and step-policy.ts; no credential vault. |
| Execution | Load old pinned plan, apply effective step policy, honor live revocation, preserve existing executor manifest and claim checks | workflow.ts, execute-capability.ts, executor-protocol.ts, runner as needed; no new executor. |

Use the high-level HTTP/admin, public MCP, webhook, Cron and executor interfaces as the integration-test seams. Do not add pass-through adapters, a second YAML compiler, an event bus or a generic plugin abstraction for hypothetical providers.

## 4. Catalog and canonical definition contract

4.1. Start with one independent catalog repository. Each business package contains one or more YAML definitions, relevant tests and source documentation. Engine-owned smoke fixtures remain in the engine repository. A catalog definition cannot supply executable JavaScript, infrastructure permissions or an arbitrary trusted MCP endpoint.

4.2. Each publication manifest is a bounded data object containing manifest version 1, trusted catalog repository identity, 40-character source commit SHA, relative source path, workflow ID, DSL version 1, canonical plan, definition digest, compact safe metadata and referenced approved Connection/config versions. Provenance and publication evidence are NOT included in the existing definition digest. A batch contains one or more independent entries; reject duplicate workflow IDs and mixed provenance; publish/activate per workflow ID, not as an unneeded global catalog generation.

4.3. Preserve canonicalization and SHA-256 behavior of the existing compiler (including how comments and whitespace do not change a digest). Do not silently rename steps, change expression meaning, or add non-semantic package metadata to the hashed plan. A new hash algorithm/DSL must be separately versioned; unchanged migrated source must retain its original digest. Storage serializations must not be assumed canonical: recompute from validated normalized plan using one shared canonical serializer.

4.4. Preserve existing compiler limits: plan at most 256 KiB, up to 64 steps and up to 32 triggers; existing expression/identifier/timeout constraints remain. For the first increment publish one workflow per activation request and bound the request body to one existing maximum-sized plan plus a small fixed manifest overhead (hard maximum 320 KiB). A later measured need may increase limits through a reviewed code change. Reuse a scheduler scan cap of 50 schedules/tick and maintenance batch cap of 20; reject or explicitly report unsupported workload rather than silently ignoring excess active schedules. Max 50 active schedules in this increment; duplicate registration by digest is idempotent. No speculative multi-tenant quota layer.

4.5. Source SHA is independently checked by the trusted publisher against the catalog's protected branch and immutable Git checkout. The Worker validates the data digest and the authorized publisher identity; it does not accept a user-supplied source SHA or CI status string as self-proving Git attestation. Retain the verified publisher physical run identity and source revision as audit evidence. No network fetch to arbitrary source URLs during list/get/run.

## 5. Trusted publication, approval and administration

5.1. Use ONE protected GitHub Actions publisher workflow held in the engine repository (outside the author-editable catalog). The workflow checks out the approved catalog at its exact commit, uses a pinned engine compiler and tests, evaluates current authorized policy, verifies the generated canonical result, and submits a candidate. A subsequent deployment job behind a protected GitHub Environment provides separate activation approval. Single-owner installations must allow an approval path the actual GitHub account can complete; do not enable an impossible self-review policy. Publication and activation can be jobs of the same trusted pipeline, not distinct services.

5.2. Reuse the existing GitHub OIDC verifier only as a cryptographic primitive; configure a separate publication audience and exact publisher repository ID/workflow ref, protected branch/ref, allowed workflow SHA when available, job run identity and token freshness. Publisher OIDC authority is not executor claim authority: never allow a publisher token on /executor or an executor token on /admin. Match the authorized job to the recorded candidate at activation. The approved catalog SHA is bound to the trusted publisher's controlled checkout procedure and recorded evidence. Reject replayed mismatched digest, workflow, catalog SHA, identity or stage. No production publishing credentials or OIDC minting in untrusted catalog workflows. Fail closed if GitHub Environment approval, issuer, job identity or expected trust policy is unverified.

5.3. Minimal administration commands (HTTP JSON, not new MCP tools): (a) GET /admin/connections/snapshot (trusted, read-only publisher view of approved non-secret configuration and monotonic revision), (b) POST /admin/definitions/stage, (c) POST /admin/definitions/activate, (d) POST /admin/definitions/deactivate, (e) POST /admin/connections/register, and (f) POST /admin/connections/disable. Rollback is activation of an existing validated digest, not a separate code path. Limit methods and body size, reject unknown fields, use explicit error codes, Cache-Control: no-store, and redact all credentials. Ordinary MCP_ACCESS_TOKEN authenticates /mcp only and never authorizes /admin. Do not expose raw admin functionality through the seven existing MCP tools. Authorization and transport are evaluated before any mutation.

5.4. Stage verifies canonical plan shape, DSL version, digest, bounded size, supported capabilities, executor placement, referenced connection revisions, tool policy, approved webhook credential references, and engine compatibility; it writes an immutable version/evidence row but does not update the active registry. Repeated stage of identical digest with identical source evidence is idempotent. A conflicting source claim for the same digest is handled as separate provenance evidence, not a rewrite of immutable plan semantics. Invalid candidates fail with no activation.

5.5. Activate requires an existing validated digest, approved caller and expected current active digest (nullable for first activation); use compare-and-swap semantics. A conflict returns an explicit conflict without overwriting another publication. Deactivate similarly requires the expected current digest and affects new admissions only. Rollback activates an existing previously validated compatible digest, subject to current approved dependencies and revocation; it never restores revoked authority merely by choosing an older plan. Append a compact activation/deactivation audit fact in the same D1 transaction, with actor job identity, old/new digest, catalog source, timestamp and safe reason. No generic event-sourcing service.

5.6. Connection registration is owner-approved non-secret metadata (endpoint, supported protocol, header format, server-held secret reference, per-tool effect/operationIdArg, annotation-trust opt-in). Only the administrator may register it; the catalog may only refer to approved IDs/revisions. Restrict endpoint to approved HTTPS origins; prevent loopback/private/reserved destinations and unsafe redirect behavior in credentialed calls. Replacing a target or widening operation policy requires a newly approved Connection version. Secret reference MUST come from a finite server-side allowlist of already provisioned bindings with a constrained intended endpoint/operation policy; never let YAML pick arbitrary env names. Existing shared MCP_ACCESS_TOKEN may continue only for specifically approved current trusted MCP endpoints per ADR 0028. Provisioning an additional secret is an independently authorized platform configuration task; absence fails closed.

5.7. Webhook Secret references follow the SAME explicit allowlist rule, scoped to the exact workflow ID and trigger ID rather than merely to a generally allowed binding name. An author-controlled trigger cannot name EXECUTOR_LEASE_SECRET, GITHUB_ACTIONS_TOKEN, R2 keys, admin credential, another workflow's webhook token or an unrelated Connection credential; a missing/disabled webhook secret disables new trigger admission. Preserve existing per-trigger auth and required stable event key. All admin, Connection and webhook error responses omit raw credentials or authorization material.

## 6. Minimum D1 schema and version invariants

6.1. Reuse workflow_definition_versions (definition_digest primary key and stored normalized_plan_json), workflow_runs (pinned definition_digest), run_admissions (unique admission_key), step_runs.effective_policy_json, and scheduler_state. Add only additive forward-compatible migrations; do not drop old columns or rewrite old runs.

6.2. Add workflow_active_definitions: workflow_id primary key, nullable active_digest foreign key to immutable definition versions, registry_revision integer, activated_at, and a state distinguishing never published vs deliberately disabled if necessary. A NULL digest means no new admissions. A CAS update checks prior digest AND registry_revision to avoid ABA conflict. The metadata for list/get comes from the immutable definition, not duplicated editable data. If disabled, the workflow is absent from normal list/get and cannot start; historical run status/result/logs stay available.

6.3. Add definition_publications as the minimum durable publication/activation evidence: publication identity (trusted publisher GitHub run ID/attempt, revision and source SHA), workflow_id, validated digest, validation state, approver identity when activated, timestamp and audit event kind. Unique constraints prevent duplicate publisher event replays; canonical plan remains stored once in workflow_definition_versions. Avoid storing whole package ZIP, approval event bus, or separate R2 package history.

6.4. Add connection_config_versions: immutable (connection_id, config_digest) primary identity and approved non-secret metadata JSON, created_at and trusted provenance. Add connection_controls: connection_id primary key, active_config_digest and enabled flag, revision and updated_at. This separation is necessary to preserve target/policy semantics for already admitted Runs while allowing immediate disable. Only reference known approved credential binding names; neither table contains credential values.

6.5. Add nullable workflow_runs.connection_versions_json, a bounded map of the specific Connection IDs referenced by its pinned plan to their approved immutable config digests. This must be recorded with admission. The only per-step persisted policy remains step_runs.effective_policy_json; do not duplicate an independent policy-history table. Older v0.1 runs with NULL snapshot use the v0.1 static compatibility mapping until terminal or explicitly migrated, and still respect live revocation. Definition content digest does not hash live Connection Secret values or revocation flags.

6.6. Retain scheduler_state keyed by workflow ID and stable trigger ID. During activation update its cursor/activation boundary transactionally with active pointer, using a monotonically increasing last_evaluated_at and preserving last_admitted_scheduled_time. If a trigger is removed, retain its historical state but stop evaluating it. If a trigger ID is reused with new cron/timezone, new evaluation begins at activation minute and does not backfill old missed times; UTC epoch minute identifies the logical occurrence. For same ID + occurrence, preserve the existing admission key semantics. Require distinct trigger ID when an author wants two different concurrent schedules.

6.7. Never garbage-collect immutable definitions or Connection versions referenced by a Run (including nonterminal and retained terminal history); no automatic historical GC is in v0.2. Reject an attempt to activate a definition whose required historical or current dependencies are unavailable. Keep reads of activation/admission from an authoritative-consistency D1 path; do not introduce unverified stale per-isolate registry caches. If read replication is enabled later, explicitly preserve read-after-write consistency.

## 7. Compiler, policy and execution contracts

7.1. Extract a reusable compiler input for known capability descriptors and an explicit APPROVED Connection policy snapshot. Structural YAML/IR validation uses the same compiler as v0.1, but hasConnection/compileTimeMcpRetryLimit must not depend on one bundled production map. The trusted publisher obtains the approved non-secret policy via authenticated GET /admin/connections/snapshot, which returns current Connection versions, allowed tool policies, permitted webhook binding IDs and revision but never Secret values or generic env names. The manifest records the configuration revision and referenced immutable digests. The admin checks that each referenced revision remains approved and that no scope has been revoked at stage AND activation; if the snapshot became stale, reject with a retryable conflict requiring revalidation. There is no fallback to an untrusted repo file or stale cached snapshot. Unknown capabilities, invalid tool references, unapproved webhook credential refs, unknown Secret names and retry requests above permitted operation policy fail closed. Do not accept arbitrary server-provided annotation to override explicitly approved local policy.

7.2. Pin Connection target/protocol/auth header configuration for existing Runs using connection_versions_json. Read current protected Worker Secret value at each invocation so authorized rotation works without rewriting plans; check live connection/operation enablement and endpoint permission before every new external attempt. Current revocation or stricter constraints always win. Do not silently reinterpret an older Run using a new endpoint, loosened effect class or new idempotency argument; if historical semantics cannot be safely fulfilled, return a terminal or explicitly indeterminate outcome consistent with possible side effects. Current, already transmitted external operations cannot be revoked or rolled back retroactively.

7.3. Preserve step_run effective policy across retries and Operation ID stability. Check live deny/revoke in the Cloudflare MCP adapter, after dependency inspection and immediately before sending tools/call. For heavy GitHub attempts, recheck at Claim/manifest issuance and at the last platform-controlled authorization point; a task already holding a valid lease cannot be assumed interruptible. Keep existing OIDC binding, Attempt Claim, callback inbox, cancel/wait behavior, indeterminate-write classification, and R2 presigned upload constraints unchanged unless a regression reveals a specific gap.

7.4. The generic http.read capability continues to accept bounded public URL inputs under its existing URL validation, size, timeout and redirect limits; it does not acquire a credential by referencing a Connection. Do not confuse public HTTP read with creating an arbitrary credentialed MCP Connection. New credentialed egress and webhook secret references must follow the allowlists in §5.6–5.7.

7.5. Runtime verifies restricted normalized plan shape using one shared versioned IR schema (not the permissive asRuntimePlan cast alone), recomputes its canonical hash at stage, and checks supported DSL/engine/execution manifest versions before activation or recovery. Do not parse author-supplied YAML at runtime. A reused digest with a different plan is rejected. The existing release compatibility gate must consider current staged/active definitions AND old nonterminal Runs, including historical Connection compatibility. No automatic AI repair of changed external MCP tool contracts.

## 8. Registry, new Run admission and public interfaces

8.1. Change workflow_list/get to query active D1 definitions and return the existing response fields only: ID, name, description, digest, safe trigger/input/capability metadata and safe source path. Do not return source credentials, Connection metadata or admin state. Preserve workflow_run/status/result/logs/cancel input and output types. Implementation may extend safe metadata only compatibly, not rename the seven tools.

8.2. New manual, webhook and scheduled admissions first obtain a candidate active digest and immutable plan. Validate inputs and selected trigger against that exact plan. At persistence, use one D1 transactional/conditional operation that verifies active digest and revision have NOT changed and selects/persists that digest with the unique admission record, run row, and Connection version snapshot. No two statements may leave a new Run admitted without the matching immutable plan or select a different digest than its validated inputs. If the version changed, re-read and revalidate before retry; never silently re-use an authorization or input validated against a different definition.

8.3. Duplicate admission returns the existing Run ID, pinned digest and alreadyAdmitted=true, including when the old definition has since been disabled. It must not create a second Run or substitute the new active version; any idempotent re-drive of external instance creation remains bound to the existing Run ID. New admissions to disabled/unpublished definitions fail explicitly; a missing workflow and a temporarily changed registry produce safe stable error codes. Each manual start without an idempotency key remains a distinct Run as in v0.1.

8.4. Webhook route authenticates against a specific selected digest/trigger and only then attempts CAS admission of that digest. When activation races authentication, reject or re-authenticate using the new active trigger; never let an old token authorize a new trigger. Disabling a workflow invalidates new webhook and scheduled starts without invalidating historical Run reads.

8.5. After durable admission, create the Cloudflare Workflow instance with the existing deterministic Run ID and idempotent createBatch behavior. A failed network response after a committed Run is not proof that the instance is absent; retry/reconcile using stored run/admission facts. No global distributed mutex or imaginary cross-system D1/Cloudflare transaction. Maintain bounded repair of committed-but-unstarted Runs and observability of that condition; do not overwrite an uncertain business result.

## 9. Scheduling and activation race semantics

9.1. Use one existing Cron trigger and latestDueOccurrence. Tick obtains active schedules from D1 (bounded to 50). For a given trigger, evaluate only times strictly after the stored last evaluation, respecting the declared timezone and misfire: latest. Preserve stable workflow:trigger:scheduled UTC epoch occurrence keys.

9.2. On activation, one D1 transaction checks expected active revision, writes the new digest, records audit, and advances or preserves each affected trigger's evaluation cursor to the activation minute (never backwards). This is the activation point. At the exact boundary, the old version owns occurrences already committed before activation; the new version owns subsequently admitted occurrences. If the old and new schedules have the same logical due time, unique admission prevents a second Run. Do not attempt automatic catch-up for disabled windows or old schedules.

9.3. A tick that evaluated an older registry revision MUST use a conditional admission+cursor update checking the same revision; on conflict it drops stale calculations and reloads the active version. Preserve due-occurrence facts if D1 commit succeeded but Workflow creation failed; the existing idempotent Run ID and repair path allow reconciliation. Two concurrent ticks cannot move the cursor backward, duplicate an occurrence or lose a due fact due to a stale overwrite.

9.4. Deactivation stops new schedule evaluation and webhook/manual admissions but preserves already admitted Run progression, callback maintenance, and historical scheduler cursors. On rollback, treat the restored validated digest as a fresh activation point, without replaying the intervening period.

## 10. Migration and release plan

Phase M0: Freeze the source baseline and obtain a nonterminal-Run compatibility record. Add new tables/columns and tests without changing production readers. Do not rotate credentials or change scheduled Cron. Confirm old plans and scheduler state are backed up/exportable using authorized mechanisms.

Phase M1: Import the exact four existing production registry IDs (local-http-smoke, raindrop-daily-snapshot, sequential-http-smoke, web-archive-smoke) and their original digests/source provenance into the immutable store and active pointers; seed matching Connection version records from the existing approved static metadata and preserve every existing scheduler cursor. The existing smoke-related production exclusions remain excluded. Reject hash or schema mismatch; do not rehash or mutate historical plans to fit a new format.

Phase M2: In an isolated environment switch list/get/run/webhook/scheduler new-admission readers to D1. Verify old nonterminal Run recovery continues through its historical digest even after active registry updates. Keep one tested rollback route to the bundled registry while the migration remains under review; ensure the gate prevents rolling the engine back to a version unable to interpret new Run data. No dual independently writable source of truth.

Phase M3: Establish and protect the independent catalog and publisher; migrate Raindrop YAML and its business acceptance scripts out of the engine repository without moving the Raindrop MCP business API into Workflow Worker. Publish a digest-identical definition first, then test a genuine definition-only change, disable, rollback, cron/timezone update and conditional webhook behavior. Engine repository retains generic compiler and smoke fixtures.

Phase M4: After offline and isolated checks, separately authorize production cutover. Verify manual and scheduled Raindrop runs and the heavy GitHub/R2 path as applicable to the changed runtime. Observe nonterminal recovery and activation audit. Only then remove obsolete business-specific bundling and duplicated release scripts; keep necessary compatibility code until historical references no longer need it. Never use the historic #107/#108 evidence as substitute for v0.2 live acceptance.

Rollback: Before cutover, revert reader activation and configuration without losing staged immutable data. After cutover, restore an existing validated digest using CAS and preserve all Run history; if an engine downgrade cannot understand newer stored Runs, block it rather than deleting/misinterpreting them. Record the exact commit/digest/engine and evidence for each reversal.

## 12. Explicitly out of scope

No runtime GUI or editable workflow API; no arbitrary user code, dynamically loaded Capability implementation or executor; no multi-tenant or full RBAC framework; no direct arbitrary Git URL fetch from workflow_run/list/get; no credential vault, automatic cross-Worker Secret synchronization or Secret material in D1/R2; no generic marketplace; no new GitHub/R2 execution implementation; no workflow compensation/exactly-once claim; no automatic historical definition GC; no additional queue, event bus, global distributed lock, separate attestation server, or independent package R2 store; no replacing existing http.read public-URL rules with blanket prohibition; no forced engine redeployment for a definition-only update.

## 13. Completion criteria and engineering handoff

- Every accepted Q1–Q16 requirement has an implementation mapping and passing applicable AC.
- The catalog, protected publisher, minimum additive schema, active registry, conditional admission, scheduler transition and approved connection/revocation path are implemented behind the current public contracts.
- No v0.1 in-progress run, historical digest, retry/idempotency safety or existing trust surface is silently changed.
- Offline and isolated acceptance has passed at a precisely reported implementation SHA, with separate live-production AC16 evidence before any release-complete declaration.
- Reviewed docs include operator instructions for registering a permitted Secret, publishing, activating, deactivating, rolling back, recovering uncertain starts and verifying compatibility.
- Split to-tickets by independently testable interfaces and migration gates. Do not reopen completed #107/#108 or claim implementation progress from this documentation PR. Before a production change, re-read remote PR/issue/CI state and obtain explicit cutover authorization.
