# Email MCP v0.1 Technical Specification

Status: ready for implementation  
Date: 2026-09-18  
Target repository: `lirtual/mcp-workers`  
Target app: `apps/email-mcp-worker`  
Target Worker: `email-mcp-worker`  
Target MCP Portal server id: `email`

This specification turns the settled multi-provider email design and the completed QQ Mail/Cloudflare protocol prototype into an implementation contract. It is intentionally small: one Cloudflare Worker, one generic IMAP/SMTP provider, multiple configured accounts, seven MCP tools, bounded reads, explicit write gates, and user confirmation for irreversible or externally visible actions.

## 1. Problem

The current MCP estate can connect to provider-specific services, but personal email is fragmented across QQ Mail, Gmail, iCloud, Fastmail, self-hosted IMAP/SMTP, and future providers such as Microsoft 365.

A QQ-Mail-specific MCP is not a durable foundation because QQ Mail's official OAuth MCP currently applies a trusted-platform redirect policy that prevents direct Cloudflare MCP Portal onboarding. The long-term need is broader: one MCP surface should work across multiple mailbox providers without adding provider-specific MCP tools or one Worker per provider.

The solution must fit the existing `mcp-workers` operating model:

- independently deployed Worker app;
- Cloudflare MCP Portal bearer authentication through the existing `@mcp-workers/portal-auth` package;
- Cloudflare Runtime Secrets for credentials;
- no persistent service required for v0.1;
- bounded work suitable for the Workers runtime;
- no hidden mailbox mutation during reads;
- no blind retry of externally visible writes.

## 2. Solution

Add `apps/email-mcp-worker` as an independent MCP Worker.

v0.1 uses one application-local provider abstraction with one concrete provider implementation:

- **IMAP/SMTP provider**
  - IMAP for account/folder/message discovery, search, read, flags, move, and trash.
  - SMTP for new mail, reply, reply-all, and forward.
  - short-lived connections per tool invocation;
  - no IMAP IDLE, connection pooling, background watcher, local mailbox index, or sync database.

The MCP surface remains provider-neutral. Provider names, hosts, ports, passwords, authorization codes, and app-specific passwords are configuration concerns, not tool names.

The public v0.1 tool set is exactly:

1. `email_accounts`
2. `email_folders`
3. `email_search`
4. `email_get`
5. `email_modify`
6. `email_send`
7. `email_respond`

A future Microsoft Graph provider must fit the same app-local provider interface and must not require provider-specific MCP tools.

## 3. Prototype evidence that informs this spec

The pre-spec Cloudflare prototype established the following facts against a real QQ Mail account:

- a deployed Cloudflare Worker established implicit TLS to `imap.qq.com:993`;
- QQ Mail returned an IMAP capability greeting;
- the Worker authenticated successfully with the configured QQ Mail authorization code;
- the Worker executed LIST, opened INBOX read-only, and fetched the latest envelope;
- the Worker established implicit TLS to `smtp.qq.com:465`;
- the Worker completed EHLO and SMTP AUTH PLAIN successfully;
- no production email was sent during protocol authentication testing.

These observations prove the target runtime can reach and authenticate to the intended QQ IMAP/SMTP endpoints. Production implementation still requires a deployed integration acceptance test using the selected production libraries before cutover.

## 4. User stories

1. As an email user, I want to see all configured mail accounts, so that I know which mailboxes are available through one MCP.
2. As an email user, I want one account to be configured as the default, so that routine requests do not require an account identifier every time.
3. As an email user, I want to list folders in an account, so that I can navigate Inbox, Sent, Trash, Archive, and provider-specific folders.
4. As an email user, I want folder counts only when I request them, so that routine folder discovery stays inexpensive.
5. As an email user, I want to search messages with structured filters, so that I do not need to know IMAP search syntax.
6. As an email user, I want search results to contain bounded metadata rather than full bodies, so that large mailboxes do not create oversized MCP responses.
7. As an email user, I want search pagination to remain stable when new mail arrives, so that I can continue browsing without relying on unstable IMAP sequence numbers.
8. As an email user, I want to read one selected message without marking it read, so that inspection does not silently change mailbox state.
9. As an email user, I want message bodies clearly marked as untrusted external content, so that email text is not confused with instructions to the agent.
10. As an email user, I want attachment names and metadata visible without downloading attachment bytes, so that I can understand a message without paying the cost of large attachments.
11. As an email user, I want oversized messages to fail or degrade explicitly, so that the Worker never tries to parse an unbounded MIME message.
12. As an email user, I want to mark messages read/unread or flagged/unflagged, so that common mailbox organization is available when modifications are enabled.
13. As an email user, I want to move messages between folders, so that I can organize mail without provider-specific commands.
14. As an email user, I want deletion to mean moving mail to Trash rather than permanent deletion, so that accidental destructive actions remain recoverable.
15. As an email user, I want Trash actions to require explicit confirmation, so that an agent cannot remove mail from its current folder silently.
16. As an email user, I want to compose a plain-text email and review exactly what will be sent, so that I retain control of externally visible communication.
17. As an email user, I want sending to require a positive confirmation step, so that generation and transmission are separate decisions.
18. As an email user, I want replies to preserve normal threading headers, so that recipients see replies in the existing conversation.
19. As an email user, I want reply-all recipients derived safely from the original message, so that I do not have to reconstruct recipient lists manually.
20. As an email user, I want forwarding to show when original attachments are omitted, so that I do not mistakenly believe v0.1 forwarded attachment bytes.
21. As an operator, I want send and mailbox-modification capabilities disabled by default, so that a newly deployed server is read-only until explicitly enabled.
22. As an operator, I want account credentials stored only in Cloudflare Runtime Secrets, so that source control and build logs do not contain mailbox passwords or app passwords.
23. As an operator, I want tool callers unable to choose arbitrary IMAP/SMTP hosts, so that model input cannot turn the Worker into an arbitrary TCP proxy.
24. As an operator, I want ambiguous send or mutation outcomes reported explicitly instead of automatically retried, so that external side effects are not duplicated.
25. As an operator, I want logs to contain operation metadata but not subjects, message bodies, recipients, passwords, tokens, or raw provider responses, so that normal observability does not become a privacy leak.
26. As a maintainer, I want the app to use the repository's existing Portal authentication and CI conventions, so that email does not create another platform layer.
27. As a maintainer, I want provider behavior behind one narrow app-local interface, so that a future Microsoft Graph adapter does not rewrite MCP tools.
28. As a maintainer, I want a deployed read-only smoke test against a real mailbox, so that local mocks cannot be mistaken for proof that Workers can operate the selected mail libraries.
29. As a maintainer, I want unrelated app changes not to rebuild the email Worker, so that adding this app does not recreate the build fan-out observed during prototyping.

## 5. Repository and module boundaries

Add one new workspace app:

`apps/email-mcp-worker`

Expected responsibilities:

| Boundary | Responsibility |
| --- | --- |
| HTTP entrypoint | `/health`, `/mcp`, Portal authentication, configuration fail-closed behavior |
| MCP server | seven public tools, schemas, tool annotations/descriptions, confirmation flow |
| configuration | parse and validate `EMAIL_ACCOUNTS_CONFIG`, provider presets, default account, feature gates |
| normalized model | provider-neutral account/folder/message/address/result types |
| provider contract | app-local interface for list/search/get/modify/send/respond operations |
| IMAP/SMTP provider | ImapFlow-backed mailbox operations and Nodemailer-backed SMTP operations |
| message references | provider-neutral opaque message/cursor encoding and validation |
| MIME normalization | bounded conversion of provider message data into text/html/attachment metadata |
| safety | limits, untrusted-content marking, sender/recipient validation, destructive-action gates |
| tests | MCP-surface behavior plus provider/config tests and environment-gated live integration |

Do not add a new workspace package for email v0.1. The provider contract remains inside the app until a second provider creates a real reuse boundary.

The only required shared runtime dependency is the existing `@mcp-workers/portal-auth`.

## 6. Runtime and dependency decisions

### 6.1 Worker runtime

- Worker name: `email-mcp-worker`.
- Main entry: `src/index.ts`.
- `workers_dev: true`.
- `preview_urls: false`.
- `keep_vars: true`.
- Node compatibility: `nodejs_compat`.
- Node/toolchain baseline follows the monorepo Node 24 / pnpm 10 baseline.
- Use the repository's standard Workers Observability configuration.

### 6.2 Production libraries

Production implementation uses maintained libraries instead of the hand-written protocol code from the prototype:

- ImapFlow for IMAP.
- Nodemailer SMTP transport for SMTP.
- Zod for configuration/tool schema validation.
- A bounded MIME parser suitable for serverless/Workers execution when raw MIME parsing is necessary; `postal-mime` is the preferred implementation because it is designed for browser/serverless environments and has explicit parsing limits.

Do not copy the prototype's hand-written IMAP or SMTP parser into production.

If the selected production IMAP library cannot pass the live Worker integration acceptance gate, stop implementation as a spec blocker. Do not silently replace it with a hand-written general IMAP client.

### 6.3 Connection lifecycle

Every MCP operation opens only the connections required by that operation and closes them in `finally`/equivalent cleanup.

v0.1 does not keep live IMAP connections between Worker invocations and does not use:

- IMAP IDLE;
- long-lived connection pools;
- Durable Objects for mailbox connections;
- D1/KV/R2 mailbox caches;
- scheduled mailbox synchronization.

## 7. Runtime configuration contract

### 7.1 Required secrets

`wrangler.jsonc` declares exactly these required runtime secret names for v0.1:

- `MCP_ACCESS_TOKEN`
- `EMAIL_ACCOUNTS_CONFIG`

The actual values are Cloudflare Runtime Secrets and must not be build variables or committed values.

### 7.2 Non-secret feature flags

The Worker exposes these non-secret vars:

- `EMAIL_ALLOW_MODIFY`, default `false`.
- `EMAIL_ALLOW_SEND`, default `false`.

Only the exact string `"true"` enables a gate. Missing, malformed, or other values resolve to disabled.

No tool argument can enable a disabled gate.

### 7.3 Account catalog

`EMAIL_ACCOUNTS_CONFIG` is one JSON object with:

- mandatory `default_account`;
- mandatory `accounts` object;
- 1-20 configured accounts;
- account keys are stable account IDs used by MCP tools;
- `default_account` must identify an enabled account.

Each account supports:

- `provider`: `qq`, `gmail`, `icloud`, `fastmail`, or `custom`;
- `display_name`: optional UI label;
- `address`: canonical mailbox address;
- `enabled`: optional, default true;
- `auth.type`: v0.1 accepts only `password`;
- `auth.username`: optional, defaults to `address`;
- `auth.password`: authorization code/app password/password stored inside the Secret JSON;
- `senders`: optional configured From-address allowlist, defaulting to `[address]`;
- optional endpoint overrides allowed only from configuration, never tool input.

The `custom` provider requires explicit IMAP and SMTP endpoint configuration.

### 7.4 Initial provider presets

The initial preset set is:

| Provider | IMAP | SMTP |
| --- | --- | --- |
| QQ Mail | `imap.qq.com:993`, implicit TLS | `smtp.qq.com:465`, implicit TLS |
| Gmail | `imap.gmail.com:993`, implicit TLS | `smtp.gmail.com:465`, implicit TLS |
| iCloud Mail | `imap.mail.me.com:993`, implicit TLS | `smtp.mail.me.com:587`, STARTTLS required |
| Fastmail | `imap.fastmail.com:993`, implicit TLS | `smtp.fastmail.com:465`, implicit TLS |

A preset may be overridden only through the account Secret configuration.

v0.1 accepts only encrypted transport:

- IMAP must use implicit TLS.
- SMTP may use implicit TLS or STARTTLS with TLS required.
- plaintext authentication without TLS is rejected by configuration validation.

### 7.5 Authentication scope

v0.1 provider authentication is password-style only. This includes provider app passwords and QQ Mail authorization codes.

The following are not v0.1 auth modes:

- Gmail OAuth;
- Microsoft OAuth / Microsoft Graph;
- arbitrary XOAUTH2 token onboarding;
- provider web OAuth callback flows.

Accounts that require those modes are unsupported until the relevant provider adapter is implemented.

## 8. HTTP and Portal interface

### 8.1 Health

`GET /health` is public and shallow.

It returns HTTP 200 with:

- `status: "ok"`;
- `service: "email-mcp-worker"`.

It does not:

- open IMAP/SMTP connections;
- parse account credentials;
- report account addresses;
- report whether secrets are present;
- expose feature-gate state.

### 8.2 MCP route

`/mcp` uses the repository's stateless Streamable HTTP MCP handler.

Portal authentication uses `authenticatePortalRequest` with:

- `expectedToken: env.MCP_ACCESS_TOKEN`;
- `allowedOrigins: []`.

Expected entrypoint failures:

- missing Worker Portal token configuration -> HTTP 503, `portal_auth_not_configured`;
- missing/empty email catalog -> HTTP 503, `email_config_not_configured`;
- invalid email catalog -> HTTP 503, `email_config_invalid`;
- missing/incorrect bearer -> HTTP 401 + `WWW-Authenticate: Bearer`;
- invalid browser Origin -> HTTP 403;
- unknown route -> HTTP 404.

The inbound Portal Authorization header is removed before MCP/tool handling.

## 9. Normalized identifiers and message model

### 9.1 Account IDs

Account IDs are configuration keys and are stable public MCP identifiers. They are not email addresses and may be short labels such as `qq`, `personal`, or `work`.

Tools that accept optional `account_id` resolve the configured `default_account` when omitted.

### 9.2 Folder IDs

For the IMAP/SMTP provider, a `folder_id` represents the decoded IMAP mailbox path.

The provider performs all necessary protocol encoding internally. Callers never provide raw IMAP commands.

### 9.3 Message IDs

Public `message_id` values are opaque strings.

For IMAP, the underlying locator must bind at least:

- mailbox identity;
- IMAP UIDVALIDITY;
- UID.

The implementation must not expose or depend on IMAP sequence numbers as durable public identifiers.

If UIDVALIDITY changes or a message reference no longer maps to the expected mailbox, return `MESSAGE_REFERENCE_STALE` or `MESSAGE_NOT_FOUND`; do not silently resolve a different message.

### 9.4 Search cursors

Search pagination returns an opaque `next_cursor`.

The cursor is:

- stateless;
- versioned;
- scoped to account/folder/query;
- based on stable provider pagination facts such as IMAP UID, never sequence number.

Cursor contents are not a security boundary, but malformed or query-mismatched cursors are rejected.

## 10. MCP tool contracts

### 10.1 `email_accounts`

Purpose: discover configured accounts and effective capabilities.

Input: none.

Returns one record per enabled account:

- `id`;
- `display_name`;
- `address`;
- `provider`;
- `default`;
- `read_enabled`;
- `modify_enabled`;
- `send_enabled`.

`modify_enabled` requires IMAP capability plus `EMAIL_ALLOW_MODIFY=true`.

`send_enabled` requires SMTP configuration plus `EMAIL_ALLOW_SEND=true`.

Never return:

- passwords/app passwords/authorization codes;
- IMAP/SMTP usernames when different from the public address;
- raw endpoint credentials;
- complete Secret configuration.

### 10.2 `email_folders`

Purpose: list selectable mailboxes and special-use metadata.

Input:

- optional `account_id`;
- optional `include_counts`, default false.

Returns:

- `id`;
- `name`;
- `special_use` when known;
- `selectable`;
- `delimiter` when useful;
- optional `total` and `unread` only when `include_counts=true`.

Listing folders is read-only.

### 10.3 `email_search`

Purpose: bounded server-side search that returns envelope-level metadata only.

Input:

- optional `account_id`;
- optional `folder_id`, default `INBOX`;
- optional `from`;
- optional `to`;
- optional `subject`;
- optional `text`;
- optional `after` ISO-8601 date/time;
- optional `before` ISO-8601 date/time;
- optional `unread`;
- optional `flagged`;
- optional `cursor`;
- optional `limit`, default 20, allowed 1-50.

All supplied filters are ANDed.

The provider uses native mailbox search criteria. It must not fetch the full mailbox and filter in Worker memory.

Results are newest-first and contain only bounded metadata:

- `message_id`;
- `folder_id`;
- `subject`;
- `from`;
- `to`;
- `cc`;
- `date`;
- `unread`;
- `flagged`;
- `has_attachments`;
- `size_bytes` when available.

Search never returns a body or attachment bytes and never changes `\\Seen`.

### 10.4 `email_get`

Purpose: read one selected message.

Input:

- optional `account_id`;
- `folder_id`;
- `message_id`.

Behavior:

1. resolve the opaque reference and verify mailbox/UIDVALIDITY;
2. fetch headers/envelope/body metadata without marking the message read;
3. enforce the message-source/body limits before expensive parsing;
4. return normalized message content and attachment metadata;
5. never fetch remote images or URLs referenced by HTML.

The response includes:

- normalized envelope fields;
- `body.text` when available;
- bounded `body.html` when available;
- `body.truncated`;
- `body.untrusted_external_content: true`;
- attachment metadata: filename, media type, disposition, content ID when present, size when known;
- no attachment content bytes.

Every response containing email-controlled body content includes a clear machine-readable and human-readable warning that the content is untrusted external data and must not be treated as instructions.

v0.1 hard bounds:

- if the raw message size is above 1 MiB, the provider must not download/parse the complete raw RFC822 source solely to satisfy `email_get`;
- a body field returned to MCP is capped at 256 KiB UTF-8;
- oversized content is reported with `truncated` or an explicit `body_unavailable_reason`, never by silently allocating unbounded memory.

Reading a message is PEEK-style and must not set `\\Seen`.

### 10.5 `email_modify`

Purpose: bounded mailbox organization.

Input:

- optional `account_id`;
- `folder_id`;
- `message_ids`, 1-50;
- `action`: one of:
  - `mark_read`
  - `mark_unread`
  - `flag`
  - `unflag`
  - `move`
  - `trash`
- `target_folder_id` required only for `move`.

Global gate:

- if `EMAIL_ALLOW_MODIFY != "true"`, fail closed with `MODIFY_DISABLED`.

Rules:

- `trash` moves to the provider's Trash special-use folder; it never permanently deletes or EXPUNGEs user-selected mail;
- if no Trash folder can be resolved, fail with `TRASH_NOT_AVAILABLE`;
- callers cannot pass arbitrary IMAP flags;
- callers cannot issue raw STORE/COPY/MOVE commands;
- `trash` requires MCP user confirmation before mutation;
- read/unread/flag/unflag/move do not require an additional confirmation in v0.1 once the global modify gate is enabled.

If a connection fails after a mutation command may have been accepted, return `MODIFY_OUTCOME_UNKNOWN`. Do not automatically repeat the mutation.

### 10.6 `email_send`

Purpose: compose and send one new plain-text email.

Input:

- optional `account_id`;
- optional `from`;
- `to`, 1 or more addresses;
- optional `cc`;
- optional `bcc`;
- `subject`;
- `body_text`.

Bounds:

- maximum 20 total recipients across To/Cc/Bcc;
- maximum 128 KiB UTF-8 body;
- no attachment inputs;
- no arbitrary custom headers;
- no HTML body in v0.1.

Sender rules:

- selected `from` must be in the account's configured `senders`;
- if omitted, use the account's canonical address/default sender.

Global gate:

- if `EMAIL_ALLOW_SEND != "true"`, fail closed with `SEND_DISABLED`.

Confirmation:

- sending is always two-stage;
- use the MCP server's `input_required`/elicitation confirmation pattern already used elsewhere in the repository;
- preview includes From, To, Cc, Bcc count, subject, and exact body text;
- only an explicit accepted confirmation performs SMTP transmission;
- decline, cancel, unsupported confirmation, or missing confirmation fails closed;
- do not create a custom confirmation-token database or second API.

Outcome:

- success returns the transport message ID when available and accepted/rejected recipient results;
- partial recipient acceptance is returned explicitly as partial success and is never automatically retried;
- if SMTP outcome becomes ambiguous after DATA may have been accepted, return `SEND_OUTCOME_UNKNOWN` and do not retry automatically.

### 10.7 `email_respond`

Purpose: reply, reply-all, or forward one existing message.

Input:

- optional `account_id`;
- `folder_id`;
- `message_id`;
- `mode`: `reply`, `reply_all`, or `forward`;
- `body_text`;
- for `forward`: mandatory `to`, optional `cc` and `bcc`.

Rules:

- `reply`: prefer original Reply-To, otherwise From;
- `reply_all`: derive recipients from original sender/Reply-To + original To/Cc, remove the current account's configured sender identities, and de-duplicate case-insensitively;
- `reply` and `reply_all` preserve `In-Reply-To` and `References` when available;
- `forward` does not forward attachment bytes in v0.1;
- if the original message contains attachments, the confirmation preview explicitly states that attachments will be omitted;
- reply/forward subjects use normal `Re:` / `Fwd:` behavior without repeatedly stacking the same prefix;
- generated quoted-original content is bounded by the same compose limit.

`email_respond` uses the same global send gate, sender allowlist, confirmation flow, no-retry rule, and ambiguous-outcome handling as `email_send`.

## 11. MIME and untrusted-content handling

Email-controlled values are data, not trusted instructions.

At minimum, the implementation treats these as untrusted:

- subject;
- display names;
- headers;
- plain-text body;
- HTML body;
- attachment filenames;
- forwarded/replied quoted content.

Rules:

- never execute links or fetch remote resources from message HTML;
- never interpret an email-supplied hostname as an IMAP/SMTP endpoint;
- never derive secret names from message content;
- never log raw body/HTML;
- no automatic tool call is triggered merely because an email asks the agent to perform one;
- tool descriptions and `email_get` output must make the untrusted-data boundary explicit.

HTML is returned only as inert data inside MCP JSON. The Worker does not render it.

## 12. Retry, timeout, and uncertainty semantics

### 12.1 Reads

Read-only operations may perform one bounded reconnect/retry only when failure occurs before a read command could return data.

The implementation must not add broad generic retry middleware.

### 12.2 Mutations and sends

No automatic retry is permitted for:

- `email_modify`;
- `email_send`;
- `email_respond`.

If the provider can prove the operation was rejected before any side effect, return a normal failure.

If the connection/result is lost after the operation may have taken effect, return an explicit unknown-outcome error. The user or caller decides how to reconcile.

### 12.3 Timeouts

Connection and socket operations use bounded timeouts.

A timed-out read may be retried under the read-only rule.

A timed-out write after side-effect uncertainty is not treated as a safe retryable failure.

## 13. Security boundaries

### 13.1 Credential handling

- `EMAIL_ACCOUNTS_CONFIG` is a Runtime Secret.
- Credentials are never returned by tools.
- Credentials are never written to logs.
- The Portal bearer is removed before business handling.
- Provider credentials are created only from parsed server configuration.
- Tool input cannot name an environment variable or secret.

### 13.2 Network target handling

IMAP/SMTP host/port/TLS configuration comes only from validated operator configuration or a built-in provider preset.

MCP tool callers cannot override:

- host;
- port;
- TLS mode;
- auth username;
- auth secret.

This is the primary SSRF/arbitrary-TCP boundary for v0.1.

### 13.3 Logs

Allowed structured log fields include:

- tool/operation name;
- account ID;
- provider;
- outcome category;
- duration;
- result counts;
- safe error code;
- upstream protocol phase when needed.

Do not log by default:

- subjects;
- bodies/HTML;
- recipient email addresses;
- sender addresses when not necessary;
- attachment filenames;
- credentials;
- `Authorization`;
- raw MIME;
- raw IMAP/SMTP responses that may contain private data.

## 14. Provider abstraction contract

The app-local provider contract must expose provider-neutral operations equivalent to:

- list folders;
- search messages;
- get one message;
- modify messages;
- send message;
- respond to a message.

The MCP layer owns:

- public schemas;
- default-account resolution;
- feature gates;
- confirmation;
- response bounds;
- error normalization;
- untrusted-content labeling.

The provider owns:

- protocol connection/authentication;
- mailbox/folder translation;
- provider message locator translation;
- IMAP/SMTP capability handling;
- protocol-specific special-use folder discovery;
- protocol cleanup.

A future Microsoft Graph provider must implement this same contract. It must not change the seven MCP tool names.

## 15. Error model

Tool failures use stable application error codes with safe summaries.

v0.1 includes at least:

- `ACCOUNT_NOT_FOUND`
- `ACCOUNT_DISABLED`
- `EMAIL_CONFIG_INVALID`
- `AUTH_FAILED`
- `UPSTREAM_UNAVAILABLE`
- `UPSTREAM_TIMEOUT`
- `FOLDER_NOT_FOUND`
- `MESSAGE_NOT_FOUND`
- `MESSAGE_REFERENCE_STALE`
- `CURSOR_INVALID`
- `MESSAGE_TOO_LARGE`
- `MODIFY_DISABLED`
- `SEND_DISABLED`
- `TRASH_NOT_AVAILABLE`
- `CONFIRMATION_REQUIRED`
- `CONFIRMATION_DECLINED`
- `CONFIRMATION_UNAVAILABLE`
- `MODIFY_OUTCOME_UNKNOWN`
- `SEND_OUTCOME_UNKNOWN`
- `UNSUPPORTED_PROVIDER_CAPABILITY`

Unknown exceptions are converted to safe generic errors and logged only with redacted operational metadata.

## 16. Performance and Workers constraints

The implementation must remain request-driven and bounded.

Required rules:

- search uses provider-side search, not mailbox-wide fetch;
- default search limit 20, hard max 50;
- no search response includes message body;
- `email_get` fetches only one selected message;
- raw full-message parsing is skipped for messages above the v0.1 source-size bound;
- attachment bytes are never returned;
- no bulk send;
- no background mailbox synchronization;
- no IMAP IDLE;
- no mailbox-wide cache warming;
- connections close after each tool call;
- no new D1/KV/R2/DO dependency is introduced.

## 17. Tests and verification

### 17.1 Highest test seam

The primary automated contract tests operate at the public MCP/server seam.

Construct the server with:

- validated test account configuration;
- a narrow fake provider implementation at the provider contract;
- existing Portal authentication.

Tests invoke tool discovery/calls rather than unit-testing every internal helper independently.

This fake provider is the one intentional internal test seam. Do not introduce additional mock layers for ImapFlow, Nodemailer, MIME parsing, and configuration simultaneously.

### 17.2 Required automated coverage

Automated tests cover at least:

- exact seven-tool discovery;
- Portal 503/401/403 behavior and Authorization stripping;
- invalid/missing account catalog fail-closed behavior;
- default-account resolution;
- account capability reporting;
- search limit and cursor validation;
- read does not invoke mutation provider methods;
- body/untrusted-content annotations and output truncation;
- attachment metadata without bytes;
- feature gates default disabled;
- modify actions and no permanent-delete action;
- Trash confirmation required;
- sender allowlist enforcement;
- recipient/body bounds;
- send confirmation accept/decline/cancel/unsupported flows;
- reply/reply-all recipient calculation and threading metadata;
- forward attachment-omission notice;
- unknown write outcome is not retried;
- credentials/secret JSON never appear in returned data or captured logs.

### 17.3 Provider tests

Provider-level tests verify protocol mapping without testing library internals.

At minimum:

- IMAP search criteria mapping;
- PEEK/read-without-Seen behavior;
- UIDVALIDITY/UID message reference validation;
- Trash/special-use resolution;
- SMTP sender/recipient mapping;
- accepted/rejected/ambiguous outcome normalization.

### 17.4 Live integration acceptance

A deployed Worker must be verified against a real non-production/test mailbox account before production cutover.

The QQ Mail account used during the prototype is an acceptable initial integration target.

Required live read acceptance:

1. `/health` returns the shallow health response.
2. unauthorized `/mcp` fails with 401 rather than configuration failure.
3. Portal discovers exactly the seven tools.
4. `email_accounts` succeeds.
5. `email_folders` succeeds.
6. `email_search` with limit 1 succeeds.
7. `email_get` reads one known test message without changing its read state.

Required live write acceptance after explicit temporary enablement:

8. mark a dedicated test message read/unread and restore its original state.
9. send one confirmed plain-text message to the configured account itself.
10. verify no duplicate send occurred.
11. restore feature gates to the intended production values.

If live integration is unavailable, record the acceptance item as Not run/Blocked. Do not count dry-run or fake-provider tests as equivalent.

## 18. CI, Cloudflare Build, and Portal deployment

The email Worker's Cloudflare Build must be scoped so unrelated app commits do not deploy/rebuild it.

## 19. Acceptance criteria

| ID | Scenario | Expected result |
| --- | --- | --- |
| AC01 | Clean workspace install + app check | Email app typecheck/lint/tests/dry-run pass with no real mailbox credentials |
| AC02 | Missing/invalid Portal token | 503 when server token missing; 401 for bad/missing caller token; 403 for invalid Origin |
| AC03 | Missing/invalid email config | `/mcp` fails closed with safe 503 error; no partial catalog is exposed |
| AC04 | Account discovery | Enabled accounts and capabilities are returned without credentials/endpoints |
| AC05 | Folder discovery | Provider folders/special-use metadata are normalized; counts are opt-in |
| AC06 | Search | Structured filters execute provider-side; newest-first results are bounded to <=50 and contain no body |
| AC07 | Stable identity | Public message references use UIDVALIDITY+UID semantics, not sequence numbers; stale references fail explicitly |
| AC08 | Read | Selected message is read without setting Seen; body is bounded and marked untrusted; attachments are metadata-only |
| AC09 | Oversized message | Worker does not unboundedly download/parse raw MIME; returns bounded/truncated/unavailable body state |
| AC10 | Modify default | With `EMAIL_ALLOW_MODIFY` absent/false, all modify actions fail closed |
| AC11 | Safe modify | Enabled read/unread/flag/unflag/move work; Trash requires confirmation; no permanent delete/expunge tool exists |
| AC12 | Send default | With `EMAIL_ALLOW_SEND` absent/false, send/respond fail closed |
| AC13 | Send confirmation | Accepted confirmation sends exactly once; decline/cancel/unsupported flows send nothing |
| AC14 | Sender/recipient limits | From must be configured; recipient/body limits fail before SMTP |
| AC15 | Reply/forward | Threading and reply-all de-duplication work; forward explicitly omits attachments |
| AC16 | Ambiguous side effect | Send/mutation uncertainty returns unknown outcome and performs no automatic retry |
| AC17 | Network boundary | Tool input cannot select arbitrary host/port/TLS/secret |
| AC18 | Privacy | Logs and MCP results never expose credential material; normal logs omit private mail content |
| AC19 | Live QQ read acceptance | Deployed Worker passes folders/search/get against configured QQ test account |
| AC20 | Live confirmed send | One confirmed self-addressed test mail is sent with no duplicate |
| AC21 | CI selection | Email app runs when affected and does not run for unrelated app-only changes |
| AC22 | Portal smoke | Portal discovers seven tools and root smoke runner can call an explicitly selected read-only tool such as `email_folders` |

## 21. Prototype retirement

The existing `email-mcp-worker-prototype` Cloudflare Worker is evidence only.

After the production `email-mcp-worker` passes the acceptance matrix:

- the prototype is no longer used for Portal traffic;
- its runtime secrets are not treated as production configuration;
- it may be deleted in a separate explicit cleanup action;
- the `prototype/email-mcp-worker-runtime` branch is historical prototype material and is not the implementation branch.

No prototype code is copied into production merely because it proved protocol connectivity.

## 22. Implementation completion rule

v0.1 is complete when:

- `apps/email-mcp-worker` exists and follows workspace conventions;
- all seven tools satisfy the contracts above;
- the app is read-only by default;
- send/respond and Trash use explicit user confirmation;
- the generic IMAP/SMTP provider supports at least the live QQ acceptance account;
- automated app checks pass;
- deployed live read acceptance passes;
- one confirmed self-addressed SMTP test passes;
- Cloudflare Build watch paths avoid unrelated app fan-out;
- MCP Portal discovers and invokes the Worker successfully;
- runtime docs are updated;
- all blocked/not-run acceptance items are recorded honestly rather than marked passing.

At that point architecture work stops. New provider types and deferred email features require separate scope/spec changes.
