# Spec #279 — Email MCP (generic IMAP/SMTP)

Status: Draft PR #284; blocked on live Workers-network mail acceptance.
This is the current scope. The earlier Gmail/Graph OAuth design is superseded
by the user's 2026-10-26 decision to use the existing ChatGPT Gmail and
Outlook Email plugins for those mailboxes.

## Objective

Add `apps/email-mcp-worker` to `lirtual/mcp-workers` for a single owner's
multiple **other** IMAP/SMTP mailboxes. Do not reimplement Google's Gmail
API, Microsoft Graph, OAuth app registration, provider token lifecycle,
cross-system plugin orchestration, mailbox mirroring or local message storage.

The Gmail/Outlook plugins operate independently in ChatGPT. The Email Worker
does not invoke them. ChatGPT can use the appropriate connected integration
for each mailbox, but neither this Worker nor standalone Cloudflare
Workflows automatically sees the plugins' accounts or tool results.

## Architecture and contract

- Independently deployed TypeScript Cloudflare Worker, stateless `/mcp`
  protected by the existing Portal bearer.
- Owner-only `/setup` on `email.lirtual.dpdns.org` protected by Cloudflare
  Access email OTP; host-locked signed JWT and CSRF checks. No OAuth callback.
- One D1 stores account metadata, encrypted login secrets and send fences.
  Root encryption keys remain only in Worker Secrets. Controlled rotation
  with old/new key readback, no second key manager.
- `mail_accounts` permits only `imap_smtp`; account identity `account_id`
  and email address verified on credential replacement. No legacy data,
  token refresh state or OAuth sessions.
- Account setup authenticates IMAP 993 TLS and SMTP 465 TLS / 587 mandatory
  STARTTLS before credentials can be saved. Fail closed for unverified
  TLS, forbidden mail IP ranges, private/loopback targets, and unauthorized
  alternate domains/paths. Native Gmail/Microsoft endpoint presets excluded.
- Provider-native folders and IMAP UID+UIDVALIDITY references, bounded
  searches without silent partial success, plain-text safe mail parsing.
- Sender and recipients are always explicit. Up to 5 MiB raw attachments,
  only inline or same-mailbox references, no arbitrary download URLs.
- D1 request fence for sends and forwarding/replies: submitted, accepted,
  failed and indeterminate. Unknown delivery MUST NOT be automatically retried
  with a fresh request ID. No unbounded bulk write/permanent delete.

## MCP tools

13 tools: `account_list`, `capabilities_get`, `mail_search`, `mail_get`,
`folder_list`, `attachment_get`, `draft_create`, `mail_send`,
`mail_reply`, `mail_forward`, `mail_mark`, `mail_move`, `mail_trash`.

IMAP Drafts requires supported native folder/UIDPLUS and does not support
draft edit or draft attachments. Native thread lookup is not modeled when
the provider does not expose a reliable conversation ID; no fabricated
thread based on subject. For unsupported capabilities report `unsupported`.

## Agreed 2026-10-26 socket security boundary

The initial design attempted to pin the exact resolved public IP into every
TCP connection. Actual Workers remote probes rejected those numeric targets,
while hostname-based Node TLS connected and validated certificates. The user
authorized this bounded change to the unshipped design, **not** a silent claim
of equivalent DNS-rebinding isolation.

- Before connection, validate hostname/port and every returned A/AAAA record
  through Cloudflare DoH. Reject any unsafe or non-public response.
- Connect using the verified hostname, relying on Cloudflare Workers TCP
  address prohibitions and TLS hostname certificate validation.
- IMAP: native ImapFlow `createSocketsTransport` + `cloudflare:sockets` with
  implicit TLS on 993.
- SMTP: Nodemailer `getSocket` with a hostname TLS socket on 465 or a TCP
  socket with mandatory STARTTLS on 587; no auth before TLS.
- A DNS change between the precheck and connection remains possible. A
  verified connected numeric IP is unavailable, so strict IP pinning is **not**
  part of the current security guarantee. Do not reintroduce arbitrary
  IP-literal connects, proxy fallback or unvalidated redirect destinations.

2026-10-26 one-shot remote previews: six public IMAP/SMTP TLS certificate
handshakes succeeded on 993/465; ImapFlow's native `cloudflare:sockets`
transport read unauthed IMAP greetings from 163 and QQ; Nodemailer pre-socket
verified an unauthed SMTP 465 handshake at 163 and an unauthed 587 STARTTLS
handshake at QQ. SMTP 163:587 timed out. No mailbox credentials, IMAP LOGIN
or SMTP AUTH were attempted; actual send/read acceptance is still pending.
