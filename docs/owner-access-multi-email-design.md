# Unified Owner Access multi-email design

Status: **Design agreed, 2026-11-10; implementation, Access edits, release, and cleanup NOT authorized by this document.** Matt Pocock Grill With Docs decisions Q1=B; Q2=A; Q3=A; Q4=A; Q5=A; Q6=A.

## Goal and verified baseline

Make the same existing explicit Owner email allowlist eligible at every active Owner Access entrypoint, without any extra maintainable email configuration, identity store, role system, Worker, queue, database, or runtime API credential. Cloudflare account-level Access inventory on 2026-11-10 showed 15 Access applications (one page, 15/15). Thirteen applications already attach the reusable `Default Allow Rule` (policy ID `659d043c-e957-4c91-9f33-2416c52ecbe5`), with **three exact email Include selectors**. Browser Profile Activation and EdgeSSH each attach a separate single-email Allow policy. The retired Database Setup and Weixin applications are not recreated. Do not commit the mailbox values to source or log them.

Browser Profile Activation: fixed app ID `77945f97-e1ea-4b2b-b89a-ec71c0472afa`, existing independent 15-minute application session, Owner-only SSO+OTP and same-Profile one-use proof. EdgeSSH: existing `ssh.lirtual.dpdns.org` self-hosted Access app, 720-hour application session and SSO+OTP. Other Access applications' current reusable human-Allow and service-token policies are already distinct; leave non-identity policies and OAuth/Portal authorization unaffected. See [the existing SSO/OTP acceptance](owner-access-sso-browser-review-design.md) and [Spec #804 decision](adr/0001-global-config-owner-names.md).

## Authorization model

1. The exact existing reusable `Default Allow Rule` is the **only maintained Owner-email set**. Read its complete, paginated policy inventory through Cloudflare API with an existing protected release token. Require the reviewed policy ID, `decision=allow`, a nonempty bounded set of explicit email Include rules only, no wildcard / domain / Everyone / group / broad grant, and no unexpected Require, Exclude, session-duration override, policy-precedence or identity-provider drift. Validate each address, reject duplicates, invalid entries and incomplete API responses; use deterministic sorting/encoding. Policy read failure or unexpected rule shape fails closed. The selected app's reviewed Access identity, issuer and audience must still be verified independently.
2. Browser Release Worker stages this validated set as a **runtime snapshot**, not as a second human-maintained GitHub Variable and not as a new runtime Cloudflare API dependency. Prefer retaining the existing `BROWSER_OWNER_EMAIL` runtime binding name for release/rollback continuity while changing its value to a deterministic, bounded encoded email set and the Worker verifier to exact membership. For the transitional old version, a single email remains one allowed member; keep issuer, audience, expiration, signature/JWKS validation and other JWT checks unchanged. Existing no-shadow and candidate/active readback gates must be revised to verify the newly derived canonical set and explicit migration rather than stale single-email equality. Never accept arbitrary string splitting or an empty/bad policy as authorization. No email addresses in logs, PR evidence or public receipts.
3. The **identity eligibility** of all addresses is equal. Each application's existing additional checks stay effective: Browser's user-initiated local gesture, extension installation identity and same-Profile one-use proof; SSH upstream's existing authentication and connection ownership; MCP/Portal its separate service-token/OAuth and app-specific authorization. Email membership alone never grants arbitrary browser/SSH operations or expands service tokens.
4. New entries and deletions are managed **only in the shared Cloudflare Policy**. A changed Policy takes effect immediately for its attached applications, but the Browser release snapshot only changes after separately authorized publish. Do not claim the two converge automatically; approved rollout must verify both sides. A future normal release can accept a reviewed *email-set-only* difference from the active Browser binding while other identity/security values must match and the candidate must exactly match the live source at prepublication and readback. No new general bypass or permanent drift waiver.
5. On email removal, revoke that exact user's Cloudflare Access sessions using the platform's native per-user operation (which can affect all their Access applications) and verify the session-removal receipt. Also publish and verify the updated Browser runtime snapshot through the normal authorization path. Access-session revocation is not equivalent to invalidating independently stored Browser Endpoint credentials, already running SSH connections or all previously issued offline JWT bytes; do not promise instantaneous universal revocation. Browser already-paired Endpoints remain authorized under the Owner-approved Q6=A model unless separately revoked through the existing Stop/Revoke mechanisms. Incident response may separately stop/revoke all affected grants after inspecting impact; do not silently invent email ownership fields or a new revocation service.

## Implementation plan (non-production work first)

1. Snapshot current Access application/Policy links, allow rules, IDPs, policy effective session settings and active Worker version/bindings through **read-only** API checks. Verify all 15 apps covered without assuming that their policies are the same; do not change the existing service-token policies. Verify the shared policy has no session-duration override; its reuse must preserve Browser 15m and EdgeSSH 720h effective sessions.
2. Update only Browser auth, Browser Policy discovery, release staging and identity-continuity validation, their targeted unit/Workers tests, related docs and minimum existing CI. Remove obsolete GitHub `OWNER_EMAIL` consumption **in code**, while retaining the live Repository Variable until separately approved cleanup. No changes in the EdgeSSH repository are presumed without an actual code-level dependency.
3. Validate single-email historical behavior, multi-email success for every configured address, unknown/malformed/duplicate/empty/overbroad policies, wrong issuer/audience, invalid/expired/tampered JWT, unexpected Access Policy/IDP/app drift, candidate/current set difference during an explicitly approved migration, service-token separation, same-Profile proof and replay denial. Verify that CI/merge alone cannot deploy production.
4. After **separate explicit production release authorization**, publish the Browser Worker first using a newly read approved shared Policy snapshot while Browser Activation still keeps its former single-email Access policy. Check exact active 100% version, issuer/audience/origin, normalized email-set runtime binding, DO identity, original Portal auth and valid/invalid real activation flows. During this transition, the Browser set can be broader than its old front-door Access policy; this is intentional fail-closed login behavior, not a promise of broader effective access.
5. Only after Browser has passed, and with **separate explicit Access permission-change authorization**, attach Browser Activation to the existing shared Allow policy, without changing its app ID, domain, selected SSO/OTP IdPs, session or other rules. Verify all authorized mailbox identities can authenticate and unlisted identities cannot; independently test Browser's app-level JWT and one-use same-Profile proof. Then attach EdgeSSH to that same existing policy with separate identity/session and real-login validation. Verify 15m and 720h effective session lifetimes; if policy reuse changes either, stop without proceeding until corrected within the authorized scope. Leave all other applications and service tokens unchanged.
6. After independent production confirmation, **only with separate configuration-cleanup authorization**, delete GitHub Repository `OWNER_EMAIL` and read back absence; no secret changes, release or Access changes are implied by this doc. Preserve prior Access policy IDs as rollback references until separately reviewed retirement; don't delete policies merely because unreferenced.

For future additions: update Policy first, then separately authorize and release the Browser snapshot; newly added emails may temporarily pass Access but fail Browser until publication. For removals: update Policy, revoke targeted Access user sessions and publish a snapshot excluding the removed address; between those steps a prior Browser version can retain a stale allowlist and existing grants remain. Security-critical emergency revocation must explicitly address existing Browser/SSH grants in addition to normal Access changes. Any write with Unknown outcome requires read-only readback before retry.

## Acceptance and non-goals

Pass only on independent evidence of source/Policy correctness, exact app attachment and unchanged effective session/auth methods, successful protected Browser release and all required binding readbacks, legitimate mailbox logins, denied unlisted mailboxes and invalid JWTs, Browser same-Profile one-use proof, retained historic Endpoint/grant records, unchanged EdgeSSH behavior, and negative inventory for retired GitHub Variable after its own authorization. Report partial or waived live tests precisely, not as Pass. No new independent Access apps, new global identity provider, auto-synchronizer, cron, database, per-email Browser ownership storage, role model, silent revocation of existing grants, PAT changes, or production rollout follows from this design alone.
