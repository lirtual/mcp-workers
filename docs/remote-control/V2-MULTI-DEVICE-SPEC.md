# Remote Control MCP v2 — One authoritative multi-device Spec

**Status:** owner approved **single-code pairing** on 2026-10-18 (design only; source implementation and new nonproduction approval tests pending). Earlier two-code #47/#50 results remain historical and do not certify the new protocol. Source implementation is under [Draft PR #58](https://github.com/lirtual/mcp-workers/pull/58), but production deployment and full multi-device acceptance are **not** authorized. Updated 2026-10-17 (no tombstones under ADR-0017; temporary grants have a fixed 24-hour lifetime under ADR-0018; both implementation changes pending).
Authority: [ADR-0014 — transport](./adr/0014-v2-multi-device-ws-do.md), [ADR-0015 — pairing](./adr/0015-v2-pairing-and-identity.md), [ADR-0017 — device removal](./adr/0017-v2-device-revocation-without-tombstones.md), [ADR-0018 — temporary 24-hour authorization](./adr/0018-v2-temporary-agent-pairing-lifecycle.md), [ADR-0019 — standalone CLI distribution](./adr/0019-standalone-linux-agent-distribution.md). Existing [v1 Spec](./SPEC.md) continues to govern the deployed single-device path.

## Goal

One Remote Control MCP controls separately paired Linux/WSL2 Agents across unrelated networks, with near-one-command installation, explicit per-operation device selection and independent revocation. Reuse the existing native Node.js file/Shell/managed-process implementation and **Agent-local operation receipts**. The v2 Agent opens outbound WSS to one **SQLite-backed Durable Object using WebSocket Hibernation**. No device public IP, port forwarding, Tunnel, Cloudflare One Client or Mesh enrolment for v2.

## Standalone Linux/WSL2 CLI onboarding — approved Q1=A / Q2=A / Q3=A (2026-10-17)

Authority: [ADR-0019 — standalone Linux Agent distribution](./adr/0019-standalone-linux-agent-distribution.md). These decisions describe the *target design*, not currently available GitHub artifacts or a working installer.

**Q1=A — initial operating systems:** Target Linux **x86_64 and ARM64**, including WSL2 distributions that run the Linux Agent. Native Windows/macOS are excluded. **Full Shell Supervisor currently depends on Linux 6.9+**: its `pidfd_send_signal` uses `PIDFD_SIGNAL_PROCESS_GROUP`. Run a harmless *actual capability probe* in the preflight before creating or pairing a cloud identity; version strings, Node 24 or CPU compatibility alone are insufficient. Only advertise tested kernel/libc/ABI combinations; do not claim universal distro/musl support, automatically downgrade Shell process safety or create a second process manager. WSL2 user systemd cannot wake a stopped distro.

**Q2=A — prebuilt GitHub Releases:** Publish **versioned, ready-to-run Linux Agent packages** as GitHub Release assets, bundling the required **Node.js 24 runtime, existing JavaScript Agent code and the precompiled C Shell Supervisor** for the supported architecture. New devices require **no Git checkout, local Node/npm/pnpm setup, C compiler, or TypeScript build**. This must use the existing Agent implementation and must not turn into a source-building one-line wrapper. The exact portable layout, build provenance/signing and `x86_64`/`arm64`/libc artifact matrix are subject to the next grilling round. At present the repository has **no standalone GitHub Release assets**.

**Q3=A — one command, interactive local mode selection:** One terminal command downloads/starts the **reviewed** installer, and that installer **asks the owner to choose `Permanent device` or `Temporary device (24 hours)`** before requesting approval. The permanent/temporary answer is unambiguous and must be propagated through actual approval so the server commits the correct device expiry. Do not silently default to permanent. The CLI displays one **10-character pending code**. Owner submits it to authenticated MCP `pairing_lookup` and explicitly calls `pairing_approve` for the same reviewed pending identity; the new Agent automatically proves private-key possession to claim its approved device ID. **No 12-character local challenge input.** The CLI cannot self-approve, grant Cloudflare/Portal privileges or embed owner credentials.

**Installer/Agent boundary:** Packaging, mode selection and user prompts are installation concerns; the Worker/DO authorizes an explicit device identity with permanent or fixed 24-hour grant according to ADR-0018. Repeat installation must respect ownership and identity preservation. Any default service lifecycle and temporary foreground behavior remain pending (see ADR-0019); the existing `--foreground` path can be reused only after standalone packaging support and safety review. Do not overwrite v1 production, another working v2 unit or live identity automatically.

**Current code gap (Draft PR #58):** `apps/remote-control-agent/scripts/install-v2.mjs` currently uses a **trusted source checkout**, checks **Node.js 24 + `cc`**, locally compiles the Session Supervisor, and writes a `systemd --user` service referencing checkout paths. A source installation cannot be called successful one-command onboarding; change the on-device runtime layout/service paths for the portable package.

**Approved Q4–Q8 (ADR-0019):** Q4=A official GitHub HTTPS + verified immutable version + SHA-256 checksum (prefer GitHub Release API asset `digest`; no extra manifest service); Q5=A owner-initiated upgrade that preserves keys and receipts, **refuses running Managed Sessions**, and rolls back only versioned executable files on *local activation failure* (never implicitly revert SQLite or re-pair); Q6=A local v2-only uninstall retaining identity/receipts and instructing independent authenticated MCP `revoke_device`; Q7=A rerun **the same installer command** for safe, idempotent recovery without new install database; Q8=A permanent via `systemd --user` and 24-hour temporary **foreground**. Installation URL and bootstrap command are **not live**. No new CI workflow, deploy, package upload, secret or production change is authorized by this round.

### Standalone installer safety and release-contract details

- **GitHub trusted channel:** Release assets from canonical `lirtual/mcp-workers` must be immutable **in verified repository settings** before trusting that property. Resolve one fixed version, commit, expected asset ID/name, architecture and GitHub REST API asset SHA-256 `digest`; fail closed on missing/invalid digest rather than invent a redundant checksum manifest. Download over HTTPS, compare local archive SHA-256 before extraction, then safely extract (no traversal/symlink escalation). No `latest` switch midway through installation or on-device source compilation.
- **Important trust limitation:** GitHub's archive `digest` authenticates byte consistency **relative to GitHub's asset metadata**, not an independently trusted publisher. The installer script itself is executable code: fetch it from the reviewed, version-bound official HTTPS origin and do not claim its own checksum self-authenticates it. Optional attestation verification is not a Q4=A requirement; **do not invent a live `curl | sh` download URL**.
- **Single-command interactive stdin:** the downloaded/bootstrap script must start the pairing CLI using the device's **actual local controlling terminal**. A pipe that consumes standard input for a script must not consume the user's subsequent mode selection and code display; fail with a clear local error if no independent TTY exists. A shell installer does not authorize the device by itself.
- **Upgrade simplicity and safety:** stage a verified release; keep only **current and previous** versioned program files with a simple active pointer/service reference. Device key/ID, endpoint, selected mode and SQLite operation receipts remain outside versioned binary directories. **Refuse routine upgrade while Agent-owned sessions are running/starting or ownership is uncertain**; never surprise-terminate them via systemd restart. Validate local binary startup separately from remote WSS reachability: a transient network outage should be reported as `connectivity_unconfirmed`, not automatically trigger rollback. Restore previous executable on **definitive local activation failure only**, not SQLite data; deny schema/protocol-incompatible migrations and never blindly replay unknown operations.
- **Local uninstall is not remote revoke:** stop/disable/remove only the installer-owned v2 service/CLI/files; do not alter production v1 or other accounts. Preserve user keys, identity and receipts by default. Optional local purge requires explicit confirmation and precise path scope. Clearly direct owner to `revoke_device({device_id})` through independently authenticated MCP, and show when cloud-side revocation **has not** occurred. Do not give the Agent an owner Bearer or silently create a self-revoke endpoint.
- **Rerun is safe without a state machine:** reuse existing `flock`, verified archive staging, owner-only identity/staging and atomic promotion. Infer the safe next step from **few persisted facts** (fully verified release, local pending/approved ID, owned v2 service); add only an indispensable bounded recovery marker. A revoked/expired device cannot silently re-pair: the current Draft PR #58 expects a permanent `status: revoked` tombstone proof, which **must be replaced** with an authenticated exact-old-identity no-longer-approved result plus **explicit independent owner confirmation** for a fresh key/ID. A bare 404 or network outage never authorizes identity overwrite. Preserve old identity/receipts until confirmed promotion.
- **Mode lifecycle and preflight:** prompt `Permanent` or `Temporary (24 hours)`. **Before generating an identity or contacting the pairing endpoint**, verify supported platform/ABI and Shell Supervisor kernel capability; also verify the user-systemd manager for permanent mode. If unsupported, fail safely without leaving an approved-but-unrunnable identity; do not silently run permanent mode in an unmanaged foreground. Temporary mode starts foreground with separate owner-only key/ID from any permanent Agent and **no** systemd unit. Closing terminal/network loss does not revoke early; the server enforces the full 24-hour fixed deadline. WSL2 distro shutdown cannot be automatically undone by user systemd.
- **No added surface:** no root installer, global binary overwrite, native Windows startup automation, central device account, cloud receipt database, special cron, package registry, long-lived installer credentials, auto-updater or new Workflow solely by default. Reuse existing Node Agent, local user service code, operation receipt store, WSS/pairing protocol and GitHub CI as applicable.

### Final minimal-design blockers (2026-10-17 review)

- **P0 Linux process ownership:** `session-supervisor.c` uses the Linux 6.9+ `PIDFD_SIGNAL_PROCESS_GROUP` flag; preflight a harmless actual process-group pidfd signal probe before pairing. Explicitly reject unsupported kernels/ABI; no unsafe fallback or new process engine.
- **P0 removed tombstones vs re-pair:** PR #58's `assertRemoteRevocation()` calls `/agent/re-pair/status` and expects `status: revoked`. ADR-0017 removes that record. Replace with an authenticated proof that the old device ID no longer has authorization, and require a fresh 10-character code, explicit owner-authenticated MCP approval and signed device-key proof for a new key/ID. Never convert a generic 404/offline into automatic replacement.
- **P0 capability claims:** PR #58 `v2-main.ts` currently sets `readOnly: true, writeFile: false, shell: false`. Packaging and successful WSS auth do not enable Shell/file mutation; restrict initial smoke claims to signed connection + approved nonsensitive read. Destructive capabilities retain independent permissions and acceptance.
- **P1 running-command upgrade:** any active/starting/uncertain Managed Session blocks routine binary switching. No hot migration, no surprise process kill, no receipt wipe; remote offline is not definitive local binary failure.
- **Remove excess:** prefer the GitHub Release asset `digest` to generating a second SHA-256 manifest; reuse current `flock`, identity staging and atomic promotion rather than a full install database; current/previous executable versions are sufficient; no new release service, scheduler, custom compiler or CI workflow by default.

### Acceptance evidence required before coding can be called complete

1. A **clean x86_64 and ARM64 Linux** and WSL2 installation without preinstalled git, Node, pnpm or `cc`; verified native Supervisor compatibility on declared libc/kernel/architecture matrix; unsupported ABI and no-systemd permanent mode fail predictably. The package must come from an actual published GitHub Release, not GitHub's auto-generated repository source archive.
2. A real interactive device terminal displays one code; owner separately approves the exact pending key through Portal/MCP; device completes automatically with signed key proof; no-TTY/interactive-stdin case rejects safely; no automatic installer approval or lookup-side effect (separate authenticated MCP approval is possible and not a cryptographic human-presence proof), no secrets in command arguments/logs, correct 24-hour server expiry and per-mode identity isolation.
3. Manifest mismatch, tampered archive, unsafe entry, wrong architecture, missing asset, broken HTTPS download and locally interrupted extraction all fail before executing unchecked bytes, leave previous working installation intact and are recoverable by rerunning the same command.
4. Manual upgrade preserves keys/IDs/receipts, validates local data/wire compatibility, performs versioned binary switch with rollback after activation failure, never masks an uncertain WSS result, and never replays an unknown mutating operation. An incompatible schema upgrade stops without claiming a reversible data migration.
5. Local uninstall touches only v2-owned files, leaves existing keys and receipt store unless separately confirmed, warns when remote authorization remains live, and keeps v1 intact. Optional explicit purge must not be mistaken for remote revocation.
6. A permanent Agent uses a verified user-systemd service; a temporary Agent has no service unit and doesn't silently stay running after CLI foreground termination. Test WSL2 suspend/reboot, SIGINT/SIGKILL, reconnect, duplicate installer lock and both existing/new device states.
7. Per [Issue #57](https://github.com/lirtual/mcp-workers/issues/57), require **one actual device observed for 48 real hours** with verified DO Hibernation/wake, cross-account Free quota metrics and v1 isolation. The former five-device/72-hour scope was **removed from this rollout gate**; do not reintroduce it as a hidden requirement or claim fleet scale was tested. No production deploy, release or forced CI expansion authorized by these docs.

## User stories

1. As an owner, I want one straightforward install on Linux/WSL2, so that devices on other networks can join without Cloudflare account setup.
2. As an owner, I want a short locally displayed pairing code, so that I can identify an installation before approving it.
3. As an owner, I want to enter one pending code into authenticated MCP, review the matching identity and **explicitly approve only that pending key**, while the Agent proves possession of the matching Ed25519 private key automatically; a lookup must never approve.
4. As an owner, I want `list_devices` with stable IDs and observed status, so that I can target the correct host.
5. As an owner, I want every v2 file/Shell/process command to name its target device, so that concurrent clients cannot redirect actions by changing a default.
6. As an owner, I want disconnected hosts to reject commands, reconnect automatically and reconcile local receipts, so that stale or uncertain mutations are not replayed.
7. As an owner, I want to remove a lost device without harming others, so that its identity and access remain revoked.
8. As an owner, I want online removal to attempt stopping only Agent-owned managed processes, so that the result is accurate without claiming to control an offline host.
9. As an owner, I want reinstallation to require new pairing, so that copied labels/old keys do not inherit authority.
10. As a maintainer, I want the current **one-device 48-hour preview acceptance** with observed Hibernation, Free usage and v1 isolation before requesting initial production authorization, so that the release is assessed against the scope actually approved in Issue #57. This does not prove five-device fleet throughput.

## Stable identities and MCP contracts

- `device_id`: opaque server-issued per-installation identifier; public to authenticated MCP, never based on hostname/IP or user-provided URL. Friendly `name` is untrusted presentation only. Reinstallation creates a new ID/key.
- `operation_id`: existing Agent-local stable mutation identity and receipt; never substitute a WSS correlation identifier. Unknown outcome is `timeout_unknown`, not “failed / safe to retry”.
- `list_devices()` returns bounded **currently approved** `[{device_id,name,status,last_seen_at?}]` only; availability means observed Agent connectivity, not merely network/host state. Removed identities are not returned.
- `pairing_lookup({code})`: Portal-authenticated **read-only** pending device lookup returning `pairing_id`, `name`, `fingerprint`, `expires_at`. Never approves a device.
- `pairing_approve({pairing_id,expected_fingerprint,expected_grant_type})`: separate **mutating Portal-authenticated** approval for one exact immutable pending key, name and permanent/temporary grant type. Consume a valid pending item **once, atomically**; no approval during lookup or background installation. Explicit owner intent is required but Portal Bearer / model invocation is **not cryptographic proof of human presence**. Agent must automatically prove possession of that exact Ed25519 key before claiming approved ID. No second human-entered challenge; old `pairing_prepare` clients must fail closed or use a separately reviewed compatibility plan.
- `revoke_device({device_id})`: atomically delete durable approval and its outstanding session challenge/epoch **before** any socket or process cleanup; then reject fresh connections/dispatch and close live sockets. Attempt an authenticated internal best-effort stop of owned managed sessions if online, reporting `stop_confirmed`, `stop_unconfirmed` or `offline` honestly. An already absent device is `not_found`, not `already_revoked`. No Cloudflare One registration exists to delete.
- Every v2 existing curated tool adds a validated `device_id` while retaining original tool names/arguments and mutation IDs. No global mutable default. The single-device v1 compatibility route cannot silently pick a v2 target.

**Device removal retention refinement (2026-10-17):** This supersedes earlier permanent-tombstone wording only. Removing a device deletes its authorization; there is no persistent removed-device history or automatic 90-day cleanup. The DO must fail closed on missing records, prevent revoke-vs-login/dispatch races, reject stale WSS sessions, and count **approved** identities against the existing device cap. The current Draft PR #58 still implements tombstones and must be updated and independently tested before this design is claimed complete. Temporary-device authorization follows the owner-approved fixed 24-hour lifetime in ADR-0018; it is not implemented by this documentation update.

## Temporary Debug Device — fixed 24-hour grant (2026-10-17)

Owner revision **Q1: fixed 24-hour validity** (supersedes earlier Q1=C exit-coupled revoke) and **Q2 (superseded 2026-10-18): one-code MCP owner approval** ([ADR-0018](./adr/0018-v2-temporary-agent-pairing-lifecycle.md)). This is a *device authorization lifetime*, not a new lifetime for the pending pairing code or individual development commands.

- **Creation and expiry:** Owner deliberately selects temporary mode as part of new-device pairing. On successful explicit owner-MCP approval and Agent key proof, DO records `approved_at` and `expires_at = approved_at + 24 hours` using its server clock, exactly once. Regular permanent identities remain unexpired. Reconnect, activity and ordinary Agent restart never extend this fixed deadline.
- **Pairing security (owner revision 2026-10-18):** The sole local 10-character code is valid **10 minutes and once**. A new registration carries a **signed `pairing_protocol: "single-code-v1"` marker**; old unsigned/old-signed registration or pre-migration pending DO records lacking this marker must fail closed instead of being silently approved (regardless of whether an old local challenge was already prepared). Previously approved old device IDs retain their old signed WSS authorization. Authenticated MCP lookup is read-only, explicit `pairing_approve` atomically authorizes the immutable pending key, and Agent proves the matching Ed25519 private key automatically to claim its ID. A **fresh internal signed WSS session nonce** remains mandatory but is never manually entered. The approved 24-hour `expires_at` is unrelated to the 10-minute code lifetime; the code is not a long-lived bearer token.
- **Fail closed after expiry:** From `now >= expires_at`, DO must deny new WSS login, identity recovery, and new/previously unadmitted remote dispatch, including via an already-open socket and after Hibernation. Check expiry on server-side authorization paths; never rely on socket-close delivery or the Agent's local clock for enforcement. Revoked/deleted/expired devices are absent from usable `list_devices` results.
- **No exit-triggered revoke:** Foreground exit, Ctrl+C, SIGKILL, WSL suspend, power loss and transient network disconnect do **not** trigger additional remote revocation work or a special grace timer. An offline temporary device can reconnect while its original grant is still valid; after 24 hours it must re-pair explicitly to get a new approved identity. The existing owner-authenticated `revoke_device` remains available for early removal.
- **Storage housekeeping:** Expired approval/nonce/epoch records may be **lazily removed on the next applicable DO access**; no DO alarm, extra Worker, polling job or cleanup scheduler. Physical cleanup may lag past the expiration instant, but authorization may **never** outlive the server deadline. Device-capacity counting must exclude/clear expired grants without being fooled by old 65-entry scans. No permanent tombstone.
- **Already-admitted commands:** Deadline expiry blocks **new commands**, not the effects of writes already applied. Existing Agent-owned managed commands keep their **original absolute 60-minute maximum** and usual safe stop/receipt logic; a process started before expiry may run after expiry until its own deadline or normal termination. Do not promise force-stopping offline work at the exact expiry instant or blindly replaying `timeout_unknown`.
- **Reuse, not new infrastructure:** `install-v2.mjs --foreground` already avoids systemd, but current Draft PR #58 still creates durable device identities without expiration. Explicit temporary mode must avoid accidentally altering a normal installed identity (small separate local identity location if required). No self-revoke endpoint, new Portal/admin secret on Agent, new authentication system, scheduler, CI, or production changes.

**Required validation:** approval at T; reject at T+24h (including an already-open WSS), allow at T+24h−1ms; no sliding lease on reconnect; permanent identity unaffected; DO sleep/wake and stale session fencing; repeated temporary expiration/re-pair and 64-active-device capacity; SIGINT/SIGKILL/network interruption; reliable missing-identity response rather than autonomous re-pair; and truthful in-flight operation receipts. The browser/list view must not claim a physically idle socket has closed exactly at expiration without a wake event.

## Agent-only pairing and authentication (separate from MCP)

1. Installer generates a new **Ed25519** pair locally and a cryptographically uniform **10-character Base32 code (50 random bits)**; displays it locally with **10-minute** expiry. The private key remains device-local with restricted OS permissions.
2. A **bounded public, tool-less Agent bootstrap endpoint** registers a pending code verifier + exact public key/fingerprint in the fixed owner DO. It receives no Shell/file authority. Rate-limit submissions and code guesses, cap outstanding pending requests, expire and clean on access; no general queue or always-on alarm.
3. Owner enters the code into Portal-authenticated **read-only** `pairing_lookup`, reviews the immutable fingerprint, device name and mode, then explicitly calls **`pairing_approve({pairing_id,expected_fingerprint,expected_grant_type})`**. Only the owner-scoped DO may atomically authorize this exact pending public key. An intercepted code without MCP authority cannot approve or impersonate any device.
4. After approval, the waiting Agent automatically calls existing `/agent/session/challenge` **by its registered public key**, signs the fresh server nonce with its Ed25519 private key, and calls existing `/agent/session/recover` to obtain its previously approved `device_id`. A lost response is retried with a **new nonce and the same key/ID**, never by creating another grant or rotating identity. There is no new claim endpoint, and old `/agent/pair/complete`, DO `/prepare`/`/complete`, and MCP `pairing_prepare` are not alternate authorization paths. **Recovering an ID is not a WSS login**: each operational socket subsequently signs its own fresh server nonce. No local second code or manually entered challenge, and never send owner Portal Bearer to Agent/public bootstrap.
5. Every subsequent WSS reconnect uses a new challenge and the same approved local private key. Verify current SQLite authorization at connection and before **each command dispatch**, including after Hibernation wake. Use a deterministic per-device connection epoch to fence duplicate old sockets. Removal permanently invalidates the old `device_id`; no old authorization survives. Without historical key blacklists the same old public key can still submit a **new pending pairing request**, which has no operational authority until new explicit owner-MCP approval and matching signed device proof.

**Security gate (owner revision 2026-10-18):** static Portal Bearer authenticates **credential possession, not a human**, and MCP approval is now the authorization trust boundary. This deliberately removes the old independent local-terminal factor: an authorized/compromised MCP client or prompt-injected model may approve a malicious pending key. The user explicitly accepted this single-user trade-off, but it must be disclosed and tested; code theft **alone** cannot approve without MCP access or establish signed WSS without the matching private key. Require explicit approval action, bounded pending TTL/rate limits, one-use key-bound consumption and signed Agent claim; never describe model-only authorization as impossible or equal to past two-code security.

## Device control and failure model

- Only authenticated MCP can request curated operations; only an approved, currently authorized Agent socket receives them. Agent independently validates operations and its OS permissions. Public bootstrap never executes tools.
- One short-lived WSS message envelope: `{version,type,request_id,device_id,operation_id?,tool?,arguments?,result?}`. Validate size/tool/schema and bind device identity on both ends; responses must match the initiating request ID and connection epoch. No arbitrary target host/URL, generic proxy, or cloud file/command-output archive.
- Short/read calls and acknowledgement of long-running `start_process` use **bounded RPC deadlines**. Extended processes run only under the Agent's existing managed-session contract. Do not await a multi-minute Shell command inside a DO request/promise: it prevents Hibernation.
- A known disconnection immediately marks offline; a silent partition has a bounded detection delay (must be measured, not claimed instantaneous). Auto reconnects with backoff, no queued commands and **no resubmission of uncertain mutations**. Status can be reconciled with the same `device_id + operation_id` after reconnection.
- An ordinary network loss **does not stop** an Agent-owned running process. Explicit removal denies new work first, attempts stopping *owned* sessions via a narrow internal control when possible and then closes the connection; an offline/compromised device's process may continue.
- WSL2 may be stopped while its Windows host is online; only actual Linux Agent reachability counts as “online.” Automatic start across Windows host reboot/WSL2 shutdown must be tested and must not be asserted by design alone.

## Hibernation, persistent state and Free quota

- The **SQLite-backed owner DO** stores minimal `pending_pairing` (code verifier, public key, 10-minute expiry, status, attempts) and `device` (approved opaque ID, key, label, approval time, temporary/permanent type and optional fixed 24-hour expiry) records. Deny expired grants immediately in authorization; lazily remove expired/revoked device grants and associated session state, with no permanent history or extra D1/KV/R2.
- Use `ctx.acceptWebSocket()`, connection `serializeAttachment()`/`deserializeAttachment()` and `getWebSockets()`; attachments hold **nonsecret** `device_id`/epoch, but **SQLite** remains authoritative after DO eviction or code deployment.
- DO Hibernation requires *no scheduled `setInterval`/`setTimeout`*, no unbounded `waitUntil` or held-open outgoing I/O. Prefer protocol ping/pong or Cloudflare automatic WS responses; **frequent application-layer heartbeats on multiple devices can keep the one DO awake**. Read auto-response timestamps when requested and use measured offline detection, not a busy poller.
- Verified official Workers Free SQLite-DO limits: **100,000 DO request-billing units/day**, **13,000 GB-s/day**, **5 million rows read/day**, **100,000 rows written/day**, **5 GB stored total**. WebSocket application messages bill 20:1 for DO requests; Workers requests are an additional quota. Duration for a continually non-hibernating DO allocated 128 MiB for 24h is ~**10,800 GB-s**. Free limits are shared with other account DOs, including IMA; crossing a limit causes errors, not automatic paid usage.

## Out of scope and deployment controls

No native Windows/macOS Shell, GUI/mouse/screen, general fleet dashboard, OAuth server, Cloudflare One/Mesh/Tunnel per v2 device, multi-tenant DO routing, per-device DO shard, D1/KV/R2, offline queue, forced termination of offline processes, auto-waking sleeping hosts, fake sandbox claims, new CI or changes to live secrets/configuration.

**This spec is design-only.** Do not create Cloudflare resources, provision secrets, install on the real production device, deploy v2 or cut over the working v1 without a separate explicit authorization.
