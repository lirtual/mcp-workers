# RCA GUI Tool Retirement — Grill With Docs (2026-10-31)

**Status:** Final design consensus accepted 2026-10-31 (Q1–Q7=A); **design only, not implemented or deployed**. This document does not authorize code changes, runtime implementation, PR merge, Agent release, production deployment, device upgrade, or on-device deletion. Earlier dated production facts remain historical evidence, not assertions of the latest live state.

**Context:** [Remote Control MCP](./CONTEXT.md), [ADR-0008 curated MCP surface](./adr/0008-curated-mcp-tool-surface.md), [Computer Use Spec #505 — not planned](https://github.com/lirtual/mcp-workers/issues/505), [independent Browser MCP #418](https://github.com/lirtual/mcp-workers/issues/418), and public Agent repository `lirtual/remote-control-agent`.

## Accepted decisions — first round

1. **Q1=A — Retire only the RCA-owned GUI capabilities.** Remove the ten Agent-owned `browser_*` tools and the RCA `computer_*` tool family, including their Worker dispatch, Agent executors, related packaging and active contracts. **Do not retire** the independently deployed Browser MCP #418 Worker, Chrome/Edge extension, distribution, Profile grants or its operational resources. Continue the RCA file, search, Shell, managed-session, device-pairing, signed-WSS and operation-receipt functions.
2. **Q2=A — Clean up RCA-only GUI state, preserving shared identity and evidence.** The intended retirement includes RCA's Agent-private automation Browser Profiles, desktop grant/stop settings and GUI-specific runtime components. Leave existing paired device identities/keys, authorization boundaries, shared local operation receipts and audit history intact. Device-local deletion is a separate destructive action requiring explicit authorization at execution time; do not interpret a design choice as permission to perform it. Do not delete the ordinary owner's Chrome/Edge Profiles or independent Browser MCP Profile state.

## Accepted decisions — second round

3. **Q3=A — Remove public names without a compatibility facade.** Delete all 13 RCA-specific `browser_*`/`computer_*` entries from MCP `tools/list` **and** from authenticated `tools/call`, Worker/DO allowlists and device dispatch. Any stale client request for a retired name must fail closed without reaching an old Agent. Clients refresh the tools list; no deprecated aliases, compatibility flag, stub endpoints or parallel server. Preserve the generic `get_operation_status` for existing operation IDs, including historical Browser/Computer receipts; a status lookup is not permission to replay a retired effect.

4. **Q4=A — Controlled two-stage official release.** First release the Remote Control MCP Worker using the existing GitHub Actions path, verify that 13 retired tool names are absent and unreachable (including direct stale-name calls) while file, Shell, sessions, pairing, signed WSS and receipts remain operational. Then publish the simplified public Agent via its existing signed/immutable release procedure and update already paired devices via the existing owner-initiated one-command installer, without a new device identity or separate update flow. Each production release and any device-local destructive cleanup still requires its own explicit authorization; a prior design approval alone is not deployment authority. The two product releases are separately verified; no all-or-nothing atomic cutover or new feature flag is required.

5. **Q5=A — One-time, narrowly scoped on-device cleanup after verified upgrade.** Inventory RCA-only GUI state, establish the exact owner-private paths (e.g., `browser-automation-profile-chrome`/`browser-automation-profile-msedge`, `desktop-grant.json`, `desktop-stop.json`) and ensure no owned GUI process or active effect uses them. On separate explicit destructive authorization, run a controlled **one-time** local cleanup, verify outcome, and avoid integrating permanent migration/cleanup machinery into every future Agent upgrade. Never recursively delete the shared Agent store, regular Chrome/Edge Profiles, Browser MCP extension/profile data, keys, receipts, logs, enrollment or managed-session state. An uncertain deletion result must be inspected before any retry.

## Verified implementation facts (not yet retirement completion)

- `apps/remote-control-mcp-worker/src/browser-tools.ts` registers ten RCA Browser tools; `src/worker.ts` also exposes `computer_status`, `computer_observe` and `computer_stop`. The shared Worker and Durable Object still route these tools.
- `lirtual/remote-control-agent` contains Browser Playwright gateway, optional Windows Browser bundling and private Profile, plus desktop grant, screenshot capture and related Windows CLI paths. Removing public tools alone does not remove those on-device components.
- The existing release archives are versioned historical artifacts; no decision proposes rewriting past immutable releases. Current running Agent versions must be assessed independently of changes in the Worker source.
- Existing `CONTEXT.md` documents the currently/historically active GUI behavior; it is not evidence of removal.
- Worker `src/worker.ts` exposes RCA GUI capabilities in `tools/list` and routes calls through `callPairedBrowser` and `callPairedDeviceRead/Operation`; `src/v2-pairing.ts` independently validates and dispatches Browser/Computer messages through the shared signed-WSS coordinator. The retirement must remove **both advertising and all actual admission paths**; merely hiding the manifest is insufficient.
- The Agent `src/v2-connection-lifecycle.ts` parses GUI read/mutation frames, `src/execution.ts` owns Browser effects/desktop Stop and shared receipts/managed sessions, and Windows `src/windows-v2.ts` has local `desktop-*` CLI commands, browser loading and owner-private GUI state. Remove the GUI-specific portions without dropping generic session protocol, revocation cleanup, upgrade freeze, or operation receipt semantics.
- The Agent's existing upgrade freeze rejects active Browser contexts, pending effects and non-quiescent managed sessions; it does not establish that a pre-cutover GUI effect has settled. Never auto-retry an unknown operation or force-kill an unverified unrelated browser process.
- Current Windows release/build scripts (`build-v2-release.mjs`, `build-windows-preview.mjs`) optionally bundle a pinned Playwright runtime and check Browser source contracts; update active build/verification/installer rules as part of retirement while preserving normal Agent release integrity guarantees.
- The independent Browser MCP #418 is a **different** Worker/Chrome-Edge extension and must not be deleted, detached or migrated as part of this design; its Profile authorization and production acceptance remain separate.

## Implementation and acceptance boundaries already implied by Q1–Q5

- Delete RCA GUI sources, routing parsers, local CLI, runtime package/dependencies, active docs, obsolete GUI-only tests and build rules where no other live consumer remains. Retain or update cross-cutting tests for signed WSS, revoked devices, receipt reconciliation, Shell/sessions, installer upgrades, Windows/Linux behavior, and unknown tool rejection. Do not delete or rewrite historical design discussions, Git commit history or immutable prior Releases; mark archived descriptions historical.
- Do not edit the independent Browser MCP context, package, distribution/download page, Browser MCP extension grants, Portal registration or Cloudflare resources. Verify its existing registration and versioned operation contract are unaffected, without repeating broad E2E tests when unchanged.
- The resulting Agent must continue to accept the established device identity and operation/receipt schema. Old Agent versions may remain temporarily installed after the Worker cutover; their GUI dispatch is unreachable from the upgraded Worker. A later Agent upgrade cannot be declared complete just because the Worker public tool list changed.
- Test both stale MCP tool names and old GUI request frames against the *new* Worker/Agent, ensuring fail-closed behavior without disconnecting an otherwise healthy signed device session or preventing generic `get_operation_status`. Reuse existing CI; no new deployment or compatibility system.

## Accepted decisions — third round

6. **Q6=A — Drain/verify GUI operations before cutover and cleanup.** Before **Worker** cutover, inventory all relevant paired devices and existing RCA-owned Browser sessions/GUI work. Confirm an authorized RCA-owned Browser session has closed (never kill an unrelated Chrome/Edge process or touch its ordinary Profile). Locally **stop** any active RCA Desktop Grant on affected devices while the old local CLI still exists; do not revoke/re-pair a device merely to stop GUI access. Freeze/suppress new GUI work during the release window using the existing operational controls; confirm no identified in-flight browser effect, screenshot, or cleanup is unresolved before declaring quiescence. If identity, session ownership, completion, or an effect's outcome cannot be established, **hold the affected stage**, preserve authoritative local operation receipts and reconcile by the *same* original operation ID when available. Never automatically replay an Unknown effect, erase its marker, or assume a transport disconnect means the effect was rolled back. GUI reads do not necessarily leave durable operation receipts; assess in-flight reads separately. Recheck quiescence immediately before the Agent upgrade and one-time local cleanup. Do not invent a new distributed drain protocol, control plane or standing feature flag to implement this gate.

7. **Q7=A — Fail closed and prefer GUI-disabled rollback.** Preserve the newly released Worker denial of all retired GUI names even when a later Agent build/install fails. Roll back only the Agent to an existing verified compatible release, following its ordinary identity/receipt-safe rollback checks; an old Agent's local GUI implementation does **not** mean the new Worker may dispatch it. If the new Worker harms essential file/Shell/session/pairing functions, first use the existing release mechanism to fix or re-release a minimal Worker that still denies GUI tools. Returning to a historical Worker that exposes GUI calls is a **distinct emergency exception** requiring explicit Owner authorization, acknowledgement of the renewed GUI capability, and an independent production gate; never automatically roll back both components. No permanent kill switch, alias layer, extra Worker or parallel migration service is justified.

## Final security, compatibility and complexity review

- **Security boundary:** Deny the 13 retired public names at **both** MCP admission and shared Durable Object dispatch; older Agent builds must not be indirectly reachable through an internal endpoint. Fail closed for stale MCP clients and forged old GUI operation/read names. The new Agent must also refuse removed GUI functions; preserve standard authenticated transport and device identity checks. Local stop and GUI process quiescence precede the Worker switch so removing remote `computer_stop` does not strand an enabled grant. No unauthorized background access to an ordinary browser Profile.
- **Protocol and receipts:** Retain signed WSS authentication, device list/rename/revoke, revocation of owned managed processes, operation-id deduplication, Unknown markers and generic `get_operation_status` without rewriting historical records. Remove only GUI-specific image-chunk reconstruction and optional Browser payload handling; ensure ordinary message framing/unknown-tool policy remains safe and non-GUI tools work. Distinguish *retired-tool rejection* from loss of device connectivity; don't accidentally disconnect a healthy Agent simply because a stale tool name was sent. The exact rejection behavior must be checked against existing WSS policy rather than presumed.
- **Build and dependency scope:** Remove no-longer-referenced Browser/Computer source, optional Playwright and screenshot packaging, desktop-specific CLI/storage ACL entries, GUI-only build/hash checks, GUI-specific tests and public documentation. Reassess actual imports before deleting shared browser-named helper code, generic host metadata, Windows installer or security functions. Existing immutable historical Releases are never rewritten, and retaining them is not a requirement to preserve executable compatibility with removed GUI tools.
- **Upgrade/cleanup:** Existing installer verification, immutable asset SHA-256, identity continuity, startup/task behavior and rollback protection remain gates. Verify the new executable has no GUI entry points/dependencies. A separate one-time cleanup requires confirmed ownership, exact paths, an idle process, an independent explicit destructive authorization, and post-cleanup evidence. Don't delete or change `v2-identity.pem`, its `.device-id`, shared receipts, historical Unknown entries, ordinary Chrome/Edge profiles or independent Browser MCP state.
- **Non-GUI acceptance:** Reuse existing CI and targeted integration checks for Worker `tools/list`/`tools/call`, DO dispatch, stale tool requests, Agent signed WSS, file read/write/search, command/session ownership, pairing, revocation, receipt lookup, Linux/WSL2 and Windows x64 installation/upgrade/rollback. Stage 1 and stage 2 independently require real paired-device verification appropriate to what changed. After removal, the independent Browser MCP #418 Worker/extension/download/Portal remain untouched; confirm registration and smoke functionality only insofar as release impact warrants. No new acceptance environment, service, database, CI workflow, compatibility facade or artificial stage labels.
- **Evidence and stop conditions:** Record exact Worker/Agent commits, successful CI, official release identifiers, tested platform/device versions, stale-call denial, preserved device UUIDs, non-GUI functional smoke tests, local GUI process/grant status and (if separately authorized) cleanup path results. An unverified step is **Not performed** or **Blocked**, never Pass. Source removal, CI success, deployed Worker, installed Agent and physical device cleanup are **different** completion states.

## Packaging/runtime simplification — pending Grill round (2026-10-31)

**Scope:** Follow-on clarification to the accepted GUI retirement; **Q1–Q7=A remain unchanged**. The following are verified implementation facts and **recommendations**, not yet confirmed Owner decisions. Do not treat this section as permission to alter release artifact layout or device installation.

### Facts verified against public Agent `main`

- The core Agent runs from JavaScript on **Node.js 24**. The current Windows x64 and Linux x64/ARM64 Release packaging compiles TypeScript to JavaScript and bundles a pinned Node executable, including paths such as `bin/node.exe` / `bin/node`; it **does not** compile the whole Agent application to a single native EXE/ELF.
- `scripts/build-v2-release.mjs` packages both `bin/node` and `.build/session-supervisor` on Linux; `src/sessions.ts` uses the supervisor for managed Shell process groups. `scripts/session-supervisor.c` provides Linux `pidfd`/subreaper-based group termination and owned descendant cleanup. This is independent of Browser/Computer tools.
- `scripts/build-windows-preview.mjs` packages both `bin/node.exe` and `bin/rca-background.exe` on Windows; `scripts/windows-background-launcher.c` launches Node without a console, attaches its process to a Windows Job Object and enforces job cleanup. `scripts/windows-user-task.ps1` validates the exact packaged paths and uses the launcher as the existing scheduled-task entry. This is also independent of Browser/Computer tools.
- Optional Playwright sources, `playwright-core`, screenshot scripts, Desktop Grant, and Browser packaging checks are GUI-only retirement targets. Existing self-contained distribution preserves a one-command owner-controlled install/upgrade without requiring the system to preinstall a matching Node version; the absence of any global Node dependency is an existing installer contract.
- Removing or changing either native helper or the packaged Node binary is therefore a **separate operational/protocol and upgrade compatibility choice**, not a necessary consequence of GUI retirement. No published runtime, integration test, or live device proves that a Node-only replacement for either helper would preserve all process-lifetime guarantees.

### Current decision frontier (Owner response required)

- **Q8 — Node delivery:** Recommended **A** = retain a version-pinned **bundled Node.js 24 runtime**, compiled JS payload and existing standalone one-command installers (no system-wide Node precondition, no Node SEA/native monolith). Alternative **B** = depend on a separately installed system Node.js and redesign installation/validation for that precondition.
- **Q9 — Windows native background helper:** Recommended **A** = retain `rca-background.exe` for background Task Scheduler + Job Object ownership, with no Browser/Computer code. Alternative **B** = remove/replace it with a Node-only start mechanism, accepting the need to redesign and revalidate service lifecycle/termination behavior.
- **Q10 — Linux native Shell helper:** Recommended **A** = retain `session-supervisor` for `pidfd`-based command process-group ownership/termination. Alternative **B** = replace it with a Node-only command supervisor, requiring new evidence for timeout, descendant termination, signal handling, revocation and Unknown receipt semantics.

### Consequential implementation guidance if Q8–Q10=A

Keep existing versioned archive paths, `bundle.json`/manifest integrity checks, verified official release pins, task/systemd startup and rollback semantics. Remove only GUI-specific sources, optional runtime libraries and build verification rules; don't rename the release profile or introduce a second package/update format merely for this retirement. Reuse existing Linux native and Windows CI; preserve real paired-device identity and check managed-session process behavior during staged rollout. No permanent compatibility layer, new release process, global Node prerequisite or new cross-platform executable framework.
