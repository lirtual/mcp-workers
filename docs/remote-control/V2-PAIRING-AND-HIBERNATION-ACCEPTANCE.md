# Remote Control MCP v2 — Pairing security and Hibernation acceptance plan

Status: **engineering candidate / not a finalized protocol or completed verification**. Date: 2026-10-15.
Authority: [ADR-0018](./adr/0018-v2-websocket-do-transport-and-portal-pairing.md) (accepted architecture, Q14=A/Q15=A/Q16=A). This note distinguishes required outcomes from proposed implementation defaults, all of which still need explicit grilling acceptance.

## Accepted round-seven decisions — 2026-10-15

- **Q17=A:** Portal Bearer-authenticated **lookup/review** followed by a **distinct, explicit approval** for the same immutable pending Agent/public-key fingerprint. The real client confirmation UX must be tested: static Bearer possession and an autonomous LLM tool invocation are not proof of human presence.
- **Q18=A:** exactly **10 cryptographically random Base32 symbols** (50 bits entropy), **10-minute** lifetime, **single-use** atomic redemption, strict bounded attempts and no code logging.
- **Q19=A:** each installation generates an independent **private/public keypair** locally; private key never leaves Agent. Use nonce-based, fresh challenge-response proof of key possession on connection and a durable revocation check before every dispatch.
- **Q20=A:** **five simulated devices continuously connected for 72 hours** in nonproduction; record DO hibernation/wake, DO requests and GB-s, SQLite rows/storage, Workers quota, mixed activity and failure recovery including the account's other DO consumers.
- These requirements and the lean end-to-end contracts now live in [ADR-0019](./adr/0019-pairing-code-device-keys-and-72-hour-gate.md) and [V2 Spec](./V2-MULTI-DEVICE-SPEC.md). **No hosted verification has been performed yet**.
- **Hibernateable heartbeat warning:** use `setWebSocketAutoResponse()` and `getWebSocketAutoResponseTimestamp()` as candidates instead of frequent per-device application events; otherwise staggered heartbeats can prevent an owner-scoped DO from becoming idle. Platform docs: https://developers.cloudflare.com/durable-objects/api/state/.

## 1. Trust boundaries and security model

| Principal or component | Has or may receive | MUST NOT receive |
| --- | --- | --- |
| ChatGPT / MCP Portal client | Remote Control MCP Bearer, approval tools | Device long-lived secret, Cloudflare admin key |
| Public v2 Agent bootstrap endpoint | Only bounded, unauthenticated registration inputs until approved | Portal Bearer or any ability to dispatch device file/Shell tools |
| Durable Object (owner coordinator) | Hashed/token-verified registration, device IDs, pairing and revoke state, socket attachments | Raw long-lived secrets in logs, unrelated Cloudflare account API tokens |
| Installed Linux/WSL2 Agent | Its own device-specific credential or private key and short-lived local pairing code | MCP Portal Bearer, Cloudflare admin key, other devices' credentials |
| Existing production v1 | Current VPC/Tunnel, independent existing device token | Automatic mutation or migration from unapproved v2 experiment |

A `MCP_ACCESS_TOKEN` check is **bearer possession**, not a verifiable human-in-the-loop attestation. An LLM may independently invoke tools. Q15 requires the owner explicitly communicate consent for this particular device; acceptance must verify actual client behavior rather than assert the ChatGPT permission dialog reliably implements owner approval. Pairing must be safe against a leaked code, copied chat history or untrusted Agent-supplied name.

## 2. Candidate pairing state machine (subject to the next grilling decisions)

1. **Local install / agent initiation:** generate a new per-installation identity keypair and a cryptographically random **short-lived** one-time code; render code in Agent's local terminal. No shared secret or Portal token in the installation command. Linux account-scoped storage and `0600`-equivalent file protection.
2. **Bootstrap pending:** Agent initiates outbound TLS/WSS enrollment to narrowly bounded unauthenticated Agent-only endpoint, proves possession of local key, registers one pending challenge with expiry and limited attempt budget. Return *no remote command capability*. Pending state and pairing/credential digests are durable; never log code, private key, secrets or raw command payloads. Unauthenticated user-controlled identifiers must not choose a DO owner/account.
3. **Owner lookup / confirmation:** through the **existing Portal Bearer-authenticated MCP** tool, the owner supplies the locally displayed code, sees sanitized pending device label and a short fingerprint/nonce, then explicitly confirms this pairing. Owner approval may require two separable steps if one call could be silently generated by a model. An approval call with `confirm: true` alone is **not sufficient evidence of a human**. If an independently verified human proof is required, this design must be revisited.
4. **Atomic activation:** match pending code to the exact device key/challenge, reject expiry, duplicate/replayed approvals and concurrent claim races in one atomic durable state transition. Issue/store one per-device credential or verified public-key binding, associate an opaque server-issued stable `device_id`, invalidate code immediately; Agent auto-persists its own credential.
5. **Operational connection:** validate the bound identity at WebSocket upgrade, associate authenticated connection metadata using Hibernation attachments, and check current durable authorization again before dispatching *each* command. Duplicate connections must have a deterministic replacement/reject policy. Only approved device IDs are visible through `list_devices`.
6. **Revoke / reinstall:** persist a deny/tombstone, reject upgrades/dispatches, request best-effort stop of reachable Agent-owned managed sessions, close any attached WebSockets. Reinstall uses new identity/code and re-pairing; old identity cannot silently regain authorization. The owner must receive an accurate result for process termination attempts. No Cloudflare One network registration exists in this transport.

**Accepted Q18/Q19 protocol boundary:** expiry is **10 minutes**, code is **10 random Base32 characters (50 entropy bits)**, approval is one-use, and Agent has a device-generated **asymmetric keypair** with signed challenge proof. Use cryptographic randomness, a server-side verifier, rate limits and bound approvals atomically. **Still implementation details:** exact alphabet normalization, attempt budgets, signature algorithm/wire encoding, key storage/rotation and human-review UI verification. Never use a guessable six-digit code as a substitute.

## 3. Protocol and hibernation invariants

- One SQLite-backed DO scoped to the individual owner for the small fleet, initially; device registry, tombstones and active pairing records use DO storage. Do not depend on mutable JS fields after Hibernation, isolate restart or migration.
- `ctx.acceptWebSocket(serverSocket)` plus `webSocketMessage()`, `webSocketClose()` and socket attachments (`serializeAttachment` / `deserializeAttachment`) are required; no `ws.accept()` or permanent `setInterval`/unresolved `waitUntil` keeping DO awake. Lifecycle tests must show that sockets survive object hibernation and authorization is revalidated on reawakening.
- RPC/request envelopes must bind authenticated `device_id`, one per-call correlation identifier and, for mutations, stable `operation_id`. Preserve native Agent `operation_id` semantics, digest matching, receipts and session ownership. Do not infer idempotence from a message response ID alone.
- On known offline status, MCP rejects new work immediately; absence of a clean close needs a bounded stale/offline detection policy (undecided). On reconnect, **never drain an offline queue**, replay pending mutating commands or silently route to a different device.
- A lost response means `timeout_unknown` with recoverable `device_id` + `operation_id`, not safe-to-retry. RPC must have a bounded deadline; avoid unbounded handlers holding DO in non-hibernating state.
- Use bounded, authenticated messaging, body size, concurrency/backpressure and cancellation. Files and command output must obey existing paging/size limits. Large files or streaming transfers need independent design if required later.
- Deleting a Cloudflare One registration is **not** a v2 requirement because no Cloudflare One enrollment is granted. A revoked app key cannot be replaced by bootstrapping another identity without **new explicit owner approval**.

## 4. Acceptance matrix: required tests (none executed yet)

| Gate | Test scenario | Required pass criterion |
| --- | --- | --- |
| P1 / owner consent | no Portal Bearer, wrong Bearer, LLM-only autonomous approval attempt, omitted confirmation | No device gains command access; explicit owner intent only via proven client flow |
| P2 / code abuse | wrong, expired, brute force, replayed, duplicated, intercepted code; same code claimed by different device keys | Reject/fail closed; bounded requests; no capability escalation or credential exposure |
| P3 / identity | client-chosen hostname/IP, wrong device ID, stolen or revoked key, duplicate WS, owner scope mismatch | Cannot impersonate/route to different device; revoke blocks connect and dispatch |
| P4 / lifecycle | Linux install/restart, WSL2 host reboot/shutdown and restart, home vs office/cloud networks | Outbound WSS works; offline reflected without stale commands; reconnect restores identity safely |
| P5 / receipts | network cut after start or write, duplicate `operation_id`, slow command, Agent crash | No blind replay; authoritative receipt reconciles if present, otherwise `timeout_unknown` |
| P6 / revoke | revoke one online device and one offline device, request process stop, retry reconnect using old key | New commands always refused; online owned session stop best effort with actual outcome; other devices unaffected |
| P7 / Hibernation | at least 5 idle WS Agents, **72h required**, mix idle and active RPC, Worker/DO restart/wake | Objects demonstrably hibernate, sockets/wake state restored, device revocation persists across wake |
| P8 / Free quota | DO requests, billable GB-s, SQLite rows read/write/storage, Worker calls, existing IMA DO shared account usage | All below Free limits with margin in both idle and realistic burst tests; no hidden perpetual duration |
| P9 / rollback | v1 remains production-valid during disposable v2 validation; v2 opt-in and tool metadata | No v1 regressions or unauthorised deployment; explicit safe cutover and rollback proven |

The words “immediately offline” mean immediate once a transport disconnect is **known**. Detecting a silent network partition requires a separately agreed bounded timeout and may not be literally instantaneous.

## 5. Official Cloudflare platform limits (checked 2026-10-15)

| Free-plan dimension | Limit |
| --- | --- |
| Durable Object request billing | 100,000/day, includes RPC and WS message equivalents |
| Durable Object duration | 13,000 GB-s/day, shared among objects in the account |
| SQLite rows read / written | 5,000,000 / 100,000 per day |
| SQLite stored | 5 GB total per account |
| Durable Object storage backend | SQLite only on Workers Free |
| Incoming DO WS application messages | 20 incoming messages billed as 1 DO compute request |
| Workers Free front-end requests | separate Workers requests quota; verify current account rules independently |

Cloudflare Hibernation is recommended and must be used for persistent idle device connections. Standard `ws.accept()` keeps a DO in memory and duration-billed as long as the socket is connected. An always nonhibernating object allocated 128 MiB for 24h uses ~10,800 GB-s of the 13,000 GB-s/day DO Free allowance; 5 idle devices must not hold the DO awake continually. No outgoing WS messages or protocol ping billing for DO compute requests; application-level messages still count. **This table represents published allowances, not measured account usage**, and limits are shared with existing DO consumers such as IMA.

## 6. Remaining frontier for grilling (no implementation approval yet)

- Q17 was settled **A**: Portal-authenticated two-step review and explicit approval; **verify on the real client** that human review is not bypassed by autonomous tool calls. A separate confirmation surface is only a fallback if this gate fails.
- Q18 was settled **A**: 10 random Base32 chars, 10-minute expiry, one use; finalize rate limits and pending-record cap as server-side constants.
- Q19 was settled **A**: per-device asymmetric key proof; finalize algorithm, challenge transcript and safe key rotation/storage.
- Q20 was settled **A**: five simulated Agents for continuous 72-hour nonproduction soak; define measurable failure thresholds and report shared account quota headroom.
- Q21: Device-scoped active connection replacement policy, offline detection bound, and how to surface lifecycle outcomes in tool responses.
