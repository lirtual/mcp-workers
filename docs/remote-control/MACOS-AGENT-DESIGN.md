# RCA — Native macOS Agent support (Grill With Docs)

> **Status:** Design in progress — accepted first-round **Q1–Q4=A** and second-round **Q5=A, Q6=A, Q7=B, Q8=A, Q9=A** on 2026-11-01. Third-round installation/upgrade, macOS permissions and live acceptance decisions remain **open**.
> **Scope:** Existing Remote Control MCP in `lirtual/mcp-workers` and the existing Node.js Agent in `lirtual/remote-control-agent`. This document records **design decisions only**. It authorizes no code implementation, PR merge, CI/Release publication, production Worker deployment, local installation, pairing, privileged operation, or device-data deletion.
> **Active design context:** [CONTEXT.md](./CONTEXT.md); existing cross-platform and distribution decisions [ADR-0015](./adr/0015-v2-pairing-and-identity.md), [ADR-0016](./adr/0016-agent-local-receipts-and-bounded-commands.md), [ADR-0018](./adr/0018-v2-temporary-agent-pairing-lifecycle.md), [ADR-0019](./adr/0019-standalone-linux-agent-distribution.md), [ADR-0020](./adr/0020-public-agent-repository.md), [ADR-0021](./adr/0021-retire-rca-owned-gui-tools.md). Historical #505 macOS Computer Use is **cancelled** and is not the basis for this design.

## Problem and current implementation boundary

RCA currently distributes verified, version-pinned, bundled-Node.js Agent archives for **Linux glibc x64/ARM64** (including WSL2) and **Windows x64**. It has no approved native macOS installer, managed-process supervisor, lifetime manager, CI Release target, or real macOS acceptance. The currently delivered GUI retirement in Spec #628 removed RCA-owned Browser/Computer execution tools; a new platform must not reintroduce them.

Source-level reasons a Linux archive cannot simply be relabelled as macOS include the Linux-only `v2-main.ts` platform guard, Linux ELF/glibc and kernel/pidfd checks in build and bootstrap scripts, Linux-specific `.build/session-supervisor`, systemd-only permanent-service management, and a current Release workflow requiring exactly three pre-existing targets. The common TypeScript/Node file, search, transport, pairing and receipt code is the starting point, **not** proof of tested macOS compatibility. Darwin ARM64 and Darwin x64 have separate binary and host-validation requirements; official Node 24 support alone does not validate the RCA package or native helper.

## Accepted decisions — round 1 (Q1–Q4=A)

1. **Q1=A — Supported personal-Mac host matrix.** Target **macOS 15 or newer**, both native **Apple Silicon ARM64** and **Intel x64**. Ship architecture-correct native artifacts, not a Linux artifact, Rosetta-only workaround, source checkout, or host-installed runtime prerequisite. A platform/CPU combination is advertised as supported only after a genuine native build and real-host acceptance. Node 24's upstream availability is not an RCA acceptance certificate; macOS x64 upstream support may require more targeted verification than ARM64.
2. **Q2=A — Full existing RCA *core* capability parity.** Target current approved file read/write/edit, filesystem search, bounded Shell, owned Managed Sessions (including explicit stop, bounded output and timeouts), owner-approved device pairing, device lifecycle, signed WSS and local Operation Receipts with Unknown/no-blind-replay semantics. Preserve each tool's existing authorization and OS-user execution boundary; neither a working directory nor an installation path is a security sandbox. **Do not** revive RCA `browser_*`, `computer_*`, GUI capture/input, or the cancelled Computer Use #505. The separate Browser MCP #418 is out of scope.
3. **Q3=A — Both owner-selected installation modes.** A **permanent personal device** uses a non-root, per-user **LaunchAgent** rather than system-wide LaunchDaemon; a **temporary device** runs in the foreground with its existing fixed, nonrenewable **24-hour cloud grant**, without a background service. Keep the existing one-code, explicit authenticated owner approval, identity/key continuity, public installer/upgrade intent, and truthful separation of local service state from remote online state. The detailed login/logout/sleep behavior and secure local upgrade implementation are subject to further review; do not promise always-on operation.
4. **Q4=A — Personal Macs only in this scope.** Do **not** add GitHub-hosted macOS Runner/Session enrollment, OIDC bootstrap, Workflow MCP SessionAuthorization changes, or new temporary CI-device grant policy. Existing Windows/Ubuntu GitHub Session behavior remains unchanged. This restriction does not preclude ordinary local temporary mode on a personally owned Mac.

## Invariants carried forward

- Reuse **one existing RCA Worker/DO, Ed25519 paired-device authorization, signed WSS, local receipt database and immutable public Agent GitHub Release channel**; no new Worker, database, credentials authority, background updater, second distribution service, language rewrite, or acceptance environment.
- Retain **self-contained, version-pinned Node.js 24 plus compiled Agent JavaScript**; no requirement to install Node, npm/pnpm, compiler, Xcode or project sources on the **target Mac**. Build-machine requirements are separate.
- All local install, upgrade and uninstall actions are explicit and owner-scoped. Preserve private device key, device ID, prior receipts and unresolved operation markers on safe upgrades/rollbacks; never automatically re-pair or extend a temporary grant. Local uninstall and cloud revoke are distinct.
- macOS Shell executes with **the actual authorized macOS user's privileges**. No automatic elevation, Full Disk Access grant, TCC bypass, custom path sandbox, GUI-permission request, or shared account installation. If the OS denies access, report the denial. Protect identity/receipts from other users and avoid secrets in logs or artifacts.
- Preserve existing Linux/Windows release and install contracts. Any macOS rollout needs independently evidenced platform-native CI/build, immutable asset integrity, real Mac pairing/WSS/file/Shell/Session/receipt/upgrade-rollback checks, and separate release/production authorization. CI, Release, Worker pin, local installation and real-device online validation are separate gates.

## Accepted decisions — round 2 (Q5=A, Q6=A, Q7=B, Q8=A, Q9=A)

5. **Q5=A — Minimal native Darwin Managed Session Supervisor.** Add a narrowly scoped, locally bundled macOS **Mach-O native process helper** for RCA-owned development command lifecycle; reuse current Node.js `ManagedSessions` boundaries, stable session identity, bounded output, deadlines, stop, revocation, upgrade freeze and existing Operation Receipt/Unknown semantics. Linux `pidfd` and `PR_SET_CHILD_SUBREAPER` are **not** macOS facilities and must not be called there. Design the macOS helper around verifiable child/process-group ownership and a control channel with safe parent-death cleanup; refuse unsafe signaling rather than `kill` by an unverified numeric PID/PGID. A process that deliberately daemonizes/escapes the managed group or an unreconciled stop remains a documented limit, **not** a claimed proof that every descendant was killed. The concrete mechanism/ownership proofs and native fault-injection acceptance remain to be worked out without adding a privileged daemon or fleet-level process manager. The Mac runtime must not accidentally select the Linux supervisor for `process.platform === "darwin"`.
6. **Q6=A — Login-scoped per-user LaunchAgent.** Permanent mode is a normal non-root **LaunchAgent** owned by the enrolling macOS login, not a root LaunchDaemon or unattended login substitute. It starts/restarts in that user's supported session according to OS lifecycle, preserves identity and reconnects when available. After logout, system shutdown or sleep, the service is **not guaranteed online**; resume/login should lead to signed WSS reconnection when the OS permits, but local launch state is not proof of remote reachability. Do not add keep-awake hacks, background privilege escalation, automated login, systemwide persistence or promises of access while logged out. Temporary mode remains foreground only.
7. **Q7=B — First official macOS releases need not have Developer ID signing/notarization.** Continue the **reviewed immutable GitHub Release + exact pinned tag/commit + architecture-specific asset + SHA-256 and strict unpack verification** distribution trust boundary; do **not** claim that SHA-256 constitutes Apple publisher verification, signing, notarization, malware scanning, or Gatekeeper clearance. Apple may block unsigned/unnotarized binaries, including the bundled Node executable and native Supervisor; **there is no guarantee that a one-liner automatically succeeds on a clean macOS 15+ host**. Never automatically clear quarantine, run recursive `xattr -dr com.apple.quarantine`, disable Gatekeeper (`spctl --master-disable`), or evade organizational policy. Only present transparent, narrowly scoped Apple-supported manual user approval **if** real-host testing demonstrates it can safely unblock the verified asset; otherwise mark install **Blocked**, or reconsider the signing decision rather than invent bypasses. Public instructions must explain this trade-off and lower assurance. Evidence: [Apple's Gatekeeper and unsigned-app guidance](https://support.apple.com/en-us/102445) and [macOS Sequoia manual confirmation requirements](https://developer.apple.com/news/?id=saqachfa). A later decision can require proper signing/notarization without altering the device protocol.
8. **Q8=A — Separate macOS one-command installer using the same distribution architecture.** Add planned **`GET /install-macos.sh`** on the **existing approved RCA Worker** and a macOS installation-page tab; keep Linux `/install.sh` and Windows `/install.ps1` behavior unchanged. The new public bootstrap is an explicitly reviewed, owner-interactive command; it must select **`darwin-arm64`** or **`darwin-x64`** correctly and download only the reviewed **immutable public Agent GitHub Release** asset for that exact host. Reuse upstream build/module/code/manifest logic where it is safe, and maintain Linux/Windows archives unchanged. Do not add a Worker, storage bucket, third-party release host, privileged package manager, arbitrary `latest` downloader, or platform autodetection that silently falls back to a Linux archive. A new public route needs its own source/Worker release authorization when implementation is eventually approved; this design is not a deployment.
9. **Q9=A — Stable POSIX Shell default.** On macOS use **`/bin/sh -c`** as the documented noninteractive default Shell, with **`/bin/zsh` only on explicit safe local configuration** and matching process-supervisor validation. Current `defaultAgentShellPath()` uses `process.env.SHELL ?? "/bin/sh"` for non-Windows hosts, so implementation must make the Darwin default independent from incidental login/LaunchAgent `SHELL` values; Linux and Windows contracts remain unchanged. Shell execution runs under the authorized macOS user's OS permissions, not as a new sandbox or elevated process. If the selected Shell does not exist or fails validation, reject the command before admitting execution when possible.

## Cross-cutting consequences and implementation review points

- **Darwin is not Linux.** Platform gate in `src/v2-main.ts`, Linux-only ELF/glibc inspection in `scripts/bootstrap-v2.py`, Linux-only immutable release verifier and package builder, `systemd` lifecycle helpers, and `sessions.ts` supervisor dispatch all require explicit Darwin paths or conservative reuse of genuine platform-neutral code. Preserve Linux and Windows non-GUI helpers.
- **Q7=B is an accepted risk, not a pass for launch readiness.** The first unsigned build may be blocked by Gatekeeper or macOS privacy controls. Document and validate actual first-run behavior on **both** processor architectures and in LaunchAgent mode. A device is not approved/online merely because the bootstrap reported success. No blanket OS security disable or silent user-approval simulation. If the owner needs fully unattended clean-host onboarding, a future round must revisit signing/notarization.
- **Q5=A does not assert a Linux-identical kernel guarantee.** Native helper should make owned-process failures **fail-closed**, and must not kill an unrelated process based on a stale/reused process ID; report explicit uncertain completion. Test process escape, supervisor/Agent crash, stop, timeout, descendant cleanup, WSS disconnect and revocation with OS-level evidence before claiming parity.
- **Signing and file permissions are separate.** No Apple signing requirement does **not** permit storing device private keys in a public-readable home directory or bypassing macOS file privacy/TCC. Preserve non-root owner-private 0700/0600-style protection, file ownership/no-symlink constraints, sensitive log redaction and protected receipt state.

## Third-round decision frontier — **OPEN, NOT ACCEPTED**

- **Q10 — Transactional local upgrade and repair:** preserve reviewed immutable Release pin, owner interactive confirmation, freeze active/Unknown operations, side-by-side versions, verified launch/rollback and old device identity; choose fail-closed strict state handling vs a reduced installation-only initial release.
- **Q11 — Unnotarized first-run behavior:** keep OS-level manual authorization as an explicitly guided, local owner action if required (and block if unavailable), or require no Gatekeeper prompts at the cost of revisiting Q7=B.
- **Q12 — macOS protected files and user permissions:** do not request Full Disk Access, TCC exemptions or root privileges automatically; decide on explicit owner-managed consent vs anything broader.
- **Q13 — Real-device acceptance matrix:** determine whether each native ARM64 and Intel x64 target needs a real personal Mac for installer/LaunchAgent/stop/reconnect/rollback/permissions E2E before that target is advertised, or allow reduced claims with explicit unsupported status.
- **Q14 — Process safety limits and unknown effects:** choose strict fail-closed behavior on unverifiable descendants/groups/restart rather than taking the risk of weaker cleanup or signaling unidentified PIDs.
- **Q15 — Cross-platform CI and release gate:** choose minimal extension of existing CI + immutable Release verification for two macOS targets, with independent Worker pin and real-host validation gates, versus a separate macOS release pipeline.

**The decisions Q10–Q15 are not approved yet.** The design session must update this same document as choices settle. An ADR is warranted only if a difficult-to-reverse choice genuinely needs explanation beyond this living design; avoid duplicating this spec prematurely.
