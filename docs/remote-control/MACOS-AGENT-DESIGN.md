# RCA — Native macOS Agent support (Grill With Docs)

> **Status:** **Design consensus reached (2026-11-01)** — Q1–Q6=A, **Q7=B**, Q8–Q15=A. Security, compatibility, minimum-complexity and release-boundary review complete at design level; **no macOS implementation or real-device validation has occurred**. [ADR-0022](./adr/0022-native-macos-owned-session-boundary.md) records the long-lived native process-safety choice. This design does not authorize implementation or any production action.
> **Scope:** Existing Remote Control MCP in `lirtual/mcp-workers` and the existing Node.js Agent in `lirtual/remote-control-agent`. This document records **design decisions only**. It authorizes no code implementation, PR merge, CI/Release publication, production Worker deployment, local installation, pairing, privileged operation, or device-data deletion.
> **Active design context:** [CONTEXT.md](./CONTEXT.md); existing cross-platform and distribution decisions [ADR-0015](./adr/0015-v2-pairing-and-identity.md), [ADR-0016](./adr/0016-agent-local-receipts-and-bounded-commands.md), [ADR-0018](./adr/0018-v2-temporary-agent-pairing-lifecycle.md), [ADR-0019](./adr/0019-standalone-linux-agent-distribution.md), [ADR-0020](./adr/0020-public-agent-repository.md), [ADR-0021](./adr/0021-retire-rca-owned-gui-tools.md). Historical #505 macOS Computer Use is **cancelled** and is not the basis for this design.

## Problem and current implementation boundary

RCA currently distributes verified, version-pinned, bundled-Node.js Agent archives for **Linux glibc x64/ARM64** (including WSL2) and **Windows x64**. It has no approved native macOS installer, managed-process supervisor, lifetime manager, CI Release target, or real macOS acceptance. The currently delivered GUI retirement in Spec #628 removed RCA-owned Browser/Computer execution tools; a new platform must not reintroduce them.

Source-level reasons a Linux archive cannot simply be relabelled as macOS include the Linux-only `v2-main.ts` platform guard, Linux ELF/glibc and kernel/pidfd checks in build and bootstrap scripts, Linux-specific `.build/session-supervisor`, systemd-only permanent-service management, and a current Release workflow requiring exactly three pre-existing targets. The common TypeScript/Node file, search, transport, pairing and receipt code is the starting point, **not** proof of tested macOS compatibility. Darwin ARM64 and Darwin x64 have separate binary and host-validation requirements; official Node 24 support alone does not validate the RCA package or native helper.

## Accepted decisions — round 1 (Q1–Q4=A)

1. **Q1=A — Supported personal-Mac host matrix.** Target **macOS 15 or newer**, both native **Apple Silicon ARM64** and **Intel x64**. Ship architecture-correct native artifacts, not a Linux artifact, Rosetta-only workaround, source checkout, or host-installed runtime prerequisite. A platform/CPU combination is advertised as supported only after a genuine native build and real-host acceptance. The pinned **Node.js v24.21.0** upstream support matrix lists **both macOS ARM64 and macOS x64 as Tier 1** ([version-tagged source](https://github.com/nodejs/node/blob/v24.21.0/BUILDING.md)); this does not replace independent RCA real-host acceptance. Support tiers can differ in other Node majors, so do not infer the pinned version's status from the upstream `main` branch.
2. **Q2=A — Full existing RCA *core* capability parity.** Target current approved file read/write/edit, filesystem search, bounded Shell, owned Managed Sessions (including explicit stop, bounded output and timeouts), owner-approved device pairing, device lifecycle, signed WSS and local Operation Receipts with Unknown/no-blind-replay semantics. Preserve each tool's existing authorization and OS-user execution boundary; neither a working directory nor an installation path is a security sandbox. **Do not** revive RCA `browser_*`, `computer_*`, GUI capture/input, or the cancelled Computer Use #505. The separate Browser MCP #418 is out of scope.
3. **Q3=A — Both owner-selected installation modes.** A **permanent personal device** uses a non-root, per-user **LaunchAgent** rather than system-wide LaunchDaemon; a **temporary device** runs in the foreground with its existing fixed, nonrenewable **24-hour cloud grant**, without a background service. Keep the existing one-code, explicit authenticated owner approval, identity/key continuity, public installer/upgrade intent, and truthful separation of local service state from remote online state. The detailed login/logout/sleep behavior and secure local upgrade implementation are subject to further review; do not promise always-on operation.
4. **Q4=A — Personal Macs only in this scope.** Do **not** add GitHub-hosted macOS Runner/Session enrollment, OIDC bootstrap, Workflow MCP SessionAuthorization changes, or new temporary CI-device grant policy. Existing Windows/Ubuntu GitHub Session behavior remains unchanged. This restriction does not preclude ordinary local temporary mode on a personally owned Mac.

## Invariants carried forward

- Reuse **one existing RCA Worker/DO, Ed25519 paired-device authorization, signed WSS, local receipt database and immutable public Agent GitHub Release channel**; no new Worker, database, credentials authority, background updater, second distribution service, language rewrite, or acceptance environment.
- Retain **self-contained, version-pinned Node.js 24 plus compiled Agent JavaScript**; no requirement to install Node, npm/pnpm, compiler, Xcode or project sources on the **target Mac**. Build-machine requirements are separate.
- All local install, upgrade and uninstall actions are explicit and owner-scoped. Preserve private device key, device ID, prior receipts and unresolved operation markers on safe upgrades/rollbacks; never automatically re-pair or extend a temporary grant. Local uninstall and cloud revoke are distinct.
- macOS Shell executes with **the actual authorized macOS user's privileges**. No automatic elevation, Full Disk Access grant, TCC bypass, custom path sandbox, GUI-permission request, or shared account installation. If the OS denies access, report the denial. Protect identity/receipts from other users and avoid secrets in logs or artifacts.
- Preserve existing Linux/Windows release and install contracts. Any macOS rollout needs independently evidenced platform-native CI/build, immutable asset integrity, real Mac pairing/WSS/file/Shell/Session/receipt/upgrade-rollback checks, and separate release/production authorization. CI, Release, Worker pin, local installation and real-device online validation are separate gates.

## Accepted decisions — round 2 (Q5=A, Q6=A, Q7=B, Q8=A, Q9=A)

5. **Q5=A — Minimal native Darwin Managed Session Supervisor.** Add a narrowly scoped, locally bundled macOS **Mach-O native process helper** for RCA-owned development command lifecycle; reuse current Node.js `ManagedSessions` boundaries, stable session identity, bounded output, deadlines, stop, revocation, upgrade freeze and existing Operation Receipt/Unknown semantics. Linux `pidfd` and `PR_SET_CHILD_SUBREAPER` are **not** macOS facilities and must not be called there. Design the macOS helper around verifiable child/process-group ownership and a control channel with safe parent-death cleanup; refuse unsafe signaling rather than `kill` by an unverified numeric PID/PGID. A process that deliberately daemonizes/escapes the managed group or an unreconciled stop remains a documented limit, **not** a claimed proof that every descendant was killed. The concrete mechanism/ownership proofs and native fault-injection acceptance remain to be worked out without adding a privileged daemon or fleet-level process manager. The Mac runtime must not accidentally select the Linux supervisor for `process.platform === "darwin"`.
6. **Q6=A — Login-scoped per-user LaunchAgent.** Permanent mode is a normal non-root **LaunchAgent** owned by the enrolling macOS login, not a root LaunchDaemon or unattended login substitute. It starts/restarts in that user's supported session according to OS lifecycle, preserves identity and reconnects when available. After logout, system shutdown or sleep, the service is **not guaranteed online**; resume/login should lead to signed WSS reconnection when the OS permits, but local launch state is not proof of remote reachability. Do not add keep-awake hacks, background privilege escalation, automated login, systemwide persistence or promises of access while logged out. Temporary mode remains foreground only.
7. **Q7=B — First official macOS releases need not have Developer ID signing/notarization.** Continue the **reviewed immutable GitHub Release + exact pinned tag/commit + architecture-specific asset + SHA-256 and strict unpack verification** distribution trust boundary; do **not** claim that SHA-256 constitutes Apple publisher verification, signing, notarization, malware scanning, or Gatekeeper clearance. Apple may block unsigned/unnotarized binaries, including the bundled Node executable and native Supervisor; **there is no guarantee that a one-liner automatically succeeds on a clean macOS 15+ host**. Never automatically clear quarantine, run recursive `xattr -dr com.apple.quarantine`, disable Gatekeeper (`spctl --master-disable`), or evade organizational policy. Only present transparent, narrowly scoped Apple-supported manual user approval **if** real-host testing demonstrates it can safely unblock the verified asset; otherwise mark install **Blocked**, or reconsider the signing decision rather than invent bypasses. Public instructions must explain this trade-off and lower assurance. Evidence: [Apple's Gatekeeper and unsigned-app guidance](https://support.apple.com/en-us/102445) and [macOS Sequoia manual confirmation requirements](https://developer.apple.com/news/?id=saqachfa). A later decision can require proper signing/notarization without altering the device protocol.
8. **Q8=A — Separate macOS one-command installer using the same distribution architecture.** Add planned **`GET /install-macos.sh`** on the **existing approved RCA Worker** and a macOS installation-page tab; keep Linux `/install.sh` and Windows `/install.ps1` behavior unchanged. The new public bootstrap is an explicitly reviewed, owner-interactive command; it must select **`darwin-arm64`** or **`darwin-x64`** correctly and download only the reviewed **immutable public Agent GitHub Release** asset for that exact host. Reuse upstream build/module/code/manifest logic where it is safe, and maintain Linux/Windows archives unchanged. Do not add a Worker, storage bucket, third-party release host, privileged package manager, arbitrary `latest` downloader, or platform autodetection that silently falls back to a Linux archive. A new public route needs its own source/Worker release authorization when implementation is eventually approved; this design is not a deployment.
9. **Q9=A — Stable POSIX Shell default.** On macOS use **`/bin/sh -c`** as the documented noninteractive default Shell, with **`/bin/zsh` only on explicit safe local configuration** and matching process-supervisor validation. Current `defaultAgentShellPath()` uses `process.env.SHELL ?? "/bin/sh"` for non-Windows hosts, so implementation must make the Darwin default independent from incidental login/LaunchAgent `SHELL` values; Linux and Windows contracts remain unchanged. Shell execution runs under the authorized macOS user's OS permissions, not as a new sandbox or elevated process. If the selected Shell does not exist or fails validation, reject the command before admitting execution when possible.

## Cross-cutting consequences and implementation review points

- **Darwin is not Linux.** Platform gate in `src/v2-main.ts`, Linux-only ELF/glibc inspection in `scripts/bootstrap-v2.py`, Linux-only immutable release verifier and package builder, `systemd` lifecycle helpers, and `sessions.ts` supervisor dispatch all require explicit Darwin paths or conservative reuse of genuine platform-neutral code. Preserve Linux and Windows non-GUI helpers.
- **Q7=B is an accepted risk, not a pass for launch readiness.** The first unsigned build may be blocked by Gatekeeper or macOS privacy controls. Document and validate actual first-run behavior on **both** processor architectures and in LaunchAgent mode. A device is not approved/online merely because the bootstrap reported success. No blanket OS security disable or silent user-approval simulation. If the owner needs fully unattended clean-host onboarding, a future round must revisit signing/notarization.
- **Q5=A does not assert a Linux-identical kernel guarantee.** Native helper should make owned-process failures **fail-closed**, and must not kill an unrelated process based on a stale/reused process ID; report explicit uncertain completion. Test process escape, supervisor/Agent crash, stop, timeout, descendant cleanup, WSS disconnect and revocation with OS-level evidence before claiming parity.
- **Signing and file permissions are separate.** No Apple signing requirement does **not** permit storing device private keys in a public-readable home directory or bypassing macOS file privacy/TCC. Preserve non-root owner-private 0700/0600-style protection, file ownership/no-symlink constraints, sensitive log redaction and protected receipt state.

## Accepted decisions — round 3 (Q10–Q15=A)

10. **Q10=A — Transactional, owner-interactive installation and upgrade.** Use the same verified, version-pinned immutable Release channel and one reviewed macOS local installer for initial installation, safe repeat, staging and owner-confirmed upgrades; do not add an Agent-initiated upgrade tool or background updater. Check OS/CPU, local user/TTY, archive size and exact source/tag/asset identity, SHA-256, package member layout/permissions, Mach-O architecture and owner-private paths **before executing downloaded bytes**. Stage a new version **beside**, rather than over, the known-good version; hold the old package for a bounded rollback. Before a permanent-device switch, freeze new dispatch, prove no in-flight/owned commands or unreconciled *active* side effects, preserve all historical Unknown receipts and the existing key/device ID; refuse unsafe or uncertain upgrades. An already historical, durably retained Unknown receipt is **not by itself** grounds to delete history or falsely claim a fresh side effect. Respect intentionally stopped LaunchAgents; do not silently restart one. Change only RCA-owned plist/program pointers after validating current ownership/permissions, and verify activation, actual signed WSS identity, selected device availability and harmless remote operation. If activation fails, restore the old program/plist without re-keying or resetting receipts; if rollback or final effect cannot be confirmed, stop further writes, retain recovery evidence and report **Blocked/Unknown**, not success. An interrupted installer must inspect observed state before retrying. Remote approval and local installation remain distinct.
11. **Q11=A — Explicit, narrow, owner-controlled handling of unsigned first launch.** Because Q7=B does **not** require Developer ID signing/notarization for first macOS release, identify an actual Gatekeeper/launch block before offering documentation for a **manual** owner decision through **System Settings → Privacy & Security → Open Anyway**, where supported and after reviewing the exact verified artifact. Never automate the UI consent, loosen system-wide policy, remove quarantine recursively, change other software or hide malware warnings. Treat command-line executables and both the bundled Node binary and native Mach-O helper as separately subject to actual OS enforcement; do not assume that the app-oriented Open Anyway path is always offered for every CLI binary. If no supported manual path works, or a managed device blocks exceptions, installation stays **Blocked** on that target. Revisit a properly signed/notarized release in a separate design change if this proves incompatible with the required experience; do not pretend Q7=B is a guarantee of one-line unattended success. Sources: [Apple Gatekeeper release note](https://developer.apple.com/news/?id=saqachfa), [Apple support instructions](https://support.apple.com/en-us/102445).
12. **Q12=A — Ordinary user permissions, owner-controlled macOS privacy.** Run only as the enrolled non-root user; do not request Full Disk Access, Accessibility, Screen Recording, password/admin access, or additional TCC exemptions from the installer. Standard file/search/Shell operations remain confined to **actual OS-user permissions**, including macOS privacy policy; fail safely on denied paths, without calling them a work-directory sandbox. Restrict private keys, receipts, upgrade/rollback markers and LaunchAgent plist changes to validated owner-private locations and paths; reject unsafe symlinks, foreign ownership, unexpected file types and broadly writable metadata. A user may independently decide to authorize specific OS access through supported system controls, but the Agent may not change OS privacy settings or demand broad grants as a default. Local uninstall does not implicitly revoke the separate cloud grant or discard keys/receipts.
13. **Q13=A — Native, independent real Mac acceptance on both architectures.** **ARM64 and Intel x64** each require a genuinely native macOS 15+ Mac to independently pass the reviewed install, initial manual Gatekeeper decision (when encountered), permanent/temporary mode, explicit authenticated pairing, signed WSS/identity continuity, file/search and mutation, POSIX Shell, owned Session lifecycle and descendant/timeout/stop, receipt/Unknown and fail-closed paths, LaunchAgent boot/login/logoff/sleep/reconnect, one-command upgrade, interruption recovery/rollback, permission-denial, local uninstall vs cloud revoke, and stale/revoked device denial. Invariant: no disabled Gatekeeper or TCC bypass in acceptance. **Neither a CI artifact nor Rosetta execution stands in for native Intel x64 physical acceptance.** A missing device or blocked unsigned launch is **Not performed/Blocked** for that target; do not market or mark the architecture as supported. A passed architecture never certifies the other.
14. **Q14=A — Fail closed whenever process identity or completion is uncertain.** Darwin Supervisor may terminate **only** the verified process/group it created and still owns. Do not treat guessed/reused PIDs, PGIDs, global process listing or a stale status record as authorization to signal unrelated host processes. A bounded, explicitly owned process group and an authenticated local control channel are required before reporting an admitted managed command. If a process deliberately detaches/escapes the group, the Agent/OS kills the Supervisor at the wrong time, a safe signal target cannot be proved, or side effects have unknown completion, **do not** claim full descendant cleanup, retry the same effect, or change Unknown receipts to success. Return an explicit uncertainty/failure status and preserve markers. **There is no macOS pidfd/subreaper-equivalent guarantee**; implement an OS-specific minimal helper with real failure tests and do not add a privileged daemon, persistent process inventory, general-purpose kill service or fleet coordinator. If the required bounded stop/revocation/timeout guarantees cannot be demonstrated on a target, **hold that platform's support claim** rather than weaken Q2/Q5/Q14.
15. **Q15=A — Extend existing native CI and immutable Release process only.** Add two macOS native candidate targets and architecture-correct prebuilt Node.js 24 + Darwin Mach-O helper bundles **to the existing GitHub Actions pipeline and verified public Agent Release model**; no separate workflow, release host, Homebrew dependency, installer mirror, Worker, database, acceptance environment or new package-signing service. The current publish pin verifies **exactly three** Linux/Windows assets and hardcodes three filenames; the eventual implementation must update that same contract and pin to **five exact reviewed assets**, checksum evidence, native target/artifact linkage and safe manifest verification, without weakening existing three-platform gates. Native CI on macOS runners is useful build/runtime evidence, but cannot replace the real personal-Mac E2E requirement in Q13. New Worker `/install-macos.sh` and the installation page must be deployed separately **only after explicit production authorization**; real-agent Release, Worker pin, per-Mac installer and online verification have separate status, rollout and rollback evidence. Never use a draft design PR, a release-pin commit or a mere CI pass as an implicit production authorization.

## Final design — minimal implementation shape and boundaries

- **Unchanged:** existing Portal/MCP authentication, Worker and Durable Object, Ed25519 owner pairing and 24-hour grant, signed WSS, Agent Node.js 24 program, file/search core, local SQLite receipts, stable operation IDs, no blind replay, Linux systemd/pidfd, Windows Task/Job Object, retired GUI denial, independent Browser MCP and existing release authority.
- **New, platform-specific only:** Darwin runtime/entrypoint selection, least-privilege per-user LaunchAgent lifecycle, minimal Darwin native managed-process Supervisor (see [ADR-0022](./adr/0022-native-macos-owned-session-boundary.md)), platform-aware noninteractive `/bin/sh` default, Darwin artifact/manifest/verification and owner-interactive `/install-macos.sh` bootstrap, two native GitHub Actions candidate targets, existing formal Release extension, and the third macOS tab on the existing install page. Prefer reuse of existing tests and staging/rollback primitives. Do not create a second Agent architecture or cross-platform generic plugin framework.
- **No hidden compatibility concession:** Linux ELF/glibc/pidfd and systemd mechanisms cannot be executed on Darwin; macOS Mach-O, native OS/CPU checks and actual process policy must be verified. macOS filesystem case-sensitivity, APFS metadata/xattrs, symlinks, hardlinks and TCC can differ from validated Linux behavior. Keep **explicit rewrite and best-effort conflict semantics** as currently documented; do not claim universal atomic replacement, preservation of all metadata, or complete concurrent-write exclusion. Tests must cover these differences before claiming file-edit parity.
- **Security/operational disclosure:** unsigned release has materially weaker publisher authentication than Developer ID and can be blocked by Gatekeeper, especially after a new version. SHA-256 and immutable GitHub provenance protect the *reviewed asset match*, not the publisher's Apple identity or OS malware/security assessment. Owner-only Open Anyway may be a **manual exceptional path**, not an installer prerequisite the software tries to evade. In the **pinned Node.js v24.21.0 release**, both macOS x64 and ARM64 are **Tier 1** in the [version-specific support matrix](https://github.com/nodejs/node/blob/v24.21.0/BUILDING.md); the Node.js `main` branch can differ. Both still require independent first-party native RCA E2E before support is advertised.
- **Failure rules:** download/asset/host mismatch → stop **before execution**; foreign/unsafe Agent files or service properties → stop without clobbering; Gatekeeper or privacy block → honest manual decision or **Blocked**; owned group identity uncertainty → **Unknown**, never kill unrelated PID; active session or uncertain effect → no upgrade; failed switch → verified local rollback or **Blocked**, preserving keys/receipts; stale/disconnected WSS ≠ an approved/online device. Keep local uninstall separate from remote grant revocation.
- **Non-goals:** macOS GUI/Browser/Computer use, lock-screen desktop control, remote OS login, GitHub-hosted macOS Workflow Session/OIDC, full PTY emulator, system LaunchDaemon/root-level installer, Homebrew distribution, automatic updater, signing certificates or Apple developer credentials, separate Release/workflows and changes to the independent Browser MCP.

## Bootstrap trust boundary and first-install prerequisites (design clarification)

- **Do not require Python 3, a preinstalled Node runtime, Xcode/Command Line Tools, npm/pnpm, Homebrew, or a native compiler on a fresh supported Mac.** Use existing macOS-provided POSIX shell and standard OS utilities for the shortest initial bootstrap; once the pinned, reviewed package is staged, use its **bundled Node.js** and current Agent management primitives for interactive pairing, lifecycle and upgrade. Reuse common verified logic where safe; do not fork a second general-purpose installer framework.
- **Trust is staged, not retroactive.** The Worker-delivered `/install-macos.sh` executes **before** any GitHub Release asset digest check. Clearly describe its trusted HTTPS canonical Worker origin and reviewed script source/version, with no dynamic third-party script, untrusted redirects or credential/token in the installer. Then verify the exact immutable Release tag/source commit/asset SHA-256/size/architecture and archive members **before executing archive binaries**. Do not claim that the executable bootstrap itself is hash-verified by code that has not yet run, or that GitHub SHA-256 authenticates an Apple Developer ID.
- A public `curl | sh` example's exit status is **not** sufficient evidence of successful download because a shell may exit successfully after receiving no script. Require an explicit download-error check and real installation result, followed by owner-approved device pairing and signed-WSS online verification; do not weaken existing Linux/Windows install commands. Keep local prompts connected to a real terminal, never silently select permanent mode on no-TTY execution.
- Gatekeeper/manual authorization and TCC access must be validated for the **actual program identity that runs as the LaunchAgent**, not assumed from an interactive Terminal session's access. A newly upgraded embedded Node/native helper may present different Gatekeeper outcomes; preserve rollback and explicit Blocked reporting.
