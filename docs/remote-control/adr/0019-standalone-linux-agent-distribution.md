# ADR-0019 — Remote Control v2 standalone Linux/WSL2 CLI distribution

**Implementation checkpoint (2026-10-18; historical plan statements below do not define today's completion):** The relevant no-tombstone and single-code changes exist in the nonproduction stacked Draft #79, supported by real #71/#97 nonproduction acceptance and public Agent immutable TEST v0.1.8. Both native architecture CI checks have succeeded; *real externally paired native ARM64*, connected-device 24-hour expiry/Hibernation, genuine continuous #57 48-hour observation, and all formal merge/production authorization remain separate unfulfilled gates. There is no v1 production cutover.

**Status:** Grilling Q1–Q8 accepted; public immutable v0.1.8 Python-free bundled-Node TEST assets, existing Preview `/install.sh`, and real x64 one-code owner pairing have been delivered. Native ARM64 owner-device/48h release gates and formal production approval remain open. Updated 2026-10-18.

Related: [v2 multi-device Spec](../V2-MULTI-DEVICE-SPEC.md), [ADR-0015 — independent on-device pairing](./0015-v2-pairing-and-identity.md), [ADR-0017 — remove device authorization](./0017-v2-device-revocation-without-tombstones.md), [ADR-0018 — 24-hour temporary device grants](./0018-v2-temporary-agent-pairing-lifecycle.md).

## Context / observed current implementation

The existing Agent is a native Linux/WSL2 program. The unmerged v2 [Draft PR #58](https://github.com/lirtual/mcp-workers/pull/58) has a source-checkout installer `apps/remote-control-agent/scripts/install-v2.mjs`, which requires Node.js 24, `cc` and a C pidfd/session-supervisor helper built locally. Persistent service mode additionally requires a systemd user manager and points its unit at files in the source checkout. `--foreground` avoids creating a service, but still requires the checkout/toolchain. The public Agent repository now contains immutable v0.1.8 TEST native archives; the checkout-only #58 baseline above is historical. Merely providing a one-line wrapper around `git clone` and native compilation does not achieve the user goal.

## Accepted choices — first grilling round

1. **Q1=A: Linux-first device scope.** The first supported standalone installer targets **Linux x86_64 and ARM64**, including those architectures running inside **WSL2**. Native Windows and macOS agents are not within this rollout; WSL2 is a Linux execution environment, not a native Windows Agent. The distribution/CPU ABI, supported Linux libc and minimum OS version still require verification. Do not infer all Linux distributions or all ARM64 devices are compatible.
2. **Q2=A: GitHub Releases bundled portable runtime.** Publish versioned **prebuilt Agent distributions as GitHub Release assets**, containing the required **Node.js runtime**, Agent JavaScript and **precompiled native Shell Supervisor** for a supported OS/architecture. Installing must **not** require `git clone`, `pnpm`, TypeScript builds, locally installed Node.js, or local `cc`. The package uses the **existing Node Agent and execution engine**; do not introduce a Rust/Go rewrite or require a single self-extracting executable. Package topology, checksums/signatures, artifact provenance, how assets are produced and supported libc matrix are not yet decisions.
3. **Q3=A: interactive single-command onboarding.** A supported new host begins with **one terminal command** to obtain and launch the installer. The **local CLI guides the user to choose either a normal permanent enrollment or a temporary enrollment**, rather than selecting a hidden default. The CLI must complete or safely resume the owner-approved single-code MCP pairing (supersedes two-code UX on 2026-10-18). Whether the permanent Agent is started as a user service and temporary as foreground, and how to handle hosts without a user-systemd manager, remain explicit next-round decisions.
4. **Keep authorization independent from installation.** The new device generates a private Ed25519 identity and shows **one 10-character, 10-minute pending code**; the owner submits it to authenticated MCP `pairing_lookup` and explicitly runs `pairing_approve` for the exact public key and chosen mode. The device then automatically proves private-key possession to claim its approved ID. **No local 12-character challenge input.** MCP Bearer authenticates credential possession, not independent human presence; the single-user owner explicitly accepted this risk. Neither a downloaded file nor the one-line command is itself authorization. Never ship a private key, owner Portal Bearer, Cloudflare admin token, or reusable secret in an asset or command.
5. **Preserve approved device lifetimes.** Temporary approval is fixed and nonrenewable **24 hours after the server confirms enrollment**, with server-side denial of new operations at expiry; permanent approval does not inherit that expiry. Revoked device records are deleted per ADR-0017. Local installer experience must not automatically recover previously revoked/expired server authorizations or silently replace another approved identity.
6. **No v1 or production interference.** Distribution installs and service changes must be scoped to v2 and the operator's chosen Linux user, never overwrite v1 production or another existing v2 identity without explicit review. No new Worker, DO, D1/KV/R2, login service, new CI workflow or release/production action is authorized by these documentation decisions.

## Expected visible UX (illustrative, not a publishable command)

An owner may use the already verified nonproduction Preview HTTPS Worker `/install.sh` command; local CLI then prompts `Permanent device` or `Temporary device (24 hours)`, displays a pending code and optional fingerprint, waits for explicit MCP approval and automatically verifies its signed approved identity, and reports the device ID, mode, connectivity and next management steps. The present Preview URL and v0.1.8 assets were verified; do not advertise them as production or claim native ARM64 owner installation.

## Design consequences

- **Benefits:** no repository checkout, local compiler or package-manager setup; one supported Linux Agent codebase; symmetric x86_64/ARM64/WSL2 onboarding; no new authentication authority; same familiar CLI for permanent and temporary use.
- **Costs:** cross-architecture release artifacts (including Node and native helper), trustworthy distribution and upgrade/rollback paths, Linux ABI compatibility, per-user service integration and safe local credential handling all become requirements. Adding a one-line shell wrapper without those requirements is inadequate.
- **Scope restriction:** permanent/temporary selection and actual byte distribution are now accepted. Historical Draft #58 by itself lacks that path; stacked Draft #79 and public Agent v0.1.8 provide the nonproduction implementation; this ADR does not authorize implementation, changing release secrets, or deploying.

## Accepted choices — second grilling round (Q4–Q8=A)

**Q4=A — trustworthy download: official GitHub HTTPS, immutable version, SHA-256.**

- **Superseded by owner-approved ADR-0020 (2026-10-17):** use the future public `lirtual/remote-control-agent` GitHub repository Release channel, **not** the private `lirtual/mcp-workers` repository, for the reviewed installer and prebuilt Agent assets. The private repository's anonymous GitHub API and Releases returned HTTP 404. A version must refer to a specific release/tag and expected commit; pin the chosen version and artifact names so an asset cannot be silently replaced with a different architecture or mutable `latest` during one installation. Release immutability must be **enabled and verified** for the repository *before* relying on that property; it is not established by this ADR alone.
- **Use the SHA-256 `digest` exposed by the GitHub Releases asset API** as the preferred whole-archive checksum; do not introduce a custom manifest generator unless a verified platform/API constraint makes it necessary. Bind the chosen version, asset ID/name and reported digest before download; recompute SHA-256 locally **before unpacking or executing the archive**, and fail closed if the expected digest is missing or differs. Asset digests from the same GitHub origin as the binary provide consistency, **not independent publisher authentication**. Handle missing assets, untrusted redirects, unsupported ABI and malformed archive as failures.
- The **installer script itself is executable downloaded code**. Its trust comes from the reviewed, HTTPS-delivered and version-pinned official GitHub release source, **not from a checksum computed by that same script**. Never imply raw `curl | sh` is safer solely because the payload hash is checked. A one-line *interactive* bootstrap must keep its prompts connected to the actual terminal rather than read from a consumed download pipe. Do not invent a live installer domain/path or claim signed provenance is verified under Q4=A.
- No additional signing service or mandatory artifact-attestation verification is selected. A verified GitHub release attestation may be added later, but **Q4=B is not a requirement**. If GitHub's immutable Release feature is unavailable, do not silently claim immutability; stop and surface the limitation for another decision.

**Q5=A — manual upgrade with executable rollback.**

- Provide an explicit **owner-initiated CLI upgrade** to a reviewed version; **no unattended check-and-install, automatic download/upgrade, timers or background updater**. Download/stage/verify the complete new release before touching the running installation. Keep the prior working release available for a bounded rollback.
- Preserve the existing **device private key, device ID, chosen endpoint/mode and local Agent receipt store** as *separate user data*, never embed them in versioned replaceable binaries. An upgrade does **not** start a new pairing, renew a 24-hour grant, discard unknown receipts or silently retarget the service/Worker.
- Before replacing the active executable, check compatibility of the new Agent with persisted local SQLite/receipt formats and the remote v2 wire protocol. **Refuse upgrade while Agent-owned Managed Sessions are running, starting or have an uncertain active ownership state**; prompt the owner to wait/stop them explicitly. The existing Agent stop path otherwise sends TERM/KILL and could interrupt work. Stage and switch only **owned v2** versioned program files after the check. Verify local startup separately from remotely authenticated WSS availability: a transient network outage is not, by itself, evidence that the new binary is broken. On definitive local activation failure, restore previous program files/service reference without changing identity/receipts.
- **Rollback is limited to versioned program files**; keep only the current and immediately previous executable release, not a general package manager or multi-version retention system. SQLite/schema changes do not reverse with a binary switch. Reject any incompatible or destructive migration during ordinary upgrade pending a separate migration/backup review. Do not call a process healthy merely because `systemctl is-active` succeeds, and distinguish WSS `offline` from broken local activation.

**Q6=A — local uninstall and separate remote revocation.**

- The default uninstall disables/stops and removes **only this installer's own v2 service/CLI/program files**; no touching v1, other users, system services, unrelated paths, or other v2 identities. **Keep private key, device ID and receipt/operation history by default** under existing owner-only permissions. Local file cleanup **does not revoke** the remote grant.
- The CLI must clearly display an action to revoke the matching `device_id` via **the existing authenticated MCP `revoke_device`** and disclose that the still-approved server-side identity can remain authorized and usable if credential material is copied or the Agent is restarted elsewhere. Never grant the Agent the Portal/admin Bearer or silently call an unapproved self-revocation endpoint.
- Any optional **local identity/data purge** requires an explicit, precise confirmation, cannot be default and cannot claim to undo already executed work; ideally guide the owner to revoke remotely first, particularly for permanent grants. If server is unreachable, say remote revocation remains **unconfirmed**, rather than claiming success. `revoke_device` is subject to ADR-0017 delete-based semantics.

**Q7=A — rerunning the same one-line command safely resumes.**

- The user can rerun the **same install entrypoint** after interruption. Reuse the existing per-user `flock`, atomic file operations and identity checks. Detect the minimal durable facts (verified complete release, approved/pending local identity, installed v2 unit) and recompute the next safe action; **do not build a persisted workflow engine or separate multi-state installation database**. Never execute partial or unverified bytes.
- Rerun should be **idempotent with respect to already-approved device keys/IDs**: preserve valid identity and pending confirmation when appropriate; don't create a duplicate cloud grant or change the selected lifetime. For a revoked/expired identity or mismatched endpoint/key, fail closed and require a **fresh, explicit interactive owner-approved pairing** using the already accepted recovery workflow, not automatic silent re-enrollment.
- Use a temporary directory and atomic promotion of fully verified versioned program files, plus existing owner-only identity staging; add a small recovery marker **only when necessary to resolve an otherwise ambiguous promotion**. Unexpected file owners, symlinks, cross-user paths, corrupt identity and concurrent installer invocations fail safely. No cloud queue, separate transaction framework, duplicate receipt store or generalized installation state machine.

**Q8=A — local CLI mode and lifecycle.**

- **Permanent device:** interactive selection starts the existing **systemd --user v2 service** only after successful independent pairing and verified install. Require a usable user manager; if unavailable, report a clear unmet host prerequisite **without silently starting an unmanaged duplicate foreground Agent**, changing `/etc/wsl.conf`, enabling lingering or altering another user's service.
- **Temporary device (24 hours):** interactive selection starts a **foreground Agent**, with no automatically enabled systemd unit. Closing the terminal ends that local process/connection but **does not revoke early**; the server independently denies new operations after 24 hours. The user may use MCP `revoke_device` to end authorization early. Temporary identity and permanent-service identity cannot accidentally share/overwrite the same key/ID or active socket; use distinct owner-only local identity scopes as required.
- **CLI prompts:** locally and interactively show scope/mode, target endpoint and any existing identity warning; display one 10-character pending code, explain authenticated `pairing_lookup` then **explicit** `pairing_approve`, automatically sign an internal one-use server nonce with the matching device key after approval and print approved device ID, mode and observed connection state. The installer cannot auto-approve via MCP, and an authorized MCP action is **not** independent cryptographic human-presence proof.
- A noninteractive install (no usable controlling TTY) must **fail before generating or activating an identity**, with a concise nonsecret diagnostic, rather than bypass mode selection, inventing defaults or hanging. For a downloaded bootstrap, stdin must remain available for real CLI interaction.
- **WSL2 caveat:** installing inside WSL2 does not arrange Windows host startup or wake a stopped distribution. User systemd can maintain the Agent only while WSL2 is actually running. No automatic Windows Task Scheduler, root service, linger change or host startup side effect is authorized.

## Scope and consequences of second-round decisions

- **Benefit:** one command and interactive mode, trusted immutable downloadable version, no local source/dependency build, manual rollbackable binary upgrades, idempotent retries and no extra authorization service.
- **Tradeoffs:** HTTPS + same-origin SHA-256 is **not a separate publisher-signature guarantee**; local uninstall doesn't remove existing cloud authorization; temporary foreground can leave an offline yet still approved identity until its 24-hour expiry; runtime rollback cannot reverse arbitrary state migrations; a stopped WSL2 cannot be woken by its Linux user service.
- **Compatibility boundary:** Node 24 runtime and the prebuilt Linux C helper must be verified on the selected libc/CPU/kernel targets. A GitHub Release source tarball is **not** the bundled executable asset required by this ADR. GitHub published release assets, immutable settings, and production acceptance have not yet been observed.
- **Implementation scope:** reuse existing `apps/remote-control-agent`, CLI and systemd generator, actual session supervisor and operation receipt store, existing v2 pairing endpoints and owner's single DO. Do not replace native Linux process ownership supervision with a weaker shell runner; do not introduce D1/R2/KV, another OAuth provider, full fleet manager, auto-updater or new CI workflow without independent justification.

## Final simplification and blocker review (2026-10-17, owner approved)

**P0 — exact Linux process-control capability, not merely a Node/CPU check.** The existing `apps/remote-control-agent/scripts/session-supervisor.c` calls `pidfd_send_signal(..., PIDFD_SIGNAL_PROCESS_GROUP)`. This flag requires **Linux 6.9+**; a compatible Node.js 24/glibc build on an older kernel does not make this helper work. For the initial minimal release, document **kernel 6.9 or newer and a successful harmless pidfd process-group capability preflight** as prerequisites for the current Shell Supervisor; a version string alone is insufficient. Reject unsupported hosts **before creating/pairing a cloud identity**. Do not silently fall back to unsupervised Shell/group-kill behavior; supporting older kernels requires a *separately reviewed safe design*, not another automatic fallback subsystem. Architecture and actual libc/native binary compatibility still need on-host checks.

**P0 — no-tombstone re-pair compatibility.** Draft PR #58's `assertRemoteRevocation` requires `/agent/re-pair/status` to answer `status:"revoked"`, but ADR-0017 deliberately removes revoked rows. These contracts conflict. When adapting, a precisely authenticated response that the *old device ID is no longer approved* may permit a fresh **interactive owner-approved** enrollment, with the old local identity protected/archived until the new key and ID are verified. A bare 404, transient failure or ambiguous 401/403 **must not silently overwrite** any previously approved identity or be treated as proof of revocation. Do not restore permanent tombstones or build a new blacklist to solve this. Protect rollback of interrupted local identity promotion and preserve every receipt; do not automatically re-pair revoked/expired identities in unattended contexts.

**P0/P1 — action availability is independent from installation success.** Current `v2-main.ts` constructs the WSS connection with `readOnly:true, writeFile:false, shell:false`. A new packaged Agent connecting successfully must not be described as having verified Shell/writes. Default first acceptance should prove signed connection and a nonsensitive read; enable destructive capabilities only through their already defined, separately approved security gates.

**P1 — upgrade active work and unknown outcomes.** Reject routine manual upgrades while managed child sessions are running/starting or their ownership is uncertain; never rely on service restart to terminate them safely. Preserve original 60-minute command deadlines and Agent-local operation receipts; no hot-upgrade, cross-version process migration or automatic replay. After staging, test *local execution* separately from *remote connectivity*. If cloud is offline, report `connectivity_unconfirmed` rather than forcibly rolling back a locally sound release.

**P1 — minimum package and recovery shape.** One archive per *actually compatible* target ABI/architecture, including bundled Node 24 + JS + prebuilt Supervisor. One reviewed HTTPS/GitHub-version-bound bootstrap and one interactive CLI; use the official release-asset `digest` instead of a duplicate manifest system. A versioned current/previous binary location, a pointer/service reference, existing `flock` and atomic staging are sufficient. No new install database, general package manager, scheduled auto-updater, CDN, alternative distribution registry, compiler-at-target, duplicate pairing engine, extra server revoke endpoint or new Worker.

**Release gate separation:** [Issue #57](https://github.com/lirtual/mcp-workers/issues/57) explicitly reduced the **current** nonproduction release gate to **one device over 48 real hours**, with DO Hibernation, shared Free quota and v1-isolation evidence. The earlier five-device/72-hour language is **historical and removed from this rollout requirement**, not a second hidden blocker; future fleet-scale performance validation would need separate scope. Do not substitute a packaging smoke test for the actual 48-hour evidence.

**Official factual references:** `PIDFD_SIGNAL_PROCESS_GROUP` version: https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html ; GitHub Release asset `digest` response: https://docs.github.com/en/rest/releases/assets ; immutable releases: https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases .

## Deep-review outstanding acceptance gates — no further product choices presumed

1. **Verified publishing/install supply chain:** immutable Releases configured; version/commit/archive mapping checked; clean-host bootstrap works with real terminal stdin; TLS/origin/redirect/download error handling; sha256 mismatch and malicious archive traversal/symlink/permission refusal. Version- and checksum-pinned archive matched to x86_64/ARM64 and supported libc. Build reproducibility/provenance beyond Q4=A is optional, not falsely claimed.
2. **State isolation and upgrade reversibility:** identity, endpoint, device grant type, operation receipts and active process ownership survive executable upgrades; preflight rejects incompatible `node:sqlite`/receipt formats and protocol versions; rollback doesn't reinterpret newer schema; failed binary promotion/restart recovers without touching v1, without unknown-operation blind replay and without claiming the service healthy when WSS is unconfirmed.
3. **CLI onboarding/recovery UX:** device-key proof remains separate from MCP owner approval; no automatic MCP approval; pending-code expiry and repeat installer invocation; interrupted delivery and atomic promotion; revoked/expired/foreign identity rejection; concurrent CLI lock; wrong endpoint selection; sanitized local diagnostics; no TTY and stdin/pipe interaction.
4. **Two lifecycles:** permanent mode only with a verified user systemd service; temporary mode foreground only with server-enforced nonrenewable 24h expiry. Verify Ctrl+C, SIGTERM, SIGKILL, WSL2 stop, native Linux reboot, service restart and normal transport disconnection, and prevent duplicate permanent/temporary identities or clobbered service files. Check shell session's existing 60-minute cap and local receipt semantics.
5. **Uninstall and remote permission:** owned v2 binary/service removal without changing v1; private key + receipt retained by default; an explicit data purge warning; remote grant still approved until authenticated MCP removal or scheduled 24h expiry; offline/unreachable remote does not lead to false revoke-success.
6. **Operational delivery prerequisites:** documented compatible Linux glibc/kernel matrix and ARM64 run evidence, package size, GitHub release handling/retention, installing without preinstalled Node/git/cc, no unreviewed privilege escalation. Reuse existing CI; add no workflow unless a later approved implementation requires it. Preserve nonproduction 48h single-device gate if separately approved, otherwise verify the current acceptance baseline before claiming production readiness.

**No code, release artifact, CI workflow, systemd or production/preview device change is authorized by this ADR.** The approved Q1–Q8 choices should be consumed by a later explicit spec/implementation process.

## Owner-approved amendment · 2026-10-17 · Worker-origin convenience entry + Python-free bootstrap

**Decision (supersedes the original bootstrap-entry and Python implementation mechanism, not the immutable release channel):** The supported one-line install UX will use `https://<selected-approved-mcp-worker>/install.sh`. The **existing** v2 MCP Worker returns a small public, version-pinned Shell bootstrap and binds the exact validated request origin as the device endpoint, rather than asking the user to supply `REMOTE_CONTROL_AGENT_ENDPOINT`. This changes the origin of the *entry script only*: all substantial Agent archives, bundled Node 24 and native Supervisor stay in reviewed, immutable `lirtual/remote-control-agent` GitHub Releases, with exact release/commit/architecture/whole-archive SHA-256 pins. No new Cloudflare Worker, DO, secrets, D1/R2/KV, auto-update channel, OAuth or second build host. The isolated `remote-control-v2-preview` Worker already serves reviewed `/install.sh`; no production route is authorized.

**Trust and implementation:** Public installation route is narrowly path/method-scoped, must accept only explicitly approved HTTPS Worker hostname(s)/origins, must not trust arbitrary Host/Forwarded/client endpoint overrides, and cannot grant/prepare a device identity, expose Bearer or loosen `/mcp` authorization. It must serve static/reviewed Shell code with properly escaped exact origin and pinned asset digest(s), not user-influenced executable text. The Shell must check its Linux tools/platform first, download a bounded official GitHub archive into owner-private staging, compute `sha256sum` and compare against the reviewed pinned whole-archive digest **before** extracting or executing the reviewed single `bin/node`; the bundled Node then performs full secure archive inspection/staging/TTY pairing by reusing the existing Agent implementation. No Python, pip, installed system Node/npm, local Git or compiler is required. The installed `rca` manager is migrated from Python to the same bundled Node; preserve keys, endpoint, installed version, SQLite receipts, ownership and rollback semantics.

**UX:** Mandatory explicit Permanent vs Temporary choice stays before pairing because it is bound to the owner-reviewed grant type. The optional post-install `Open Agent manager now?` loop is removed; show exact executable path and correct instructions for modifying the **current Bash** PATH (a downloaded child Shell cannot change its parent). Optional WSL2 label defaults may use `WSL_DISTRO_NAME` when available but must not determine device authorization. No automatic re-pair, production/v1 change or privilege expansion.

**Delivery:** Implement/review on existing Draft PRs, reuse existing x64/ARM64 CI and install tests, and add fail-closed cases for origin/header spoofing, wrong checksum, malicious archive, missing tool/ABI, no-TTY, interrupted staging, idempotent replay and upgrade rollback. Publishing a new immutable release, enabling Preview `/install.sh`, or production switching remains a **separate explicit authorization**. Existing v0.1.1 and the one-device 48-hour acceptance gate #57 remain unchanged. The detailed acceptance matrix is in the 2026-10-17 revision of `SPEC-standalone-agent-cli.md`.

## 2026-10-18: release/protocol compatibility gate for single-code Preview

The latest unmerged Worker #79 implements `pairing_protocol: "single-code-v1"`; a new Agent must include this marker **in the signed pending enrollment transcript** and use authenticated MCP `pairing_lookup` → explicit `pairing_approve` → existing signed device-ID recovery. Historical immutable Agent **v0.1.2 is a two-code release**, so its correctly verified tag/commit/x64+ARM64 archive digests do **not** establish compatibility with this newer Worker wire protocol. The archived v0.1.2 pin is retained only for historical provenance.

**Deployment lock:** new-protocol `/install.sh` returns **503, no executable Shell** until a **new, separately authorized immutable public Agent release** with native x64+ARM64 build/test evidence, exact commit/tag/digests and single-code enrollment compatibility has been reviewed and explicitly pinned. No fallback to v0.1.2, no `latest`, runtime API discovery or second Worker. Adding the protocol field to the *reviewed* pin guards against accidental mixing of a correct digest with the wrong pairing protocol. A future publication/deployment still requires the separately approved release and live owner-client acceptance; this Draft edit itself does not authorize publishing or deploying.

**Preview preservation:** The active `remote-control-v2-preview` deployment remains the pre-existing two-code version with existing approved device grants and one observed online device. Do not replace the active Preview merely to test the new route; first record current deployment/version ID, bindings and rollback target, verify new release/Worker pairing compatibility in an isolated candidate context, and obtain separate deployment authorization. Any rollback to an older Worker can re-expose its old pending-challenge endpoints, so treat it as a controlled trust-boundary change and never reinterpret legacy pending records as a new MCP-only grant. #97 genuine new-client signed-WSS/benign-read gate is Closed; #57 continuous 48-hour gate remains OPEN until genuinely observed.
