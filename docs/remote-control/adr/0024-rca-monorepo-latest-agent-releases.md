# ADR-0024 — Keep RCA Agent source with its Worker; distribute latest stable native Release

**Status: Accepted (2026-11-10). Supersedes ADR-0020 for future Agent source and distribution. Not a production Release, Worker deployment, or physical-device verification by itself.**

The RCA Worker already lives in `lirtual/mcp-workers` while its five-platform native Agent lives in a separate public repository. That split requires fetching and verifying an externally pinned source revision for Worker tests and separately maintaining workspaces and release code. The owner chooses to **nest the Agent source inside `apps/remote-control-mcp-worker/agent/`**, with one pnpm workspace and one repository, while **keeping native Agent and Worker release/execution authority independent**. Import only the reviewed source snapshot; the old repository remains historical evidence and is not a supported runtime fallback.

**Distribution decision:** New native assets publish as manually authorized, stable GitHub Releases of `lirtual/mcp-workers`. An explicit install or authorized upgrade selects **that repository's latest non-draft, non-prerelease Release**, without configured tag/commit/source-pin tables or old-repository compatibility. The existing RCA Worker public installer URLs remain unchanged. Ordinary `main` merges/CI must not publish native artifacts, deploy Workers or upgrade devices. Existing device keys, IDs, approvals, intentional STOP and durable/Unknown receipts must not be reset by the source move; preserve existing native archive/internal program paths where practicable to avoid a separate on-device format migration.

**Trade-offs and bounds:** GitHub's `/releases/latest` is **repository-wide**. The owner/publisher can explicitly assign `make_latest=true` for a stable Release; GitHub's legacy selection instead considers Release chronology/version. Reserve stable GitHub Releases in `mcp-workers` for RCA Agent, explicitly mark the reviewed five-platform Release Latest, and independently read back `/releases/latest` before Worker cutover. The first complete stable Release must exist before the new Worker installer is published. Require `immutable=true` on the published Release (enable GitHub's native immutability setting before first publication), exact platform asset presence, GitHub-reported SHA-256 matched against downloaded bytes, safe HTTPS/redirect/archive handling and owner-only transactional staging; missing/unrelated latest or invalid artifact fails closed. Since the digest and assets share the GitHub Release authority, this **does not attest an uncompromised publisher**, which is the explicitly accepted cost of discarding independent source/tag/commit pins. At publication time, the manual workflow must check that all five native candidates derive from the same reviewed source/CI run, without adding installer-side source pins. An explicit, separately authorized correction may re-mark an **already verified, stable new-repository** Release as Latest; this affects future downloads, not installed devices. Existing paired `v0.1.51` installations require a one-time real upgrade test using the new Worker bootstrap: remove old *remote source* pin requirements while preserving local identity, STOP/Resume, operation freeze, receipts, Unknown/no-replay and rollback. For public GitHub Latest requests, handle 403/429 by stopping safely (no new cache service or uncontrolled retry). No automatic latest polling in the delivered contract (see #1035 below), forced upgrade, re-pairing, extra release service, database, cross-repository download or old-repo fallback.

This decision **supersedes ADR-0020's future source/distribution-repository choice and pinned-repo migration strategy**, because `mcp-workers` is now public; it does not erase ADR-0020's historical release evidence or supersede the existing Ed25519, authorization, STOP, receipts and no-blind-replay safety boundaries. A single coordinated cutover still uses dependent gates: nonproduction test/build; separately authorized and independently verified first *stable* Agent Release; separately authorized Worker production release; and explicit real-device acceptance. No implementation, merge, publication, production or destructive-device authorization is conveyed by this ADR.

**Spec #914 initial phased runtime plan (owner decision 2026-11-24; superseded by the 2026-11-25 decision below):** retain the same immutable Latest, five archives and canonical manifest. Linux x64/arm64 and Windows x64 move to native-only Rust; Linux x64 and Windows x64 retain dedicated Rust Session entries. The initial plan deferred macOS Rust migration. It did not change the distribution contract or create a platform-version table or separate channel. The compatible Worker installer had to be deployed and verified against the existing Node stable Latest before switching to the first native-only Latest; the original source-move first-Release ordering above was already satisfied by the existing stable release. Preserve exact same-source candidate review, explicit owner-only manual publication, immutable readback, and separately authorized device actions. Candidate preparation does not authorize publication or waive actual acceptance.

See [Spec #803](https://github.com/lirtual/mcp-workers/issues/803) and [Spec #810](https://github.com/lirtual/mcp-workers/issues/810) for historical decisions and acceptance.

## 2026-11-24: retired Node compatibility (#914)

Owner explicitly waived Node and hybrid upgrade/rollback compatibility for Linux/Windows on 2026-11-24 and extended the same decision to macOS on 2026-11-27 ([Spec #914](https://github.com/lirtual/mcp-workers/issues/914#issuecomment-7207376137)). Across all five platform targets, old Node installations may be manually replaced by Rust; direct Node-to-Rust upgrade and Rust-to-Node rollback are not supported delivery requirements. Retire the dedicated old runtime, installers, build fixtures and migration-only tests with the completed native-only replacement. Preserve native enrollment, signatures, supported Rust-to-Rust upgrade/recovery, identity, authorization, intentional STOP and receipt safety. Keep historical immutable releases and evidence, including failed tests; an obsolete compatibility test is not a passed native acceptance. This decision authorizes neither production changes nor device-data deletion.


## 2026-11-25: accepted evolution — automatic update (#1035)

[Spec #1035](https://github.com/lirtual/mcp-workers/issues/1035) changes only the prohibition on automatic Latest polling and per-update authorization for eligible devices once the applicable delivery gates pass. Current delivered behavior remains authoritative; this design does not authorize implementation or production changes.

New permanent Standard installs disclose default enabled Automatic Update Policy; existing installs require one explicitly authorized migration. Missing/unmigrated policy is not consent. The local policy can be disabled or explicitly changed remotely. Only running, authorized Owner-ON Standard stable installations check the official Immutable Stable Latest (about six hours, startup delay and jitter) and install qualifying forward releases. Exclude temporary grants, Workflow Sessions, STOP, revoked/expired grants and candidates; candidate promotion remains explicit. Disable blocks automatic cutover not yet admitted; admitted transactions safely complete or recover.

Reuse existing platform lifecycle locking, executor Freeze, verified staging, independent execution, identity/receipt continuity and recovery. Stage while busy, cut over only when locally proven idle; never kill tasks to update. Bound checks, downloads, storage and retries; suppress repeated attempts at a failed target after verified recovery; preserve uncertain transactions. Isolated historical Unknown alone does not prevent safe upgrade (ADR-0016). API failure affects updating, not ordinary service. Dispatch is not final success.

Preserve manual production publication, complete five-platform same-source candidates, immutable assets and verification, compatible Worker ordering. Once enabled, publication of compatible Stable Latest can cause automatic device changes; account for downstream impact at publication authorization. Re-marking Latest does not downgrade. Worker publication, explicit downgrade, enrollment/revocation and existing-device migration remain independently authorized. No new update server, daemon, policy database, channel, version table or framework. #914 and #1018 boundaries unchanged.


### Accepted final refinement — version identity and update simplicity (#1035)

The sole public stable product version is the actual release tag vMAJOR.MINOR.PATCH; report platform, architecture and runtime state separately. Never strip a historical prerelease suffix to imply a stable release. Ordinary unpublished release candidates use the intended stable tag and existing run ID, source commit and digest provenance; CI artifacts do not become releases merely by bearing that tag. Stop creating Rust-migration prerelease versions for routine builds. Preserve immutable historical releases and evidence; no extra version channel, mapping, registry or source of product versions.

Retire migration-only candidate/preview/SPEC914 names and metadata only where their actual references and duties are exhausted. Platform asset names and protocol, receipt, archive, runtime and upgrade validation identifiers may encode distinct required contracts, not product versions. In particular, released executables' paths and manifest profiles participate in old installers, process ownership, rollback and release guards. Before changing any such contract, prove supported stable-to-stable upgrade and recovery with actual old consumers; preserve supported Rust upgrade/recovery, do not add permanent compatibility for cosmetic renaming, and retain necessary internal identifiers if benefit is insufficient. Do not reintroduce retired Linux/Windows Node support.

Reuse existing authoritative Latest selection and validation across applicable update entry points. Status reads local and already-known facts (staleness/unknown explicit), without a mandatory remote query; explicit update --check refreshes the release observation without changing installed software. Project user-facing update states from existing transaction and runtime evidence, retaining only necessary policy, failed-target suppression and result evidence; no parallel persistent state machine or duplicate version-check implementation. Existing release authorization covers the reviewed downstream impact on enabled devices, without an extra per-device approval or rollout service. These refinements remain accepted design, not runtime delivery or production authorization.

## 2026-11-25: complete the macOS native-only transition (#914)

The Owner cancels the macOS deferred scope. Existing Node releases remain immutable historical artifacts, and currently installed Node behavior remains the parity reference until the replacement passes review and tests. Final RCA runtime and installed macOS management paths must not depend on Node; retire their obsolete source, package and validation paths. Continue the same five-platform Latest and independently authorized publication; #1035 and #1039 macOS contracts target Rust. Do not build a permanent Node compatibility path. This is an implementation scope decision, not evidence of completed retirement or authorization to publish. See [current decision and evidence](https://github.com/lirtual/mcp-workers/issues/914#issuecomment-7162906800).
