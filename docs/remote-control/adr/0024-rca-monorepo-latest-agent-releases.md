# ADR-0024 — Keep RCA Agent source with its Worker; distribute latest stable native Release

**Status: Accepted (2026-11-10). Supersedes ADR-0020 for future Agent source and distribution. Not a production Release, Worker deployment, or physical-device verification by itself.**

The RCA Worker already lives in `lirtual/mcp-workers` while its five-platform native Agent lives in a separate public repository. That split requires fetching and verifying an externally pinned source revision for Worker tests and separately maintaining workspaces and release code. The owner chooses to **nest the Agent source inside `apps/remote-control-mcp-worker/agent/`**, with one pnpm workspace and one repository, while **keeping native Agent and Worker release/execution authority independent**. Import only the reviewed source snapshot; the old repository remains historical evidence and is not a supported runtime fallback.

**Distribution decision:** New native assets publish as manually authorized, stable GitHub Releases of `lirtual/mcp-workers`. An explicit install or authorized upgrade selects **that repository's latest non-draft, non-prerelease Release**, without configured tag/commit/source-pin tables or old-repository compatibility. The existing RCA Worker public installer URLs remain unchanged. Ordinary `main` merges/CI must not publish native artifacts, deploy Workers or upgrade devices. Existing device keys, IDs, approvals, intentional STOP and durable/Unknown receipts must not be reset by the source move; preserve existing native archive/internal program paths where practicable to avoid a separate on-device format migration.

**Trade-offs and bounds:** GitHub's `/releases/latest` is **repository-wide**. The owner/publisher can explicitly assign `make_latest=true` for a stable Release; GitHub's legacy selection instead considers Release chronology/version. Reserve stable GitHub Releases in `mcp-workers` for RCA Agent, explicitly mark the reviewed five-platform Release Latest, and independently read back `/releases/latest` before Worker cutover. The first complete stable Release must exist before the new Worker installer is published. Require `immutable=true` on the published Release (enable GitHub's native immutability setting before first publication), exact platform asset presence, GitHub-reported SHA-256 matched against downloaded bytes, safe HTTPS/redirect/archive handling and owner-only transactional staging; missing/unrelated latest or invalid artifact fails closed. Since the digest and assets share the GitHub Release authority, this **does not attest an uncompromised publisher**, which is the explicitly accepted cost of discarding independent source/tag/commit pins. At publication time, the manual workflow must check that all five native candidates derive from the same reviewed source/CI run, without adding installer-side source pins. An explicit, separately authorized correction may re-mark an **already verified, stable new-repository** Release as Latest; this affects future downloads, not installed devices. Existing paired `v0.1.51` installations require a one-time real upgrade test using the new Worker bootstrap: remove old *remote source* pin requirements while preserving local identity, STOP/Resume, operation freeze, receipts, Unknown/no-replay and rollback. For public GitHub Latest requests, handle 403/429 by stopping safely (no new cache service or uncontrolled retry). No automatic latest polling, forced upgrade, re-pairing, extra release service, database, cross-repository download or old-repo fallback.

This decision **supersedes ADR-0020's future source/distribution-repository choice and pinned-repo migration strategy**, because `mcp-workers` is now public; it does not erase ADR-0020's historical release evidence or supersede the existing Ed25519, authorization, STOP, receipts and no-blind-replay safety boundaries. A single coordinated cutover still uses dependent gates: nonproduction test/build; separately authorized and independently verified first *stable* Agent Release; separately authorized Worker production release; and explicit real-device acceptance. No implementation, merge, publication, production or destructive-device authorization is conveyed by this ADR.

See [final Grill With Docs design](../RCA-MONOREPO-DESIGN.md) for exact checks, failure policy and acceptance matrix.
