# ADR-0025 — Curated atomic browser actions, semantic targets, and durable action identities

Status: **accepted design choices (Grill With Docs round 5, 2026-10-20); documentation only; implementation and release not authorized**.

**Q17=A — expose a minimal curated atomic browser tool surface.** The existing Remote Control MCP will expose separate, single-purpose browser operations for the relevant browser-session, tab, navigation, observation and element-interaction capabilities as their individual contracts are later agreed. A generic unrestricted `browser_action` dispatcher, arbitrary Playwright/JavaScript execution and a nested Playwright MCP server are **not** the product interface. The exact first-release set, tool names, arguments and required/optional operations are still open; this decision does not approve a particular tool inventory.

**Q18=A — semantic element targeting with a uniqueness requirement.** Element operations prefer semantic/accessibility identity—role, accessible name, label and meaningful text—over CSS/XPath or guessed screen coordinates. The intended target must resolve unambiguously in the current selected tab at the time of action; ambiguous, missing or stale targets must fail safely and prompt a fresh page observation, not an automatic blind click. Supported locator forms, freshness handling and any visual-coordinate fallback remain unsettled. The browser page is untrusted data, not authority to choose an unrelated action.

**Q19=A — keep browser uploads and downloads local to the selected device.** Uploads reference explicitly authorized paths on the Agent device; browser downloads land in an Agent-managed dedicated local download directory, not an uncontrolled browser default location. Inspecting or moving those files should reuse the existing Remote Control file capabilities when applicable; **browser file bytes are not routed through MCP/Cloudflare as the normal upload/download mechanism**. Local path authorization, filenames, collision policy, file-size limits and retention/cleanup remain open. This does not imply that any path automatically becomes readable or writable merely because browser automation is enabled.

**Q20=A — reuse stable Operation IDs and Agent-local Operation Receipts for potentially effectful browser actions.** An action that might produce side effects is identified consistently and locally receipted, allowing the client to query known execution status after lost responses or WSS interruption rather than automatically re-issuing the browser action. An uncertain outcome remains uncertain and is **not safe to retry simply because a timeout occurred**. Critically, a receipt that reports successful browser execution (for example, a click) is **not proof that the remote website completed a purchase, sent a message or committed a form**. Independent page or service evidence may be needed to conclude business success. The concrete admission/receipt state machine, action classification, reconciliation and retention details are not yet approved; do not claim exactly-once external effect.

**Trade-offs:** separate atomic tools make each operation auditable and independently authorizable; semantic-first matching is less brittle than screen coordinates; device-local file transfer avoids unnecessary large or sensitive file data moving through Cloudflare; Agent-local receipts reuse Remote Control's existing no-blind-retry invariant while acknowledging the fundamental difference between browser execution and remote business outcomes.

**Follow-on decision (round 6):** [ADR-0026](./0026-browser-capabilities-tab-and-approval-scope.md) confirms initial end-to-end common workflow coverage, stable tab IDs explicitly scoped to device/session, one-use consequential-action confirmation bound to the intended target, and explicit Profile clearing only in a provably safe state.

**Follow-on decision (round 7):** [ADR-0027](./0027-browser-tools-visual-consent-and-recovery.md) selects a compact curated tool inventory, bounded fresh visual fallback, fail-closed action-specific approval, and non-destructive crash/lock recovery.

**Follow-on decision (round 8):** [ADR-0028](./0028-browser-data-files-provenance-platform-acceptance.md) resolves the default privacy direction, existing Agent file authority, trusted/version-compatible Chromium requirement and independent real-platform acceptance, while leaving exact implementation limits open.

**Follow-on decision (round 9):** [ADR-0029](./0029-browser-results-outcomes-downloads-gated-release.md) selects a compact result envelope with Operation IDs for effectful calls, separate website-effect evidence, and refusal to blindly retry unknown browser operations; seven-day cleanup applies only to unreferenced managed downloads.

**Follow-on decision (round 10):** [ADR-0030](./0030-browser-conservative-gating-consent-evidence-acceptance.md) confirms existing local receipt reuse without a second transaction ledger, and no execution of uncertain-effect actions under a presumed low-impact classification. High-impact enablement depends on verified end-to-end one-use confirmation.

**Follow-on accepted decision (round 11, Q42=A):** Atomic MCP calls share a **minimal** target contract: an explicit `device_id`, `session_id` when operating on a browser session, and `tab_id` only when needed to target a tab. Each tool adds **only its own operation-specific inputs**, rather than a large universal request envelope or generic action dispatcher. Results consistently identify the target and supply known status, an applicable machine-readable error identifier, only necessary bounded data, an explicit truncation indication when relevant, and an `operation_id` for a potentially effectful operation. This does **not** define final field names beyond already agreed identity concepts, fixed nested JSON structure, status enum or result transport. No duplication of existing tools solely for shape conformity.

**Still open:** exact typed tool-specific arguments, result/error fields and lifecycle status encoding, real low-impact scope, tab identity implementation, snapshot freshness/limits, managed-download references, owner approval proof/expiry/consumption and website-effect evidence, OS/file permissions, browser binary trust and platform rollout gates. No code, runtime changes, new implementation Issues/Tickets, or deployment is authorized.
