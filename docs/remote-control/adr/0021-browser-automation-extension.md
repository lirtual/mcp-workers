# ADR-0021 — Browser automation is a scoped Remote Control capability

> **Later phase-one scope amendment (2026-10-20):** [Windows PoC / trusted-device scope](../BROWSER-BACKEND-POC-20261020.md) replaces conflicting broad sandbox acceptance expectations with an explicit personal paired-device threat model. Existing Remote Control ownership and browser-only user interface scope remain unchanged. Strict hostile-execution containment is deferred/unverified, not waived as a passed test. High-impact actions still require verifiable user approval.


Status: **accepted design boundary (Grill With Docs round 1, 2026-10-20); documentation only, no implementation or release approval**.

Remote browser automation belongs to the existing **Remote Control MCP** product rather than a new `browser-mcp-worker`. It reuses the existing authorized device identity, explicit device routing, authenticated Agent transport, and ownership boundaries. The browser-specific runtime is an Agent-side capability, not a second device registration, Worker, Durable Object, public CDP endpoint, or browser-wide permission implied by pairing.

The first delivery **prioritizes an independently managed automation browser**. Attaching to an owner's already-open Chrome/Edge and reusing an existing login session is a **later, separately designed capability**; it must not be represented as available by this ADR alone.

The scope is **browser automation only**: navigation, page/element inspection, tab and browser-session management, webpage interactions, and browser-scoped file transfers as subsequently specified. Full desktop screen sharing, arbitrary OS mouse/keyboard control, and other native GUI applications remain out of scope. This does **not** supersede the first-release exclusion of graphical desktop control in the v1 Remote Control spec.

Existing **device pairing is necessary but insufficient as blanket browser authorization**. Operations must target an explicitly authorized `device_id` and identified browser session/tab as applicable. Access to an existing personal browser profile/tab requires the owner's explicit scope selection; sensitive external actions must have an explicit confirmation boundary. The precise approval UX, supported operations and action classes remain unsettled.

**Why:** reusing the established device trust and WSS/DO route avoids duplicating authentication and fleet coordination. Isolated automation sessions reduce interference and exposure before enabling the riskier existing-profile path. Restricting scope prevents browser support from becoming a general remote-desktop product.

**Follow-on accepted decision (round 13, Q52=A) — close the design interview through explicit owner confirmation, not implicit implementation.** After recording Q1–Q52, perform a comprehensive design-tree and cross-document consistency review, identify any actual missing decision rather than indefinitely inventing questions, and consolidate redundant prose without erasing accepted trade-offs. Record independent **evidence gates** (supported ChatGPT/MCP one-use approval, trusted browser artifacts, OS-specific browser and Agent behavior, receipts, privacy and real-device acceptance) separately from the policy decisions made in the interview. Present the final design summary and any true remaining choices to the owner for **separate explicit confirmation of shared design understanding**. Such confirmation may permit **subsequent discussion/planning only**, not automatically authorize coding, creating development Issues/Tickets, PR merge, CI changes, rollout or deployment. This existing Draft PR #117 stays Draft until independently authorized otherwise; it does not itself grant implementation permission. The deferred personal Chrome/Edge attachment is out of this release scope, not a reason to silently reopen settled decisions.

**Still open / outside this documentation interview:** independent owner confirmation of final design; real low-impact safety enforcement, verified one-use approval transport, browser source integrity and OS dependencies, precise privacy/output quotas, download reference cleanup, idle/recovery and typed tool/receipt implementation contracts, platform validation, and any later separately approved implementation plan/merge/deployment. None of these has been executed by Q52.
