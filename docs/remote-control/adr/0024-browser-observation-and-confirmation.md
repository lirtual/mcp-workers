# ADR-0024 — Browser idle lifetime, observation and sensitive-action confirmation

> **Windows Goal A round 2 (H5=A, H6=A, H7=A, H8=A, H11=A; 2026-10-21):** Verified activity within the automation browser counts against the existing **30-minute idle rule**, including during Human Control. After 30 actual idle minutes, the browser session is closed automatically while Profile state and receipts persist; warning UX is not settled. The owner explicitly resumes via **ChatGPT / existing MCP**; handoff stops admissions of new Agent effects while already-admitted bounded effects settle/timeout without replay. A missing usable Windows interactive desktop means clear startup failure **not headless fallback**; mid-session lock/logout remains undecided. Precise detection, race, approval and state-recovery mechanisms are unimplemented. [H5–H11 decision](../BROWSER-ARCHITECTURE-REVIEW-20261020.md#windows-browser-handoff-and-default-selection--new-grill-with-docs-round-1-2026-10-21). No production or code authorization.

> **Windows-only amendment, 2026-10-21 (new Grill With Docs H1=A, H2=A, H4=B):** For native Windows automation sessions the owner selected an **always-visible headed window** to permit on-demand handoff, superseding the original Q14 headless default for Windows only. Agent or owner may initiate handing off control; only **explicit owner instruction** returns control to Agent. Resuming is not an independent high-impact website-action authorization. The existing **30-minute inactivity cleanup continues even while a human controls the browser**; activity accounting and warning/expiration UX are undecided. Historical Q13, Q15, Q16 remain otherwise intact. See [current Windows amendment](../BROWSER-ARCHITECTURE-REVIEW-20261020.md#windows-browser-handoff-and-default-selection--new-grill-with-docs-round-1-2026-10-21). Documentation-only; no shipped change.

Status: **accepted design choices (Grill With Docs round 4, 2026-10-20); documentation only; implementation and release not authorized**.

**Q13=A — idle cleanup after 30 minutes.** An Automation Browser Session is eligible for local cleanup after **30 minutes without activity**. This closes its Agent-owned browser process/session but preserves the dedicated Automation Browser Profile and its retained local sign-in state. An offline or stopped Agent cannot promise exact wall-clock cleanup; the precise activity signal, timer ownership, shutdown race handling and observable session states remain to be specified. The owner may close a session explicitly without waiting for the timeout.

**Q14=A — headless by default; headed on request.** Independent automation sessions normally run without a visible window (**headless**). An expressly selected **headed** session is permitted only where the target device has a supported, usable graphical desktop. Headed mode is a browser window on that device, **not** remote desktop/screen control, and does not imply that a Windows host browser can be driven from an unrelated WSL2 Linux Agent. Display prerequisites and behavior when a graphical session is unavailable remain open.

**Q15=A — semantic page inspection first, screenshots when needed.** The assistant normally receives **bounded, task-relevant page text, semantic/accessibility structure and element information**. Screenshots are available when visual layout, canvas, graphics or insufficient semantic structure make them useful, **not automatically on every action**. This is a data-minimizing preference rather than a claim that all pages are fully accessible, that a snapshot is a trusted instruction source, or that snapshots and screenshots are inherently free of secrets. Exact budgets, redaction, element targeting and fallback rules remain open.

**Q16=A — confirm every high-impact external effect.** Browsing, inspecting, navigating and ordinary form preparation may proceed without confirmation for each low-risk interaction; **each externally consequential high-impact action** requires explicit owner approval *before* committing it. Examples include paying or purchasing, actually sending a message, deleting data, and modifying user permissions. The confirmation is scoped to that specific intended action rather than a blanket approval for a whole workflow. Page contents, a button label, the presence of a logged-in browser, device pairing or an MCP bearer credential do not themselves constitute that owner confirmation. The exact action classifier, review payload, confirmation mechanism and replay resistance remain unsettled; cannot claim independent cryptographic human presence merely from a confirmed MCP tool call.

**Trade-offs:** a fixed idle duration balances multi-step reuse with Agent resources; headless-first supports unattended operation without forcing a GUI; semantic-first cuts unnecessary screenshots while retaining visual fallbacks; per-high-impact-action confirmation slows consequential workflows deliberately to avoid granting ambient authority to untrusted webpages. These choices do not add a general desktop-control surface.

**Follow-on decision:** [ADR-0025](./0025-atomic-browser-actions-and-receipts.md) selects atomic curated browser tools, semantic-first uniquely resolved element targets, device-local upload/download boundaries, and Agent-local Operation IDs/Receipts for potentially effectful browser actions. Browser-level execution is not website-side success.

**Follow-on decision (round 6):** [ADR-0026](./0026-browser-capabilities-tab-and-approval-scope.md) fixes one-use confirmation scoped to the intended device, session, tab, action and material target; changed targets require a new approval. Safe-state Profile clearing and stable tab identity are also accepted.

**Follow-on decision (round 7):** [ADR-0027](./0027-browser-tools-visual-consent-and-recovery.md) confirms semantic-first inspection with constrained current-tab screenshot fallback, and a prepare → owner confirm → execute path that refuses high-impact execution if the specific authorization cannot be reliably validated.

**Unsettled:** concrete tool/element schemas; screenshot/page-data privacy bounds and freshness proofs; local-path authorization and transfer cleanup; receipt details, approval transport/consumption and ambiguous website outcomes; browser download trust, lock-ownership recovery implementation and platform rollout acceptance. No feature code, new issues/tickets, CI, configuration or production deployment is authorized by this document.
