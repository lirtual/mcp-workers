# ADR-0023 — On-demand browser runtime, exclusive local profile, and interruption policy

> **Windows Goal A round 4 (H22=A, H24=A; 2026-10-21):** Owner-closing the Agent-owned headed Chrome/Edge window terminates that automation session; do not automatically relaunch or replay operations, and preserve the independent Agent-owned browser Profile. On next action require new session creation and the existing process/Profile safety checks. Human/Agent control ownership is **volatile state inside the current Agent-local browser session**, survives temporary WSS loss while the Agent session lives, but is **not** placed in a new SQLite table or Worker/DO store. Existing durable Operation IDs/receipts preserve effects/Unknown Outcomes independently. After Agent restart never auto-reattach or pretend a prior ownership phase still controls an orphaned browser (H16); a safely created new session begins with its own state. See [round-four design and convergence](../BROWSER-ARCHITECTURE-REVIEW-20261020.md#grill-with-docs-fourth-round--h19h24-2026-10-21). Design only; no code/merge/deploy authorization.

> **Windows Goal A round 3 (H16=A, H17=A; 2026-10-21):** After Agent restart, never automatically attach to leftover Chrome/Edge or its Profile; positively establish owned process exit and safe Profile access before permitting a new browser session. Uncertain lock/ownership blocks startup without deleting browser state, receipts or unrelated Chrome/Edge processes or introducing CDP reconnect. If the interactive desktop locks during a session, stop new Agent browser page actions but do not immediately close solely for lock; keep the 30-minute idle rule and truthfully preserve bounded/Unknown effects. Safe unlock/recovery details remain open. [Round 3](../BROWSER-ARCHITECTURE-REVIEW-20261020.md#grill-with-docs-round-3--h12h18-2026-10-21). Docs only.

> **Windows Goal A round 2 (H9=A, H10=A; 2026-10-21):** On each new session require the current Windows user's effective **HTTP and HTTPS** default associations to agree on installed, launchable **Chrome or Edge**. If missing, different, unreadable or unsupported, report an error; never guess or silently fall back. Do not switch a live session on default changes. **At most one Agent-managed live automation browser session per paired device** even though each supported family has its own isolated Profile. Reuse the same Playwright backend, not a second launcher or service. [H5–H11 decision](../BROWSER-ARCHITECTURE-REVIEW-20261020.md#windows-browser-handoff-and-default-selection--new-grill-with-docs-round-1-2026-10-21). This remains design-only.

> **Windows-only amendment, 2026-10-21 (new Grill With Docs H3=A):** On a new native Windows automation session, resolve the current user's **default Chrome or Edge** and use the appropriate channel in the same Playwright backend. Do not switch a session in progress if the OS default changes. Keep separate Agent-owned private Chrome and Edge automation Profile directories, never daily personal browser Profiles. This is a scoped exception to historical Q11's single-Profile-per-device assumption, **not** permission for concurrent sessions or arbitrary named Profiles. Exact Windows app-association behavior and Profile ownership checks remain open. The old auto-provision-Chromium guidance is historical for Windows Goal A; no new downloader/runtime is selected. See [current Windows amendment](../BROWSER-ARCHITECTURE-REVIEW-20261020.md#windows-browser-handoff-and-default-selection--new-grill-with-docs-round-1-2026-10-21). Documentation-only.

Status: **accepted design choices (Grill With Docs round 3, 2026-10-20); documentation only; implementation and release not authorized**.

The Agent will **provision a Playwright-compatible Chromium on demand** when browser automation is first requested and a compatible browser is not already available (Q9=A). Browser downloads are Agent-local and pinned to the compatible Playwright runtime rather than following an arbitrary “latest” browser; OS-level prerequisites that cannot be satisfied without elevated permissions are reported clearly, **not silently installed with privilege escalation**. Bundling a complete Chromium distribution into every Agent release and relying exclusively on any installed personal Chrome/Edge are rejected. Exact trusted download/integrity handling, offline failure reporting, upgrade compatibility and installation locations remain unsettled.

**A persistent Automation Browser Profile permits at most one active Automation Browser Session at a time** (Q10=A). A single session may use multiple tabs. Multiple simultaneous browser processes must not open the same profile; there is no new general-purpose job scheduler implied. How conflicting start requests, profile locks or unexpected browser exits are presented and recovered remains open.

**Initially, each paired device has one dedicated Automation Browser Profile** (Q11=A). It is separate from the owner's existing personal profiles and retains local sign-in data between sessions unless the owner explicitly clears it. Multiple named automation profiles and per-website profile creation are deferred rather than secretly emulated. Clearing stored identity data is distinct from closing a browser session; its precise safely-idle preconditions remain open.

**Caller transport disconnection does not immediately close a running local browser session** (Q12=A). It remains eligible for Agent-local idle-timeout cleanup; after reconnection, clients must query actual session/action status rather than replaying a click, form submission, or other possible side effect. An explicit device revocation **must deny further server-side authorization and dispatch**, and when possible asks the connected Agent to stop owned automation sessions. A disconnected, offline, or compromised Agent cannot be claimed to have stopped or to have cleaned its profile. Profile data is not implicitly deleted by revocation, and an Agent that is not running cannot be guaranteed to enforce an idle cleanup timer.

**Why:** on-demand provisioning keeps regular Agent packages small while requiring honest dependency checks; single-profile exclusivity avoids file/identity collisions and reduces unnecessary multi-account complexity; retaining sessions across transient network loss supports multi-step workflows without creating accidental repeated external actions. Revocation's cloud-side authority is stronger than its best-effort effect on already-running local processes.

**Follow-on decision:** [ADR-0024](./0024-browser-observation-and-confirmation.md) accepts a 30-minute idle threshold, headless-first operation with optional headed mode, semantic-first page inspection with on-demand screenshots, and explicit confirmation for each high-impact external effect.

**Follow-on decision (round 8):** [ADR-0028](./0028-browser-data-files-provenance-platform-acceptance.md) requires trusted, compatible and verifiably sourced on-demand Chromium and separate real Linux/WSL2/native Windows acceptance, without choosing a distribution-verification mechanism or deployment pipeline.

**Unsettled:** exact idle activity accounting and timer races, browser-action error and receipt contracts, consent mechanism and classification edge cases, cleanup/profile reset implementation, session lock checks, browser artifact integrity metadata, per-platform acceptance evidence format and release rollout. This document creates no runtime changes, new MCP tools, new Worker, issues or tickets.
