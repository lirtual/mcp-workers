## Decision: one device-local code, owner approval entirely inside authenticated MCP

1. **Device starts pending, not authorized.** A new Agent locally generates a distinct Ed25519 keypair and a cryptographically uniform **10-character Base32 (50-bit) pending pairing code**, valid for **at most ten minutes and once**. The private key remains owner-only on that host. The Agent posts an Ed25519-signed, domain-separated registration of the exact public key, code verifier, device label, grant type and **`pairing_protocol: "single-code-v1"` marker bound into that signature** to the existing bounded bootstrap endpoint. New Worker rejects obsolete old-protocol registration signatures. A stored old pending record without this signed protocol marker must not be silently upgraded to MCP-only approval, even if no old challenge had yet been generated. Pending registration grants **no** file/Shell/WSS authority.
2. **One manual input: code into MCP.** The owner supplies that code to **Portal Bearer-authenticated** `pairing_lookup({code})`. Lookup returns pending name, immutable public-key fingerprint, grant type, expiry and an opaque `pairing_id`; it **does not approve or issue a device ID**. No local fingerprint comparison, second 12-character challenge, or second copy/paste into the Agent terminal is required. Advanced fingerprint diagnostics remain optional.
3. **Explicit authenticated approval, not lookup side effects.** A **separate, deliberate** MCP `pairing_approve({pairing_id,expected_fingerprint,expected_grant_type})` action confirms the same immutable pending record, including its mode/expiry. The owner must explicitly instruct/approve this action; a read-only lookup, installation, background polling or unrelated tool invocation cannot cause approval. The DO atomically consumes that pending request and records one authorization for exactly that public key and grant type. Reject expired, already consumed, guessed, altered, substituted, cross-owner and competing approvals. An MCP account token alone is not a device private key.
4. **Agent completes automatically without a human-entered challenge.** The waiting Agent proves possession of the **same registered private key** over authenticated HTTPS using a fresh server nonce or comparably replay-safe signed, domain-separated claim; the DO returns its approved opaque `device_id` bound to that key. A lost response can be recovered only by signing another **fresh session nonce** with the same key and retrieving the same already-approved device ID, never by creating a new grant, changing mode or rotating identity. Reuse existing `/agent/session/challenge` and `/agent/session/recover`; the old `/agent/pair/complete`, DO `/prepare` and `/complete`, and MCP `pairing_prepare` routes are removed, **not** alternative pairing authorities. No second service, index or database. Do not expose the Portal Bearer to the Agent or public bootstrap. The Agent may then establish WSS with a **separate fresh signed session nonce**. This internal cryptographic nonce is **not a user-entered pairing challenge**.
5. **No implicit elevation.** MCP review/approval creates a device identity only; it does not authorize Shell/write. Each command still requires an explicit `device_id`, server-side current grant, signed authenticated WSS and existing operation authorization/receipt safeguards. Per-device removal/revocation must invalidate future connections and dispatches. Re-enrollment is fresh owner approval, never automatic restoration; permanent/temporary identity separation and fixed temporary **24-hour grant expiry** remain intact.

## Deliberate trust trade-off

Portal Bearer proves **possession of an MCP credential**, not physical-human presence. Removing the independent local-terminal confirmation **permits an authenticated MCP actor/compromised client or tool-call prompt injection to approve a malicious pending device**. A code intercepted by itself cannot approve or impersonate the device: it lacks MCP authorization and the Ed25519 private key. However, a stolen code *combined with* the authorized MCP approval capability may redirect the owner's attention to the wrong pending host, and a malicious MCP actor may approve its own pending key without stealing another code. UI confirmations/prompt requests are useful but **not cryptographic independent human proof**. This residual risk is **explicitly accepted for the owner's single-user deployment**; do not claim cryptographic human confirmation or equivalent security to the old two-code protocol.

The narrow replacement remains one owner-scoped DO and the existing Portal bearer, bounded pending storage, key proof, rate limiting, expiration, existing WSS session authentication and authorized operations. **Do not add OAuth, a new dashboard, another service/DO/database, a background enrollment job, or another code.**

## Minimal migration and acceptance gate

- Update MCP contracts from lookup/prepare to **lookup/approve** and update Agent bootstrap from manual local challenge entry to **key-authenticated automatic approval claim**. Use one atomic pending-to-approved transition; maintain compatibility/clear failure for in-flight **old two-code pending enrollments** without silently authorizing them. A pending item may expire and require the owner to restart enrollment; **existing approved devices and their signed WSS sessions must remain valid** during deployment. Do not reinterpret legacy challenge signatures as new approval.
- New tests MUST cover missing/wrong MCP Bearer, lookup-only/no side effects, wrong fingerprint/pairing ID/mode, invalid/guessed/expired/replayed codes, duplicate/racing approval, false approval via autonomous calls, wrong-key or unsigned automatic claim, claim replay, uncertain/lost response recovery with same key, no accidental grant/key rotation, revoked/expired identity, signed WSS authentication and unchanged readonly operation scope.
- Conduct a **new explicitly owner-reviewed nonproduction real-client pairing** and device proof/reconnect/remote nonsensitive read. Old #47/#50 closed evidence is historical for the superseded protocol, not acceptance of single-code. Do not merge or deploy new protocol, alter production/v1 or modify an existing paired test device without separate authorization. #57 remains the independent single-device real 48-hour gate.
