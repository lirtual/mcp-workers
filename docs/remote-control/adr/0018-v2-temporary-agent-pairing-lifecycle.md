## Context and decision history

The owner initially chose **Q1=C** (temporary identity revoked on voluntary Agent exit) and **Q2=A** (keep existing independent two-code pairing). On 2026-10-17, the owner explicitly **replaced Q1=C with a simpler fixed 24-hour temporary pairing authorization**. The exit-coupled model, authenticated self-revoke endpoint, offline grace-period policy and failed-exit recovery design are therefore **withdrawn, not outstanding requirements**. Q2=A's **two-code** confirmation was superseded by the owner's **one-code MCP approval** decision on 2026-10-18; the 24-hour grant decision remains unchanged.

Current v2 Draft PR #58 has `install-v2.mjs --foreground` without creating a systemd unit, but it uses a normal persistent approved identity and does not distinguish a short-lived authorized identity. The following is a **design target**, not a description of deployed behavior.

## Accepted owner decisions

1. **24-hour, nonrenewable temporary authorization.** A newly approved *temporary* device identity is valid for exactly **24 hours from the server's successful atomic pairing approval**, not from pending pairing-code creation, installer start, first WSS connection, or last activity. Define `expires_at = approved_at + 86_400_000 ms` using the server clock; the approved type is permanent or temporary. Reconnects, reads and writes **do not refresh** this deadline. Existing permanent device identities have no such temporary expiry.
2. **Owner-approved one-code pairing (supersedes Q2=A two-code workflow).** Keep the locally shown 10-character pending code (10-minute, one-use), authenticated MCP **read-only** `pairing_lookup` followed by **explicit mutating** `pairing_approve` for the exact pending key/mode. Agent automatically proves possession of its Ed25519 private key to claim the approved ID; fresh signed WSS session nonce remains mandatory. **No second challenge typed in the device terminal.** Only the approved temporary *device grant* lasts 24 hours. Portal Bearer/MCP approval is not independent human-presence proof; this is an explicitly accepted single-user trust trade-off.
3. **Authorization expires on server enforcement, regardless of Agent state.** Starting at `now >= expires_at`, new signed WSS sessions, identity recovery, device routing, queued/in-flight dispatch **not yet admitted**, and any other protected operation must fail closed. The DO must revalidate `expires_at` on each authorization/dispatch, including for a socket opened before expiry and after Hibernation. Socket closure is best-effort; *permission denial*, not instant physical close, is the security promise. `list_devices` excludes expired temporary grants, or makes them unselectable if listing must momentarily show them before cleanup.
4. **No exit-coupled revoke or offline countdown.** Closing the foreground Agent, SIGINT/SIGTERM, network loss, WSL suspend, process crash or power loss simply makes the device unavailable. It may reconnect **only before the original 24-hour deadline**. Closing early does **not** promise immediate deletion; the owner can use existing authenticated `revoke_device` to terminate authorization early. No new Agent self-revoke endpoint, 15-minute disconnect grace, device heartbeat-based TTL, DO alarm or periodic worker scheduler.
5. **Lazy removal rather than permanent tombstone.** Expired temporary approvals and their outstanding session nonce/epoch are removed **on next relevant DO access**, using the same deletion-based authorization model as ADR-0017. An idle, expired record may physically remain in storage until the next access, but can never authorize work after expiration. Admission and active-device capacity accounting must disregard/clean expired grants; repeated short-lived pairings must not exhaust the existing 64-active-device limit. Revoke and expiry race handling must remain fail-closed.
6. **No new managed-operation semantics.** Existing bounded processes retain the **60-minute maximum lifetime**, Agent-owned stop/close semantics and Agent-local `operation_id` receipts. Expiration prevents *new* dispatch; it does **not** retroactively undo a file write or guarantee instant termination of a process already started before expiry. A process may run past the authorization expiry within its original 60-minute command deadline, and uncertain outcomes remain `timeout_unknown` until reconciled, never blindly replayed.
7. **No additional system or secret.** Reuse the owner-scoped SQLite Durable Object and Node Agent, existing local-key protection and Portal review. A temporary mode must be explicit and must not accidentally convert the regular permanent identity into an expiring one. Reusing existing foreground runtime is preferred; isolated temporary key/ID storage (distinct from normal systemd identity) is a narrow implementation detail, not a new database/identity service. No extra OAuth, D1/KV/R2, broker, scheduler or CI workflow. V1 production remains unchanged.

## Technical seams and verification

- In Draft PR #58, `registerPending`, `completeLocalConfirmation`, `issueSessionChallenge`, `authorizeSession`, `acceptAuthenticatedSocket`, `listApprovedDevices` and each DO remote operation dispatch must agree on the same server-side `expires_at`. Updated expiry admission and bounded cleanup are implemented in the stacked Draft #79; the original #58 source is historical.
- Avoid conflating `pending_pairing.expires_at` (10-minute code window) with `device.expires_at` (24-hour approved-grant window). Fresh internal WSS nonce signatures and connection-epoch checks remain binding even before expiry.
- Enforce expiry at grant-sensitive decision points; never rely on an Agent-local clock, WSS close event, auto-pong, Hibernation callback, timed background cleanup or a list result to revoke authority. Lazy cleanup at a bounded read/list/registration is sufficient for physical storage; ensure capacity checks remain correct even when expired records exist.
- The server may become idle exactly at expiry; **do not claim the socket instantly closes at the 24-hour mark without a scheduler**. A subsequent use or connection must be denied, and list display must not present an expired grant as available.
- Verify tests for `approved_at + 24h - 1ms` / `+24h`, no renewal on reconnect, ordinary permanent device unaffected, old open WSS no dispatch after expiry, Hibernation wake, multiple temp devices and 64-cap with expired entries, deletion/re-pair and concurrent issuance, remote outage before/after expiry, Ctrl+C/SIGKILL/reconnect, and long-running operation receipts across the boundary.

## Consequences

- **Positive:** eliminates the need for self-revocation on process exit, missed-exit recovery, disconnect grace, a DO alarm and extra token/configuration management. Guarantees that after a fixed server-enforced 24 hours, no new remote operation can be authorized under the temporary identity.
- **Trade-off:** closing the temporary Agent early does *not* revoke the grant immediately; it remains authorized for re-connection until expiry or explicit owner revoke. Existing managed processes are not forcibly killed merely because the grant expired. Lazy physical removal means an expired row may remain at rest until a future request, without remaining authorized.
- **Scope:** accepted design and Draft-only code, with nonproduction validation recorded separately. No additional Preview or production deployment authorized by this document.
