# ADR-0030 — Conservative browser-effect gating, verified consent acceptance, and lean rollout evidence

> **Later phase-one acceptance clarification (2026-10-20):** [Minimal trusted-device PoC and revised release gates](../BROWSER-BACKEND-POC-20261020.md) separate **Goal A** (personal paired-device browser control) from **Goal B** (strictly isolated hostile execution). Prior network isolation P0 is deferred/unverified for Goal A, **not passed**; browser restrictions cannot constrain existing authorized Shell networking. Verified exact single-use owner approval remains required for high-impact external actions in both goals; without a real verifiable approval channel they stay disabled. The older all-subresource/OS egress gates below apply to Goal B and are not claimed by a basic CLI launch.


**Current backend selection:** See the [2026-10-20 architecture review](../BROWSER-ARCHITECTURE-REVIEW-20261020.md). The earlier CLI-first PoC has been superseded by **direct Playwright inside the existing Agent**. Under the owner's later P9 Goal A decision, strict SSRF/private-network egress isolation is **not a first-stage acceptance prerequisite**; it remains unverified and must not be claimed. High-impact one-use approval remains unverified.

## P9 — Owner-approved Goal A risk boundary (2026-10-21)

**Accepted scope amendment (owner explicitly selected Option A):** The first stage targets only the owner's personally paired **native Windows** device, its already-installed Chrome, one Agent-owned independent Automation Profile and existing Portal / signed WSS / SQLite machinery. The owner **accepts residual risk that untrusted public webpages, redirects, subresources, DNS changes or WebSockets can reach localhost and LAN resources accessible from this host**. This is an *informed scope choice*, not evidence of an SSRF sandbox or a waiver of any unrelated approval gate. Other operating systems, remote/untrusted hosts and production activation are NOT covered.

**Q45/Q49 scope clarification:** Earlier Q49's every-redirect/effective-IP fail-closed mandate remains the **strict network isolation Goal B policy**, not a condition to enter the newly accepted trusted-host Goal A. For Goal A, preserve the existing direct initial HTTP(S) URL deny rules as *best-effort hygiene* for local-looking user inputs; do not claim they block redirected/DNS-resolved internal traffic. The owner accepts incidental egress risk but has **not** broadly pre-authorized explicitly commanding internal administration, credentials/metadata access, or consequential actions. Continue to deny unsupported schemes and direct local/private initial URLs under the current Draft parser; later changes would need a distinct authorization/scope review. Record P5's real redirected loopback hit (`attempted=1, blocked=0, localHits=1`) as **NOT ISOLATED, RISK ACCEPTED FOR GOAL A**, never as a passing zero-hit test.

**Preserved interaction gate:** Q37/Q38/Q41/Q51 and one-use, action-and-target-specific verification remain in force for **high-impact or ambiguous website effects**. A device grant, a model-authored `approved: true`, an assistant's restatement of this Goal A risk acceptance, a tool annotation, or an `operation_id` is not sufficient approval. Even GET navigation may cause effects: no blanket classification of arbitrary public URLs as read-only. Keep click/fill/submit/download/upload/JS/CDP and other high-impact interactions out of the staged first five browser tools. Do not enable `browser_navigate` for unreviewed targets while the user-confirmation gate is unverified.

**Acceptance states, not conflated:** Network egress isolation = **not achieved and not required for this accepted Goal A threat model**; independent Profile/process ownership = validate/reuse already-passing real-device evidence; tool identity/receipts = reuse and regression-check; authentic action-specific user confirmation = **unverified**, must fail closed; MCP browser end-to-end over signed DO/WSS = **unverified**; installed immutable Windows release/rollback and explicit promotion approval = **pending**. A local PoC/CI pass does not enable a deployed browser tool.

**Complexity/stop rule:** No second Agent or Worker, proxy, firewall rule, DNS service, approval backend, confirmation portal, extra DB or automatic MCP protocol migration. Run only bounded tests on a disposable Agent identity/Profile and controlled non-account test pages; reuse P3/P5 unchanged evidence, retest only altered behavior. If reliable confirmation requires a new platform, return to the design decision rather than accumulating components. All existing PRs remain Draft; no merge/deploy/release/installed-Agent change/production enablement is authorized.

---

Status: **accepted design choices (Grill With Docs round 10, 2026-10-20); documentation only, no implementation, Tickets, merge or deployment authorization**.

**Q37=A — uncertain webpage interactions are not presumed low-impact.** A browser capability may run without high-impact approval only when its permitted operation is **positively established as low-impact** within the agreed safe scope. If a click, fill, keyboard action, navigation or page behavior might cause a material external effect and its impact cannot reliably be classified, the action **fails closed** pending a reliably verified, action-specific owner approval (or stays disabled if such approval is unavailable). A button's caption, website text, the page's claims, or an assistant's judgment alone is insufficient to designate an effectful action safe. Browser content cannot give itself authorization. This is a conservative eligibility rule, **not** a promise that arbitrary web code can be proven side-effect-free. The exact allowed low-impact interaction set, trust boundary for any classification data, and ambiguous-effect handling are still open; do not silently grant the whole generic `click`/`fill`/`keyboard` surface at the low-impact gate.

**Q38=A — real end-to-end acceptance before enabling high-impact confirmation.** Enabling any high-impact action requires actual acceptance evidence from a supported ChatGPT client through MCP and the existing Worker/Agent execution boundary: the intended user explicitly approves an **identified single-use proposed action**, the execution boundary reliably verifies that authorization for the same device, session, tab, operation and significant parameters/target, and changed, absent, reused or otherwise invalid approvals are rejected. Do **not** treat a conversational “yes,” the model's memory, MCP bearer possession, or untrusted page content alone as proof. If the existing client/transport cannot convey enforceable confirmation evidence, high-impact tools must **remain disabled**, consistent with Q27 and Q36; the design does not authorize inventing a new approval portal/service. The exact channel, actor authentication, proof format, issuance, expiry, atomic consumption, replay protection and E2E acceptance procedure remain to be resolved and must not be represented as already available.

**Q39=A — reuse the minimal Agent-local operation receipt lifecycle.** Browser effects use existing stable Operation IDs and Agent-local durable receipts for admission/execution state and ambiguous outcomes. Distinguish work not yet performed, in progress, known browser-level completion/failure and **Unknown Outcome** as applicable to the established receipt contract; **do not assume these phrases are newly approved field names or a new fixed enum**. On disconnect, use the existing status lookup/reconciliation path rather than replaying actions. Website-side success remains separately evidenced through read-only observation when feasible and cannot be guaranteed by a browser click receipt. Do not add a new transaction database, event-sourced website ledger, or cross-site exactly-once coordinator. Exact state names/transitions, restart semantics, receipt retention, and evidence-link data remain open.

**Q40=A — lightweight, platform-scoped real acceptance with evidence reuse.** Before enabling browser operations on a particular Linux, WSL2 or native Windows target, require relevant actual end-to-end evidence for browser launch, normal page interactions, local file read/write or transfer flows, disconnect/recovery, denial of sensitive or unauthorized operations, OS privilege boundaries, and Agent upgrade/rollback compatibility. Reuse already-passing evidence where the relevant code, protocol, target runtime and risk have not materially changed; repeat only affected validations. One platform's acceptance does not establish another's readiness and does not block independently accepted targets. macOS remains deferred. The detailed cases, pass/fail thresholds, release automation, artifact provenance evidence and product authorization to deploy are still open. This ADR is **not** permission to run CI, deploy or create Tickets.

**Rationale and complexity boundary:** conservative effect gating is safer than trusting website presentation; true end-to-end confirmation avoids relying on unverifiable conversational state; reuse of existing receipts avoids a second reliability subsystem; per-platform targeted checks avoid repeated unrelated testing and lockstep release. No new Worker, approval service, file manager, transaction coordinator or independent test platform is selected.

**Follow-on accepted decision (round 11, Q41=A):** The initial *candidate* low-impact surface is deliberately narrow: authorized browser session/tab **status/listing**, bounded **read-only semantic observation**, and **explicitly requested screenshots** subject to privacy controls. A specifically targeted navigation may be considered **only after** its destination and possible effects pass the conservative safety boundary: even navigation can trigger mutations. The general `click`, `fill`, `select` and `keyboard` primitives are **not** classified as low-impact merely by tool name, page label, model inference or presumed intent. If meaningful effects are not demonstrably within the permitted safe subset, fail closed, requiring enforceable single-use confirmation (or leaving that action disabled if confirmation is unavailable). Session/tab creation and closure, file operations, and even sensitive page reads need their own applicable authorization and should not be silently included by the examples above. No claims of automated safety proof for arbitrary webpages.

**Follow-on accepted decision (round 12, Q45=A):** Normal browser navigation is intended for **HTTP(S) webpages**; nonordinary executable/local schemes such as `javascript:` and `file:` are not automatically available navigation destinations. Localhost/loopback, link-local, cloud instance metadata, and other sensitive internal/admin targets must **not be treated as automatically low-impact** simply because an authenticated Agent can reach them; they require explicit owner authorization and a meaningful effect/target safety review. This is **not** a blanket ban on approved intranet administration or a per-site global allowlist. Even public-looking GET navigation can produce side effects. DNS resolution, redirects, rebindings, address classification, mixed-content and iframe/subresource behavior remain undecided and must not be assumed safely filtered by this statement. Unknown effect or target fails closed under Q37/Q41.

**Follow-on accepted decision (round 13, Q49=A):** The Q45 HTTP(S)/sensitive-target boundary must be **re-evaluated whenever a navigation changes its effective target**, including each redirect hop, a host change and relevant DNS resolution or resolved-address change. Reject navigation when a new scheme, network address or destination is not demonstrably authorized and safe; do not trust only the initial user-supplied URL or the first DNS resolution. Loopback, link-local, cloud metadata and sensitive internal/admin addresses remain outside the default low-impact grant even if reached indirectly. Do not establish a universal per-site website allowlist and do not claim all browser traffic is filtered merely by checking top-level navigation. Exact redirect interception, DNS rebinding protection, iframe/subresource requests, prefetch/service-worker behavior, TOCTOU resolution races and validation API still require evidence/design; no working enforcement is claimed.

**Unresolved / external proof:** real supported ChatGPT/MCP high-impact confirmation transport; exact network request coverage and redirect/DNS enforcement; safe interaction classifications; actual Agent receipt and privacy implementations; trusted Chromium provenance; real platform acceptance. The accepted policy does not authorize a browser feature, runtime test, Ticket, merge or deployment.

**Post-convergence source feasibility review (non-decision):** Existing ChatGPT UI confirmation / MCP elicitation capabilities have not been shown to carry independently verifiable one-use human-approval evidence into the present Agent, and the current Remote Control Worker exposes no browser-approval protocol. Do not reinterpret any accepted Q23/Q27/Q38/Q51 outcome as an implemented approval token. Separately, Playwright's usual route handler sees the initial redirect URL once, and Service Workers can escape ordinary route interception; the Q45/Q49 effective-target policy requires **actual browser-wide network tests** before it can be claimed enforced. If Playwright interception cannot cover this, any OS egress-control alternative is a **future owner decision**, not a silently approved new subsystem. See [post-convergence feasibility audit](../BROWSER-AUTOMATION-DESIGN.md#post-convergence-feasibility-audit--recommendations-not-new-decisions).
