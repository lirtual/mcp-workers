# ADR-0027 — Minimal browser tools, bounded visual fallback, and fail-closed recovery

Status: **accepted design choices (Grill With Docs round 7, 2026-10-20); documentation only, no implementation or release authorization**.

**Q25=A — compact, complete atomic tool inventory.** The initial curated browser MCP surface is organized around five single-purpose capability groups: browser-session **start/status/close**; tab **list/create/close**; page **navigate/semantic snapshot/screenshot**; interaction **click/fill/select/keyboard**; and file **local upload/download-result access**. This is the accepted *shape of the inventory*, not approval of exact tool names, signatures, counts or how a download is initiated versus how its result is retrieved. Do not convert the inventory to an unrestricted `browser_action` router, arbitrary page JavaScript, generic Playwright code execution or a second MCP server. Operations must still target the explicitly selected device, session and tab where applicable, and comply with the action confirmation and receipt requirements already agreed.

**Q26=A — constrained, fresh visual fallback.** Semantic/accessibility element targeting remains primary. A control that cannot be addressed unambiguously through that path may be targeted using **visual evidence from a fresh screenshot** of the explicitly selected tab, bound to the contemporaneous page state and intended on-screen target region. Do not click arbitrary guessed or stale coordinates; if the target/viewport/page has materially changed or cannot be safely matched, fail and re-observe rather than guessing. Visual fallback is not a privilege escalation, remote desktop capability or bypass of Q16/Q23 approval for high-impact actions. The precise page freshness signal, viewport change checks, output limits and target arguments remain open.

**Q27=A — prepare → owner confirm → execute, fail closed.** An operation with a high-impact external effect first produces a **non-executable proposed action** for specific owner review. The owner must explicitly approve that intended action through the ChatGPT-facing interaction. An Agent/Worker execution path must reliably validate that **one-use approval is bound to the same device, session, tab, operation, significant parameters and target** before effectful execution. If a supported ChatGPT client or MCP/Worker/Agent path cannot establish or carry valid confirmation, it must **refuse high-impact execution** instead of accepting model recollection, a webpage's instructions, or possession of the existing MCP Bearer token as a substitute. Exact approval transport, authority, expiry, issuance/consumption, race handling and replay prevention are **not** decided. This decision does not claim that today's ChatGPT/MCP runtime provides an independent cryptographic proof of a human's presence. Browser action receipts must not imply website-side transaction completion.

**Q28=A — verify before crash/lock recovery.** When the Agent restarts or a browser crashes, it checks whether an Agent-owned browser process still owns the dedicated automation Profile and whether any Operation ID has an unresolved outcome. It may re-open the browser only after positively determining that the previous process has exited, Profile access is safe, and outstanding operations have been reconciled sufficiently for that step. An unknown process/lock or uncertain action is reported as a conflict; it is **not** permission to forcibly delete lock data, erase the Profile, invent a new Profile, clear receipts or replay actions. Exact process ownership probes, lock formats, crash-loop prevention and recovery state reporting are open.

**Why:** a bounded, useful tool inventory avoids duplicate commands while remaining usable for everyday browser work; visual fallback covers Canvas and poorly accessible controls without arbitrary desktop interaction; the confirmation boundary is enforced by the system rather than the language model's recollection; and state-first recovery preserves session/profile integrity and the existing no-blind-retry contract.

**Follow-on decision (round 8):** [ADR-0028](./0028-browser-data-files-provenance-platform-acceptance.md) selects bounded, task-relevant page data with no ordinary credential extraction; on-demand screenshots without assuming automatic redaction; reuse of Agent filesystem authority and managed local downloads; verified trusted/compatible Chromium; and separately evidenced, staged Linux/WSL2/native Windows acceptance.

**Follow-on decision (round 9):** [ADR-0029](./0029-browser-results-outcomes-downloads-gated-release.md) requires separate Agent and website-effect status, seven-day default retention of unreferenced downloads, and refusal of any high-impact action without reliably checked one-use approval, while proven safe low-impact tools can be gated independently.

**Still open:** exact tool result schemas and download triggering; page freshness and numeric snapshot/screenshot/redaction limits; owner confirmation delivery/expiry/one-use consumption; execution receipt states and website-effect evidence; file-reference tracking/collisions; binary provenance metadata; platform acceptance and rollout. No code, new Issues/Tickets, CI, cloud, configuration or production change is authorized by this ADR.
