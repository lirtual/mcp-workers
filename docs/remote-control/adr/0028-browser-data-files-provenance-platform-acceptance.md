# ADR-0028 — Minimize browser data, reuse host file authority, verify browser provenance, accept platforms independently

Status: **accepted design choices (Grill With Docs round 8, 2026-10-20); documentation only, no implementation or release authorization**.

**Q29=A — task-relevant, bounded page output by default.** Browser MCP observation normally provides a compact, size-bounded selection of task-relevant text and semantic/accessibility structure, not a raw full DOM plus unconditional screenshots. Do not deliberately extract, serialize or log passwords, cookies, bearer tokens or other credential-bearing browser/profile data as ordinary page results. Screenshots are returned on demand and **may visibly contain sensitive information**; do not claim they are automatically safe, wholly redacted, or equivalent to semantic text output. Page content is untrusted data, not instructions. No website allowlist or separately administered permitted-site registry is introduced by this decision. The numeric result limits, sensitive-field recognition, screenshot redaction/handling, truncation semantics, and error reporting remain open.

**Q30=A — reuse the Agent's existing filesystem authority.** Browser upload requires an explicitly selected Agent-local file path and is bounded by the Agent process's ordinary OS account permissions plus the applicable existing Remote Control authorization; do not silently grant access to other files. Downloads go to a dedicated Agent-managed local directory and are subsequently read, moved or deleted via existing Remote Control file tools as applicable. Do not add a separate browser-only filesystem allowlist, extra authorization configuration, new file manager, or default bulk file tunneling through Worker/MCP. Directory permissions, file collisions, download retention, cleanup and oversized-file behavior remain open, as do the limits of the existing Remote Control file tool surface. Existing OS permissions are necessary, not a substitute for explicit path intent or browser action confirmation.

**Q31=A — fixed compatible Chromium with verifiable trusted provenance.** On-demand installation uses a browser build compatible with the selected Playwright runtime from a reviewed/trusted distribution source. Before trusting it, the Agent verifies origin/integrity using the authoritative provenance and verification data actually available for that artifact; do not invent an upstream checksum or claim a specific cryptographic guarantee that has not been established. If a required browser is absent offline, the source is untrusted, the artifact fails integrity verification or a compatible binary cannot be established, report the failure and do not silently switch to an unverified mirror, arbitrarily choose a newer build or execute suspect bytes. No independently managed Chromium distribution service is selected. Exact artifact selection, signature/digest source, rollback, cache and platform packaging contract remain open.

**Q32=A — independent real-device acceptance with staged release per platform.** Linux, WSL2 (a Linux runtime), and native Windows each need separate relevant acceptance evidence for supported browser startup, common interactions, local file handling, interruption/recovery, authorization boundaries and Agent upgrade compatibility before enabling their browser tools in production. An accepted unchanged behavior may reuse relevant earlier evidence; do not repeat unrelated already-passing tests without a changed dependency or risk. One platform may progress on its own rather than forcing all targets to finish together. Platform selection does **not** assert that browser automation is currently implemented or that native Windows support is production-ready. macOS remains later. The release stages, CI matrix, go/no-go evidence format and deployment automation are unresolved; this ADR does not approve deployment or create Tickets.

**Why:** bounded output reduces data exposure and token/transport costs without rigid site lists; reusing host-level file authority avoids duplicate configuration and file management; fixed verified binaries reduce supply-chain and compatibility risks; independent platform acceptance avoids premature claims or unnecessary cross-platform release blocking.

**Still open:** concrete output budgets and redaction behavior; download-path permissions, collisions and retention; verifiable upstream provenance and offline/error details; exact browser tool input/result schemas; owner confirmation transport and authorization checks; action receipt and website-outcome evidence; actual Linux/WSL2/Windows test matrix, rollout stages and release gates; future separately authorized personal-browser attachment.
