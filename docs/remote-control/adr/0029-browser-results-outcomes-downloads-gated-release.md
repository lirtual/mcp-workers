# ADR-0029 — Compact browser results, separate effect evidence, bounded downloads, and staged safe capability

Status: **accepted design choices (Grill With Docs round 9, 2026-10-20); documentation only; implementation and release not authorized**.

**Q33=A — common compact, structured browser tool result.** Every curated browser tool should return a small, consistent result envelope identifying the targeted **device** and **browser session**, and a **Tab ID** when the operation addresses a tab. The result distinguishes execution status, machine-readable error identity, and only the bounded operation-specific data needed by the caller. Potentially effectful operations also carry their stable **Operation ID** for Agent-local receipt lookup. Text/screenshot payloads are not always included and must report when the supplied result was truncated. This is a shared *contract principle*, not approval of exact field names, JSON schema, screenshot transport, error codes, or fixed byte/token quotas; do not pass raw Playwright objects or rely on free-form prose alone.

**Q34=A — browser execution evidence is separate from website-side outcomes.** An Agent-local **Browser Action Receipt** records what is known about execution or failure of a potentially effectful action, including an explicit **unknown** outcome when interrupted or unverifiable. Evidence that the website actually completed an effect (for example, an order saved or a message sent) must come from **separate read-only observation or relevant service evidence**, when available, and must not be inferred from a successfully dispatched click. A timeout or unknown effect is **not** permission to automatically retry, including after reconnection. Do not claim exactly-once website execution, universal verification or a terminal “website success” when such evidence is absent. Precise receipt/status enum, reconciliation API, evidence lifecycle and retention remain open.

**Q35=A — clean unreferenced managed downloads after seven days.** Browser downloads remain on the Agent in its dedicated, managed download area, available for explicit owner access and deletion through existing Remote Control file capabilities. **Seven days** is the default retention period before automatic cleanup of **unreferenced** downloads; do not remove a file still referenced by an active session or an unresolved/unknown-outcome operation. Scope cleanup **only to the browser-managed download directory**, not arbitrary host files or the retained browser Profile. How references are tracked, whether an explicit owner transfer constitutes reference release, cleanup concurrency, paths, collisions, and error handling remain open.

**Q36=A — independently release permitted low-impact operations while unverified high-impact actions remain disabled.** Subject to actual platform-specific acceptance and release authorization, safely classified navigation, reads and permitted low-impact interaction may be enabled before the one-use high-impact approval transport is proven. A **High-Impact Browser Action for which valid single-use owner approval cannot be reliably conveyed and checked by the execution boundary must be refused**, not downgraded to ordinary click. This is a **capability gate**, not an exception to Q16/Q23/Q27 confirmation requirements, and not automatic permission to deploy anything. A page's semantics, button caption, domain or model judgment alone cannot establish that a generic click/fill is low-impact. The operation-effect classifier, conservative default for uncertain actions, confirmation transport and safe-enabled subset remain open.

**Why and alternatives:** common structured results limit brittle client parsing and needless page data; separate browser and website evidence prevents false “success” claims; bounded managed-download cleanup avoids indefinite storage without destroying pending work; capability-level gating avoids a single unavailable high-impact approval capability blocking proven safe browser operations while retaining a fail-closed boundary.

**Follow-on decision (round 10):** [ADR-0030](./0030-browser-conservative-gating-consent-evidence-acceptance.md) selects conservative no-approval action classification (unknown consequence fails closed), an actual end-to-end proof gate for single-use high-impact confirmations, reuse of existing Agent-local receipt states, and lean platform-specific acceptance with reuse of unchanged relevant evidence. These are design constraints, not verified functionality.

**Follow-on accepted decisions (round 11):** Q42=A keeps browser tool results and arguments small and consistent without a generic dispatcher ([ADR-0025](./0025-atomic-browser-actions-and-receipts.md)); Q43=A sets an initial approximately 8,000-character semantic snapshot budget and on-demand single screenshots ([ADR-0028](./0028-browser-data-files-provenance-platform-acceptance.md)); Q44=A **reuses only minimal Agent-local session and Operation Receipt metadata** to establish whether a managed download is still referenced. A managed file is cleanup-eligible only when it is **positively known unreferenced** and older than the previously agreed seven days; retain or report uncertainty if an active session, unresolved operation or uncertain ownership may still depend on it. Owner-initiated access, moving or deletion continues through existing Remote Control file operations. Never scan, delete or create a new file-manager index for unrelated host data, and do not introduce a separate download database or service solely for retention. Whether the existing metadata suffices, exact reference capture, collisions, cleanup races and interrupted deletions require design/validation; do **not** claim those features already exist.

**Still open:** exact low-impact eligibility and typed input/result schema; precise browser receipt and website-effect evidence; download reference detection, race-free cleanup/collision handling and filesystem state when metadata is incomplete; supported verified approval transport, validity and consumption; browser binary provenance, platform acceptance matrix and separately authorized rollout. This ADR authorizes no source code, development Issue/Ticket, CI/secret change, Worker deploy or merge.
