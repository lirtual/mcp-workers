# ADR-0022 — Native macOS Agent without weakening owned-process safety

**Status:** Accepted (2026-11-01); **implemented and shipped (2026-11-03)** under [Spec #657](https://github.com/lirtual/mcp-workers/issues/657). The [immutable public Agent v0.1.51 prerelease](https://github.com/lirtual/remote-control-agent/releases/tag/v0.1.51), five-platform native CI and the existing [RCA Worker production release](https://github.com/lirtual/mcp-workers/actions/runs/41557653717) are verified. Source: macOS Agent Grill With Docs, Q1–Q15, especially Q2/Q5/Q6/Q14. This extends the original Linux-first ADR-0001 platform scope without discarding Linux or Windows safety mechanisms.

RCA supports personal **macOS 15+ ARM64 and Intel x64** through its existing bundled **Node.js 24 Agent**, pairing, signed WSS, file/search/Shell, SQLite operation receipts and one reviewed release channel. **Owned Managed Sessions on macOS use a small native Darwin process Supervisor**, kept within the existing Agent execution/receipt boundary, rather than sharing Linux-only pidfd/subreaper code or relying on unchecked Node.js/POSIX numeric-PID killing. Permanent operation is a **non-root, login-scoped user LaunchAgent**; temporary operation is foreground with the original fixed 24-hour grant. No privileged LaunchDaemon or parallel process manager is allowed.

**Trade-off:** A platform-specific Mach-O helper and native tests are necessary to respect the established **owned-process-only** stop/timeout/revocation invariant. Darwin cannot provide the identical Linux pidfd guarantee; if an owned process/group cannot still be proven safe to signal, the Agent **fails closed**, preserves **Unknown** outcomes and does not target arbitrary PIDs or claim universal descendant cleanup. If native host acceptance cannot demonstrate a safe bounded lifecycle, macOS support is **blocked** rather than relaxed. Windows Job Object and Linux pidfd paths remain unchanged.

**Implementation and acceptance evidence:** The native Darwin owned-group Supervisor and non-root LaunchAgent reuse the existing Agent/receipt and signed-WSS boundaries; the original permanent ARM64 Mac passed its [v0.1.51 remote-upgrade / identity / reconnect E2E](https://github.com/lirtual/mcp-workers/issues/660#issuecomment-6593124915). Physical Intel, lifecycle/fault-injection, independent fresh final public first-install, TCC negative/context differential, and old SQLite row-level continuity remain scoped **Waived** rather than Pass. The real TCC `read_file` timeout is **Unknown**. Finder first-launch of the quarantined Supervisor was genuinely **Blocked by macOS** (safe-denial Pass), not granted execution. No promise is made to stop descendants that deliberately leave the managed process group.

**Separate reversible distribution decision:** The initial macOS Release is **not required to be Developer ID signed/notarized** (Q7=B); this must be disclosed, requires individually reviewed immutable assets and real Gatekeeper tests, allows only supported **manual owner** OS approval, and can block launch. It never authorizes automated Gatekeeper bypass. It is not a reason to redesign the Agent, introduce a new Worker or require separate credentials. This ADR alone did not authorize implementation, PR merge, publication, host installation, or production; the separate approvals and resulting evidence are recorded in Spec #657.
