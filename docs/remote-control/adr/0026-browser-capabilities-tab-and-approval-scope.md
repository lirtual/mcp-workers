# ADR-0026 — Complete common browser workflows with stable tabs and scoped approval

Status: **accepted design choices (Grill With Docs round 6, 2026-10-20); documentation only; implementation and release not authorized**.

**Q21=A — cover complete common browser workflows through atomic capabilities in the initial scope.** The first browser automation capability must cover the ordinary end-to-end workflow categories: browser session lifecycle, tab lifecycle, navigation, page observation, click and form fill, selection, keyboard interaction, screenshot, and browser-scoped upload/download. Each action remains a curated single-purpose tool consistent with [ADR-0025](./0025-atomic-browser-actions-and-receipts.md); this does **not** authorize arbitrary JavaScript, direct CDP/Playwright passthrough, network interception or the entire Playwright API. Concrete tool names, exact parameter contracts and any elimination of overlapping operations remain undecided; scope does not imply that every possible web interaction can be completed.

**Q22=A — stable, explicitly targeted tab identity.** Each managed browser tab has a stable **Tab ID** associated with its exact **device_id** and **session_id**. Tab actions must identify their intended tab where one is required; navigation in that tab does not change its ID. Closing a tab invalidates that ID: reusing a closed tab's identity must not silently target another tab. Tab index, title and URL are **not** substitutes for identity because they can change or collide. Generation, discovery, identity validity across Agent restarts, tab-created events, and error conventions remain unsettled.

**Q23=A — one-use confirmation bound to one consequential action.** Before each High-Impact Browser Action, the owner reviews and explicitly confirms an authorization bound to the particular device, browser session, tab, intended action and significant arguments/target. The approval is consumable for **that one intended execution only**, not a blanket workflow grant; a material change of the target or execution inputs invalidates its applicability and requires a new confirmation. The exact confirmation transport, comparison criteria, expiry, replay prevention and audit mechanism remain to be designed. A page prompt, MCP credential possession or a previous conversation approval is not automatically independent proof of human intent. This decision does not weaken the existing requirement to retain Operation IDs/Receipts for effectful actions, nor does it claim the website completed the external effect.

**Q24=A — owner-requested Profile clearing only in a provably safe state.** The Automation Browser Profile, including retained sign-in data, is cleared only on explicit owner request when there is **no active browser session and no unresolved or unknown-outcome operation** whose state could be affected. If that safe state cannot be established, reject clearing and explain the obstacle rather than forcibly close the browser or discard local operation evidence. Closing an Automation Browser Session, expiry of its idle timer or revocation of cloud device authority does **not** by itself clear the Profile. Exact clearing API, race-free checks, on-disk deletion/cleanup guarantees and interrupted-clear recovery remain open.

**Why:** a complete ordinary workflow without arbitrary script execution makes the MCP genuinely useful while preserving a reviewed authorization surface; stable tab identity prevents wrong-target operations; one-use approvals prevent an authorization from drifting between different consequential effects; safe Profile clearing protects retained identity and unknown outcomes without adding a new account-management service.

**Follow-on decision (round 7):** [ADR-0027](./0027-browser-tools-visual-consent-and-recovery.md) selects the compact first-release atomic tool inventory by capability, current-tab visual fallback where semantic targeting is insufficient, prepare → confirm → execute with failure closed when authorization cannot be verified, and state-checked rather than destructive crash/lock recovery.

**Follow-on decision (round 9):** [ADR-0029](./0029-browser-results-outcomes-downloads-gated-release.md) distinguishes the intended complete common workflow capability from a potentially narrower initially enabled low-impact subset when reliable high-impact approval is unavailable. This does not authorize treating a generic click as low-impact by default.

**Follow-on decision (round 10):** [ADR-0030](./0030-browser-conservative-gating-consent-evidence-acceptance.md) requires unknown webpage action effects to fail closed without an actually verified approval, and sets a lean real E2E authorization/per-platform acceptance gate rather than a new approval service or all-platform lockstep release.

**Follow-on accepted decision (round 13, Q51=A):** Only **if** a supported ChatGPT→MCP→Worker→Agent channel can reliably establish Verified Browser Approval, a proposed High-Impact Browser Action receives an **explicitly short-lived and one-use** authorization bound to the exact owner-approved device/session/tab, action, significant target and parameters. Expired, consumed/replayed, materially changed, mismatched or no-longer-provable authorization **cannot** execute; it requires fresh specific confirmation. Reconnection, Agent restart and an unknown receipt must never refresh an expired/consumed approval or trigger automatic replay. Reuse current device authentication and Agent-local operation identities; do not introduce an independent approval service or universal workflow grant by default. No specific TTL, proof format, storage, token issuance/atomic consumption mechanism or independent human-attestation capability is asserted available; these remain feasibility and contract requirements. If reliable verification is absent, high-impact effects remain disabled.

**Still open / external proof:** actually supported end-to-end owner approval channel, its safe expiry and atomic one-use enforcement, precise tool/status schemas, safe interaction subset and network checks, tab/restart/lock ownership, screenshot freshness, file handling, trusted Chromium and per-platform evidence. This ADR does not authorize code, Tickets, CI/configuration, merge or production changes.
