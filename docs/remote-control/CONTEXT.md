# Remote Control MCP — context

Remote Control is a single-owner MCP Worker backed by a signed per-device WebSocket relay and native Agent. The Worker owns authenticated ingress, device grants and routing; the bundled Agent under `apps/remote-control-mcp-worker/agent` executes authorized local file, search, Shell and Agent-owned managed-session operations on Windows, Linux/WSL2 or macOS. Browser GUI operations are owned by the independent Browser MCP and are not RCA tools.

**Identity and permission**

- Browser pairing (#1018) authenticates the fixed Clerk Owner with a short-lived standard Session JWT, then requires explicit review and approval of the pending identity and grant type. Login is not device authority. Clerk failure is scoped to browser pairing. The canonical installer (v0.1.60 or later) prints the browser link with a fragment and the local key fingerprint. Local grant selection and signed identity claim are unchanged. Old MCP pairing lookup/approval were retired from discovery and production execution in #1018; its acceptance and explicit waivers are recorded in the closed Spec. Existing valid identities reconnect unchanged; use the current official installer for new pairing/re-pair, including recovery from a revoked identity on an older package. Noncanonical endpoints must never forward pairing data to the canonical origin; no alternate production pairing ingress is maintained.
- Pairing requires an explicit Owner grant tied to a device identity. A temporary grant is bounded and nonrenewable; permanent grants retain independent revocation and online/idle rules. Neither installation nor a valid MCP token alone grants a device.
- GitHub-hosted temporary Session devices require independent Workflow physical Attempt authorization; an approved personal device is not a substitute for a Session grant.
- The Agent's OS account and host permission model remain authoritative. Native process ownership, session stops, device revocation and receipts must fail closed when identity cannot be verified.

**Effects and recovery**

- Mutating requests have stable operation identities and local receipts. An Unknown response is not permission to retry an external effect; reconcile the original operation before continuing.
- Secure Input (#1039) binds one-time delivery to the exact approved target and live device/Workflow Attempt, outside generic command arguments and receipt digests. Task stdin delivery irreversibly suppresses all captured output for that session before writing, while continuing to drain its pipes; other sessions retain ordinary output. The selected process itself must be trusted not to disclose the value through its own files, network, or other side effects. Owner-local hidden terminal input must restore the original console state on ordinary return and Ctrl+C cancellation without submitting partial input; abrupt process termination that cannot execute cleanup is outside that guarantee.
- Cloudflare Secure Input resolves the same physical Worker script for preflight and writing (named environments use Wrangler's `worker-environment` convention). Its private per-invocation configuration contains only the bound Account ID, never the input or credentials, and is removed at process completion; unrelated project config and `.env` do not select the target. Provider inputs that the native CLI would trim (Wrangler trailing ECMAScript whitespace; GitHub CLI trailing CR/LF) are rejected rather than silently altered. Wrangler whoami authenticates user identities by email and Account API Token identities by the verified matching Account ID (`account:<id>`), not by token value or digest. Rotating credentials for the same account does not change that account principal; authorization and target access are checked again before writing. Wrangler deploy-mode secret updates require the latest Worker version to be deployed; a pending version is rejected by the provider, not automatically deployed by RCA. Actual Provider acceptance remains separate from local CLI evidence.
- A cancellation or Worker acknowledgment does not itself prove physical job or subprocess termination. Distinguish Agent-managed session, actual OS process, GitHub job and temporary device cleanup.
- Installation, Agent Release publication, Worker publication, native upgrade, pairing and production acceptance are separate operations. An upgrade must preserve identity and historical receipts; an unknown or unsafe upgrade must not silently re-pair or discard history.
- Distributing public installers does not authorize pairing. Artifact integrity checks are not independent proof of production deployment or physical-device acceptance.

**Accepted lifecycle design — G1 non-production implementation in progress (#1035)**

- [Spec #1035](https://github.com/lirtual/mcp-workers/issues/1035) unifies RCA public management across the native platform executors. The Owner superseded the prior macOS Node delivery scope on 2026-11-25: [Spec #914](https://github.com/lirtual/mcp-workers/issues/914#issuecomment-7162906800) now requires macOS Rust-only parity and retirement before final macOS delivery. Remove fixed human confirmation words, not identity or high-risk authorization. Pairing follows #1018 independent acceptance and retirement gates.
- Implementation is integrated on Draft #1042 with #1038 as a source of verified lifecycle behavior. Windows refreshes same-generation connection proof and displays the verified versioned management path without changing PATH. All platforms retain the original identity and receipt stores; an old connection marker is not current signed evidence. Current implementation and acceptance evidence belong in #914 and #1035, including unresolved production cutover and prior platform refusal. Do not retry or bypass refused real-device operations; no additional staging service.
- Automatic Update Policy is local to permanent Standard installs: disclose default enabled on new installs, explicit migration consent on existing installs, support disabling. Only eligible Owner-ON stable devices update from official Immutable Stable Latest, at bounded low frequency and safe idle cutover. No temporary/Workflow Session automatic update, downgrade, forced termination, automatic re-pair or STOP bypass. Release and Worker publication remain independently authorized.
- Upgrade Transaction reuses staging, lifecycle lock, Freeze, independent execution and recovery. Preserve identity and receipts. Isolate updating failures; historical Unknown alone does not block if execution risk is independently isolated and receipts safe; never replay. Dispatch and process state do not prove signed connection or actual service recovery.
- Installed macOS `pair` reconciles only the existing approved identity via signed recovery at the installed endpoint; the local terminal and lifecycle lock are required, pending transactions are refused, and no replacement enrollment or service state change occurs. Normal Restart preserves Owner-ON intent, unlike Stop followed by Resume; reuse existing platform management and safe admission, and report unsupported remote restart rather than building a new lifecycle mechanism. Uninstall, revocation and identity purge are distinct; ordinary uninstall preserves identity and necessary receipts. Status, doctor and logs are read-only and share authoritative facts: status is a local/current or explicitly stale summary, doctor adds targeted diagnosis, logs expose existing evidence, recover is a separately authorized effect. Explicit update --check checks Latest without installing; ordinary status does not require GitHub or Clerk. Remote tooling resolves exact device identity.
- Stable product version is the actual vMAJOR.MINOR.PATCH release tag; show platform/architecture separately and keep historical candidate identity truthful. Routine candidates are unpublished artifacts of the intended stable tag with existing provenance. Manual candidate builds and new native-only package builders accept only the stable tag; the retired Rust-migration artifact branch is not a supported producer. Historical prerelease readers and the temporary macOS mixed reference fixture remain until their respective retirement criteria are met. Retire obsolete migration naming only after verifying real consumers and upgrade/recovery compatibility; retain necessary internal validation contracts. User-facing update state is derived from existing evidence, not a parallel state machine.
- macOS attended Stable Latest update uses the same installer-shell generator at Worker and package build time; the owned installed package carries one private `macos-update.sh` and passes the existing target binding into the verified next manager. The initial rollout must update the existing Worker archive allowlist before publishing the first immutable Agent archive containing that exact new member; historical packages stay accepted. No new network service, script-fetch dependency or repeated Worker release is required for subsequent Agent updates. These changes are not production-supported until the applicable gates pass.
- The macOS Rust candidate reuses the private lifecycle journal for interrupted uninstall: before removal it can retain or restore the proven original service and Owner intent; after removal is reserved it can finish only the exact previously reviewed package inventory. If the local executable is missing or incomplete, recovery requires the same independently verified original extracted native package. Unknown identity, registration, inventory or foreign files block recovery; identity, receipts and authorization remain separate. Native host acceptance is still required.
- No new service, permanent updater, cloud policy store or parallel lifecycle system. #911/#912 remain out of scope; macOS Rust-only delivery is owned by #914. This is design and candidate implementation, not supported runtime behavior before acceptance.

The executable implementation, tests, [Agent skill](../../apps/remote-control-mcp-worker/skills/remote-control/SKILL.md), existing release gates and reviewed GitHub Issues are authoritative for current details. High-impact rationale still relevant to implementation is retained in selected ADRs; completed migration and version acceptance logs remain in Git/Issues.
