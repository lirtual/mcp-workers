# Remote Control MCP — context

Remote Control is a single-owner MCP Worker backed by a signed per-device WebSocket relay and native Agent. The Worker owns authenticated ingress, device grants and routing; the bundled Agent under `apps/remote-control-mcp-worker/agent` executes authorized local file, search, Shell and Agent-owned managed-session operations on Windows, Linux/WSL2 or macOS. Browser GUI operations are owned by the independent Browser MCP and are not RCA tools.

**Identity and permission**

- Browser pairing (#1018) authenticates the fixed Clerk Owner with a short-lived standard Session JWT, then requires explicit review and approval of the pending identity and grant type. Login is not device authority. Clerk failure is scoped to browser pairing. The canonical installer (v0.1.60 or later) prints the browser link with a fragment and the local key fingerprint. Local grant selection and signed identity claim are unchanged. Old MCP pairing lookup/approval are removed from discovery and execution in the retirement source; production cutover remains separately authorized in #1018. Existing valid identities reconnect unchanged; use the current official installer for new pairing/re-pair, including recovery from a revoked identity on an older package. Noncanonical endpoints must never forward pairing data to the canonical origin; no alternate production pairing ingress is maintained.
- Pairing requires an explicit Owner grant tied to a device identity. A temporary grant is bounded and nonrenewable; permanent grants retain independent revocation and online/idle rules. Neither installation nor a valid MCP token alone grants a device.
- GitHub-hosted temporary Session devices require independent Workflow physical Attempt authorization; an approved personal device is not a substitute for a Session grant.
- The Agent's OS account and host permission model remain authoritative. Native process ownership, session stops, device revocation and receipts must fail closed when identity cannot be verified.

**Effects and recovery**

- Mutating requests have stable operation identities and local receipts. An Unknown response is not permission to retry an external effect; reconcile the original operation before continuing.
- A cancellation or Worker acknowledgment does not itself prove physical job or subprocess termination. Distinguish Agent-managed session, actual OS process, GitHub job and temporary device cleanup.
- Installation, Agent Release publication, Worker publication, native upgrade, pairing and production acceptance are separate operations. An upgrade must preserve identity and historical receipts; an unknown or unsafe upgrade must not silently re-pair or discard history.
- Distributing public installers does not authorize pairing. Artifact integrity checks are not independent proof of production deployment or physical-device acceptance.

**Accepted lifecycle design — G1 non-production implementation in progress (#1035)**

- [Spec #1035](https://github.com/lirtual/mcp-workers/issues/1035) unifies RCA public management across Linux/Windows Rust and current macOS Node, not platform executors. Remove fixed human confirmation words, not identity or high-risk authorization. Pairing follows #1018 independent acceptance and retirement gates.
- Implementation is on Draft PR #1038. Linux, Windows and macOS reuse the existing per-owner update policy, platform lifecycle admission, and original identity and receipt stores. Public diagnostics distinguish installed version, local service and signed connection evidence; a connection marker is historical unless a current process and authenticated local observation corroborate it. Windows refreshes a same-generation connection proof after a new signed handshake using the existing private atomic-record boundary. Uninstall and recovery validation remain incomplete; see Spec #1035 for current head, CI, platform-specific evidence and blockers. No candidate or CI result establishes production acceptance.
- Owner chose the existing production RCA Worker/route for G0; do not create a staging Worker/DO, domain, route or service. A read-only file read through the existing production connection to `WORK` succeeded, but proves only the already-installed Agent baseline. `WORK` is an online permanent Linux/WSL2 device; a real cutover would restart its Agent and interrupt its RCA connection. The exact production target and stop/recovery boundary remain unconfirmed before device mutation.
- G0 remains Partial: actual signed TLS/WSS cutover, post-cutover read-only service, long-task continuity, detached update completion and signed recovery remain unverified. Owner subsequently approved proceeding with G1 non-production implementation and retaining all outstanding real-device criteria in G2; final acceptance and publication gates are unchanged. The prior platform rejection of those real operations is a hard stop; do not retry or bypass it. No merge, Release, Worker deployment or production device update has occurred.
- Automatic Update Policy is local to permanent Standard installs: disclose default enabled on new installs, explicit migration consent on existing installs, support disabling. Only eligible Owner-ON stable devices update from official Immutable Stable Latest, at bounded low frequency and safe idle cutover. No temporary/Workflow Session automatic update, downgrade, forced termination, automatic re-pair or STOP bypass. Release and Worker publication remain independently authorized.
- Upgrade Transaction reuses staging, lifecycle lock, Freeze, independent execution and recovery. Preserve identity and receipts. Isolate updating failures; historical Unknown alone does not block if execution risk is independently isolated and receipts safe; never replay. Dispatch and process state do not prove signed connection or actual service recovery.
- Normal Restart preserves Owner-ON intent, unlike Stop followed by Resume; reuse existing platform management and safe admission, and report unsupported remote restart rather than building a new lifecycle mechanism. Uninstall, revocation and identity purge are distinct; ordinary uninstall preserves identity and necessary receipts. Status, doctor and logs are read-only and share authoritative facts: status is a local/current or explicitly stale summary, doctor adds targeted diagnosis, logs expose existing evidence, recover is a separately authorized effect. Explicit update --check checks Latest without installing; ordinary status does not require GitHub or Clerk. Remote tooling resolves exact device identity.
- Stable product version is the actual vMAJOR.MINOR.PATCH release tag; show platform/architecture separately and keep historical candidate identity truthful. Routine candidates are unpublished artifacts of the intended stable tag with existing provenance. Retire obsolete migration naming only after verifying real consumers and upgrade/recovery compatibility; retain necessary internal validation contracts. User-facing update state is derived from existing evidence, not a parallel state machine.
- macOS attended Stable Latest update uses the same installer-shell generator at Worker and package build time; the owned installed package carries one private `macos-update.sh` and passes the existing target binding into the verified next manager. The initial rollout must update the existing Worker archive allowlist before publishing the first immutable Agent archive containing that exact new member; historical packages stay accepted. No new network service, script-fetch dependency or repeated Worker release is required for subsequent Agent updates. These changes are not production-supported until the applicable gates pass.
- No new service, permanent updater, cloud policy store or parallel lifecycle system. #911/#912 and macOS Rust migration are out of scope. This is frozen design, not supported runtime behavior before acceptance.

The executable implementation, tests, [Agent skill](../../apps/remote-control-mcp-worker/skills/remote-control/SKILL.md), existing release gates and reviewed GitHub Issues are authoritative for current details. High-impact rationale still relevant to implementation is retained in selected ADRs; completed migration and version acceptance logs remain in Git/Issues.
