## Historical first-cutover checklist (retained for audit)

The following steps describe the originally approved migration. Any future executor change requires a fresh baseline, independent authorization, safety checks and new acceptance evidence; do not replay these steps blindly.

### Preconditions (separately approved)
1. Owner specifies the single new `owner/repo`, confirms the repository exists, is private or public as intended, that `main` is the default branch and `.github/workflows/ci.yml` is **active**, with successful exact-main push CI. The token has exact destination repository read and Actions dispatch permissions. Read GitHub API metadata twice: full name, nonzero numeric repository ID and `ci.yml` ID. A GitHub transfer/rename is a new identity unless the numeric ID is demonstrably unchanged.
2. Confirm GitHub Repository Variable `WORKFLOW_GITHUB_ACTION_REPOSITORY` is **unique** at Repository scope, and reject a shadow of that name in `workflow-mcp-worker` Environment. Do not edit either Variable until separate approval; Environment `WORKFLOW_MCP_PORTAL_CLIENT_ID` and existing Secret `WORKFLOW_GITHUB_DISPATCH_TOKEN` keep their established scopes. Do not reuse `ACTIONS_GITHUB_DISPATCH_TOKENS` (independent GitHub Actions MCP).
3. Classify **the exact 12 known historical Unknown Run IDs**, their Attempt IDs and physical GitHub Jobs. Read-only enumerate all active/pending Runs, Sessions, Workflows, cancellation/receipt status, child reservations, GitHub queued/running Jobs, and Cloudflare native instances. Unknown is not terminal and never an excuse to replay. Freeze both new admissions and management operations; prove no old physical dispatch can restart. Resolve any unaccounted Unknown or require a new Owner risk decision; no blind retry.
4. Validate destination Actions workflow contracts, branch rules, token scope, GitHub-issued OIDC issuer/audience/**subject with new repository identity**, and Tailscale workload trust, then verify the previously active business Plans and downstream consumers. Only explicitly authorized target settings, credentials and trust changes may occur.

### Protected Worker release
5. Independently capture the current sole 100% active Worker version, GitHub bindings, Portal/Access/D1, secrets names and enabled business Plan versions. Run the usual protected `release.yml` checks on exact reviewed `main` SHA. Its **read-only** preflight verifies the destination API identity and freezes the old active executor binding; the staging step writes the verified triplet into the version candidate only. Immediately before publication re-read the destination repo/CI identity and the unchanged active Worker version/baseline. Any duplicate, drift or missing result fails closed.
   For an already-applied schema, the protected Release compares the exact production `d1_migrations` name inventory with the committed migration files and **skips D1 migration application only when every name matches**. Any pending or unexpected migration keeps the original strict migration gate (or fails closed), without writing or reclassifying historical Unknown data. The independent code-release quiescence checks still run before every publication, including full code-and-configuration cutovers.
6. After a separately authorized Publish, independently verify exactly one 100% active Worker version and one `WORKFLOW_GITHUB_ACTION_IDENTITY` binding containing the new name/repository ID/CI ID; confirm the old `WORKFLOW_GITHUB_ACTION_APPROVED_REPOSITORIES` binding is absent. Preserve D1, historic Versions, old Run/Attempt IDs and receipts. Recheck Portal, Access, native Workflow binding and secrets. Do **not** restore a historical Worker version containing the retired executor as an automatic fallback.
7. Republish only the approved current Plan definitions with the destination's freshly reviewed Workflow IDs/contracts; verify at least one **real** Task and one **real** Session end to end, including OIDC, GitHub Job identity, callbacks, readiness/cancellation, and no duplicate dispatch on Unknown. Restore only the intended active business admissions and recheck physical idle/health. Record exact evidence on #834.

## Stop/recovery conditions
Any old active/Unknown external job, new pending reservation, GitHub API identity or token failure, changing `main` CI, altered baseline, unexpected Cloudflare binding, missing OIDC/Tailscale trust, or published-version readback mismatch **stops the affected cutover**. Keep admissions paused and preserve immutable evidence; recover by an explicitly reviewed *current-executor-compatible* candidate and authorized publication, never by silently re-enabling the old repository. Escalate irreversible or unknown states for a separate Owner decision.
