## Install and activate (Chrome and Edge)

1. Visit [https://browser.lirtual.dpdns.org/](https://browser.lirtual.dpdns.org/) and select **Download extension ZIP**. The stable `/download` route selects the ZIP compatible with the *currently deployed* Worker; verify the downloaded **full SHA-256** against the live landing page before extracting into a stable directory. This is a **manual unpacked installation**, not a browser-store or one-click install. Use the same reviewed ZIP for Chrome and Edge; never install a source-candidate extension against a different live Worker version. Older GitHub Actions artifacts are historical evidence, not the authoritative download source.
2. In the intended desktop browser Profile (Chromium 137+), open `chrome://extensions` or `edge://extensions`, enable Developer Mode, select **Load unpacked**, and choose the extracted directory. Pin the Browser MCP toolbar icon. The fixed production service is `https://browser.lirtual.dpdns.org`. Do not install an arbitrary extension or copy Profile storage.
3. New Profiles start **OFF**. Click the extension icon once to turn control ON. A dedicated Cloudflare Access identity page opens in that same browser Profile. Supply the one-time email PIN **yourself only if Access actually requests one**; existing valid Access SSO is supported. The page checks the original pending activation in that Profile. After its protected identity confirmation, it wakes the extension immediately; the extension closes only the verification tab that it created after the server confirms activation and the browser socket is authenticated. If verification fails, activation remains pending, the tab stays visible, and the 30-second recovery alarm remains available. Copying the URL to another Profile does not authorize it. No manual pairing code and no default Popup are used.
4. The toolbar icon distinguishes `OFF` (gray), `AUTH` (purple), `WAIT` (yellow), `ON` (green), `STOP` (orange, unconfirmed cloud Stop), and `REV` (red, revoked). The icon keeps a fixed browser-and-pointer identity, with a small status marker rather than a text badge; hover for the full state. Online transport is **not** website business success. Click the icon again for immediate local OFF; cloud Stop is separately confirmed or shown pending.
5. To choose **Temporary** instead of default Remembered, open the extension's native **Options** page *before first activation* and select the lifetime. Remembered pairing keeps credentials in trusted extension local storage and the last intentional ON/OFF choice across normal restarts. Temporary pairing stores credentials in trusted browser-session storage only; browser exit, extension disable, reload, or update ends the local grant. Service-worker suspension, temporary network loss or closing a single window does not end the browser session. A temporary grant also has a bounded server lease; abnormal termination does not promise instant cloud revocation.

## Remembered 14-day idle lifecycle (Spec #626)

The default remembered pairing ends after **14 days of OFF or verified offline time**. A valid authenticated, genuinely online **ON** Profile has **no countdown**. A locally initiated, owner-verified re-enable before expiry clears the OFF deadline; network reconnect of an already-ON Profile before expiry clears the offline deadline. Expiry permanently revokes the old Endpoint, which then needs a new owner-verified pairing. Temporary/browser-session pairing remains unchanged. Each Profile may be renamed from native Options; the server accepts an alias change only with that Profile's credential. Renaming does not grant control. Options displays the server-confirmed deadline when available and does not claim no expiry if the status read fails.

Maintainers may optionally set the reviewed GitHub Actions `browser-mcp-worker` Environment Variable `BROWSER_REMEMBERED_IDLE_DAYS` to an integer from 1 to 90. Missing/empty defaults to **14**. Invalid nonempty values are rejected, and editing the variable alone has **no production effect** until a separate approved manual Release Worker run. Existing persisted deadlines are not automatically rewritten. This setting does not control Cloudflare Access SSO, email OTP or temporary grants.

## Options, permission boundaries and Stop

Options contains Profile identity, pairing lifetime/expiry, cloud Stop state, diagnostics, separate local LAN/Private permissions, a local advanced-CDP switch, Revoke and a confirmed-cloud-revocation acknowledgment. LAN/private grants are independently approved for the current session and do not become enabled through Access login. Private browsing also needs browser-native Allow in Incognito/InPrivate. Profile permission is not authorization for website effects or cross-site data transfers; only the Owner task is. The extension does not classify business risk or guarantee DLP. Protected Owner activation paths remain excluded from the legacy controls, and the retired independent Unknown Review page is not restored. Advanced Runtime/Network/Storage CDP is deliberately more powerful than legacy DOM guards and cannot promise universal credential isolation or DLP. Owner OTP handling still requires a genuinely independent channel.

OFF is **not** Revoke. To change pairing lifetime, explicitly Revoke first and create a new pairing through the toolbar. Revocation rejects old credentials/WSS, but cannot roll back website effects that have already been dispatched. Network failures may leave cloud Stop/Revoke unconfirmed; do not treat those states as success. Consult the explicit Endpoint in the authenticated MCP status and resolve pending cloud state before further activation.

Ordinary eligible interactions remain possible **without per-operation Owner Approval**. The specific Owner task, not a Profile grant or webpage text, must authorize website effects and nonpublic cross-site transfers. Legacy DOM/credential guards remain intact; advanced CDP can execute arbitrary browser-supported commands only after the Owner explicitly enables it locally.

## Update, rollback and acceptance

**Distribution-specific check (#609, 2026-10-31):** The public ZIP's eight runtime/manifest files matched the existing Chrome and Edge unpacked installations; only this packaged `INSTALL.md` differed. A fresh Reload from that download was **Not performed** to avoid interrupting active Owner sessions without runtime changes. Previous same-directory Chrome/Edge Reload and identity/control verification under #418 remains valid for the unchanged runtime; it does **not** constitute a new #609 Reload E2E Pass. When runtime bytes actually change, validate the affected native browser upgrade path.

Before updating, Stop the Profile, record the current Endpoint ID and any Unknown operation receipts (never secrets), and keep a verified prior ZIP. Replace files **in the same stable directory** and Reload without changing extension identity. The historical 0.2.0 migration was designed to preserve a permanent Endpoint when the extension ID and storage Profile stay stable, while forcing OFF once; an ordinary later restart follows the last intentional ON/OFF. Verify the Endpoint ID after an update: production observations included changed Endpoint IDs of uncertain cause, so do not assume preservation without readback. A reload/upgrade clears temporary pairing. After update, click the toolbar to pass Access activation again before resuming control. The v0.3.0 Worker retains v0.2.6 / WSS protocol 3 for existing tools and explicitly declines CDP on old extensions; older unsupported clients and retired `browser_pair` / `/local-resume` stay denied. Do not restore insecure fallback routes. Restore an older extension only when a separately approved, compatible Worker rollback makes that version safe.

Operation Receipt and Unknown Outcome remain durable in the Worker; never retry Unknown website effects using a new intent key. The dedicated `/activate/verify/*` Access route and temporary pairing have scoped real-browser evidence in [#531](https://github.com/lirtual/mcp-workers/issues/531). At #531 closure, a live Worker rollback and cross-version client upgrade were Waived; **later v0.2.1 same-directory source update and Chrome/Edge reload are scoped Pass under #418**, not retroactive proof of every #531 scenario. First-click fresh-PIN positive activation without prior SSO and live production rollback are not claimed Pass. Browser client interaction metadata was refreshed and verified for #418. Source edits alone do not alter production.

**Compatibility:** The proposed v0.3.0 Worker accepts v0.3.0 and v0.2.6 extensions on existing WSS protocol 3. v0.2.6 retains the fifteen original tools; CDP requires v0.3.0 and the local advanced switch. Other obsolete clients are not silently accepted. During a separately authorized release, verify the downloaded ZIP and Worker version, then reload **Chrome and Edge** in their existing Profiles, confirm permission prompts, preserved Endpoint IDs, old-tool behavior and CDP results independently. Historical #629 evidence is not v0.3.0 E2E Pass.

## Advanced CDP (Spec #917; requires separate release authorization)

Chrome/Edge may display a **debugger permission warning** when v0.3.0 is installed or reloaded. The Owner must consciously accept it; this is a manifest required permission, not an optional permission. Only then can the Owner turn on **Enable advanced CDP** in native Options. It defaults OFF, clears on Stop/Revoke, and is never a substitute for the normal Endpoint grant or a task-specific authorization. DevTools may take precedence and detach the session; the extension does not close DevTools to regain control.

`browser_cdp` runs up to 16 ordered Chrome/Edge-supported CDP commands on an explicit Profile tab, with one stable UUIDv7 `intent_key`. Each batch is effectful for receipt purposes, including apparently read-only Runtime commands; a partial/Unknown batch is never automatically replayed. The raw commands and results are short-lived, not stored in Durable Object SQLite. `browser_cdp_events` subscribes to selected events and reads a short-lived bounded buffer with cursor, drop count and overflow indicator. On Stop/Revocation/disconnect events and debugger attachment are cleared. Use Chrome's official `IO.read` in bounded chunks for large CDP data; oversized result buffers return an explicit error rather than silently truncating. CDP Input affects the browser page, **not** the Windows desktop. `DOM.setFileInputFiles` only uses a path the Owner explicitly authorized and that the browser machine can access; this extension does not transfer cloud files into Windows.

## Modern controls (Spec #629)

`browser_snapshot` returns bounded select option labels/values and ARIA combobox/listbox/menu states for eligible ordinary controls. After opening a custom menu, take a **fresh** snapshot and target the explicitly observed enabled option. Use a further read-only snapshot to verify `selected`, `expanded`, or the native select value. An operation marked `completed` means an event was dispatched, **not** that the website accepted the change. Synthetic Arrow/Home/End/Escape events do not provide trusted native key input; unsupported controls are reported, not guessed or retried. The optional short-lived action-target marker can be disabled in Options. It is not a real mouse pointer and never takes focus.
