# Browser MCP 0.2.0 — installation, local activation, recovery

Spec #531 v0.2.0 was released through [GitHub Actions run #41031042848](https://github.com/lirtual/mcp-workers/actions/runs/41031042848), with scoped production Chrome/Edge and Chrome Temporary-session acceptance documented in [Issue #531](https://github.com/lirtual/mcp-workers/issues/531#issuecomment-6519345334). Use only the independently verified release artifact with its SHA-256, JSON source manifest and matching Worker release. Neither a published artifact nor partial browser acceptance proves every negative or rollback case.

## Install and activate (Chrome and Edge)

1. Verify the published `browser-mcp-extension-v0.2.0.zip` against the trusted `.zip.sha256` and matching source metadata. Use the same reviewed ZIP for Chrome and Edge; extract each installation into a stable directory.
2. In the intended desktop browser Profile (Chromium 137+), open `chrome://extensions` or `edge://extensions`, enable Developer Mode, select **Load unpacked**, and choose the extracted directory. Pin the Browser MCP toolbar icon. The fixed production service is `https://browser.lirtual.dpdns.org`. Do not install an arbitrary extension or copy Profile storage.
3. New Profiles start **OFF**. Click the extension icon once to turn control ON. A dedicated Cloudflare Access identity page opens in that same browser Profile. Supply the one-time email PIN **yourself only if Access actually requests one**; existing valid Access SSO is supported. The page checks the original pending activation in that Profile. After its protected identity confirmation, it wakes the extension immediately; the extension closes only the verification tab that it created after the server confirms activation and the browser socket is authenticated. If verification fails, activation remains pending, the tab stays visible, and the 30-second recovery alarm remains available. Copying the URL to another Profile does not authorize it. No manual pairing code and no default Popup are used.
4. The toolbar badge distinguishes `OFF`, `AUTH` (authenticating), `WAIT` (connecting), `ON` (live authenticated WSS), `STOP` (unconfirmed cloud Stop) and `REV` (revoked). Online transport is **not** website business success. Click the icon again for immediate local OFF; cloud Stop is separately confirmed or shown pending.
5. To choose **Temporary** instead of default Permanent, open the extension's native **Options** page *before first activation* and select the lifetime. Permanent pairing keeps credentials in trusted extension local storage and the last intentional ON/OFF choice across normal restarts. Temporary pairing stores credentials in trusted browser-session storage only; browser exit, extension disable, reload, or update ends the local grant. Service-worker suspension, temporary network loss or closing a single window does not end the browser session. A temporary grant also has a bounded server lease; abnormal termination does not promise instant cloud revocation.

## Options, permission boundaries and Stop

Options contains Profile identity, pairing lifetime/expiry, cloud Stop state, diagnostics, separate local LAN/Private permissions, Revoke and a confirmed-cloud-revocation acknowledgment. LAN/private grants are independently approved for the current session and do not become enabled through Access login. Private browsing also needs browser-native Allow in Incognito/InPrivate. No permission grants an override for consequential or ambiguous targets; those actions are denied by the extension. Do not use Browser MCP on its Access authentication, mailbox OTP, or independent Unknown-review pages.

OFF is **not** Revoke. To change pairing lifetime, explicitly Revoke first and create a new pairing through the toolbar. Revocation rejects old credentials/WSS, but cannot roll back website effects that have already been dispatched. Network failures may leave cloud Stop/Revoke unconfirmed; do not treat those states as success. Consult the explicit Endpoint in the authenticated MCP status and resolve pending cloud state before further activation.

The no-per-operation-approval policy belongs to the newer #418 rollout. Before the matching Worker and extension release is validated, existing installed production versions may still follow the older policy; do not infer production behavior solely from these source instructions.

## Update, rollback and acceptance

Before updating, Stop the Profile, record the current Endpoint ID and any Unknown operation receipts (never secrets), and keep a verified prior ZIP. Replace files **in the same stable directory** and Reload without changing extension identity. The 0.2.0 migration is designed to preserve a permanent Endpoint when the extension ID and storage Profile stay stable, while forcing OFF once; an ordinary later restart follows the last intentional ON/OFF. Verify the Endpoint ID after an update: production observations included changed Endpoint IDs of uncertain cause, so do not assume preservation without readback. A reload/upgrade clears temporary pairing. After update, click the toolbar to pass Access activation again before resuming control. A newer Worker refuses obsolete protocol clients, old `browser_pair` and old `/local-resume`; do not restore insecure fallback routes. Restore an older extension only when a separately approved, compatible Worker rollback makes that version safe.

Operation Receipt and Unknown Outcome remain durable in the Worker. Never use a fresh intent key to retry an Unknown website effect. The dedicated `/activate/verify/*` Cloudflare Access policy, matching activation origin/audience and production release were verified for the published build; Chrome/Edge activation UX and Chrome Temporary lifecycle have separate scoped Pass evidence in [#531](https://github.com/lirtual/mcp-workers/issues/531). Edge live Temporary lifecycle, Access login without an existing SSO cookie, some adversarial negatives and production rollback remain **Not run**. If an MCP client still advertises retired `browser_pair`, refresh its Browser plugin metadata; do not attempt the retired flow. Editing or building source does not modify production.
