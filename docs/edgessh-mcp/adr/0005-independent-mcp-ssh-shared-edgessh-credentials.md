# ADR-0005 — Independently executed MCP SSH backed by EdgeSSH's unchanged encrypted host catalog

**Status: Architecture choice accepted (Q22=B, 2026-10-17); final design audit complete, operator's final approval for `to-spec` still required. Not approved for implementation/deployment.**
Supersedes only the infeasible responsibility clauses of Q3=A in [ADR-0001](./0001-edgessh-mcp-cross-repo-boundary.md) and Q14=A in [ADR-0003](./0003-bounded-live-sessions-and-authoritative-admission.md). All other accepted Q1–Q21 requirements remain. See [Final review](../FINAL-ARCHITECTURE-REVIEW.md).

## Context and forcing constraints

1. `lirtual/EdgeSSH` is an independently maintained fork of `aozorae/EdgeSSH`; Q21 forbids *any* changes to EdgeSSH's repository, Worker, D1 schema, secrets, bindings, or existing deployment.
2. The current EdgeSSH has browser-authorized SSH/SFTP WebSocket flows but **no** execution-only Service Binding RPC or MCP durable-admission endpoint. The previous EdgeSSH-exec/receipt design could not coexist with Q21.
3. Q2=B/Q6=B require remote commands, managed interactive Shell, session-owned background work and text SFTP mutations from the first release. Q4=B makes all saved hosts eligible; Q7=A demands human-pinned host keys; Q8=A authorizes unattended use via a *dedicated* MCP bearer.
4. Source inspection: `hosts(id, account_id, encrypted_payload, updated_at)`; `workspace_state(id=1, account_id, auth_provider, auth_revision, ...)`. Current `src/accounts/crypto.ts` uses 32-byte Base64 `ENCRYPTION_KEY`, AES-GCM with 12-byte IV, `v1.`-prefixed encrypted payload and AAD **`edgessh:v1:${accountId}:${hostId}`**. The decrypted host payload includes address/port, username, auth method, password or private key, `fingerprint`, and also `initialCommand`. `initialCommand` is data, **not a command the MCP should execute automatically**.
5. **Key scope expansion is material:** `src/accounts/github-auth.ts` derives GitHub OAuth flow/session cookie signing keys from **the same `ENCRYPTION_KEY`** using HKDF, so a second Worker holding the root secret extends the impact of compromise beyond SSH credentials. Depending on deployment auth mode and other metadata, disclosure may help forge browser login tokens. Other EdgeSSH records encrypted with that key may also be affected.
6. Cloudflare D1 binding is a general **read/write-capable `D1Database`** object. A SELECT-only implementation policy is **not** a native database-enforced read-only credential. Compromise of an MCP Worker with the binding may allow modification of the EdgeSSH host database; this residual risk cannot be honestly removed without changing the architecture/deployment trust boundary. See [Cloudflare D1 API](https://developers.cloudflare.com/d1/worker-api/d1-database/) and [bindings configuration](https://developers.cloudflare.com/workers/wrangler/configuration/#d1-databases).

## Decision — Q22=B accepted, replaces Q3 and Q14 responsibilities

- **Source of host facts:** EdgeSSH's *unchanged* D1 `hosts` + `workspace_state` remain authoritative for the saved-host catalog and ciphertext. No copied host table, sync service, scheduled polling, or edits to that D1 schema. An independently deployed `mcp-workers/apps/edgessh-mcp-worker` receives a binding to the **same existing D1 database** in its *own* configuration; it reads those records on demand, using fixed parameterized SELECTs.
- **Credential custody:** the MCP Worker additionally holds a **copy** of the root `ENCRYPTION_KEY` in its own Cloudflare Secret, deliberately provisioned out-of-band by the operator; EdgeSSH's own secret does not change. Its credential reader decrypts only in memory for the requested host and must never return **stored connection passwords, private keys, raw decrypted host payloads or the encryption root** as MCP tool fields or in logs, receipts, errors or tracing. **Separate caveat:** unrestricted remote commands and SFTP text reads may themselves expose secrets from a remote filesystem or process output; the platform cannot generically redact those. This **explicitly supersedes Q3=A**; there are now two trusted credential custodians, EdgeSSH and the MCP Worker. Security consequences are accepted as the cost of automatic host/credential reuse. No secret is provisioned by this ADR.
- **SSH ownership:** the MCP Worker executes SSH/SFTP itself, through a **single** self-contained bounded SSH transport/session implementation. First assess reuse of EdgeSSH's Apache-2.0 `src/ssh` primitives within the new MCP app, with the license and notices retained; extracting/adapting browser-oriented `SSHSession` requires a feasibility test. Alternatively evaluate one supported Workers-compatible SSH library, **not** two competing engines or a WebSocket/browser cookie automation layer. Never call the EdgeSSH browser `/api/hosts/:id/credentials` endpoint. No use of GitHub/Access login cookies as an unattended API token.
- **Receipt owner:** the new MCP SSH execution boundary atomically admits operation IDs and records outcomes **before** dispatch. A **single MCP-owned SQLite-backed Durable Object class/namespace within the same MCP Worker deployment** is the smallest viable candidate for live session ownership, atomic per-admin operation receipt claims, and bounded recent output; no new standalone Worker, EdgeSSH D1 table, D1 receipt database, queue, service gateway, R2, or remote Agent. This **explicitly supersedes Q14=A**. The exact DO identity/SQLite schema and isolation testing are Spec-level decisions; using existing Cloudflare-native DO capabilities is preferred, not an authorization to add more components.
- **Authorization:** keep one independent high-entropy `MCP_ACCESS_TOKEN` recognized by the existing `portal-auth` ingress; distinct from all other MCP apps. Strict validation for host ID, method, command/input size, file path, output size and session ownership. Q4=B remains: **all saved EdgeSSH hosts** appear eligible with no per-host opt-in, but each operation requires a usable credential, a previously human-confirmed nonempty pinned fingerprint, a reachable public SSH target, and remote OS account permissions.
- **Pinning:** obtain `fingerprint` from the authenticated encrypted host payload, never auto-enroll or change it. Verify the actual SSH server key cryptographically during key exchange **before sending credentials**; unknown/missing/mismatched fingerprints fail closed. Do not silently trust the `initialCommand` field or private DNS answers.
- **SSRF/network:** preserve or exceed EdgeSSH's existing `assertPublicTarget` behavior (public resolution, DNS rebinding/blocked address checks, port 25 denial) before any outbound TCP connection. Host name is selected by saved ID, not an arbitrary raw target supplied by an MCP call.
- **SFTP scope:** only bounded UTF-8 text CRUD/list/rename/mkdir operations with explicit overwrites/deletes, not binary transfers, streaming, arbitrary file exfiltration endpoints, or EdgeSSH browser session impersonation.
- **Session/receipt reliability:** Q11–Q20 remain: finite interactive sessions/live owned tasks beyond a tool call; no automatic SSH/process resurrection; operation ID+argument digest for session start/exec/interactive input batches and SFTP mutations; duplicate/changed payload conflict; 30-day normal terminal receipt retention and unresolved non-replay markers; human inspection for unknown effects; storage failure blocks new mutations/input with narrow authenticated *proven-owned* emergency stop; bearer rotation rejects new calls but cannot promise instantaneous remote job termination.
- **Deployment:** independently deploy/disable/roll back only the MCP Worker. No EdgeSSH schema migration or Worker change. Read-host SQL must be schema-version guarded and fail closed on upstream format changes, key mismatch, missing/ambiguous `workspace_state` or invalid AAD, rather than attempting to repair or write upstream rows. MCP receipt state must survive MCP Worker source rollbacks without unsafe replay or auto-deletion.

## Trust boundary and residual risks — explicitly accepted, cannot be claimed mitigated by intent

1. **Root encryption secret copied:** this is not least-privilege sharing of one host's SSH password. Possession of the shared root permits decrypting *all* compatible encrypted records; in GitHub auth deployments it is also the root material from which login signing keys can be derived. A compromised MCP runtime can expose credentials across all hosts.
2. **Shared D1 write capability:** the MCP code will be **logically read-only** toward the EdgeSSH tables, using fixed SELECTs; D1 Binding still exposes methods capable of writes. A malicious code change or compromised Worker can corrupt or tamper with the same production DB. Calling it "hard read-only" would be false; source review, monitoring, backup readiness and least-permission deployment practice reduce but do not eliminate this risk.
3. **Key rotation is coupled:** a change to EdgeSSH's encryption root breaks MCP decryption until the operator deliberately updates the MCP secret. Root rotation may also affect login session verification; no automatic key sync, dual-key rollout, or unattended rotation daemon in v1.
4. **Unattended full-host capability:** any valid MCP Bearer permits commands/SFTP mutations on all saved and fingerprint-pinned SSH hosts under stored SSH account privileges; prompt injection, malicious host output, leaked bearer or a malicious integration can be destructive. No per-host RBAC or per-command human confirmation was approved. Never treat model text or outputs as an authorization barrier.
5. **Upstream version drift:** the fork's schema/crypto/payload or authentication semantics can change independently. `updated_at` may not capture every encrypted payload edit (e.g. system/location refresh), so avoid using timestamp alone as the credential/pinning freshness proof; always decrypt a fresh row at execution time.
6. **Runtime limitations:** an outbound SSH TCP connection under a Durable Object can be evicted despite a persisted session ID; it is *not* a guaranteed continuously running service. An opaque remote PID does not prove ownership after disconnect. Receipt `admitted` state is not proof a remote command did or did not run.

## Minimum initial interface (proposed, pending final spec)

MCP-facing tool *categories*, rather than a generic internal enterprise API:
- hosts: `list_hosts`, `get_host` returning sanitized metadata/fingerprint readiness;
- one-off execution: `exec` with stable operation ID, explicit host ID, bounded result and separate outcome;
- interactive: `session_start`, `session_input`, `session_output`, `session_status`, `session_stop`;
- SFTP text: list/read/write/create/rename/delete/mkdir, each mutation receipt-protected;
- receipt inquiry: `get_operation_status`, no public SQL/admin command tool.

Tool naming/parameters and exact quotas are Spec-level and **not** implemented here.

## Final consensus gate

The architectural contradiction Q3/A vs Q14/A vs Q21 is **resolved by accepted Q22=B**, without pretending the old guarantees survive. Security review has **two non-removable residual risks**: shared root secret (including login-key derivation) and shared D1's write-capable binding. A design meeting the accepted feature scope while literally forbidding both requires a different Q22 choice or EdgeSSH changes, so do not add layers merely to market Q22=B as more isolated than it is.

Before any `to-spec`, the operator must explicitly accept the final synthesis and residual risks. Then the technical spec should prove offline AES-GCM AAD fixture compatibility; key rotation/invalid-version errors; host pinning and DNS rebinding defenses; Workers SSH library/PTY/SFTP feasibility; D1 static SELECT-only contract; DO atomic claim and concurrent dedup; disconnect/unknown outcomes; emergency stop and token rotation; independent rollback without receipt loss; no secret leaks; and preservation of original EdgeSSH behavior. Use existing CI; do not create new CI infrastructure by default. **No production testing with actual SSH credentials is authorized.**
